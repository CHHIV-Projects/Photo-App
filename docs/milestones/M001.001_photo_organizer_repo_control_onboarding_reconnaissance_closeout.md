### Project-specific invariants that must survive harmonization

- Original Source media is read-only from Photo Organizer's perspective.
- Canonical Vault bytes are immutable; damaged or inconsistent canonical
  state fails closed rather than being silently repaired or duplicated.
- Source Intake is the canonical library-writing authority. Provider
  acquisition is staging-only and cannot bypass common intake.
- Durable Source identity, configured root, observed route, runtime-resolved
  root, content identity, and provenance are distinct concepts.
- The selected Source Profile is the operational provenance identity;
  legitimate cross-Source provenance survives exact-content reuse, while
  unchanged same-Source repeats remain idempotent.
- Backend validation is execution authority; frontend values and provider
  output are not independent authority.
- Human curation remains authoritative over uncertain identity, grouping,
  assignment, correction, and curated meaning.
- Development, Test, and future Production must not silently share mutable
  database, Redis, application storage, Vault, configuration, release,
  network, or volume state.
- The Linux server owns the editable repository and current runtime;
  Windows is the operator/client and Windows Helper access node; NAS
  availability does not imply writable application-storage authority.
- Docker, database, NAS, secrets, mounts, deployment, live provider actions,
  and destructive operations require explicit bounded authority.
- Application milestone history, deployment history, runtime runbooks, and
  the forward-looking parking lot have distinct purposes.

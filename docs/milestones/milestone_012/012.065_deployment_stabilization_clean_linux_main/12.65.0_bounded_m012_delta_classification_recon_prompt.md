# 5. Controlling Transition Lock-Ins

The following Product Owner-approved direction supersedes the earlier assumption that all general filesystem Sources should become Linux-attached Sources.

The future Source architecture has three provider classes:

```text
Mounted Source Provider
Windows Source Helper Provider
Cloud Provider
```

## Mounted Source Provider

Used only when the Linux server legitimately has direct filesystem access.

Examples include:

```text
NAS mounted by the Linux server
Linux server-local approved storage
future disks physically attached to the Linux server when explicitly supported
```

M012 work may be retained when it is cleanly required for this provider.

## Windows Source Helper Provider

Future arc.

Used for Sources physically or logically accessible from the Windows workstation, including:

```text
Windows Local
Windows secondary/internal disks
Windows External HDD/SSD
Windows Removable Media
Windows Optical Media
```

Linux must not translate Windows paths such as `C:\Photos` into artificial Linux paths merely to pretend it has direct filesystem access.

Do not design or implement the Windows Helper in this milestone.

## Cloud Provider

iCloud remains provider-specific and independent of generic filesystem Source access.

Do not change iCloud architecture during stabilization.

# 7. Locked 12.64 Guarantees

The following are established implementation guarantees and must survive stabilization.

Do not reinterpret them as optional M012 design choices.

For a validated selected modern Source:

```text
SourceIntakeRun.ingestion_source_id
= selected Source Profile ID

IngestionRun.ingestion_source_id
= selected Source Profile ID

Provenance.ingestion_source_id
= selected Source Profile ID
```

Runtime/access evidence remains separate from durable Source identity:

```text
IngestionRun.from_path
= current backend-resolved Runtime Root

Provenance.source_root_path
= same current Runtime Root

Provenance.source_relative_path
= path relative to that Runtime Root
```

Also preserve:

- the stored configured Source/Profile root is not silently rewritten when the Runtime Root changes;

- changed access paths must not create detached path-based Sources when durable identity still matches;

- SHA-256 content identity remains separate from Source provenance;

- one Asset and one canonical Vault object may have multiple legitimate Source observations;

- exact-known content does not invoke the ordinary Vault-copy operation against an existing canonical Vault file;

- exact-known content under another extension does not create an alternate orphan Vault pathname;

- existing canonical Vault state is validated before reuse;

- missing, damaged, unreadable, or inconsistent existing Vault state fails safely;

- such Vault conflicts are not silently repaired and do not receive successful new provenance;

- `Asset.original_source_path` retains first-creation history;

- no schema, migration, backfill, or historical reinterpretation is required for these guarantees;

- concurrent first-time same-SHA ingestion remains outside this stabilization scope.

Any M012 change that weakens or conflicts with these guarantees must be classified RESTORE, REVISE, or escalated. It must not be silently accepted.

# 9. Required Classification

For every material M012 change, classify it as:

## KEEP

Use when:

- the implementation is clean;

- it fits the accepted Mounted Source Provider or provider-neutral architecture;

- it preserves established authorities;

- it remains useful substantially as written.

State whether a clean cherry-pick is feasible or whether the change should still be reconstructed manually.

## REVISE

Use when:

- the concept is useful;

- but the current implementation is broader or more complex than the accepted architecture requires;

- or it mixes Linux-mounted Source concerns with now-deferred Windows Source concerns;

- or it should become explicitly Mounted-Provider-specific/provider-neutral.

State the smallest accepted replacement.

## RESTORE

Use when:

- M012 unnecessarily changed trusted pre-M012 behavior;

- especially generic ingestion, Source behavior, or provider-independent logic;

- the accepted architecture does not require the modification.

State the exact file/function behavior that should return to the `461653e` baseline.

## DISCARD

Use when:

- the code or artifact is experimental;

- obsolete under the accepted provider architecture;

- validation-only scaffolding that should not become product architecture;

- diagnostic machinery with no ongoing product/operator value;

- or an abandoned implementation approach.

It remains available on the frozen historical branch.

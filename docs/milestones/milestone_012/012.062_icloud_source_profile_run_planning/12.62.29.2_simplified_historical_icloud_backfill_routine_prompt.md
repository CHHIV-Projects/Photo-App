# Milestone 12.62.29.2 — Simplified Historical iCloud Backfill Routine

## Purpose

Refactor the historical iCloud backfill workflow from a low-level acquisition control panel into a simple operator routine:

```text
1. Refresh Inventory
2. Show Available Inventory: Yes / No
3. Backfill Historical / Backfill Next 1000
```

The user-facing goal is:

```text
I do not want to think about scan caps, selected logical count, candidate windows, cleanup dry-runs, or Source Intake handoff.
I want to refresh inventory, know whether there is historical inventory available, and press a button to backfill the next 1000 logical assets.
```

This milestone is focused on **historical iCloud backfill only**.

Do not implement the current/new iCloud photos routine yet.

## Product-owner decisions

### Historical operator workflow

The historical workflow should be:

```text
Step 1: Refresh Inventory
Step 2: Available Inventory: Yes / No
Step 3: Backfill Historical / Backfill Next 1000
```

### Meaning of Available Inventory

`Available Inventory: Yes` means:

```text
There are eligible/acquirable historical iCloud logical assets still available to import.
```

`Available Inventory: No` means:

```text
All currently eligible/acquirable historical inventory has been imported or accounted for.
```

Important:

```text
Deferred/adjusted/ambiguous assets should not keep Available Inventory stuck on Yes.
```

Deferred items should be reported separately as:

```text
Deferred / Needs Policy: 41
```

### Historical batch target

The main historical run button should target:

```text
1000 logical assets per historical backfill routine run
```

This is user-facing.

The system should internally handle scan mechanics, candidate windows, preview, acquisition, Source Intake, and cleanup.

### Internal batch size

Use:

```text
internal batch size = 100 logical assets
```

Meaning:

```text
Backfill Next 1000 should internally process up to ten chunks of 100 logical assets.
```

Each internal chunk should:

```text
1. select eligible historical candidates
2. acquire up to 100 logical assets
3. run Source Intake
4. run guarded cleanup dry run
5. execute guarded cleanup only if safe
6. continue to next chunk
```

Stop when:

```text
- 1000 logical assets have been imported, or
- no eligible/acquirable historical inventory remains, or
- a safety gate fails, or
- a real error occurs
```

If only 250 historical assets remain, the routine should import 250 and then return:

```text
Available Inventory: No
```

### Logical assets versus resources/files

Use this terminology clearly:

```text
Logical assets = iCloud inventory items / photo/video items.
Resources/files = underlying downloaded resources, such as HEIC plus MOV for Live Photo.
```

The top-level historical target is **logical assets**.

The final report should show both:

```text
Imported logical assets: 1000
Imported files/resources: 1036
Cleaned local staging files: 1036
```

## Required backend routine semantics

Add a higher-level historical routine layer.

Preferred endpoint names, adjust to repo conventions:

```text
GET  /api/admin/icloud-routine/historical/status?source_id=<id>
POST /api/admin/icloud-routine/historical/refresh-inventory
POST /api/admin/icloud-routine/historical/run-next-batch
```

If there is a better existing admin route convention, use it, but keep the semantics clear.

### Historical status response

Return operator-level fields such as:

```text
source_id
source_label
inventory_total_logical
backfill_completed_logical
eligible_pending_logical
available_inventory
deferred_current_logical
deferred_adjusted_resource_logical
deferred_ambiguous_logical
deferred_unsupported_logical
retryable_failed_logical
last_inventory_scan_at
last_historical_run_at
last_historical_run_id
last_cleanup_run_id
local_staging_file_count
partial_file_count
backfill_execute_file_count
operator_message
```

Where:

```text
available_inventory = true only if eligible/acquirable historical logical assets remain.
```

Do not count adjusted/deferred-only rows as available inventory.

### Refresh inventory semantics

The refresh inventory routine should do metadata-only inventory refresh for the selected iCloud source.

The response should clearly state:

```text
inventory_total_logical
created_logical
updated_logical
eligible_pending_logical
available_inventory
deferred_current_logical
deferred_adjusted_resource_logical
source_exhausted if known
scan_limit_reached if known
operator_message
```

Important investigation/fix:

```text
Determine whether the current inventory scan is only refreshing the same newest/current listing window or can actually extend historical inventory deeper.
```

If current backend cannot truly scan deeper historical inventory beyond the current listing window, stop and report before inventing weak behavior.

If deeper scanning requires a provider cursor/page token/date boundary not currently available, document the limitation clearly and propose the smallest next backend step.

The desired long-term behavior is:

```text
Refresh Inventory should expand or update the known historical inventory until either the approved scan bound is reached or the source is exhausted.
```

But do not fake source exhaustion.

### Backfill Next 1000 semantics

Add a routine operation:

```text
Backfill Next 1000
```

Suggested request:

```json
{
  "source_id": 66,
  "target_logical_assets": 1000,
  "internal_batch_size": 100
}
```

The UI may not expose these values in the first version. Use defaults:

```text
target_logical_assets = 1000
internal_batch_size = 100
```

The routine should internally loop over existing validated lower-level steps:

```text
preview/select eligible historical candidates
acquire with dry_run=false
auto_run_source_intake=true
cleanup dry run
guarded cleanup execute if safe
repeat
```

Do not require the UI/user to click through each chunk.

### Per-chunk safety gates

Each internal chunk must preserve existing gates:

```text
- no adjusted/deferred/ambiguous/unsupported rows selected
- Live Photo resources remain paired
- Source Intake completes successfully
- backfill rows complete only after Source Intake evidence
- cleanup eligible paths exactly match acquired_resource_paths for that chunk
- cleanup skipped/protected/verification_failed/file_missing/delete_failed counts are zero
- no .partial files included
- no backfill_execute files included
- source root matches selected source profile
```

If any chunk fails a safety gate:

```text
- stop the routine
- do not continue to next chunk
- do not execute unsafe cleanup
- return operator_message explaining the reason
- preserve enough detail for debugging
```

### End states

Routine result states should include:

```text
completed_target
completed_exhausted
completed_partial_scan_bound
stopped_needs_review
failed
```

Definitions:

```text
completed_target:
  Imported the requested 1000 logical assets.

completed_exhausted:
  Imported fewer than 1000 because no eligible/acquirable historical inventory remains.
  Available Inventory should become No.

completed_partial_scan_bound:
  Imported fewer than 1000 because scan/listing bounds prevented finding more in this run.
  Available Inventory may remain Yes or Unknown depending on evidence.

stopped_needs_review:
  Acquisition/Source Intake succeeded or partially succeeded, but cleanup or verification needs operator/developer review.

failed:
  Hard error.
```

### No-op handling

Do not let the run silently do nothing.

If no assets are imported, return a clear reason:

```text
No historical assets imported.
Reason: no eligible/acquirable inventory remains.
```

or:

```text
No historical assets imported.
Reason: inventory refresh required before backfill.
```

or:

```text
No historical assets imported.
Reason: current scan window found no safely re-resolvable eligible rows.
```

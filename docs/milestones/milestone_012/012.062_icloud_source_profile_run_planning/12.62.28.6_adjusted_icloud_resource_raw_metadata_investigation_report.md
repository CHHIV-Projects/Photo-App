# Milestone 12.62.28.6 - Adjusted iCloud Resource Raw Metadata Investigation Report

## 1. Executive Summary

Evidence shows that `unsupported_adjusted_resource` is emitted by the isolated exact-selection helper when the provider asset exposes an actual adjusted downloadable version in `asset.versions`.

The code-proven trigger is:

```text
AssetVersionSize.ADJUSTED in asset.versions
```

The 41 stored inventory rows for source `66` all carry the normalized result of that helper decision:

```text
identity_ambiguous = true
eligibility_state = ambiguous_metadata_only
unsupported_reasons_json = ["unsupported_adjusted_resource"]
primary_content_type = public.heic
```

Per-row raw helper payloads for the 41 inventory rows are not persisted in the current inventory model. Existing docs/log searches did not find captured raw helper list payloads with `asset.versions` membership for those rows. Therefore, this report proves the exact code path and normalized stored evidence, but it does not prove per-row raw `asset.versions` keys for each of the 41 live rows without a new approved metadata-only helper listing.

No live metadata helper call was run.

No acquisition, cleanup execution, delete, eligibility rule change, Vault write, or Source Intake operation was run.

## 2. Code Path That Emits `unsupported_adjusted_resource`

`unsupported_adjusted_resource` is added in:

```text
backend/app/services/icloud_acquisition/icloud_exact_selection_helper.py
IcloudpdInternalProvider.describe_asset()
```

Relevant code path:

```text
line 141: self._asset_adjusted = AssetVersionSize.ADJUSTED
line 235: def describe_asset(...)
line 277: if self._asset_adjusted in versions:
line 278:     unsupported_reasons.append("unsupported_adjusted_resource")
```

The helper obtains `versions` from:

```text
versions = getattr(asset, "versions")
```

The trigger is item-level/provider-asset-level. It is not emitted by the inventory DB classifier directly. The inventory scan stores the helper's normalized item summary.

The adjusted marker is not added to the downloadable `resources` list. The helper only appends:

```text
AssetVersionSize.ORIGINAL -> resource_id primary_original
LivePhotoVersionSize.ORIGINAL -> resource_id live_photo_original
```

Then it separately checks whether `AssetVersionSize.ADJUSTED` exists in `asset.versions` and blocks the logical item by adding `unsupported_adjusted_resource`.

## 3. Exact Raw/Helper/Listing Fields That Trigger the Classification

Code-proven raw/helper source:

```text
asset.versions contains AssetVersionSize.ADJUSTED
```

The provider enum value is assigned at helper initialization:

```text
self._asset_adjusted = AssetVersionSize.ADJUSTED
```

Normalized helper output:

```text
unsupported_reasons includes unsupported_adjusted_resource
identity_ambiguous is true because unsupported_reasons is non-empty
resources still contain only primary_original and, for Live Photos, live_photo_original
```

Adapter/parser behavior:

```text
backend/app/services/icloud_acquisition/exact_selection_adapter.py
parse_listing_response()
```

The adapter parses `unsupported_reasons`, removes only explicitly non-blocking reasons, and sets:

```text
identity_ambiguous = bool(unsupported_reasons) or ...
unsupported_reasons = tuple(blocking helper reasons)
```

Inventory storage:

```text
backend/app/services/icloud_backfill_inventory_service.py
_upsert_inventory_row()
```

Stored fields:

```text
row.grouping = item.grouping
row.primary_relative_path = primary.relative_path
row.primary_content_type = primary.content_type
row.resource_count = len(item.resources)
```

Important negative evidence: `backend/tests/test_icloud_exact_selection_helper.py` shows `adjustmentType` metadata alone does not cause this unsupported reason. In that test, `adjustmentType` produces no ambiguity and no unsupported reason. The unsupported adjusted reason appears only after the fixture adds an adjusted version to `asset.versions`.

## 6. Original/Counterpart Analysis

Two counterpart concepts were separated:

### A. Same Helper Item Contains Primary/Original Resource While Adjusted Marker Is Present

Evidence shows this is true for all 41 rows at the normalized helper/inventory level:

| group | count | evidence |
| --- | ---: | --- |
| single-resource adjusted HEIC rows | 28 | `primary_relative_path` present, `resource_count=1`, `grouping=primary_asset_explicit`; helper code only stores a resource when original exists |
| Live Photo adjusted grouped rows | 13 | `primary_relative_path` present, `resource_count=2`, `grouping=live_photo_explicit`; helper code appends primary original and Live Photo original resources |

This means the current helper item exposed primary original metadata while also exposing an adjusted downloadable version marker. It does not prove whether the visible primary resource bytes are original, rendered, edited, or derivative; it proves the helper selected the provider original slot for the stored primary resource and blocked because an adjusted version also existed.

### B. Separate Original/Non-Adjusted Logical Item Elsewhere In Inventory

Read-only inventory comparison checked same path, same date folder plus filename stem, same filename stem, and same `created_remote_at`.

Grouped result:

| result | count |
| --- | ---: |
| adjusted row has apparent eligible original counterpart | 0 |
| adjusted row has apparent non-eligible original counterpart | 0 |
| adjusted row has no apparent counterpart in current inventory | 40 |
| unknown / insufficient metadata | 1 |

The one unknown row was `IMG_5472.HEIC`: it shared the same filename stem with an eligible inventory row, but the eligible row had a different date folder and different capture timestamp. That is insufficient evidence to call it an original counterpart.

## 9. What Is Known With Evidence

- `unsupported_adjusted_resource` is emitted by `IcloudpdInternalProvider.describe_asset()`.
- The exact code-proven trigger is `AssetVersionSize.ADJUSTED in asset.versions`.
- `adjustmentType` metadata-only is not the trigger according to the helper test.
- The trigger is item-level/provider-asset-level, not a stored DB classifier invention.
- The helper lists primary original resources separately from the adjusted-version check.
- The inventory model stores normalized helper fields, not raw `asset.versions` keys.
- All 41 rows are stored as `ambiguous_metadata_only`.
- All 41 rows are still unresolved: `backfill_completed=false`, `acquisition_state=null`.
- The 13 `resource_count=2` rows are Live Photo grouped rows based on `grouping=live_photo_explicit` and `is_live_photo=true`.
- Current acquisition preview/execution selection skips these rows because ambiguous inventory is not eligible.

## 10. What Remains Unknown

- The stored data does not prove whether each adjusted version is an edited rendered image, an alternate resource, a provider derivative, or another resource class.

- Separate original/non-adjusted logical counterparts are not proven in current inventory.

## 11. Policy Options Based On Evidence

| option | supported by current evidence | risk |
| --- | --- | --- |
| Keep adjusted resources skipped for v1.0 | yes | conservative; leaves 41 rows unresolved |
| Import primary_original while ignoring adjusted version | not yet | may discard meaningful edited/rendered user-visible version |
| Import adjusted version as standalone original | not yet | raw adjusted resource payload and version semantics are not persisted |
| Link adjusted version as derivative/version | not yet | requires product/versioning policy and likely schema/workflow design |
| Treat adjusted resource as internal-only and ignore | not yet | not proven by stored metadata |
| Add redacted helper diagnostic in a future milestone | yes | must avoid secrets, URLs, raw CloudKit payloads, and downloads |

## 12. Recommendation For Adjusted-Resource Handling In v1.0

Recommendation:

```text
Keep adjusted resources non-eligible for acquisition in v1.0 unless a later approved metadata-only diagnostic proves a narrower safe policy.
```

Evidence supports the current conservative block. It does not support making adjusted resources eligible, importing them as standalone originals, or silently ignoring the adjusted marker.

The next policy milestone should decide whether to:

```text
1. ignore adjusted provider versions and import only primary_original,
2. import adjusted versions as derivatives,
3. import adjusted versions as standalone visible assets,
4. keep them skipped with an operator-visible explanation.
```

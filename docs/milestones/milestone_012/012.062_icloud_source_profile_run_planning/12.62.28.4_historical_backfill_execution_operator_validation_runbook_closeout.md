## Known Limitations

- The current backfill status API is count-focused. Detailed per-inventory-row post-execution state may require read-only DB inspection or a future narrow status endpoint.
- The current backfill status endpoint reports `eligible_metadata_count` as inventory classification, not unresolved/acquirable remaining count. After the successful Step 8 completion, status still reported `eligible_metadata_count=959`; operators may reasonably expect a remaining-work count such as 958. Follow-up needed: expose separate completed, unresolved, and acquirable counts.
- During the first live metadata-only inventory validation for source `66`, the scan response reported `last_scan_created_count=1000` while `inventory_total_count=0` and `eligible_metadata_count=0`. A second scan reported the expected totals. This appears to be a first-scan count snapshot defect caused by counting before pending ORM rows are flushed when `autoflush=False`. The scan still saved the rows, but future scans that create new rows may report stale total/eligible counts until a follow-up scan. Recommended fix: add a targeted `db_session.flush()` before `_inventory_counts(...)` in the inventory scan service and add a regression test for first-scan count accuracy.
- During Step 6 live operator preview for source `66`, `skipped_ambiguous_count=41` while the selected item remained safe (`selected_inventory_count=1`, `matched_listing_count=1`, `unsafe_manifest_count=0`). This did not block the tiny preview because ambiguous inventory rows are skipped independently. Follow-up needed: inspect representative ambiguous inventory rows and helper metadata to understand whether ambiguity comes from helper duplicate item identity, Live Photo/resource grouping, unsupported resource relationship metadata, or another listing classification reason before broader acquisition runs.
- During Step 7 live operator dry-run acquisition for source `66`, the request used `include_items=true`, but the response returned an empty `items` array even though counts matched the Step 6 preview (`selected_inventory_count=1`, `matched_listing_count=1`, `selected_logical_count=1`, `selected_resource_count=1`). This is not a safety issue because no download, staging, Source Intake, run IDs, or completion updates occurred, but it is a response-detail gap. Follow-up needed: carry preview item details through the `dry_run=true` acquisition response when `include_items=true`, or document that dry-run acquire returns count-only details.
- The 12.62.28.3 synchronous `auto_run_source_intake=true` path maps Source Intake results back to inventory rows by durable batch item order. This is acceptable for immediate in-process execution, but it is not a durable reconciliation contract for later/asynchronous completion.
- When `auto_run_source_intake=false`, inventory rows are not marked `backfill_completed`; later completion should require a future stronger persistent inventory-to-batch mapping or explicit follow-up milestone.
- The optional `acquire_limit=5` validation has not been run yet.

# 12.62.29.3 — Durable iCloud Intake Run, Resume, and Timing

You are working in the Photo Organizer repo.

This milestone builds on 12.62.29.2. Do **not** redesign the unified iCloud Intake model again. Preserve the 12.62.29.2 product direction:

```text
Refresh / Prepare Next 1000 creates the exact candidate set.
Import Next 1000 imports that exact prepared set.
Top-level UI focuses on this run, not old historical accounting totals.
```

The goal of 12.62.29.3 is to harden the Import Next 1000 routine so full 1000-logical-asset runs are durable, resumable, and observable.

## Background / live findings from 12.62.29.2

12.62.29.2 successfully added:

```text
- durable prepared candidate snapshot
- exact prepared-set import
- deterministic expanding prepare scan
- unified iCloud Intake UI
- schema-aware durable manifest safety check
- small iCloud JPG Source Intake minimum-size fix
```

Two full live UI runs then exposed the next hardening needs.

### Finding 1 — Small iCloud JPG rejection

A valid iCloud JPG was acquired/staged but Source Intake rejected it because the internal iCloud batch handoff inherited the generic 51,200-byte minimum file-size filter.

This was fixed in 12.62.29.2 by:

```text
- adding PipelineContext minimum_file_size_bytes override
- using minimum_file_size_bytes = 1 for internal iCloud acquisition-batch Source Intake
- preserving the generic minimum for ordinary Source Intake
- adding regression coverage
```

In 12.62.29.3, do **not** reopen this design unless you discover a regression. Preserve it and make Source Intake chunk failures visible/resumable in the routine ledger.

### Finding 2 — Interrupted long import between chunks

A full Import Next 1000 run prepared 1000 logical candidates. The first 7 chunks completed cleanly:

```text
logical imported: 700
resources imported/cleaned: 1138
cleanup safety counters: all 0
staging files after interruption: 0
drop zone files after interruption: 0
```

The process then stopped after cleanup execution for chunk 7 and before chunk 8 acquisition was created.

No failed acquisition, Source Intake, cleanup, unsafe staged file, active operation, or Drop Zone problem was recorded.

The prepare run was stranded as:

```text
status: running
remaining prepared candidates: 300
```

Manual local DB repair was required to resume.

This is the main 12.62.29.3 problem.

## Product goal

Make Import Next 1000 safe for real use even when:

```text
- browser disconnects
- HTTP request times out
- backend process stops between chunks
- one chunk fails but prior chunks succeeded
- a prepared set is partially consumed
```

The operator should never need manual DB repair.

The UI should make it clear:

```text
- what is running
- what chunk completed
- how many logical candidates were imported
- how many files/resources were imported and cleaned
- whether the run can resume
- where time is being spent
```

## Core requirement 2 — Persist chunk completion before moving on

The live interruption happened between chunks. Therefore:

```text
After each chunk completes cleanup successfully, persist the chunk result and import-run aggregate before starting the next chunk.
```

A completed chunk must remain completed even if the backend/browser dies immediately afterward.

Do not leave the entire prepare run stuck as `running` merely because a later chunk was never started.

At any point, the system should be able to answer:

```text
- chunks completed
- chunks pending
- current or last active chunk
- exact remaining prepared candidate IDs
- whether resume is safe
```

## Core requirement 3 — Resume interrupted import

Add a safe operator path to resume interrupted or partially complete imports.

Acceptable API approaches:

### Preferred bounded-request approach

Avoid one long fragile HTTP request for all 1000 candidates. Prefer a chunk-at-a-time or short-bounded execution model.

For example:

```text
POST /api/admin/icloud-routine/intake/import/start
GET  /api/admin/icloud-routine/intake/import/status?source_id=<id>
POST /api/admin/icloud-routine/intake/import/advance
POST /api/admin/icloud-routine/intake/import/resume
```

or equivalent repo-appropriate endpoint names.

The UI can call `advance` repeatedly, one chunk at a time, while polling status.

### Compatibility approach

If you keep existing endpoint names for now, that is acceptable, but the behavior must still become durable and resumable.

Existing endpoints may remain:

```text
GET  /api/admin/icloud-routine/historical/status?source_id=<id>
POST /api/admin/icloud-routine/historical/refresh-inventory
POST /api/admin/icloud-routine/historical/run-next-batch
```

But the UI label must remain:

```text
iCloud Intake
```

not historical backfill.

### Resume behavior

Resume should:

```text
1. Find the latest incomplete import run for the selected source/profile.
2. Verify the prepare run and candidate snapshot still exist.
3. Verify already-completed candidates remain completed and are not re-imported.
4. Identify pending prepared candidates.
5. Continue with the next pending chunk.
6. Preserve the exact prepared candidate identity.
7. Continue reporting cumulative totals.
```

If resume is unsafe, stop with a clear operator message and do not mutate data.

Examples:

```text
Resume available: 300 logical candidates remaining from prepare run 3.
Resume unavailable: active cleanup operation still exists.
Resume unavailable: prepared candidate snapshot expired and has no safe incomplete import run.
Resume unavailable: candidate state mismatch detected.
```

## Core requirement 4 — Stale running-state recovery

Add safe recovery for stale `running` states.

On status refresh, and optionally backend startup if there is an existing project pattern, detect:

```text
- import run marked running but no active acquisition/source-intake/cleanup operation exists
- prepare run marked running but no active child operation exists
- chunk marked running but no active operation exists
```

Do not automatically continue importing without operator action unless the existing app has a safe pattern for that.

Preferred behavior:

```text
- mark the run as resume_available or paused_interrupted
- show Resume Interrupted Import in the UI
- preserve all completed chunk records
- keep pending prepared candidates intact
```

Avoid manual DB repair.

## Core requirement 5 — Retryable execution failures stay separate from deferred / needs policy

Preserve the distinction added in 12.62.29.2.

Deferred / needs-policy means:

```text
adjusted
ambiguous
unsupported
policy-blocked
```

Retryable execution failure means something like:

```text
fresh helper listing incomplete
transient manifest incompleteness
download/staging not attempted or not completed
```

Top-level run report should include:

```text
New deferred / needs policy this run: <count>
Retryable execution failures: <count>
```

Do not mix retryable execution failures into deferred/needs-policy.

The known `IMG_4883.HEIC` style case should remain retryable and visible, not silently lost and not counted as deferred.

## Core requirement 6 — Source Intake and cleanup failure visibility

Make chunk failures visible and resumable/reviewable.

If Source Intake fails for a chunk:

```text
- record the Source Intake run id
- record logical/resource counts where known
- record failure count
- stop the import run as stopped_needs_review or failed, depending on severity
- do not automatically cleanup unless existing safety gates prove it is safe
- allow a safe retry/recovery path if repo patterns already support it
```

If cleanup dry run or cleanup execution fails:

```text
- record cleanup dry-run/execution ids
- record safety counters
- stop needs review
- do not proceed to next chunk
```

Do not weaken existing cleanup gates.

## Core requirement 7 — Timing instrumentation

Add per-run and per-chunk timing so we can understand where time is going.

The operator noticed that 1000-asset routines take a long time and there can be a big lag between chunks.

Record timing fields in the chunk ledger and/or associated JSON report.

Capture at least:

```text
chunk_total_seconds
candidate_load_seconds
fresh_resolution_seconds
download_stage_seconds
source_intake_seconds
cleanup_dry_run_seconds
cleanup_execute_seconds
db_state_update_seconds
inter_chunk_gap_seconds
```

If exact phase timing is difficult because lower-level services do not expose timings yet, implement the best safe approximation and document what is measured.

Important metric:

```text
inter_chunk_gap_seconds =
  next_chunk_started_at - previous_chunk_completed_at
```

The goal is to distinguish:

```text
- iCloud helper/listing/re-resolution time
- download/staging time
- local Source Intake compute/disk/DB time
- cleanup verification/deletion time
- pure orchestration gap between chunks
```

## Acceptance criteria

12.62.29.3 is acceptable when:

```text
- a 1000-candidate import no longer depends on one fragile long synchronous request
- completed chunks are durable
- interrupted runs can be resumed without manual DB repair
- stale running states are safely detected
- retryable execution failures are visible and separate from deferred/needs-policy
- Source Intake and cleanup failures are visible at chunk/run level
- the UI shows progress/resume status without exposing low-level noise on the main card
- timing data gives enough visibility to diagnose whether slowness is iCloud, download, Source Intake, cleanup, DB, or inter-chunk orchestration
```

Stop and ask before continuing if:

```text
- adding durable run/chunk tables conflicts with existing models
- chunk-at-a-time execution requires a broader frontend/API redesign than expected
- safe resume cannot preserve exact prepared candidate identity
- stale running-state recovery cannot distinguish active work from interrupted work
- timing instrumentation requires invasive changes to lower-level services
```

Do not commit.

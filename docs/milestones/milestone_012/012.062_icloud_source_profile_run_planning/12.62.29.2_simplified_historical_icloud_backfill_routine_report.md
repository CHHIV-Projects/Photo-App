# 12.62.29.2 Simplified Historical iCloud Backfill Routine Report

Date: 2026-07-04

## 1. Corrected Product Model

The Ingestion-page iCloud routine is now a unified `iCloud Intake` flow:

```text
Refresh / Prepare Next 1000
Import Next 1000
```

Refresh prepares the exact next candidate set. Import consumes that exact prepared set. The import path no longer silently recalculates a hidden selection from whatever inventory rows happen to be eligible later.

## 2. Durable Prepared Candidate Snapshot

Added an additive/idempotent schema:

```text
icloud_intake_prepare_runs
icloud_intake_prepared_candidates
```

`icloud_intake_prepare_runs` stores the target, ready candidate count, new deferred count, provider records scanned, scan depth used, source exhaustion state, prepared timestamp, expiry timestamp, and operator message.

`icloud_intake_prepared_candidates` stores the exact inventory ids selected for import, their order, safe path/identity metadata, resource counts, Live Photo flag, and candidate state.

Prepared sets expire after 60 minutes. Import requires a fresh, unconsumed prepare run for the same source, and blocks if prepared candidates are already completed or no longer eligible/acquirable.

## 3. Deterministic Expanding Prepare Scan

Prepare uses a conservative expanding scan sequence:

```text
1000 -> 2000 -> 3000 -> 5000 -> 10000
```

The routine scans metadata only, selects up to 1000 good unknown eligible logical candidates, and stops when the target is ready, provider exhaustion is proven, or the local scan ceiling is reached.

Available Inventory now means:

```text
Yes     logical_candidates_ready > 0
No      logical_candidates_ready = 0 and provider/source exhaustion is proven
Unknown scan ceiling/continuation limits prevent a definitive answer
```

The routine does not fake source exhaustion.

## 4. Import Behavior

`Import Next 1000` executes the latest valid prepared set in chunks of 100 logical candidates. Each chunk keeps the existing safety chain:

```text
acquisition
Source Intake
cleanup dry run
exact acquired_resource_paths match
guarded cleanup execution
```

The acquisition service now accepts explicit prepared `inventory_ids`, while retaining live re-resolution and manifest safety checks. If a candidate becomes stale/unsafe during final re-resolution, the prepared-candidate row is marked accordingly and the run can report fewer logical imports than prepared.

Follow-up fix after the first live UI attempt: the durable manifest safety check is now schema-aware instead of scanning the entire JSON for broad substrings. Safe relative paths such as filenames containing `SESSION` no longer trigger a false `unsafe_manifest` failure. Actual unsafe manifest keys or URL/absolute path leakage still fail closed.

Durable manifest exceptions now close the acquisition run/batch as failed rather than leaving an active `running` lease.

## 5. UI Behavior

The top-level Ingestion panel is now labeled `iCloud Intake` and emphasizes:

```text
Source Profile
Total Imported from Source
Last Inventory Refresh
Available Inventory
Logical Candidates Ready
Refresh / Prepare Next 1000
Import Next 1000
Last Run Summary
```

The last run summary reports logical candidates, logical imported, files/resources imported, local staging files cleaned, new deferred/needs-policy count, and retryable execution-failure count for the run.

Historical accounting such as known inventory, eligible remaining, total deferred, scan depth, run ids, chunk ids, and cleanup internals has moved to collapsed Details.

## 6. Deferred Reporting

Top-level routine results report newly deferred items for the current prepare/import pass only. Existing historical deferred totals remain available in Details and through the safe deferred-assets endpoint, but old deferred totals are not repeated as the headline result for every run.

Retryable execution failures are not counted as deferred/needs-policy. A zero-import execution failure leaves the prepared set available for retry instead of consuming it.

## 7. Live Full-Run Findings

Date: 2026-07-05

Live UI testing against source `66` (`Chuck iCloud E2E Test v3`) confirmed the chunk-level import safety chain, but also exposed issues that required intervention.

### Small iCloud JPG Rejection

A live run acquired 100 logical items / 101 resources, then Source Intake rejected:

```text
2026/02/07/IMG_5244.JPG
40655 bytes
```

The rejection happened because internal iCloud batch Source Intake inherited the generic `51200` byte minimum file-size filter. This left the operator flow stopped for review and prevented automatic cleanup, even though the resource had already passed iCloud staging safety checks.

Resolution added after discovery:

```text
- PipelineContext supports optional minimum_file_size_bytes
- internal iCloud acquisition-batch Source Intake uses minimum_file_size_bytes = 1
- ordinary Source Intake retains the existing global minimum
- regression coverage added for a small iCloud JPG
```

Manual live recovery completed safely:

```text
batch_id: 43
source_intake_retry_run_id: 91
cleanup_dry_run_id: 147
cleanup_execution_run_id: 148
deleted staging files: 101
cleanup safety counters: all 0
```

### Interrupted Long Import

Another live run prepared 1000 logical candidates in prepare run `3`. The first 7 chunks completed:

```text
logical imported: 700
resources imported / cleaned: 1138
acquisition runs: 78-84
Source Intake runs: 102-108
latest cleanup execution: 182
cleanup safety counters: all 0
staging files after interruption: 0
drop zone files after interruption: 0
```

The process stopped after cleanup execution `182` and before chunk 8 acquisition was created. No failed acquisition, Source Intake, cleanup, or unsafe staged file was recorded. The prepare run remained:

```text
prepare_run_id: 3
status: running
remaining prepared candidates: 300
```

This indicates the long synchronous UI/API request can be interrupted between chunks. Because 12.62.29.2 does not yet have a durable routine-run/chunk ledger, the remaining prepared candidates required manual DB repair:

```text
status restored to: prepared
logical_candidates_ready: 300
expiry extended: 2026-07-05T16:31:54Z
```

### Retryable Manifest Candidate

One prepared candidate remains retryable:

```text
2025/10/30/IMG_4883.HEIC
inventory_id: 1294
state: execution_failed_retryable
error: unsafe_manifest
```

This was not downloaded or staged. It appears to be a single fresh-helper-listing incompleteness rather than the earlier broad manifest false positive. It should be retried in a later run if the helper later exposes a complete safe manifest.

## 8. Follow-Up Required

The live findings point to these next hardening items:

```text
- add a durable iCloud Intake routine-run and per-chunk ledger
- persist chunk completion before starting the next acquisition
- make interrupted prepared sets resumable without manual DB edits
- recover stale running prepare runs on status refresh or backend startup
- expose a safe "resume interrupted import" operator path
- clarify logical asset counts versus resource/file counts in UI reports
- keep retryable execution failures visible and separate from deferred/needs-policy
```

## 11. Known Limitations

- There is still no persisted provider cursor/page-token/date-boundary continuation.
- The local prepare ceiling is 10000 provider records.
- The import endpoint remains synchronous.
- There is no durable routine-run/chunk ledger yet, so an interrupted long run can strand a prepared set in `running` until repaired.

# Milestone 12.62.28.7 — Source Profile Deferred Asset Ledger

## Purpose

Implement a durable, searchable, source-profile-level ledger for remote assets that are observed but not acquired/imported because they are skipped, ambiguous, unsupported, policy-deferred, stale, or otherwise unresolved.

This milestone is motivated by adjusted iCloud resources.

Current policy:

```text
Adjusted resources remain non-eligible for acquisition in v1.0 until product policy is defined.
```

But they must not disappear from operator visibility.

The system should retain enough safe metadata to answer:

```text
How many assets exist in this cloud/source profile that are not yet in Photo Organizer?
Why were they skipped or deferred?
When were they first seen?
When were they last seen?
Did the reason change?
Can they be found and reprocessed later if policy changes?
```

## Important product-owner clarification

“Append-only” does **not** mean duplicating the same skipped asset into a growing event log every run.

The desired behavior is:

```text
Append new data only when a new skipped/deferred item is first seen,
or when a meaningful state/reason/classification change occurs.
```

Do not append duplicate events for unchanged skipped assets on every run.

The desired design has two layers:

```text
Current-state ledger:
  one row per source_profile + remote identity + deferral category
  updated with first_seen_at, last_seen_at, first_seen_run_id, last_seen_run_id, current reason/state

Event/history ledger:
  append-only records for first_seen, reason_changed, classification_changed, resolved, no_longer_observed, etc.
  no duplicate event spam for unchanged observations
```

Example:

```text
Run 1:
  IMG_6247.HEIC first seen as adjusted_resource_deferred
  → create current-state row
  → append first_deferred event

Run 2:
  same IMG_6247.HEIC still adjusted_resource_deferred
  → update last_seen_at / last_seen_run_id
  → do NOT append duplicate event

Run 3:
  policy changes and item becomes eligible_original_available
  → update current-state row
  → append classification_changed event

Run 4:
  asset imported/resolved
  → update current-state row
  → append resolved event
```

Per-run JSON/report summaries may include unchanged counts, such as:

```text
41 adjusted_resource_deferred rows seen
0 new
0 changed
41 unchanged
0 resolved
```

But the durable event table should not duplicate unchanged records.

## When to write/update the ledger

Initial scope should populate/update the ledger during iCloud metadata inventory scan, because that is where adjusted/ambiguous/unsupported rows are first observed.

For each non-eligible inventory row, upsert the current-state ledger.

Rows to include:

```text
eligibility_state = ambiguous_metadata_only
eligibility_state = unsupported_metadata_only
unsupported_reasons_json not empty
identity_ambiguous = true
pending_classification if present
```

At minimum, this milestone must include adjusted-resource rows:

```text
unsupported_reasons_json includes unsupported_adjusted_resource
```

If adding all non-eligible categories is clean and tested, do it. If not, start with adjusted-resource rows and document follow-up.

Do not make eligible rows deferred.

Do not change acquisition selection rules.

If none changed:



```text

```

## Decisions

### 1. Scope of rows to include

Implement the ledger for **all non-eligible iCloud inventory rows** if the mapping stays simple and safe.

At minimum, adjusted-resource rows must be included.

Do not invent weak categories. Use clear fallback categories.

Approved category mapping:

```text
unsupported_adjusted_resource
  -> adjusted_resource_deferred

identity_ambiguous = true with no clearer reason
  -> ambiguous_metadata_deferred

unsupported_reasons_json non-empty, non-adjusted
  -> unsupported_metadata_deferred

eligibility_state = pending_classification, if present
  -> pending_classification_deferred
```

If a row does not map cleanly, classify it conservatively as:

```text
unknown_deferred
```

and report it.

### 2. List endpoint

Include a bounded list endpoint now.

The user wants the skipped/deferred assets to remain visible/searchable/retrievable later. Status counts plus JSON report are useful, but not enough.

Preferred endpoint:

```text
GET /api/admin/source-profiles/{source_id}/deferred-assets
```

Keep it narrow and safe:

```text
source_id required
limit default 100, max 500
category optional
reason_code optional
state optional
no credentials
no tokens
no signed URLs
no raw helper payloads
```

Return safe, operator-useful fields only:


Do not build UI.

### 3. Uniqueness

Use this uniqueness identity:

```text
source_profile_id + remote_identity_basis + remote_identity + deferred_category
```

`inventory_id` should be nullable/reference metadata, not part of identity.

### 4. Current-state plus event-history behavior

Proceed with:

```text
SourceProfileDeferredAsset
SourceProfileDeferredAssetEvent
```

Current-state row should update on repeated unchanged observations:

```text
last_seen_at
last_seen_run_id
observation_count
```

Do **not** append a duplicate per-asset event for unchanged observations.

Append event only for:

```text
first_deferred
reason_changed
classification_changed
policy_status_changed
resolved / no_longer_deferred, if implemented
reopened
```

### 5. JSON comparison / change detection

Canonicalize before comparison.

Specifically:

```text

```

Semantically identical reason lists must not generate noisy `reason_changed` events.

Also normalize simple strings where appropriate, such as category/reason/state values.

## Summary

Implemented a durable iCloud Intake import run/chunk ledger so `Import Next 1000` no longer depends on one long fragile HTTP request. The UI now starts or resumes an import run, then advances it one bounded chunk at a time through explicit `/intake/` endpoints.

## Durable Schema

Added additive/idempotent schema for:

```text
icloud_intake_import_runs
icloud_intake_import_chunks
```

The run ledger tracks source, prepare run, run status, cumulative logical/resource imports, local staging cleanup totals, retryable/terminal execution failures, Source Intake failures, cleanup failures, current chunk, total chunks, resume/interruption timestamps, operator message, stop reason, and durable report path.

The chunk ledger tracks candidate index bounds, chunk status, imported logical/resources, cleanup counts, acquisition/batch/Source Intake/cleanup run IDs, cleanup safety counters, timing fields, operator message, and stop reason.

Startup schema sync now ensures:

```text
ensure_icloud_intake_prepare_schema
ensure_icloud_intake_import_schema
```

after the iCloud backfill schema.

## API Behavior

Added explicit iCloud Intake endpoints:

```text
GET  /api/admin/icloud-routine/intake/import/status?source_id=<id>
POST /api/admin/icloud-routine/intake/import/start
POST /api/admin/icloud-routine/intake/import/resume
POST /api/admin/icloud-routine/intake/import/advance
```

The old `/historical/...` endpoints remain in place for compatibility; new UI-facing behavior uses `iCloud Intake` language.

`start` creates a durable import run and pending chunk rows for the exact prepared candidate set.

`advance` runs exactly one chunk through acquisition, Source Intake, cleanup dry run, exact acquired-path verification, and guarded cleanup execution. Completed chunk state is committed before the next chunk can start.

`resume` only re-arms a resumable/interrupted run. It does not automatically import; the operator action is explicit.

## Resume and Stale Recovery

Status refresh may recover stale running state when there are no active acquisition, Source Intake, or cleanup operations.

Recovery behavior:

```text
running chunk with imported resources not fully cleaned -> stopped_needs_review
running chunk without imported/uncleaned resources -> retryable_failed
running import between chunks -> resume_available
legacy running prepare with no import run and no active child work -> prepared
```

This prevents the 12.62.29.2 failure mode where a run stopped between chunk 7 cleanup and chunk 8 acquisition, leaving the prepare run stranded as `running`.

## Timing Fields

Chunk timing fields implemented:

```text
chunk_total_seconds
candidate_load_seconds
fresh_resolution_seconds
download_stage_seconds
source_intake_seconds
cleanup_dry_run_seconds
cleanup_execute_seconds

```

Known timing limitation: the lower-level acquisition service does not yet expose separate fresh-resolution, download/stage, and Source Intake phase timings. For now, the durable chunk ledger records total acquisition elapsed time as an approximation and stores a `timing_note` explaining that limitation.

## Durable Reports

Each import run writes a safe local JSON report:

```text
storage/logs/icloud_intake_import_reports/icloud_intake_import_run_<id>.json
```

The report includes run totals, chunk statuses, run IDs, cleanup safety counters, timing values, operator messages, stop reasons, remaining logical candidates, and `manual_db_repair_required: false`.

## Post-Implementation UI Refresh Failure

The first fresh UI `Refresh / Prepare Next 1000` attempt on 2026-07-06 ran for several minutes and then returned `Failed to fetch`. The backend terminal showed a PostgreSQL uniqueness violation:

```text
duplicate key value violates unique constraint "uq_icloud_remote_asset_inventory_source_identity"
Key (source_profile_id, remote_identity_basis, remote_identity)=(66, helper_item_id_observed_stable, AZkMOK6EBV3AegbQW4/Qnq9p17uq) already exists.
```

Root cause:

```text
The helper returned the same stable item_id more than once inside one metadata-only listing.
The inventory scan session has autoflush disabled.
The second occurrence did not see the first pending insert, so both inserts were queued.
The final flush then violated the unique inventory identity constraint.
```

Follow-up fix:

```text
Metadata-only inventory scan now dedupes duplicate helper item identities within the same listing before upserting rows.
Duplicate observations in one helper response count as one inventory observation.
No acquisition, download, staging, Source Intake, Vault write, or cleanup behavior changed.
```

## Known Limitations

The lower-level acquisition result does not yet expose fine-grained phase timing, so the intake ledger cannot distinguish iCloud fresh resolution, download/stage, and Source Intake duration precisely.

`stopped_needs_review` remains intentionally operator-review-only. It is not auto-resumed if imported resources may remain uncleaned or cleanup/Source Intake safety state needs review.

The old `/historical/run-next-batch` compatibility path remains synchronous and should not be the primary UI path for full 1000-candidate runs.

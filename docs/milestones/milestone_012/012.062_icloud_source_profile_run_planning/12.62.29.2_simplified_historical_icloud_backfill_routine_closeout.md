## Backend Changes

Added durable prepared-candidate tables:

```text
icloud_intake_prepare_runs
icloud_intake_prepared_candidates
```

Added idempotent schema ensure behavior for those tables.

Updated the historical routine service so refresh now:

```text
- runs metadata-only inventory scans with deterministic expansion
- prepares up to 1000 eligible unknown logical candidates
- writes a durable exact candidate snapshot
- reports candidate readiness, scan depth, provider records scanned, source exhaustion state, and newly deferred count
```

Updated import so it:

```text
- requires a fresh, unconsumed prepared set
- blocks expired/stale/completed candidate sets
- executes only the prepared inventory ids
- processes chunks of 100
- preserves acquisition, Source Intake, cleanup dry-run, exact-path match, and guarded cleanup execution gates
```

The shared backfill acquisition execution path now accepts explicit `inventory_ids` for prepared-set imports while preserving existing selection behavior for legacy callers.

## Post-Validation Fix

The first live UI attempt exposed a false `unsafe_manifest` failure. The durable manifest safety check had scanned all manifest JSON values for broad forbidden substrings, so an ordinary filename containing `ENGAGEMENT_SESSION` was treated as unsafe.

Fixes added:

```text
- manifest validation is now schema-aware and key/path based
- safe relative paths may contain ordinary words such as SESSION
- unsafe manifest keys and URL/absolute path leakage still fail closed
- manifest-validation exceptions close acquisition run/batch state
- retryable execution failures are reported separately from needs-policy deferred
- zero-import execution failures leave the prepared set available for retry
```

## Post-Closeout Live Validation Addendum

Date: 2026-07-05

Subsequent full UI runs against source `66` (`Chuck iCloud E2E Test v3`) exposed two important operator-flow gaps that were not visible in mocked/unit validation.

### 1. Small iCloud JPG Rejected By Generic Source Intake Size Rule

One live run acquired and staged 100 logical items / 101 resources, but Source Intake rejected one valid iCloud resource:

```text
resource: 2026/02/07/IMG_5244.JPG
size: 40655 bytes
generic Source Intake minimum: 51200 bytes
result: Source Intake completed with errors; cleanup did not run automatically
```

This was not an acquisition or manifest-safety failure. It was caused by the internal iCloud batch handoff inheriting the generic Source Intake minimum-file-size filter. That left the operator flow stopped for review even though the resource had already passed iCloud exact-selection staging, root/path safety, size, and hash checks.

Follow-up fix added after this discovery:

```text
- PipelineContext now supports an optional per-run minimum_file_size_bytes override
- internal iCloud acquisition-batch Source Intake uses a 1-byte minimum
- ordinary Source Intake keeps the existing global 51200-byte minimum
- regression test added for a small iCloud JPG below the generic threshold
```

Manual live recovery was required for the affected batch:

```text
batch_id: 43
source_intake_retry_run_id: 91
cleanup_dry_run_id: 147
cleanup_execution_run_id: 148
cleanup_deleted_count: 101
safety counters: all 0
```

### 2. Long Synchronous Import Interrupted Between Chunks

A later full `Import Next 1000` run prepared 1000 logical candidates in prepare run `3`. The first 7 internal chunks completed cleanly:

```text
acquisition runs: 78-84
batches: 54-60
Source Intake runs: 102-108
cleanup execution runs: 170, 172, 174, 176, 178, 180, 182
logical imported before interruption: 700
resources imported/cleaned before interruption: 1138
cleanup safety counters: all 0
staging files after interruption: 0
drop zone files after interruption: 0
```

The process stopped after cleanup execution `182` and before chunk 8 acquisition was created. No failed acquisition, failed Source Intake, failed cleanup, active operation, staged file, Drop Zone file, or cleanup safety issue was recorded. The durable prepare row was left in:

```text
prepare_run_id: 3
status: running
imported candidates: 700
remaining prepared candidates: 300
```

This points to an interrupted long-running HTTP/operator request rather than a data-safety failure. The current implementation marks the prepare run `running` at the start and finalizes only at the end, so an interruption between chunks can strand the remaining candidate set.

Manual local DB repair was required so the operator could finish the exact interrupted prepared set:

```text
prepare_run_id: 3
restored status: prepared
logical_candidates_ready: 300
expiry extended: 2026-07-05T16:31:54Z
active acquisition/source-intake/cleanup operations: 0
staging/drop-zone files: 0
```

### 3. Retryable Single-Asset Manifest Case

One prepared candidate from prepare run `2` remained retryable:

```text
resource: 2025/10/30/IMG_4883.HEIC
inventory_id: 1294
state: execution_failed_retryable
error: unsafe_manifest
message: Fresh helper listing did not expose a complete safe resource manifest.
```

This appears to be a single-asset fresh-listing incompleteness, not the earlier broad false-positive manifest bug. It was not downloaded, staged, imported, or written to Vault. It remains eligible for a later run if a future helper listing exposes a complete safe manifest.

## Follow-Up Required From Live Validation

The full live tests showed that the core per-chunk safety chain works, but the operator routine needs stronger durable orchestration for long runs:

```text
- add a durable routine-run / chunk ledger for iCloud Intake
- persist each chunk outcome before starting the next chunk
- make interrupted prepared sets resumable without manual DB repair
- finalize or recover stale running prepare runs on status refresh/backend startup
- surface "Resume interrupted import" or an equivalent safe operator path
- preserve exact prepared candidate identity while resuming
- make logical-vs-resource counts clearer in UI/reporting
- keep retryable execution failures visible but separate from deferred/needs-policy
```

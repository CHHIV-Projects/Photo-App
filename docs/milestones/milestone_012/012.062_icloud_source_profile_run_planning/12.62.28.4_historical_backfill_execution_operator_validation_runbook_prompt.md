## Required validation flow

The runbook should enforce this sequence:

### Step 0 — backend health

Confirm backend is running.

Use existing health/admin endpoint patterns if available.

Do not invent a new endpoint unless necessary.

### Step 1 — inventory status

Call existing status endpoint:

```text
GET /api/admin/icloud-backfill/status?source_id=<SOURCE_ID>
```

Expected purpose:

```text
- confirm backfill state exists
- confirm inventory rows exist
- confirm eligible/pending rows exist
- confirm no obvious failed/blocked state
```

### Step 2 — preview endpoint

Call:

```text
POST /api/admin/icloud-backfill/acquire-preview
```

Use tiny operator values first:

```json
{
  "source_id": <SOURCE_ID>,
  "acquire_limit": 1,
  "max_listing_candidates": 1000,
  "include_items": true
}
```

Expected:

```text
- no download
- no staging
- no Source Intake
- no completion updates
- count-focused preview response
```

### Step 3 — acquire endpoint with dry_run=true

Call:

```text
POST /api/admin/icloud-backfill/acquire
```

With:

```json
{
  "source_id": <SOURCE_ID>,
  "acquire_limit": 1,
  "max_listing_candidates": 1000,
  "dry_run": true,
  "auto_run_source_intake": true,
  "include_items": true
}
```

Expected:

```text
- same safety behavior as preview
- no download
- no staging
- no Source Intake
- no completion updates
```

### Step 4 — gated real execution

Prepare but do **not run** the command unless I explicitly approve it:

```json
{
  "source_id": <SOURCE_ID>,
  "acquire_limit": 1,
  "max_listing_candidates": 1000,
  "dry_run": false,
  "auto_run_source_intake": true,
  "include_items": true
}
```

This is the first real backend execution.

It must remain tiny:

```text
acquire_limit = 1
```

Expected if approved and run:

```text
- durable acquisition executes
- files stage only through managed iCloud staging path
- Source Intake runs if durable batch is ready
- inventory row is marked backfill_completed only after Source Intake proves every selected resource resolved
- cleanup remains separate/review-controlled
```

### Step 5 — inspect after real execution

Provide commands to inspect:

```text
- API response
- backfill status
- relevant logs/reports
- inventory row state
- acquisition run/batch IDs
- Source Intake run ID
- staging/cleanup next action
```

Do not require direct manual DB edits.

Read-only DB inspection is acceptable if that is the only practical way to verify state, but prefer existing API/status endpoints first.

## Stop conditions

The runbook should instruct the operator to stop if any of these happen:

```text
dry_run=true causes download/staging/Source Intake
preview and acquire dry_run=true disagree unexpectedly
source_id is ambiguous
inventory status is missing or failed
eligible inventory count is zero
preview returns stale/missing rows only
Live Photo manifest appears partial/unsafe
real execution response lacks acquisition_run_id or acquisition_batch_id when expected
Source Intake fails or is blocked
inventory row is marked complete before Source Intake success
cleanup appears to run automatically without review
any remote deletion behavior appears
any Vault write appears outside Source Intake
```

## Product-owner decisions

### Main workflow

The iCloud operator UI should be simple:

```text
Step 1: Refresh Inventory / Metadata Scan
Step 2: Preview / Set Acquisition Limit
Step 3: Run
```

The **Run** button should internally orchestrate the safe backend sequence:

```text
1. use the latest successful preview or refresh preview if needed
2. execute bounded acquisition
3. allow Source Intake handoff through the existing backend path
4. run guarded cleanup dry run
5. execute cleanup only if cleanup dry-run exactly matches the just-acquired staged resources and all safety counts are zero
6. show final confirmation summary
```

The operator should not be forced through separate cleanup steps during normal successful use.

If cleanup is not safe, the UI must stop and show:

```text
Run completed, but cleanup needs review.
```

Do not hide cleanup safety failures.

### Limit must be free-form

The acquisition limit must be a free-form positive integer input.

Defaults are okay, but do not restrict the user to preset buttons.

Examples that must be allowed by the UI:

```text
New Import limit: 500
Historical Backfill limit: 2000
```

The UI may warn on large values, but should not block unless the value is invalid or exceeds an explicit hard backend cap.

### If limit is larger than scan cap

If the requested limit is larger than the scan/candidate-search cap, do **not** kill the job and do **not** treat it as an error.

Behavior should be:

```text
Process up to what the scan window can safely find.
Stop at scan/candidate cap.
Report partial completion with notation.
```

Example UI wording:

```text
Requested: 2000
Scanned: 1000
Imported: 953
Stopped because candidate search cap was reached before the requested limit was satisfied.
```

This is a normal partial completion state, not a failure.

### Batch size

Use:

```text
default batch size = 25 logical items
```

For this milestone, batch size should not be a prominent main UI control.

Put it in one of these places:

```text
- hidden frontend constant, or
- collapsed Advanced section, or
- existing Admin/internal defaults area
```

Preferred behavior:

```text
Limit = total desired logical imports for this run.
Batch size = internal chunk size for acquire/intake/cleanup loops.
Candidate search cap = maximum candidates inspected per selection window.
```

The UI should be ready for this model even if the backend currently processes one bounded acquisition at a time.

### Candidate search cap

Default:

```text
candidate_search_cap = 1000
```

Do not make this a prominent main UI control.

It can live in:

```text
- collapsed Advanced section, or
- Admin/internal defaults, or
- hidden default for this first UI version
```

### Asset scope

Default:

```text
All supported assets
```

Do not make asset scope a prominent main UI control.

99.99% of normal use should be all supported assets.

The iCloud UI must distinguish run mode.

Use two run modes:

```text
Import New iCloud Photos

```

Purpose:

```text

```

Default UI values:

```text

batch size internal default: 25

```

Purpose:

```text
Continue importing older eligible items already discovered in the iCloud inventory/backfill ledger.
```

Default UI values:

```text

batch size internal default: 25
candidate search cap default: 1000
asset scope: all supported assets
```

The existing 12.62.28.x backend validation is primarily the historical backfill path.

If the current backend does not yet support the “new import” mode through the same UI endpoints, implement the UI structure but disable or mark the New Import mode as:

```text

```

Do not fake a new-import execution path.

## Run behavior

Button:

```text
Run
```

The operator sees one Run action.

Internally, for historical backfill mode, perform:

```text
1. use latest safe preview, or re-preview if stale/parameters changed
2. call acquisition execute with dry_run=false
3. auto_run_source_intake=true
4. wait/poll until acquisition and Source Intake complete
5. run cleanup dry run
6. verify cleanup candidates match just-staged/imported resources
7. execute guarded cleanup only if safe
8. show final summary
```

Run parameters:

```text
source_id = selected source
acquire_limit = free-form limit
max_listing_candidates = candidate_search_cap default 1000
dry_run = false
auto_run_source_intake = true
include_items = true if useful
asset_scope = all supported assets if supported
```

If the backend currently does not expose a single orchestration endpoint that includes cleanup, implement the UI as a client-side orchestrator over existing endpoints.

Do not add broad backend orchestration unless necessary.

If a small backend helper endpoint is clearly needed, stop and ask before broad backend changes.

## 2. Free-form limit and backend cap

The product decision is:

```text id="9of5wn"
Limit should be free-form.
If requested limit exceeds scan/candidate cap, do not fail the job.
Process what the scan window can safely find, then report partial completion.
```

Current backend cap of `acquire_limit <= 1000` conflicts with the desired UI, because the product owner wants values like:

```text id="xcpodf"
New Import: 500
Historical Backfill: 2000
```

Approved small backend schema change:

```text id="7al7kp"
Raise the acquire_limit validation cap high enough to allow at least 2000.
```

Recommended hard cap:

```text id="b17zec"
max acquire_limit = 10000
```

Keep the candidate search cap default at:

```text id="rjfnm0"
max_listing_candidates = 1000
```

Do not automatically increase the candidate cap just because limit is larger.

Behavior for:

```text id="eq8ovg"

candidate_search_cap = 1000
```

should be:

```text id="w8lu5c"
scan up to 1000 candidates
select/import whatever safe eligible items are found in that scan window
report partial completion if fewer than 2000 are selected/imported because scan cap was reached
do not treat this as a fatal error
```

UI wording example:

```text id="omhcrs"
Partial completion: requested 2000, scanned 1000 candidates, imported 953. Candidate search cap was reached before the requested limit was satisfied.
```

Also show a warning for large limits, but do not block valid values under the hard backend cap.


# 4. Confirmed Reconnaissance Findings

Milestone 12.64.0 confirmed two implementation risks.

## 4.1 Selected Source Profile Identity Can Be Lost

Current selected-source dispatch begins with the correct saved Source Profile ID.

However, downstream pipeline context resolution may reconstruct the ingestion Source using:

```text
Source label
Source Type
normalized Runtime Root
```

rather than carrying the selected Source Profile ID authoritatively into the pipeline.

When the current Runtime Root changes—for example, because an External drive receives a different drive letter—the pipeline may create a new path-based compatibility Source.

This can create an inconsistent relationship such as:

```text
SourceIntakeRun.ingestion_source_id
= selected modern Source Profile

IngestionRun.ingestion_source_id
= newly created path-based Source

Provenance.ingestion_source_id
= newly created path-based Source
```

That behavior defeats the purpose of durable Source Endpoint identity.

## 4.2 Exact-Known Content Reaches Vault Copy Too Early

Current pipeline ordering allows a hash-identified candidate to reach Vault copy before persistence determines that the Asset already exists.

Potential outcomes include:

```text
same SHA-256 + same extension
→ existing canonical Vault pathname rewritten or touched

same SHA-256 + different extension
→ second hash pathname created even though the existing Asset remains canonical
```

This conflicts with immutable-Vault architecture.

No live corruption is presumed.

The code-path risk must be corrected before the planned cross-Source live test is treated as release evidence.

# 5. Required Implementation A — Preserve the Selected Source Profile

## 5.1 Authoritative Source Identity

When selected-source dispatch starts Source Intake using a modern saved Source Profile, carry that Source Profile identity into the downstream pipeline context.

The selected Source Profile ID must remain authoritative for:

```text
SourceIntakeRun.ingestion_source_id
IngestionRun.ingestion_source_id
Provenance.ingestion_source_id
```

For a correctly anchored selected-source run:

```text
SourceIntakeRun source ID
= IngestionRun source ID
= Provenance source ID
= selected Source Profile ID
```

## 5.2 Runtime Root Remains Backend-Derived

This fix must not make a frontend path authoritative.

The backend must continue to:

- perform Source Selection;

- verify durable Source identity;

- resolve the current Runtime Root;

- apply endpoint-relative-root containment;

- block mismatched or unavailable Sources.

The Source Profile ID identifies the saved Source.

The Runtime Root identifies where that verified Source is currently accessible.

These concepts must remain separate.

## 5.3 Changed Drive Letter

A changed drive letter must not create another ingestion Source when the durable Source Endpoint still matches.

Expected behavior:

```text
same Source Endpoint
same Source Profile
new current Runtime Root
same Source-location provenance anchor
```

Do not rewrite the Source Profile into a new identity merely because the drive letter changed.

Do not create a new path-only compatibility Source when an authoritative selected modern Source Profile ID was supplied and validated.

## 5.4 Compatibility Boundary

Preserve existing direct, legacy, or path-only Source Intake behavior where no authoritative selected Source Profile ID exists.

A narrow compatibility fallback may remain for those established entry points.

However:

```text
when a validated selected Source Profile ID is supplied,
that ID must take precedence over label/type/path reconstruction
```

Do not broadly migrate or reinterpret legacy Sources.

## 5.5 Persistence Boundaries

Do not change:

- Source Endpoint fingerprints;

- Source creation semantics;

- Source Selection semantics;

- readiness classifications;

- endpoint-relative-root meaning;

- Observed Path history;

- Source Profile status behavior;

- Source alias rules;

- provenance schema;

- provenance uniqueness constraints.

If the narrow fix appears to require schema, migration, or backfill work, stop and escalate.

# 6. Required Implementation B — Protect Exact-Known Vault Files

## 6.1 Required Outcome

Determine whether the SHA-256 already belongs to an existing Asset before performing a Vault copy that could modify or duplicate canonical storage.

For exact-known content:

```text
reuse the existing Asset
reuse the existing canonical Asset.vault_path
do not rewrite the Vault file
do not touch the Vault file as an intended pipeline action
do not create another hash pathname
add or preserve legitimate Source provenance
```

## 6.2 Same Extension

When identical bytes arrive through another Source with the same extension:

- do not call the ordinary Vault-copy operation against the existing destination;

- do not overwrite the existing file;

- do not intentionally update its modification time;

- do not create another Asset;

- preserve the existing Asset’s canonical Vault path;

- create or preserve the appropriate new Source provenance observation.

## 6.3 Different Extension

When identical bytes arrive under a different filename extension:

- retain the existing Asset and its established canonical Vault path;

- do not create a second unreferenced hash pathname using the alternate extension;

- do not create a second Asset;

- preserve legitimate Source provenance for the newly observed Source/path.

Do not redesign extension policy in this milestone.

The existing Asset’s canonical Vault path remains authoritative.

## 6.4 New Unique Content

For genuinely new SHA-256 content:

- preserve the existing new-Asset flow;

- copy the file to the Vault once;

- create one Asset;

- create the intended Source provenance;

- continue normal metadata processing.

## 6.5 Failure Safety

If existing Asset state and Vault state conflict unexpectedly, do not silently repair or delete files.

Fail safely, preserve evidence, and escalate when the existing architecture does not provide an unambiguous safe action.

Do not add broad reconciliation or cleanup behavior in this milestone.

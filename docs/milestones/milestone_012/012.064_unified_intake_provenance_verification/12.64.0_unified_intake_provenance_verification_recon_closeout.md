Important semantics:

- `original_source_path` describes the source that first created the Asset;
- later Source origins are represented by provenance, not additional Assets;

## 5. Current Unique-File Persistence Path

Confirmed from code:

```text
Source Selection
-> Run Ingestion dispatch revalidation
-> start_source_intake(selected Source Profile ID, backend Runtime Root)
-> SourceIntakeRun
-> pipeline ingestion-context resolution
-> IngestionRun
-> scan Source root
-> skip-known comparison by Source ID + source_relative_path
-> stage selected records to Drop Zone
-> filter
-> SHA-256
-> within-batch exact deduplication
-> Vault copy
-> Asset insert
-> Provenance insert
-> metadata extraction/observation/canonicalization
-> Drop Zone cleanup
-> Source Intake report
```

For a new unique file, expected current persistence is:

```text
1 Asset
1 Vault pathname for the test hash/extension
1 Provenance row
1 IngestionRun
1 SourceIntakeRun
normally 1 ingest metadata observation for a supported image
```

The provenance row records:

```text
ingestion_source_id = resolved Source Profile/compatibility Source ID
ingestion_run_id = current IngestionRun ID
source_path = absolute original Source path
source_root_path = absolute Runtime Root used by the pipeline
source_relative_path = path relative to that Runtime Root
```

## 6. Same-Source Repeat Behavior

Confirmed from code:

1. Pipeline context resolution creates a new `IngestionRun`.
2. `_collect_input` loads all non-null `Provenance.source_relative_path` values
   for the resolved `ingestion_source_id`.
3. The same relative path is classified as already known.
4. It is not staged, hashed, copied, or persisted again.
5. A new `SourceIntakeRun` and Source Intake report still describe the repeat run.

Expected repeat result for the unchanged test folder:

```text
Asset count for SHA: unchanged at 1
Vault pathname count for SHA: unchanged
Provenance count for SHA and Source Profile: unchanged
Metadata observation count: unchanged
IngestionRun count for Source Profile: +1
SourceIntakeRun count for Source Profile: +1
report counts.skipped_already_known: includes the test image
report counts.processed_new_unique: 0
```

Qualification:

```text
Idempotency is currently enforced primarily by the pre-hash skip-known
Source-relative-path filter, not by a durable Source/Profile/path uniqueness
constraint independent of ingestion_run_id.
```

The database constraint includes `ingestion_run_id`. If the same Source/path
reaches `upsert_provenance` in another run, a new row is allowed. Current
filesystem repeat flow normally prevents that through skip-known filtering.
iCloud repeat flow normally prevents it through durable acquisition-resource
state and known-state filtering.

## 7. Cross-Source Exact Duplicate Behavior

Confirmed from code and an existing iCloud handoff test:

- SHA-256 remains the Asset primary key;
- an existing Asset is reused;
- `persist_copied_files` calls `upsert_provenance` for the new Source path;
- the new Source observation can be attached to the existing Asset;
- earlier provenance is not deleted;
- an iCloud exact-known Asset receives provenance for the selected iCloud Source.

Expected logical result after External, Local, Optical, and exact-byte iCloud intake:

```text
1 Asset
4 legitimate Source observations
1 Source Profile relationship per observation
1 Source Endpoint relationship per modern Source Profile
1 canonical Asset.vault_path
```

The four provenance rows are expected to use distinct `ingestion_source_id` values.

### 7.1 Confirmed Vault-ordering risk

Confirmed from code:

```text
copy_unique_files_to_vault executes before persist_copied_files checks whether
the SHA-256 already exists in assets.
```

`copy_unique_files_to_vault` currently calls `shutil.copy2` even when the
hash-based destination already exists.

Consequences:

1. With the same extension, exact-known cross-Source intake rewrites the existing
   hash pathname before the Asset is classified as existing. The bytes should be
   identical because SHA-256 already matched, but the file is still rewritten in
   place, which conflicts with the strict immutable-Vault architecture.

2. If identical bytes arrive with a different extension, storage may create a
   second hash pathname with the new extension. The existing Asset continues to
   point to the original Vault path, leaving a possible unreferenced duplicate
   Vault file.

This is a confirmed implementation risk, not a proven live-data corruption event.
It should be resolved or explicitly accepted before broad cross-Source live
provenance validation is treated as release evidence.

## 8. Modern Source, Runtime Path, and Provenance Relationship

### 8.1 Normal unchanged path

For a newly created Source at its current path:

```text
Run dispatch receives Source Profile ID
-> Runtime Root matches the Source Profile stored root
-> resolve_ingestion_context finds the same ingestion_sources row by
   normalized label + type + Runtime Root
-> Provenance.ingestion_source_id is the modern Source Profile ID
-> Source Endpoint is reachable through ingestion_sources.endpoint_id
```

### 8.2 Confirmed changed-drive provenance risk

Confirmed from code:

- dispatch passes the selected Source Profile ID into `start_source_intake`;
- `SourceIntakeRun.ingestion_source_id` is initially the selected Profile ID;
- the background pipeline receives label, type, and Runtime Root, but not the
  selected Profile ID;
- `resolve_ingestion_context` looks up a Source by label + type + normalized
  Runtime Root;
- a changed drive letter changes the normalized Runtime Root;
- if no row matches that new path, `resolve_ingestion_context` creates a new
  `IngestionSource` without the original endpoint linkage;
- the resulting `IngestionRun` and provenance then reference that new row.

Potential resulting inconsistency:

```text
SourceIntakeRun.ingestion_source_id = selected modern Source Profile
IngestionRun.ingestion_source_id    = newly created path-based compatibility Source
Provenance.ingestion_source_id      = newly created path-based compatibility Source
```

Source Selection itself has automated coverage for changed drive letters.
Changed-drive selected-source provenance does not.

This is a confirmed code-path defect/risk requiring a focused implementation
milestone before changed-drive provenance can be claimed correct.

### 8.3 Different roots on one endpoint

Current creation logic supports:

```text
one Source Endpoint
+ multiple intentional Source Profiles with different endpoint_relative_root values
```

Each Profile has its own `ingestion_sources.id`, so provenance can distinguish
the roots even though `endpoint_id` is shared.

Live provenance behavior for this case remains untested.

### 8.4 Status and name changes

- activating/deactivating a Profile updates the Profile and does not delete
  historical provenance;
- provenance retains the linked Source ID and denormalized source label/type;
- changing the Source display label can leave older provenance denormalized labels
  unchanged while the foreign-key link still identifies the same Profile;
- legacy Sources remain distinguishable by null endpoint linkage/root semantics.

## 9. Path Semantics

### 9.1 Persisted absolute path fields

Current provenance stores:

```text
source_path       = absolute path of the observed original/staged file
source_root_path  = absolute Runtime Root used by that pipeline run
```

For Windows filesystem Sources, these fields can contain a drive letter.

For iCloud, these fields can contain the managed local staging path.

They are runtime/access evidence, not durable identity.

### 9.2 Durable Source-relative description

Current provenance also stores:

```text
source_relative_path = source_path relative to source_root_path
```

Normal Source Review display prefers persisted `source_relative_path`.

This is the durable file-location description inside the selected Source root.

### 9.3 Endpoint-relative asset path

There is no separate provenance column containing:

```text
Source Profile endpoint_relative_root + asset Source-relative path
```

It is derivable through the Source Profile relationship.

Example for the Optical test:

```text

source_relative_path:   <test filename>
derived endpoint path:  New folder (2)\<test filename>
```

## 14. 100-Logical-Asset iCloud Accommodation

### 14.1 Normal current behavior

The normal iCloud workflow is:

```text
Refresh / Prepare Next 1000
-> durable snapshot of up to 1000 eligible logical candidates
-> Import Next 1000
-> durable import run
-> chunks of up to 100 logical candidates
-> advance/resume until all prepared candidates are handled
```

The normal prepare target is fixed in
`refresh_historical_inventory` through:

```text
target = DEFAULT_TARGET_LOGICAL_ASSETS
DEFAULT_TARGET_LOGICAL_ASSETS = 1000
```

Existing request model:

```text
RunIngestionIcloudOptions.target_logical_items
valid range: 1..1000
```

Existing import service:

```text
start_icloud_intake_import(
    target_logical_assets=<requested target>,
    internal_batch_size=100,
)
```

When `target_logical_items=100` is supplied without changing Prepare:

```text
prepared snapshot: still up to 1000 candidates
selected for import: first 100 prepared candidates
total chunks: 1
internal chunk size: 100
permanent product default: unchanged at 1000
```

This existing request parameter limits Import only. It does not satisfy the
Product Owner's requirement to prepare only 100 candidates.

The normal frontend also sends:

```text
target_logical_items: null
```

so the normal UI uses the prepared run's 1000 target.

### 14.2 Correct temporary test accommodation

The smallest functional change is to temporarily set the prepare target to 100
inside `refresh_historical_inventory`:

```text

```

With a fresh prepare run, the existing status and import path then produce:

```text

import target inherited by normal UI dispatch: 100
internal batch size: 100
total chunks: 1
```

No schema, migration, backfill, persistence redesign, or permanent default change

```

Backend operator messages containing hard-coded `Next 1000` wording in

Focused automated coverage should verify:

```

### 14.3 Safe execution and restoration

Recommended sequence:

1. Confirm there is no active prepared import, acquisition, Source Intake, or
   cleanup operation for the selected iCloud Source.
2. Apply the temporary 100-candidate prepare change and accurate temporary UI
   wording.
3. Run focused tests.
4. Restart/reload the affected runtime.
5. Run a fresh `Prepare Next 100`.
6. Confirm the prepared run target is 100 and no more than 100 candidate rows exist.
7. Confirm the intended new image is present in candidate position 1..100.
8. Use the normal UI Import action. Because the fresh prepared run target is 100,
   the existing null request inherits 100 and creates one chunk.
9. Complete and validate the one 100-item chunk.
10. Restore the backend target and all temporary UI/operator wording to 1000.
11. Rerun focused tests and restart/reload the affected runtime.
12. Confirm the next future prepare advertises and records the normal 1000 target.

If the test image is not in the first 100:

```text
Stop before import.
Do not broaden the run to 1000 merely to find it.
Reassess candidate ordering/identity with the Product Owner.
Restore the normal 1000 behavior after preserving evidence.
```

Restoration changes future behavior only. The completed test's durable prepare,
import, chunk, acquisition, Source Intake, and cleanup records should continue to
show the historically correct 100-item target.

This is a small, easily reversible temporary implementation. It should be handled
as an explicitly bounded test-accommodation action rather than an undocumented
manual edit.

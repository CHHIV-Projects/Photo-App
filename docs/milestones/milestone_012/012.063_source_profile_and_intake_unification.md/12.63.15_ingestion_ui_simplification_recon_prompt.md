## Goal

Design a simpler Ingestion page operator model.

This is a **design and reconnaissance milestone only**.

Do not implement UI changes yet.

The current Ingestion page has become functionally capable but visually and conceptually cluttered. It now contains:

```text
Create Source Profile
iCloud Intake panel
generic Source Profile registry/table
generic Run Intake controls
source readiness
source identity
legacy iCloud/generic intake remnants
details/manage drawers
audit/run counters
many technical columns
```

The desired next design should simplify the operator experience into a source-focused workflow.

Target operator model:

```text
1. Pick source type.
2. Pick source.
3. Work in one source-specific drawer/panel.
```

The design should avoid creating a long multi-step wizard. The user should not have to work through 10-12 visible steps when the real action can be expressed as one or two primary actions.

## Product Direction

The current Ingestion page is too registry/table driven.

The future Ingestion page should be organized around the source the operator wants to work on.

Desired high-level layout:

```text
Source type selector:
  Local
  External
  Removable
  NAS
  iCloud

Source selector:
  filtered list of active sources for that type

Source work area:
  source-specific workflow, status, action, result, and audit info
```

The long Source Profile registry should become secondary:

```text
Advanced / Manage Sources / Source Registry
```

It should not be the primary operator surface.

---

## Product Decisions Locked for This Recon

### 1. iCloud Should Not Be Treated Like Generic Source Intake

iCloud now has its own unified Intake panel/workflow.

Generic Source Intake is blocked for provider-specific/cloud profiles.

The design should make this obvious.

For iCloud sources, the primary workflow should be:

```text
iCloud Intake
Refresh / Prepare
Import / Resume
Current run status
Latest result
Deferred / needs policy
Audit/details
```

Do not mix iCloud into generic Run Intake as if it were a local folder.

### 2. Local / External / Removable / NAS Share a Generic Filesystem Workflow

For filesystem-backed sources, the primary workflow should be:

```text
Source readiness
Durable source identity
Run Source Intake
Latest run/result
Audit/details
```

### 3. Source Type Vocabulary Should Be Operator-Friendly

Long-term user-facing source types should be:

```text
Local
External
Removable
NAS
iCloud
```

Do not implement persisted source type migration in this milestone.

This recon should identify how current internal values map to future user-facing categories.

Current internal values may include:

```text
local_folder
external_drive
cloud_export
scan_batch
other
```

The design should propose how to present these clearly without requiring immediate backend migration.

### 4. Keep the Main Workflow Short

Avoid a 10-12 step workflow.

The primary surface should show:

```text
current source
current status/readiness
one primary action
latest result
advanced details if needed
```

For example:

```text
Local/NAS:
  Check Readiness
  Run Intake

iCloud:
  Refresh / Prepare
  Import / Resume
```

### 5. Create Source Profile Remains Important

The existing Create Source Profile drawer should remain, but the design may recommend improving it later.

This recon should consider:

```text
where Create Source Profile belongs
how source type selection affects fields
how endpoint enrollment fits
how iCloud profile creation differs from filesystem source creation
```

Do not implement create-profile changes yet.

### 6. Legacy Admin Page Cleanup Is Not This Milestone

Do not redesign or clean up the Admin page in this milestone.

The design may mention future Admin cleanup, but the focus is the Ingestion page.

```text

  Create Source Profile
```

```text
  Source dropdown/search
  Refresh

  Advanced Source Registry / Manage Sources
```

### 4. Source Type Selector Design

Propose source type categories:

```text
Local
External
Removable
NAS
iCloud

```

Define mapping from current internal source types and paths:

```text
local_folder + normal path -> Local

external_drive -> External
future removable_media -> Removable
cloud_export + iCloud -> iCloud
scan_batch -> Advanced / Legacy / unsupported until clarified
other -> Advanced / Legacy / unsupported until clarified
```

Do not implement migration.

### 5. Source Selector Design

Design the source selector behavior.

It should likely show:

```text

label
status
short path/provider hint
readiness/last status if available
```

Avoid a huge always-visible table as the main UI.

Consider whether source selector should include:

```text
search
status filter
show archived/inactive/test sources
```

### 6. Selected Source Work Area

Design the source-specific work area.

For filesystem-backed sources:

```text
Header:
  source label
  source type
  path/provider summary
  profile status

Primary cards:
  Readiness
  Source Identity
  Source Intake

Primary actions:
  Check Readiness
  Run Intake

Latest result:
  latest Source Intake run summary
  counts
  report link/path if available

Advanced:
  paths
  endpoint details
  provenance/reference counts
  run history
```

For iCloud sources:

```text
Header:
  source label
  account masked
  managed staging path
  profile status

Primary cards:
  iCloud Intake status
  Inventory / candidates
  Import progress / latest result
  Deferred / needs policy

Primary actions:
  Refresh / Prepare
  Import / Resume

Advanced:
  run/chunk history
  cleanup counts
  deferred/needs-policy details
  source profile details
```

### 7. Registry/Table Redesign

Design what happens to the current long table.

Recommended direction:

```text
move to Advanced / Manage Sources
show fewer columns by default
add expandable details
filter out iCloud from generic intake actions
show action buttons relevant to source type only
hide or collapse technical counters
```

Do not delete useful audit information; move it into details/advanced areas.

### 8. iCloud-Specific Cleanup

Design how to retire or hide confusing legacy iCloud generic Source Intake controls.

Required product conclusion unless code inspection suggests otherwise:

```text
iCloud should be managed through iCloud Intake, not generic Run Intake.
```

The design should specify:

```text
where iCloud source profiles appear
what actions are shown
what legacy action should be hidden/disabled/removed
what message is shown if the old action remains temporarily
```

```text
Reports
```

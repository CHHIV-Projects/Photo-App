# 5. Editable Source Name

## 5.1 Source Name meaning

Source Name is the operator-facing name for a Source Profile.
It is persisted as the current Source Profile label used by the existing implementation.
Source Name is not:

- endpoint identity;
- Device Name;
- drive letter;
- endpoint-relative root;
- observed path;
- fingerprint;
- provider identity.
  The durable Source definition remains:
  Endpoint identity + endpoint-relative root
  Changing or choosing a Source Name must not alter durable identity.
  
  ## 5.2 When to show the field
  
  For a genuinely new Source, show an editable field after successful path identification:
  ```text
  Source Name
  [ suggested value ]



The field must appear before the final confirmation.

Examples:

```
Suggested:DesktopOperator may enter:Chuck Desktop Photos
```

```
Suggested:2019-03-13Operator may enter:2019 Vacation Photos
```

```
Suggested:Entire shareOperator may enter:Henderson NAS Photos
```

## 5.3 Suggested default

Continue using the existing 12.63.18.3 default-generation rules:

- entire Local or External endpoint:  
  `Entire device`
- entire NAS share:  
  `Entire share`
- non-empty root:  
  final folder component
- real name collision:  
  add limited parent-folder context
- remaining collision:  
  use the current short stable fallback

The suggested name is only a default. The operator may replace it.

## 5.4 Existing Sources

Do not present an editable Source Name field when the final action is:

- Use Existing Source
- Reactivate Existing Source
- Adopt and Link Existing Source
- Adopt and Reactivate Existing Source

Those actions must retain the existing Source Profile label.

Renaming an existing Source Profile is not part of this milestone.

Endpoint Device Name rename behavior from 12.63.18.2 remains available and unchanged.

## 5.5 Validation

Before confirmation, validate the entered Source Name.

Required behavior:

- trim leading and trailing whitespace;
- reject blank or whitespace-only names;
- reject control characters;
- apply the existing safe maximum length;
- preserve normal punctuation and spaces;
- do not interpret Source Name as a filesystem path;
- do not permit silent overwrite of another Source label.

Inspect the current Source-label uniqueness constraint.

If the entered Source Name conflicts with an existing Source label:

- block confirmation;
- explain that the name is already in use;
- retain the entered value for correction;
- provide a safe suggested alternative where practical.

Do not alter the uniqueness model or perform a broad schema redesign without stopping for review.

## 5.6 Review display

Before confirmation, show:

```
Device NameSource NameSource TypeDurable IdentityIdentifier TypeIdentifierRoot Relative to DeviceCurrent Observed PathExact Action
```

The operator-entered Source Name must be clearly visible before the Source is created.

# 7. Exact Duplicate Source Review

## 7.1 Purpose

When Source Creation finds multiple Source Profiles for the same exact normalized root, provide a deliberate operator review rather than merely blocking with no supported resolution.

This workflow applies only to exact-root matches discovered during Source Creation.

It is not a broad duplicate-search or cleanup tool.

## 7.2 Duplicate review information

For every exact Source match, show safe operator-facing information:

- Source Profile ID under Advanced Details
- Source Name
- Source Type
- status
- root path
- endpoint-relative root
- linked endpoint or unlinked legacy state
- Device Name, when linked
- whether identity is verified
- ingestion-run count
- Source Intake run count where available
- provenance-row count
- asset count or other safe linked-data count where available
- creation/update timestamp where useful
- recommended action, if one can be determined safely

Do not expose raw fingerprints or credentials.

## 7.3 Exact match classifications

Classify each matching Source as appropriate:

- active modern linked Source
- inactive modern linked Source
- active legacy unlinked Source
- inactive legacy unlinked Source
- archived/test/deprecated Source
- Source with history
- Source with no history

## 7.4 Recommended canonical Source

The system may recommend a canonical Source only when the choice is strongly supported.

Examples:

### One active Source with history and one inactive Source with no history

Recommend:

```
Keep the active Source as canonical.Leave the inactive duplicate inactive.
```

### One active unlinked legacy Source with history and one inactive linked duplicate with no history

Recommend:

```
Adopt and link the active legacy Source.Leave the inactive duplicate unchanged.
```

### One inactive unlinked legacy Source and no competing active Source

Recommend:

```
Adopt and reactivate the existing Source.
```

Do not automatically choose a canonical Source when:

- multiple active Sources have history;
- multiple Sources have conflicting history;
- roots or identities are ambiguous;
- more than one candidate is equally plausible;
- the action could sever or rewrite historical relationships.

Ambiguous cases remain blocked for later management.

# 8. Allowed Duplicate-Resolution Actions

## 8.1 Adopt and Link Canonical Source

For a selected eligible unlinked legacy Source:

- retain its Source Profile ID;
- retain its Source Name;
- retain its source root;
- retain all ingestion history and provenance;
- link it to the verified endpoint;
- populate deterministic endpoint-relative root;
- add current observed-path evidence where appropriate;
- create no new Source Profile.

## 8.2 Adopt and Reactivate Canonical Source

For an eligible inactive unlinked legacy Source:

- perform adoption/linkage;
- change status from `inactive` to `active`;
- retain the same Source Profile ID and history;
- perform all changes transactionally.

Only literal `inactive` is eligible.

Do not automatically reactivate:

- archived
- test
- deprecated
- unknown custom statuses

## 8.3 Keep Existing Active Source

When an appropriate active exact Source already exists:

- return/use the existing Source;
- create no duplicate Source;
- create no duplicate endpoint;
- avoid duplicate observed-path rows unless the path represents genuinely new evidence.

## 8.4 Leave Inactive Duplicate Unchanged

An inactive duplicate may remain in the database.

The review should clearly indicate:

```
This inactive Source will remain for historical review and will not be used.
```

Do not delete it.

Do not move its runs, provenance, or assets.

## 8.5 Mark an Active No-History Duplicate Inactive

This action may be offered only when all of the following are true:

- the Source is an exact-root duplicate;
- it is not the selected canonical Source;
- it has zero ingestion runs;
- it has zero Source Intake runs;
- it has zero provenance rows;
- it has no assets or other protected history;
- the operator explicitly selects the action.

Show a clear confirmation:

```
This changes only the Source status to inactive.No files or historical records will be deleted.
```

Do not offer this action when any protected history exists without stopping for review.

## 8.6 No deletion or merge

Do not:

- delete duplicate Source Profiles;
- merge Source Profile IDs;
- transfer ingestion runs;
- transfer provenance;
- rewrite assets;
- rewrite historical labels;
- rewrite run reports.

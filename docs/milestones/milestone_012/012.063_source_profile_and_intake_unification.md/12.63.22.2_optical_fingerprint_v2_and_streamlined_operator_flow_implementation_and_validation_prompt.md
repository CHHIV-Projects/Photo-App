# 4. Product Decision

The approved direction is:

> Keep the unified Source Endpoint and Source Profile backend architecture, but give Optical a simpler operator flow appropriate for low-frequency, static media.

New-disc operator flow:

```
Choose Optical→ enter or confirm current disc path→ enter a friendly disc name→ click Use This Disc→ Photo Organizer creates the durable Optical Source→ Photo Organizer automatically selects it→ Step 3 shows Filesystem Source Intake
```

The operator should not need to manually:

- understand fingerprint versions;
- create an endpoint separately;
- return to Step 2 and find the newly created Source;
- select workflow type;
- edit a runtime root;
- enter provenance separately.

Internally, this remains:

```
Optical probe→ Source Endpoint→ Source Profile→ Source Selection→ Filesystem Source Intake
```

Do not create a path-only or run-only Optical exception.

# 6. Locked Architecture

## 6.1 Keep durable Optical Sources

Optical must continue using:

- Source Endpoint;
- Source Profile;
- endpoint-relative root;
- Source Selection;
- readiness;
- selected-source dispatch;
- existing filesystem Source Intake;
- operation guardrails;
- existing run history and reports;
- existing Vault and provenance semantics.

Do not replace Optical Sources with:

- a path-only intake;
- a temporary source object;
- free-text-only provenance;
- a frontend-only disc label;
- a separate ingestion engine;
- a one-off copy routine.

## 6.2 Keep the disc as the identity

The physical Optical drive is not the Source identity.

The drive letter is not the Source identity.

The friendly disc name is not the Source identity.

The media fingerprint remains the durable logical identity.

The friendly name is an operator-facing alias.

## 6.3 Exact matching remains mandatory

Do not weaken Optical matching.

Do not allow:

- acknowledgment-based mismatch bypass;
- drive-letter matching;
- physical-drive matching;
- volume-label-only matching;
- file-count-only matching;
- partial fingerprint evidence;
- automatic endpoint identity replacement.

A wrong or unverifiable disc must remain blocked.

# 7. Optical Fingerprint v2 Contract

Add:

```
optical_media_fingerprint_v2
```

The v2 fingerprint must remain:

- metadata-only;
- deterministic;
- versioned;
- reproducible;
- insensitive to Windows mount-allocation reporting;
- independent of drive letter;
- independent of physical Optical drive identity;
- exact-match and fail-closed.

## 7.1 Authoritative v2 inputs

The primary v2 identity payload should include stable normalized evidence such as:

### Disc metadata

- fingerprint algorithm/version marker;
- normalized filesystem type;
- normalized volume label when present;
- normalized volume serial or volume identifier when present;
- total media size only if the current code and focused tests confirm it remains stable across the supported Optical lifecycle.

### Manifest

- endpoint-relative path;
- normalized path case;
- normalized `\` separators;
- entry type;
- file size for files;
- deterministic ordering;
- file count;
- directory count.

## 7.2 Inputs excluded from v2

Do not include:

- `free_space`;
- computed `used_size`;
- drive letter;
- mount point;
- physical drive PNP identity;
- Optical drive model;
- current device path;
- access time;
- current application state;
- current operation state.

Exclude file and directory timestamps from the authoritative v2 hash.

Timestamps may remain available as diagnostic probe evidence, but must not determine v2 media identity.

Reason:

- timestamps were not the observed v1 failure;
- their cross-drive, cross-driver, and cross-machine durability remains unproven;
- they are unnecessary for the approved stable logical-media identity contract.

## 7.3 Deterministic serialization

Use:

- explicit normalized payload construction;
- deterministic entry sorting;
- deterministic JSON serialization;
- explicit fingerprint version;
- the existing stable hash helper where appropriate.

Do not duplicate hashing logic across services.

# 8. v1 and v2 Compatibility Policy

Existing `optical_media_fingerprint_v1` endpoint records must not be silently rewritten or reinterpreted.

Do not:

- change a stored v1 version to v2;
- overwrite a v1 endpoint fingerprint;
- silently compare a v2 result against a v1 hash;
- auto-migrate a v1 Source during selection;
- auto-repair Source 105;
- create a broad legacy migration framework.

The current known v1 Optical Source is test data and has not completed live Source Intake.

Required behavior for v1 Optical Sources:

- preserve the record unchanged;
- identify it as using legacy Optical fingerprint v1;
- fail closed when its exact v1 identity cannot be verified;
- provide a clear operator message that the Source should be recreated using the current Optical identity version.

Suggested message:

```
This Optical Source uses the earlier v1 identity format. Recreate the Optical Source to use the stable v2 identity.
```

Do not add complex v1/v2 dual-authority behavior solely to preserve the current test Source.

Newly created Optical Sources must use v2.

# 10. Source Selection Integration

For a current-format v2 Optical Source:

1. probe the currently presented disc;
2. verify a supported physical Optical device;
3. produce complete v2 evidence;
4. compare against the stored v2 endpoint fingerprint;
5. require exact match;
6. resolve the backend current runtime root;
7. return:
   - selected;
   - available;
   - identity matched;
   - durable identity verified;
   - `workflow_kind=filesystem_source_intake`.

Block:

- no disc;
- unreadable disc;
- unsupported filesystem;
- unverified physical Optical drive;
- incomplete v2 evidence;
- wrong fingerprint version;
- exact mismatch;
- stale endpoint;
- inactive Source or endpoint.

Do not accept v1 and v2 as interchangeable.

# 11. Readiness and Dispatch Integration

Generic readiness and selected-source dispatch must use the stored endpoint fingerprint version as an explicit contract.

For v2:

- require complete current v2 evidence;
- require exact v2 hash match;
- require backend-derived runtime root;
- require safe endpoint-relative-root containment;
- retain operation guardrails;
- reuse existing Source Intake.

For v1:

- preserve fail-closed behavior;
- return clear legacy/recreation guidance where appropriate;
- do not rewrite the endpoint.

Do not allow frontend-supplied:

- fingerprint;
- fingerprint version;
- runtime root;
- workflow type;
- endpoint identity;
- readiness authority.

# 12. Streamlined Optical Operator Flow

## 12.1 Principle

Do not remove the three-section Ingestion page architecture.

Instead, simplify the new Optical Source interaction so one operator action performs the existing create and select steps.

The page may continue to contain:

1. Create Source
2. Select Source
3. Run Ingestion

For a new Optical disc, the user-facing flow should feel like:

```
Use Optical Disc
```

rather than a multi-step enrollment process.

## 12.2 New-disc controls

When the operator chooses Optical in the Create Source section, show a focused panel containing:

- friendly disc name;
- current Optical path;
- a short explanation;
- one primary action:

```
Use This Disc
```

The current path may be entered or confirmed using the existing supported path control.

Do not add a new native operating-system file picker framework solely for this milestone.

Suggested explanatory text:

```
Insert a filesystem-readable data disc, enter its current drive path and a friendly name, then use the disc for ingestion.
```

## 12.3 `Use This Disc` behavior

The action must reuse existing APIs and services:

1. validate required input;
2. perform the existing Optical Source Creation plan;
3. confirm creation using the existing creation contract;
4. obtain the created Source Profile ID;
5. call the existing Source Selection endpoint;
6. install the selected context in the current page state;
7. show the Filesystem Source Intake tile.

Prefer frontend sequencing of the existing APIs when safe.

Do not add a new combined backend orchestration endpoint unless current API contracts make safe sequencing impractical.

Do not duplicate Source Creation or Source Selection logic in the frontend.

## 12.4 Operator-visible result

After successful `Use This Disc`:

- show the friendly disc name;
- show Source Type `Optical`;
- show selected and available;
- show identity matched;
- show the resolved Source Root as read-only;
- show the Filesystem Source Intake tile;
- enable `Run Ingestion`.

The operator should not need to manually locate and select the newly created Source in Step 2.

## 12.5 Existing Optical Sources

Existing v2 Optical Sources remain selectable through the normal Source Selection controls.

Do not remove the existing Source Selector.

A previously created v2 disc should be reusable by:

```
Select Source Type Optical→ choose friendly disc name→ Select Source
```

Existing v1 Sources should display clear legacy guidance rather than silently failing as a generic mismatch.

Provide one clear operator-facing message for each major failure:

### No readable disc

```
Insert a readable Optical data disc and try again.
```

### Drive not verified as Optical

```
Windows did not verify this path as a physical Optical drive.
```

### Unsupported media

```
Photo Organizer cannot use this Optical media format.
```

### Legacy v1 Source

```
This Optical Source uses the earlier identity format. Recreate it using the current Optical workflow.
```

### Wrong disc

```
The inserted disc does not match this Optical Source.
```

### Creation succeeded but automatic selection failed

Report:

- the Source was created;
- automatic selection did not complete;
- the operator can select the new Source from Step 2.

Do not hide a successfully created Source or retry creation blindly.

## 3. Final Source-Creation Model

Filesystem creation uses two stateless endpoints:

```text
POST /api/admin/source-creation/plan
POST /api/admin/source-creation/confirm
```

`/plan` performs read-only probing, derives the endpoint boundary and relative root, finds endpoint/Source matches, and returns blockers, warnings, required confirmations, and a plan fingerprint. It writes no rows.

`/confirm` repeats the plan from the supplied inputs, verifies the plan fingerprint and explicit confirmation, and performs endpoint, observed-path, and Source Profile writes in one database transaction.

The durable model is:

```text
Source Endpoint = durable device/share identity
Source Profile  = Source Endpoint + endpoint-relative root
Observed Path   = current access path evidence
```

## 4. Exact Operator Flow

Normal filesystem flow:

```text
Expand Create a Source

Enter Device Name
Enter Root Path or Mount Point

```

The UI requests a read-only plan. A ready plan, or an idempotent existing-Source plan, is confirmed immediately. A blocked plan stops with a specific reason. A review plan shows safe identity/root details, candidate endpoints, warnings, and the required acknowledgment before `Review and Create Source` can confirm it.

iCloud follows its existing provider-specific create request. Removable cannot be submitted.

## 6. Device Name Behavior

Device Name is free-form operator input and is used as the endpoint alias only when a new endpoint is created.

When one existing durable endpoint matches, its alias is canonical and immutable. The plan returns that existing Device Name and warns when the newly entered name differs. This avoids creating a second name for the same device.

Source display names are derived as:

```text
<Device Name> - <endpoint-relative root>
<Device Name> - Entire device
<Device Name> - Entire share
```

## 7. Local Creation Behavior

Local paths must be absolute Windows drive paths and must not be UNC paths.

- Endpoint boundary: drive root, such as `C:\`
- Durable identity: full `mountvol` Volume GUID hashed in memory
- Source root: full current path
- Endpoint-relative root: path below the drive root
- Observed path: full current path

Selecting `C:\` stores an empty relative root and displays `Entire device`. Selecting the system volume root also returns a prominent non-blocking system-volume warning.

## 8. External Creation Behavior

External paths use the same drive-root boundary model as Local, but persist Source Profile type `external_drive` and endpoint type `external_device`.

The drive letter is retained only in the current Source root and observed path. It is not included in the v2 durable identity hash or endpoint-relative root.

Selecting `E:\` stores:

```text
canonical Source root: E:\
endpoint-relative root: ""
display: Entire device
```

## 9. NAS UNC Behavior

NAS identity is based on parsed UNC server plus share.

For:

```text
\\HENDERSON-NAS\Photos\Dad Files\Scans
```

the model derives:

```text
endpoint boundary: \\HENDERSON-NAS\Photos
endpoint-relative root: Dad Files\Scans
observed path: full entered UNC path
```

The share root `\\HENDERSON-NAS\Photos` produces an empty relative root and displays `Entire share`. A server-only path remains invalid.

## 10. NAS Mapped-Path Behavior

A mapped NAS path is accepted only when the read-only Windows probe resolves it to a valid UNC server/share path. The canonical UNC path becomes the Source root; the mapped path remains observed-path evidence.

If resolution fails, creation stops. It does not create a Local, External, or ambiguous NAS Source, and it does not mount a share or request credentials.

## 11. iCloud Behavior

iCloud remains provider-specific and does not call the generic filesystem creation APIs. The inline panel retains the current iCloud fields:

- Device/Source Name
- provider fixed to iCloud
- account username
- acquisition method
- managed staging path

The generic creation API schema rejects `icloud` with HTTP 422. iCloud Intake behavior was not changed or run.

## 12. Removable Behavior

Removable is visible as `Removable - coming later` and disabled in the normal UI. It has no persisted backend mapping in this milestone. The generic creation API schema rejects `removable` with HTTP 422, and no profile is created.

## 13. Endpoint-Relative-Root Persistence

Added nullable `ingestion_sources.endpoint_relative_root` through the repo-native idempotent `ensure_source_endpoint_schema` helper.

Semantics:

```text
non-empty string = intentional root below endpoint boundary
empty string     = intentional whole device/share
NULL             = legacy, unknown, or unresolved
```

Existing rows were not backfilled or rewritten. No destructive table rebuild was used.

## 14. Observed-Path Persistence

The full current path is stored in `source_endpoint_observed_paths` with its normalized path, boundary classification, probe status, safe warning/blocker summaries, and derived root details.

Mapped NAS input preserves the mapped path as observation while the Source root uses canonical UNC. Local and External preserve the current drive-letter path as observation while durable identity remains drive-letter independent.

Raw Volume GUID values are not displayed or persisted. The complete GUID is hashed immediately in memory; only the versioned hash and masked operator identifier are retained.

## 15. Existing Endpoint Reuse

Strong reuse requires the same endpoint source type and durable fingerprint. One strong match is selected automatically. Existing endpoint alias remains canonical.

The same endpoint plus the same endpoint-relative root is idempotent and returns the existing Source. A different relative root creates another Source linked to the same endpoint.

Legacy v1 masked-evidence fingerprints require review. When an old hash is not reproducible, the service may re-probe an already recorded path on the same drive boundary and compare its current full Volume GUID hash. Only an exact strong GUID match permits transactional in-place upgrade. Path coincidence alone never permits upgrade.

Whole-device/share and nested Sources on one endpoint are allowed. Overlap is reported as a non-blocking warning.

## 21. Known Limitations

- The isolated process could not read the approved NAS paths during this validation, so live NAS persistence was not performed.
- No mapped NAS drive was available for live validation; mapped success/failure behavior is covered with fake probes.
- Pre-existing NAS Source Profiles 69 and 82 represent the same endpoint/root with legacy `NULL` relative roots. Creation blocks rather than choosing between them.
- Existing legacy Source Profiles keep `endpoint_relative_root = NULL`; only new Source creation writes the new field.
- Idempotent reuse of an inactive Source does not automatically reactivate it.
- `fsutil fsinfo volumeinfo` may return a non-admin warning. A successfully parsed `mountvol` Volume GUID remains sufficient strong evidence.
- Endpoint identity is still indirectly derivable through Source Profile links rather than stored as an immutable ingestion-time provenance snapshot.

## 22. Recommended Next Milestone

Add ingestion-time endpoint identity snapshotting while preserving original observed paths. A later focused repair tool can also reconcile duplicate legacy Source roots and migrate operator-reviewed `NULL` relative roots without making startup perform broad data backfill.

## Post-Closeout Addendum: Legacy Exact-Root Duplication and Incorrect Device Name

Date observed: 2026-07-18

### Operator Observation

After the milestone closeout, the operator created a Local Source for:

```text
C:\Users\chhen\OneDrive\Desktop\Exif provanace
```

The completed result displayed Device Name:

```text
TEST 12.63.18 Local Valid
```

This was not the intended operator-facing name, so the creation was investigated read-only.

### Database Finding

The new record was:

```text
Source Profile ID: 87
Profile status: active
Source label: TEST 12.63.18 Local Valid - Users\chhen\OneDrive\Desktop\Exif provanace
Source root: C:\Users\chhen\OneDrive\Desktop\Exif provanace
Endpoint-relative root: Users\chhen\OneDrive\Desktop\Exif provanace
Endpoint ID: 5
Observed-path ID: 10
```

Endpoint `5` is the single verified v2 endpoint for the current `C:\` volume, so endpoint reuse itself was correct. No duplicate durable endpoint was created. Its canonical alias, however, is the leftover validation name:

```text
TEST 12.63.18 Local Valid
```

The plan stored the warning:

```text
existing_device_name_reused:
Existing device identity found. This source will use the known device name:
TEST 12.63.18 Local Valid.
```

The strong endpoint match followed the approved canonical-alias rule and auto-confirmed. As a result, the test alias replaced the newly entered Device Name in the result tiles without giving the operator a useful correction path.

A second issue was found for the same root. An active legacy Source Profile already existed:

```text
Source Profile ID: 2
Source label: Chuck PC
Source root: C:\Users\chhen\OneDrive\Desktop\Exif provanace
Endpoint ID: NULL
Endpoint-relative root: NULL
```

The new service looked for an existing Source only among profiles already linked to matched endpoint `5`. It did not check for an unlinked legacy Source with the same normalized full root. It therefore created Source Profile `87` instead of stopping for review or adopting Source Profile `2`.

### Assessment

This was not a clean finished creation.

Correct behavior:

- The path was readable.
- The `C:\` Volume GUID identity was verified.
- The correct existing endpoint was reused.
- The endpoint-relative root was derived correctly.
- The observed path was stored correctly.
- No second endpoint was created.

Incorrect behavior:

- A leftover test endpoint alias appeared as the Device Name.
- A second active Source Profile was created for an already registered exact root.
- The operator had no normal correction or legacy-adoption path before creation completed.

### Safety Confirmation

The issue is limited to Source Profile and endpoint metadata. For Source Profile `87`:

```text
ingestion runs: 0
Source Intake runs: 0
provenance rows: 0
```

No source files were scanned, copied, moved, imported, or deleted. No Vault, cleanup, iCloud Intake, or provenance operation occurred.

### Required Follow-Up

Recommended non-destructive data repair, subject to explicit operator approval:

1. Mark duplicate Source Profile `87` inactive.
2. Treat existing Source Profile `2` as the canonical Source for this exact root.
3. Link or enroll Source Profile `2` to verified endpoint `5` through a supported workflow.
4. Correct endpoint `5` from its validation alias to the intended canonical Device Name through an approved metadata-correction path.
5. Do not run Source Intake from Source Profile `87` before reconciliation.

Recommended implementation hardening:

1. Before creating a Source, search for an exact normalized-root match across both linked and unlinked legacy Source Profiles.
2. When exactly one active unlinked legacy Source exists at that root, stop for review or offer an explicit adopt/link action instead of creating a duplicate.
3. When a strong endpoint match has a different canonical alias from the entered Device Name, make the name substitution unmissable before completion or provide a supported correction path.
4. Add regression tests covering an existing unlinked legacy Source with the same normalized root.
5. Add regression coverage proving that test endpoint aliases cannot silently become permanent operator-facing names during normal creation.

# 2. Goal

Define Step 3 of the unified ingestion workflow:

1. Create Source
2. Select Source
3. Run Ingestion

Source Selection is now implemented and returns:

- selection result;
- availability;
- selected-source context;
- workflow kind.

The selected Source must determine which Step 3 intake tile and controls are available.

The intended normal behavior is:

    Successful Source Selection
    → workflow_kind determines the Step 3 intake tile
    → only controls relevant to that Source appear
    → operator configures the minimum necessary options
    → operator presses the primary ingestion action
    → the existing execution pathway runs

Initial workflow-kind mapping:

    filesystem_source_intake
    → filesystem Source Intake tile
    
    icloud_intake
    → iCloud Intake tile

Do not show every ingestion control at once.

Do not make the operator choose an ingestion pathway after Source Selection has already established it.

Do not add another Source picker inside Step 3.

# 3. Product Direction

The normal operator workflow should be obvious:

    Create Source
    → Select Source
    → Run Ingestion

The selected Source controls what the operator sees in Step 3.

Examples:

## Filesystem Source selected

## iCloud Source selected

## No successfully selected Source

# 5. Simplicity and Restraint Mandate

The project is becoming complex.

This milestone must actively resist unnecessary complexity.

The correct solution is the simplest safe integration of existing pathways.

The coder must not overbuild merely because a more abstract or generalized design is possible.

Prefer:

- direct, understandable control flow;
- reuse of existing services;
- reuse of existing run records;
- reuse of existing progress/status APIs;
- straightforward conditional rendering based on `workflow_kind`;
- one obvious primary action;
- small helper functions with clear responsibilities;
- existing data models unless a concrete gap is proven;
- explicit mappings over speculative frameworks.

Avoid:

- new orchestration frameworks;
- new generic workflow engines;
- plugin systems;
- event buses;
- unnecessary state machines;
- new persistence tables without proven need;
- duplicate run records;
- parallel ingestion services;
- speculative provider abstractions;
- broad refactors;
- generalized solutions for future providers that do not yet exist;
- additional API layers that merely wrap existing APIs without adding required safety or coordination;
- background job architecture changes unless existing architecture cannot support the required behavior;
- building a new system when conditional UI and narrow dispatch would work.

Before recommending any new abstraction, the closeout must answer:

1. What exact current problem requires it?
2. Why can existing code not handle that problem?
3. What is the smallest alternative?
4. What maintenance burden would the abstraction add?
5. Can the requirement be met with a direct mapping or thin adapter instead?

If a proposed design is technically elegant but harder for the operator or future maintainers to understand, prefer the simpler design.

The final contract should be obvious enough that another coder can implement it without inventing additional architecture.

# 15. API and Service Integration Options

Evaluate the simplest safe option.

## Option A — Frontend tile dispatch to existing APIs

The frontend renders the correct tile from `workflow_kind` and calls the existing authoritative filesystem or iCloud APIs.

Use this when:

- existing APIs already revalidate safely;
- no cross-phase coordination gap exists;
- no duplicate policy logic is needed.

## Option B — Thin backend dispatch endpoint

A small backend endpoint accepts Source Profile ID and run options, revalidates the Source, then dispatches to an existing execution service.

Use this only when it provides necessary:

- authoritative workflow dispatch;
- stale-selection protection;
- shared policy;
- consistent revalidation.

It must not become a parallel ingestion engine.

## Option C — Small orchestration wrapper for existing iCloud phases

Consider only if an existing wrapper already exists or a clear current gap prevents the desired normal flow.

Do not recommend a broad new orchestration platform.

The closeout must compare these options and select the simplest one that satisfies safety and operator clarity.

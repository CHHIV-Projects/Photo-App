## UI Summary

Added `Source Readiness` between `Source Identity` and `Paths and Staging` in the Source Profile details drawer.

Before a check, the section shows:

```text
Status: Unknown
Message: Readiness has not been checked.
Recommended next action: Check readiness before running intake.
```

After a successful check, it displays the returned readiness result, operator message, recommended next action, Source Intake run flags, endpoint summary, warnings, blockers, and expandable Advanced Details.

Readiness state is scoped to the open details drawer and resets when switching profiles. In-flight readiness responses are guarded so a slow result from one profile cannot paint into another profile's drawer.

## Readiness Status Display

The UI maps readiness statuses to operator labels:

```text
ready -> Ready
path_only -> Path-only
needs_review -> Needs Review
blocked -> Blocked
provider_specific -> Provider-specific
unknown -> Unknown
```

Visual treatment reuses existing readiness badge styles:

```text
ready -> positive
path_only / needs_review -> warning
blocked -> not-ready/error
provider_specific / unknown -> neutral
```

## Warnings / Blockers

Warnings and blockers are displayed only when present.

They are rendered as readable operator messages using:

```text
Warning - <code>: <message>
Blocker - <code>: <message>
```

The normal display does not dump raw JSON.

## Button / Loading / Error

Added a manual button:

```text
Check Readiness
```

After a successful result, the button becomes:

```text

```

While the request is active, it shows:

```text
Checking readiness...
```

Repeated clicks are disabled during the in-flight request. Errors are shown inside the Source Readiness section without hiding the rest of the Source Profile details.

## Risks

Readiness results are live snapshots and can become stale if a removable device, NAS path, local path, or source folder changes after the check.

Because this milestone intentionally does not add launch gating, the UI can show a blocked readiness result while the existing Run Source Intake button behavior remains unchanged. That is expected for 12.63.13 and should be resolved by the future run-launch guard milestone.

Manual browser validation remains recommended before committing if the operator wants visual confirmation in the running app.

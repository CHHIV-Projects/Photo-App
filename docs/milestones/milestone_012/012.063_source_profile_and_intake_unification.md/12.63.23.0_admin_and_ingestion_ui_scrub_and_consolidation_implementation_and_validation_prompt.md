# 5. Definition of “Source”

For this milestone, the operator-facing term **Source** means a saved **Source Profile**.

A Source Profile consists of:

- a friendly Source name;
- a Source Type;
- a linked durable Source Endpoint;
- one configured root within that endpoint;
- Source status and relevant ingestion settings;
- associated intake history and provenance.

Examples:

```text
Source: Chuck USB Photos
Type: External
Endpoint: identified USB drive
Root: \Pictures
```

```text
Source: NAS Camera Imports
Type: NAS
Endpoint: \\HENDERSON-NAS\Photos
Root: \Camera imports
```

```text
Source: Wedding Photo Disc
Type: Optical
Endpoint: disc identified by optical_media_fingerprint_v2
Root: entire disc
```

Related terms:

### Source Endpoint

The durable device, share, provider, or Optical media identity.

### Observed Path

The current path where the Source Endpoint is accessible, such as:

```text
E:\
```

or:

```text
\\HENDERSON-NAS\Photos
```

The observed path is access evidence, not durable Source identity.

### Source Intake Run

One ingestion execution against a Source Profile.

Source Intake Runs belong in Source Intake History.

# 13. Canonical Known Sources

There must be exactly one canonical Known Sources implementation.

It must live on the Ingestion page.

Remove the duplicate Known Sources implementation from Admin.

Remove or replace any second competing Known Sources implementation on the Ingestion page.

Do not leave hidden duplicate components that can drift later.

## 13.1 Default state

Known Sources must be collapsed by default.

Example:

```text
▶ Known Sources (83)
```

The default page must not render the full Source table visibly.

Prefer loading only the count until the section is expanded when practical.

Do not load and render every row merely to hide it with CSS.

## 13.2 Required behavior

When expanded, Known Sources must support:

- sortable columns;
- a clear default sort;
- pagination or a bounded row limit;
- preserved Details action;
- preserved Manage action.

Recommended default sort:

```text
Source name ascending
```

Recommended initial page size:

```text
25 Sources
```

Use existing pagination patterns when available.

Do not introduce an entire new table framework solely for this milestone.

## 13.3 Recommended visible columns

Use a concise primary table such as:

| Source | Type | Status | Availability | Root / Provider | Last Used | Actions |
| ------ | ---- | ------ | ------------ | --------------- | --------- | ------- |

Exact wording may follow existing UI conventions.

Avoid displaying in the default row:

- full fingerprints;
- endpoint database IDs;
- raw evidence payloads;
- every observed path;
- long normalized paths;
- all run statistics;
- multiple technical status codes.

Those particulars remain available through Details.

## 13.4 Details must remain

Do not remove or reduce the existing Details functionality.

Details should continue to expose applicable Source particulars such as:

- Source name;
- Source Type;
- Source status;
- linked Source Endpoint;
- endpoint alias;
- identity or fingerprint version;
- configured root;
- observed path;
- normalized path;
- availability/readiness;
- creation date;
- last-used information;
- relevant Source settings;
- recent run summary;
- technical evidence under Advanced Details.

Preserve existing Details behavior unless a small layout cleanup is required.

## 13.5 Manage must remain

Do not remove or reduce the existing Manage functionality.

Manage must continue to support currently permitted safe management actions, including changing Source status when currently supported.

Examples may include:

- activate;
- deactivate;
- other existing safe Source Profile status controls.

Manage must continue respecting immutable identity rules.

Do not permit casual editing of:

- durable endpoint identity;
- device link;
- Optical fingerprint;
- NAS authority;
- endpoint type;
- Source Type conversion;
- immutable alias rules.

This milestone is not a Source editing redesign.

# 8. Run Ingestion API

Implement an additive endpoint:

```
POST /api/admin/run-ingestion/dispatch
```

The exact nearby route name may change only if existing routing conventions strongly require it. Document any change.

## 8.1 Request

Recommended shape:

```
{  "source_profile_id": 88,  "selection_fingerprint": "optional-value",  "filesystem_options": {    "source_intake_limit": null,    "ingest_batch_size": null,    "acknowledge_legacy_or_review": false
  },  "icloud_options": {    "target_logical_items": null
  }}
```

Rules:

- `source_profile_id` is required.
- `selection_fingerprint` is optional.
- `filesystem_options` is optional.
- `icloud_options` is optional.
- extra fields are forbidden.

The backend must reject:

- frontend-submitted workflow kind;
- frontend-submitted Source Root;
- frontend-submitted endpoint path;
- frontend-submitted endpoint ID as authority;
- frontend-submitted durable identity;
- frontend-submitted provider identity.

The backend determines the workflow from the revalidated Source.

Reject filesystem options for iCloud and iCloud options for filesystem workflows.

## 8.2 Response

Use a small normalized top-level response.

Recommended fields:

```
{  "result": "started",  "workflow_kind": "filesystem_source_intake",  "action": "source_intake_started",  "message": "Source Intake started.",  "next_action": null,  "source_profile_id": 88,  "underlying_run_id": 123,  "status": "running",  "workflow_payload": {}}
```

Possible `result` values may include:

- `started`
- `action_completed`
- `blocked`
- `stale_selection`
- `no_action_available`

Possible `action` values may include:

- `source_intake_started`
- `icloud_prepare_started`
- `icloud_import_started`
- `icloud_import_resumed`
- `icloud_import_advanced`
- `none`

Keep the schema narrow.

Do not create a new universal run-status model when existing workflow status models are sufficient.

`workflow_payload` may contain the existing safe response needed by the relevant frontend tile.

# 9. Run-Time Revalidation

Immediately before dispatch:

1. reload the Source Profile;
2. verify it remains active;
3. reload the endpoint where applicable;
4. re-run authoritative Source Selection;
5. verify current endpoint/media/provider identity;
6. resolve the current Source Root;
7. verify availability;
8. verify the workflow kind;
9. compare the optional selection fingerprint;
10. check existing operation conflicts;
11. apply existing launch readiness and safety guards;
12. dispatch only after all checks pass.

Return a clear stale-selection or unavailable response when:

- the device was removed;
- another device or medium is present;
- the drive letter changed and resolution now differs;
- the Source Root disappeared;
- the profile was deactivated;
- the endpoint changed;
- iCloud readiness became blocking;
- the selection fingerprint no longer matches.

The operator should be told to select the Source again.

# 10. Filesystem Runtime-Root Bridge

This is the primary backend correction required by the recon.

Current Source Selection can resolve:

```
current verified endpoint path+endpoint_relative_root
```

Existing Source Intake launch still relies on stored:

```
source.source_root_path
```

Implement a narrow, backend-only bridge so the existing Source Intake execution service runs against the freshly revalidated current Source Root.

Requirements:

- do not trust a frontend path;
- do not mutate `source_root_path` merely to launch;
- do not create or update observed-path rows merely to launch;
- do not bypass Source Intake readiness;
- do not bypass the operation guardrail;
- do not bypass the pipeline orchestrator;
- do not alter Vault, asset, duplicate, or provenance behavior;
- record the actual runtime path in existing run/report evidence where practical.

Preferred implementation:

- add an internal optional runtime-root argument to the existing Source Intake launch service; or
- factor a small shared runtime-root resolver used by both Source Selection and Source Intake launch.

Choose the smaller change that avoids duplicated identity logic.

Do not create a second launch service.

# 11. Filesystem Readiness and Acknowledgment

Preserve existing launch safety, but avoid contradictory routine acknowledgments.

A modern endpoint-linked Source that is freshly revalidated as:

```
selectedavailableidentity matchedroot valid
```

should not require a routine acknowledgment merely because a generic pre-comparison provider probe reports:

- `safe_to_run=not_applicable`; or
- `safe_to_run=needs_review`

when Source Selection has already completed the durable endpoint comparison and confirmed the match.

Acknowledgment may remain required for:

- safe path-only legacy compatibility;
- unresolved identity confidence;
- a real run-specific risk;
- an existing backend condition that remains unsafe after authoritative revalidation.

Do not remove readiness protection broadly.

Make only the narrow change needed so modern verified Local, External, and Removable Sources are not shown as Available in Step 2 and then asked to acknowledge the same already-resolved uncertainty in Step 3.

Add regression tests.

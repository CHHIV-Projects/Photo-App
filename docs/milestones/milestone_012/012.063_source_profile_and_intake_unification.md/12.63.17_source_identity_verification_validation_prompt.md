## Goal

Fix and validate durable source identity verification before continuing the Ingestion Workbench UI sequence.

The operator has manually tested Local and External durable source enrollment. Both produced medium / needs-review style results, warnings, and Endpoint IDs, but neither gave clear confidence that a strong durable source identifier exists.

This milestone should answer and fix the core question:

```text
Can Photo Organizer verify durable source identity for Local, External, Removable, and NAS sources in a way the operator can understand and trust?
```

The operator-facing result must be binary or near-binary:

```text
Durable identity: Verified
Durable identity: Not verified
Durable identity: Provider-specific
```

Do not present `medium`, `medium_needs_review`, `not_compared`, or Endpoint ID as the normal operator answer.

Endpoint ID is database/debug detail. It is not proof that durable identity exists.

---

## Why This Milestone Comes Before the Workbench Panel

Milestone `12.63.16` added the first source picker shell and selected-source summary, but it intentionally did not implement the selected-source workflow panel and did not change backend identity behavior.

Manual validation after `12.63.16` exposed a more foundational concern:

```text
Endpoint enrollment can succeed, but the operator cannot tell whether a real durable identifier was captured.
```

A nicer workbench UI would not fix that.

Before building more UI around source identity, the backend and UI need to distinguish clearly between:

```text
Endpoint record exists.
```

and:

```text
Durable source identity has been verified using usable source/device/share evidence.
```

---

## Background / Context

The architecture separates these concepts:

```text
Source Profile = user-facing alias and workflow container
Source Device / Endpoint = stable machine-readable identity evidence
Ingestion Source = backend compatibility/source record
Observed Path = current path/mount/UNC evidence
```

Source Profile labels and drive letters are not durable identity.

Potential durable evidence includes:

```text
device serial number
USB VID/PID
volume serial number
filesystem UUID / volume GUID
optical media/session identity
network server/share identity
NAS/share identifier
observed mount/path history
```

The current UI is confusing because it exposes:

```text
Source Label
Endpoint Alias
Endpoint ID
fingerprint evidence: medium
identity confidence: medium_needs_review
advanced plan fingerprint hashes
warning codes
```

but does not show a clear human-understandable durable identifier or a binary verification result.

## Product Decisions Locked for This Milestone

### 1. Operator Identity Status Is Binary

Normal UI must show one of:

```text
Verified
Not verified
Provider-specific
Unknown
```

Suggested semantics:

```text
Verified:
  Strong durable source identity evidence exists and is linked.

Not verified:
  Endpoint may exist, path may be readable, and Source Intake may be runnable,
  but strong durable source identity was not confirmed.

Provider-specific:
  iCloud/cloud source uses provider-specific identity and workflow,
  not generic local/external endpoint verification.

Unknown:
  Verification has not been checked or could not be evaluated.
```

`medium`, `weak`, `not_compared`, and `needs_review` may remain internal diagnostic states, but they must not be the primary operator-facing answer.

### 2. Endpoint ID Is Not Identity Proof

Do not present this as sufficient:

```text
Endpoint ID: 3
```

The operator needs to see something like:

```text
Durable identity: Verified
Identifier type: Volume GUID
Identifier: \\?\Volume{...}
```

or:

```text
Durable identity: Not verified
Reason: The app can read the path, but no strong device/volume/share identifier was confirmed.
```

Endpoint ID should move to Advanced Details / debug detail.

### 3. Strong Identity Only

For normal UI, `Verified` requires strong evidence.

Medium evidence is not good enough for the operator-facing verified state.

Suggested rule:

```text
strong evidence -> Verified
medium / weak / path-only / not_compared / needs_review -> Not verified
cloud/iCloud -> Provider-specific
missing/unavailable -> Unknown or Not verified, depending state
```

### 4. Source Name vs Endpoint Alias Clarification

This milestone must document and, where practical, improve the UI language.

Product model:

```text
Source Name / Source Label:
  User-facing workflow name. This is what the operator selects and runs.

Endpoint / Durable Identity:
  Machine-readable identity evidence for the physical/logical source.

Source Root / Observed Path:
  Current runnable folder/path/UNC path used to find files now.
```

Normal users should not have to invent both a Source Label and Endpoint Alias.

Preferred UI direction:

```text
Source Name:
  user-entered

Endpoint Alias:
  default derived from Source Name
  hidden under Advanced Details unless necessary
```

Do not implement broad rename/migration unless safe and small.

At minimum, document current behavior and make the UI less confusing.

### 5. Source Root Keeps the Current Observed Path

The operator should enter the real current path, including drive letter or UNC path:

```text
C:\Users\chhen\OneDrive\Pictures\Scan
E:\WD Backup\...
\\HENDERSON-NAS\Photos\...
```

Do not imply that the operator should manually remove drive letters.

The durable identity system should separately store machine-readable evidence.

Observed path is still needed for running Source Intake.

### 6. Source Types Must Be Testable in UI

The Create Source Profile UI and source picker must let the operator test the source types we have identified:

```text
Local
External
Removable
NAS
iCloud
Advanced / Legacy, if needed
```

This does not require a persisted source type migration unless already supported.

Presentation mapping is acceptable, but it must be explicit and understandable.

### 7. Enrollment Checkbox Should Not Be Normal UX

The current checkbox:

```text
Enroll durable source identity after creating this profile
```

is confusing.

For Local / External / Removable / NAS, the app should automatically attempt durable identity verification during source creation or immediately after source creation.

For this milestone, implement the safest achievable improvement:

```text
Do not ask the operator whether to "enroll durable source identity" as a mysterious optional checkbox.
Instead, present this as an automatic Source Identity Check / Verification step for applicable source types.
```

Actual endpoint linking may still require confirmation when identity is not verified or if the current backend requires an explicit confirm step.

Do not auto-create misleading "verified" endpoints.

### 8. iCloud Is Provider-Specific

iCloud should not use generic endpoint identity verification.

iCloud status should be:

```text
Durable identity: Provider-specific
Identity source: iCloud provider workflow
```

Do not change iCloud Intake behavior.

```text

Removable
NAS
iCloud

```

Implementation rules:

```text

If backend supports a persisted value, use it.
If backend does not support a persisted value, map presentation choice to existing supported storage value and document it.
```

Suggested mapping, subject to code inspection:

```text

External:
  stored as external_drive

  stored as removable_media if supported;

  stored as nas if supported;
  otherwise stored as local_folder with UNC path and presented as NAS.

  stored as cloud_export with cloud_provider=icloud and acquisition_method=icloudpd

  scan_batch / other / unsupported existing values only
```

Do not perform database source type migration.

### Source Dropdown Labels

```text

Search may remain from `12.63.16` if removal is not in scope, but this milestone should not make the dropdown longer or more technical.

```

Determine what evidence is actually captured for:

```text

External drive
Removable media, if supported
NAS / UNC path
iCloud / cloud_export
```

### 2. Investigate Windows Command Warning

Manual testing showed warnings such as:

```text
command_access_denied: Read-only command returned non-zero status: cmd /c fsutil fsinfo
```

Do not assume this is truly permission denial.

Verify:

```text
the exact command being run
its arguments
whether the command is incomplete
whether it requires admin
whether there is a better non-admin command
whether command parsing is failing
whether stderr/stdout is being interpreted correctly
```

If richer Windows APIs are unavailable without admin, document that clearly.

### 3. Capture Usable Durable Identifiers Where Possible

For each source type, identify whether the app can capture and display safe durable evidence.

Candidate evidence:

```text
Local:
  volume GUID / filesystem volume identity
  volume serial number
  access node / machine identity where appropriate
  normalized folder path as scope, not sole durable identity

External:
  volume GUID / serial
  USB/device instance identifier where available
  PnP/device evidence where available
  root folder path as scope, not sole durable identity

Removable:
  same as External, if supported
  plus removable media classification if available

NAS:
  UNC server + share identity
  canonical share path
  optional SMB/server/share evidence if available
  selected root folder inside share as scope

iCloud:
  provider-specific identity
  no generic endpoint verification
```

Do not rely on drive letter alone.

### 4. Define Verification Policy

Implement or document a clear policy.

Suggested initial policy:

```text
Local Verified:
  strong volume identity exists and current root path is readable.

External Verified:
  strong volume/device identity exists independent of drive letter,
  and current root path is readable.

Removable Verified:
  strong removable/device/media identity exists independent of drive letter,
  and current root path is readable.

NAS Verified:
  UNC server/share identity is parsed and current share/root path is readable.
  Optional richer SMB evidence should be included if available.

iCloud Provider-specific:
  generic durable endpoint verification does not apply.

Not verified:
  only path evidence, medium evidence, weak evidence, missing command evidence,
  not_compared, or needs_review evidence exists.
```

If this policy conflicts with current code realities, stop and ask or document the deviation clearly.

### 5. Expose Operator-Safe Identity Summary

Add or update API response fields where appropriate.

Potential fields:

```text
durable_identity_status:
  verified | not_verified | provider_specific | unknown

durable_identity_status_label:
  Verified | Not verified | Provider-specific | Unknown

durable_identity_reason:
  plain-language reason

durable_identity_identifier_type:
  Volume GUID | Volume Serial | USB Device | NAS Share | Provider | None

durable_identity_identifier:
  safe display value where available

durable_identity_evidence:
  safe list of evidence items

endpoint_id:
  advanced/debug

observed_path_id:
  advanced/debug

identity_confidence:
  advanced/debug only

warning_codes:
  advanced/debug unless converted to blocker/not-verified reason
```

Do not expose secrets.

Do not expose Apple credentials, tokens, cookies, 2FA, or session data.

Do not expose raw command output unless it is already safe and placed under Advanced Details.

### 6. Reclassify Medium Evidence

Medium evidence should not become operator `Verified`.

If the app has only medium evidence, show:

```text
Durable identity: Not verified
Reason: The source path is readable, but the app could not confirm a strong device, volume, or share identifier.
```

### 7. Preserve Existing Safety

Do not weaken launch guard behavior.

Do not bypass readiness checks.

Do not make Source Intake run because identity was verified.

This milestone is about source identity verification and display, not ingestion execution.

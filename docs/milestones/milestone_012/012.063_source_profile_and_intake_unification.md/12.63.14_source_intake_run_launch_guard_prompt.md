## Goal

Implement a simple Source Intake run-launch guard using the Source Profile readiness service.

When an operator starts **generic Source Intake** for a local, external, removable, or NAS Source Profile, the app should check readiness immediately before launch.

The operator model should remain simple:

```text
Check Readiness
Run Intake
```

This milestone should not create a long multi-step wizard.

This milestone should not redesign the Ingestion page.

This milestone should not change iCloud Intake.

---

## Product Framing

Local/external Source Intake already worked before the source identity work.

The purpose of this milestone is not to rebuild Source Intake.

The purpose is to make sure that when the operator clicks **Run Intake**, the system performs one last safety check:

```text
Is this source usable now?
Is this the expected enrolled endpoint, if enrolled?
Is this path-only but still allowed?
Does this require operator acknowledgment?
Is this blocked?
```

The result should be a simple launch decision:

```text
ready:
  allow run

path_only:
  allow run after one warning acknowledgment

needs_review:
  allow run after one warning acknowledgment

blocked:
  block run

provider_specific:
  block generic Source Intake and route operator to provider-specific workflow

unknown:
  block run and ask operator to check/retry readiness
```

## Product Decisions Locked for This Milestone

### 1. Generic Source Intake Only

This guard applies to generic Source Intake for filesystem-backed sources:

```text
local
external
removable
NAS
```

Do not apply this to iCloud Intake.

Do not change iCloud Intake.

### 2. Keep the Flow Simple

Do not create a 10-step workflow.

The user flow should be:

```text
Click Run Intake
Readiness check runs
If ready: continue to existing run confirmation
If path_only or needs_review: show one acknowledgment checkbox in the run confirmation
If blocked/provider_specific/unknown: show a clear message and do not open/start generic Source Intake
```

### 3. Backend Must Recheck

The frontend cannot be trusted as the final authority.

Even if the UI already checked readiness, the backend run endpoint must repeat readiness close to launch.

The backend guard should run before creating a Source Intake run row or starting a background intake thread.

### 4. Existing Path/Guardrail Checks Stay

Do not remove existing Source Intake safety checks.

The readiness guard is an additional layer.

Existing checks should remain as defense-in-depth, including:

```text
cross-operation guardrails
source path exists
source path is directory
Drop Zone is empty
other existing launch safety checks
```

### 5. Path-Only Is Still Allowed

For `path_only`, Source Intake may proceed only if the operator acknowledges the warning for this run.

The acknowledgment is per-run.

Do not persist a broad permanent bypass.

### 6. Needs Review Is Allowed With Acknowledgment

For `needs_review`, Source Intake may proceed only if the operator acknowledges the warning for this run.

The acknowledgment is per-run.

### 7. Blocked Hard-Stops the Run

For `blocked`, do not allow Source Intake launch.

Examples:

```text
path unavailable
path not directory
endpoint mismatch
NAS server-only path
unsupported source type
inactive/non-runnable profile
unsafe ambiguity
```

### 8. Provider-Specific Hard-Stops Generic Source Intake

For `provider_specific`, do not allow generic Source Intake launch.

Show copy like:

```text
This source uses a provider-specific workflow. Use iCloud Intake.
```

### 9. Unknown Does Not Launch

For `unknown`, do not launch.

Prompt the operator to check readiness again or review details.

## Backend Requirements

### 1. Extend Generic Source Intake Run Request

Extend the existing generic Source Intake run request schema with a small acknowledgment field.

Suggested field:

```text
readiness_acknowledged: bool = false
```

or a similarly named field consistent with project conventions.

This field should mean:

```text
The operator acknowledged the current path_only or needs_review readiness warning for this run.
```

It should not mean:

```text
ignore blocked readiness
ignore endpoint mismatch
ignore missing path
ignore provider-specific source type
```

### 2. Backend Rechecks Readiness Before Launch

In the backend path that starts generic Source Intake, call `SourceProfileReadinessService` before creating the run row or starting background work.

Use the current Source Profile and current runtime context.

### 3. Backend Launch Decision

Implement:

```text
ready:
  allow launch, no acknowledgment required

path_only:
  allow launch only if readiness_acknowledged = true
  otherwise reject with readiness result and acknowledgment-required message

needs_review:
  allow launch only if readiness_acknowledged = true
  otherwise reject with readiness result and acknowledgment-required message

blocked:
  reject; do not create Source Intake run

provider_specific:
  reject; do not create Source Intake run

unknown:
  reject; do not create Source Intake run
```

### 4. Structured Error Response

When the backend rejects launch due to readiness, return a useful safe response.

Use existing project error conventions where practical.

The response should include enough for the frontend/operator to show:

```text
readiness_status
identity_match_status
operator_message
recommended_next_action
warnings
blockers
requires_operator_acknowledgment
hard_block
```

Do not leak secrets or raw probe output.

### 5. Preserve Existing Guardrails

After readiness allows launch, existing Source Intake checks should still run.

Do not remove path existence/directory checks or Drop Zone checks.

### 6. Non-Mutation on Rejected Launch

If readiness rejects launch, backend must not create:

```text
source_intake_runs row
Vault writes
asset records
provenance records
cleanup records
observed path rows
```

## Frontend Requirements

### 1. Run Intake Click Uses Readiness

Update the generic Run Intake click flow.

Current behavior preflights basic path verification before opening the run confirmation.

New behavior should use the readiness API as the operator-facing preflight.

When the operator clicks **Run Intake**:

```text
call checkSourceProfileReadiness(sourceId)
store/display result in details/readiness state if relevant
decide whether to open confirmation or block
```

### 2. Ready Flow

For `ready`:

```text
open existing run confirmation modal
no extra acknowledgment required
submit run with readiness_acknowledged = false
```

### 3. Path-Only Flow

For `path_only`:

```text
open run confirmation modal
show warning message
require checkbox acknowledgment before enabling final start
submit run with readiness_acknowledged = true
```

Suggested copy:

```text
This source is path-only. Source Intake can run, but durable source identity enrollment is recommended.
```

### 4. Needs Review Flow

For `needs_review`:

```text
open run confirmation modal
show warning message
require checkbox acknowledgment before enabling final start
submit run with readiness_acknowledged = true
```

Suggested copy:

```text
This source needs review before relying on durable source identity. You may run Source Intake after acknowledging this warning.
```

### 5. Blocked Flow

For `blocked`:

```text
do not open run confirmation
show blocker message near the source/action area
do not call Source Intake run endpoint
```

### 6. Provider-Specific Flow

For `provider_specific`:

```text
do not open generic Source Intake confirmation
show message directing operator to iCloud Intake/provider-specific workflow
do not call Source Intake run endpoint
```

### 7. Unknown/Error Flow

For `unknown` or readiness API error:

```text
do not launch
show clear error/message
allow operator to retry readiness check
```

### 8. Acknowledgment Checkbox

Add one checkbox in the existing run confirmation modal only when needed.

Suggested label:

```text
I reviewed this readiness warning and want to run Source Intake for this source now.
```

The final Start/Run button should remain disabled until checked.

Do not persist the acknowledgment.

Reset it when modal closes or source changes.

### 9. Keep Existing UI Stable

Do not redesign the Ingestion page.

Do not reorganize the long source table.

Do not change iCloud Intake panel.

Do not add polling.

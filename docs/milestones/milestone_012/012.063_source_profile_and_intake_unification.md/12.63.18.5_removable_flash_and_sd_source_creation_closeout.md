## 3. Final Removable Product Definition

Removable now means interchangeable flash-based filesystem media registered through Windows-mounted volume identity.

Supported examples:

- USB thumb drives;
- USB flash drives;
- SD cards;
- microSD cards mounted through an adapter or reader.

Durable endpoint identity is the mounted medium volume, not the drive letter, USB port, computer, card reader, Media Name, or Source Name.

## 4. Internal Source Type Value Used

- operator-facing create category: `removable`
- backend/internal endpoint type: `removable_media`
- persisted Source Profile type for newly created removable Sources: `removable_media`

## 5. Source Creation Flow

Removable uses the normal filesystem Source Creation flow:

1. Choose `Removable`.
2. Enter a drive-root or subfolder path.
3. Select `Identify Location`.
4. Review durable identity, exact Source state, Media Name decision, Source Name, root, and final action.
5. Acknowledge only when required.
6. Confirm.
7. On success, the path/plan state clears while Source Type and completed result remain visible.

## 6. Durable Identity Implementation

The milestone reused the existing Volume GUID v2 identity path.

- `mountvol` Volume GUID evidence still drives endpoint fingerprinting.
- normal UI shows `Verified`, `Volume GUID`, and the masked identifier.
- drive letter remains observed-path evidence only.

## 7. Volume GUID Behavior

Implemented semantics:

- same removable medium at another drive letter resolves to the same endpoint;
- different medium at the same drive letter does not reuse stale identity;
- volume-label or Media Name changes do not change identity;
- Source Name does not change identity.

## 8. Volume-Level Identity Limitation

Identity remains volume-level in this milestone.

If a physical removable device exposes multiple mounted volumes, each Volume GUID is treated as a separate Source Endpoint.

No physical-device merge or serial-number identity was added.

## 9. Media Name Behavior

For Removable, the operator-facing endpoint alias is presented as `Media Name` in normal create/review/result UI where the recognized type is removable.

Behavior:

- persisted through the existing endpoint alias field;
- existing Use Existing Name / Rename behavior is preserved;
- mutable display metadata only;
- does not change endpoint UUID, fingerprint, or Source history.

## 10. Source Name Behavior

Removable reuses `12.63.18.4` Source Name behavior.

- new Sources receive a suggestion;
- operator edits are trimmed and validated;
- same-endpoint Source Name collisions block;
- exact reused/reactivated/adopted Sources retain their existing label.

## 11. Whole-Medium Root Behavior

Whole-medium removable roots persist:

- `endpoint_relative_root = ""`

Removable-specific suggested and displayed whole-root label:

- `Entire medium`

This does not change Local or External, which remain `Entire device`, or NAS, which remains `Entire share`.

## 12. Subfolder Root Behavior

Subfolder removable roots persist the deterministic relative path from the mounted volume boundary.

Examples validated by code/tests:

- `D:\Cat Videos` -> `Cat Videos`
- `H:\MISC` -> `MISC`

## 13. Classification Evidence

The Windows non-admin provider now combines existing filesystem evidence with removable-specific storage metadata when available.

Used evidence includes:

- readable local filesystem path;
- mounted Volume GUID;
- Windows drive type;
- Windows bus/interface evidence when obtainable;
- Windows physical media-type evidence when obtainable;
- SD/card-reader hint evidence when obtainable;
- system-volume detection;
- mapped-network blocking and UNC/NAS blocking.

## 14. Ambiguous USB Behavior

Implemented rule:

- acknowledgment is allowed only when at least one positive removable/USB/card-reader signal exists and no reliable HDD/SSD/internal blocker exists;
- if only Volume GUID plus local/non-network/non-system evidence exists with no removable/USB/card signal, Removable blocks instead of falling through to acknowledgment.

Message used for the ambiguous acknowledgment path:

`Windows could not conclusively classify this medium. Continue only if this is a USB flash drive or memory card. USB HDDs and SSDs should be registered as External.`

## 15. External HDD/SSD Mismatch Behavior

When reliable USB + HDD/SSD evidence is available for a new endpoint, Removable blocks and directs the operator to use `External`.

Automated coverage was added for this branch.

## 16. Local/System-Volume Mismatch Behavior

When the active Windows system volume is selected as Removable, creation blocks and directs the operator to use `Local`.

Existing endpoint reuse does not override system-volume blocking.

## 17. Optical Blocking Behavior

Optical media remains unsupported in this milestone.

The provider now emits a dedicated blocker:

- `optical_media_not_supported`

with the operator message:

`Optical media is not supported yet. Support for data CDs, DVDs, and Blu-ray discs will be added separately.`

## 18. Empty-Reader Behavior

The provider now emits `no_readable_media_inserted` only for clear no-media removable-slot conditions.

Automated provider coverage was added for the empty-slot branch.

## 19. Endpoint Reuse Behavior

Durable identity reuse takes precedence.

When a Volume GUID already matches an endpoint:

- the existing endpoint is reused;
- the registered endpoint type is preserved;
- no second removable endpoint is created;
- the existing mismatch acknowledgment flow is reused where needed.

Live validation showed this on `H:\MISC`, where removable selection reused an existing registered `Local` endpoint because the durable identity already existed.

## 20. Drive-Letter Change Behavior

The implementation continues to derive endpoint identity from Volume GUID, not drive letter.

Observed path remains current mount evidence only.

Automated coverage preserves this contract.

## 21. Media-Replacement Plan Safety

Confirm still recomputes the plan and durable identity before mutation.

This milestone did not weaken the existing plan-fingerprint safety model.

If media changes or disappears between plan and confirm, confirmation blocks and writes nothing.

## 22. Exact Source Reuse Behavior

Exact removable Source matches follow the same final UX rules as `12.63.18.4`:

- normal flow says the Source already exists;
- no duplicate exact Source is created;
- advanced duplicate/legacy details stay under Advanced Details.

Live validation on `D:\Cat Videos` reused endpoint `9`, reactivated existing Source `98`, and created no duplicate Source.

## 23. Legacy/Duplicate Conflict Behavior

No new duplicate-repair UI was added.

Ambiguous duplicate or legacy conflict handling remains blocked for later deliberate management work under `SRC-ID-006`.

## 24. Form-Reset Behavior

Removable reuses the `12.63.18.4` post-success reset behavior.

On success:

- path clears;
- plan/recognition state clears;
- Media Name and Source Name inputs clear;
- selected Source Type remains selected;
- completed result remains visible.

Blocked and failed operations preserve operator input.

## 25. Source Profile List Visibility

Removable was added to the frontend type handling so Removable-backed Source Profiles can be displayed and recognized as `Removable` in the existing list/workbench flows.

No Source Selector or Ingestion Workbench redesign was performed.

## 26. Source Intake Compatibility Assessment

Assessment result: option A.

Removable Source Creation is complete, but Source Intake compatibility is not yet proven and requires a narrow follow-up milestone.

Reasons:

- readiness mapping can represent `removable_media`;
- creation/profile visibility now support it;
- the generic intake launch and pipeline path were intentionally not broadened in this milestone;
- `backend/scripts/run_pipeline.py` still does not advertise a removable source type choice.

## 2. Executive Design Summary

The recommended design is a backend `SourceIdentityProbeService` that returns a safe, normalized `SourceIdentityProbeResult` from a provider-specific read-only probe.

Core shape:

```text
SourceIdentityProbeService
  accepts a Probe Request
  selects a SourceIdentityProbeProvider
  normalizes provider evidence
  classifies source-root validity
  compares optional expected endpoint evidence
  returns a safe Probe Response

SourceIdentityProbeProvider
  gathers OS/provider evidence
  never ingests, copies, stages, deletes, mounts, or stores credentials
  returns structured evidence items, not raw command dumps
```

Recommended location:

```text
backend/app/services/source_identity/
```

Recommended first provider:

```text
windows_non_admin_probe_v1
```

Recommended first implementation posture:

- Windows-only provider first.
- Read-only only.
- No schema writes.
- No Source Profile creation changes.
- No Source Intake behavior changes.
- No iCloud behavior changes.
- No provenance changes.
- API exposure only if explicitly scoped in the next implementation prompt.

The probe verifies that a selected or configured path appears to be the intended source. Source Intake remains the ingestion authority and performs all actual ingestion.

## 3. Core Concepts

Access Node:

The computer or runtime environment performing the probe and later running intake. Source identity is observed from the machine doing the scanning. A Windows desktop, future Linux mini-server, and future Mac may all observe the same endpoint through different paths.

Probe Provider:

The OS/provider-specific adapter that gathers evidence for an Access Node. Examples: `windows_non_admin_probe_v1`, `future_linux_probe_v1`, `future_macos_probe_v1`.

Probe Request:

A structured read-only request containing source type, observed path, mode, provider hints, redaction level, and optional expected endpoint evidence for comparison.

Probe Response:

A structured safe result containing status, normalized observed path, source-root classification, evidence summaries, confidence/match tier, safe-to-run decision, blockers, warnings, next actions, and redaction metadata.

Evidence Item:

One normalized fact gathered by a provider, such as volume serial present, path readable, UNC share unavailable, provider command access denied, or PnP evidence present. Evidence items are categorized, durability-rated, and privacy-rated.

Confidence Tier:

The system's assessment of how strongly current evidence identifies the source: strong match, medium match / needs review, weak match / manual confirmation, mismatch / block, or unavailable / not connected.

Observed Path:

The current path used by an Access Node to reach a source, such as `E:\`, `\\HENDERSON-NAS\Photos`, `/mnt/henderson-nas/photos`, or `/Volumes/ExternalDrive`. It is an observation, not durable identity.

Source Root Candidate:

The selected path that might become or verify a Source Profile root. The probe classifies whether it is a valid root candidate for its source type.

Run Launch Verification:

The future read-only check immediately before Source Intake starts for enrolled non-cloud sources. It must block mismatches before any scanning begins.

Responsibilities:

- Accept probe requests from API/readiness/run-launch callers.
- Select the provider based on `os_family`, runtime platform, or explicit diagnostic hint.
- Validate requested source type and observed path format.
- Ask the provider for read-only evidence.
- Normalize evidence into stable categories.
- Classify source-root candidate validity.
- Compare current evidence to expected/enrolled endpoint evidence when provided.
- Return safe structured responses for UI/API/readiness consumption.

Non-responsibilities:

- No Source Intake execution.
- No Vault writes.
- No asset/provenance creation.
- No iCloud acquisition or authentication probing.
- No cleanup.
- No DB writes in the first implementation.
- No mount/unmount behavior.
- No credential collection or credential-store access.
- No raw command dump exposure.

Layers that may call the service later:

- Future source identity admin API.
- Future Source Profile setup/enrollment flow.
- Future non-cloud readiness service.
- Future Source Intake run-launch verification.

Layers that must not call raw OS commands directly:

- Source Intake execution service.
- Pipeline orchestrator.
- Frontend.
- Provenance services.
- iCloud acquisition/readiness/cleanup services.

Source Intake stays downstream. It should receive a verified path only after readiness/run-launch verification says the source is safe to run.

## 5. Access Node Design

An Access Node represents the machine/environment performing source access.

Conceptual fields:

```text
access_node_id
access_node_label
os_family
os_version_summary
app_instance_id
host_fingerprint
probe_provider_name
probe_provider_version
last_seen_at
```

Store later, carefully:

- Stable app-generated access node ID.
- User-facing label such as "Chuck Windows PC".
- OS family.
- Masked or hashed host fingerprint.
- Provider capability summary.

Avoid or mask:

- Raw hostnames in normal UI.
- Usernames in paths unless operationally required.
- Machine serials.
- Credential/session data.
- Full environment dumps.

Relationship to observed paths:

- Observed paths are access-node-specific.
- The same endpoint can appear as `E:\` on Windows, `/media/chuck/ExternalDrive` on Linux, or `/Volumes/ExternalDrive` on macOS.
- Observed path history should be append-only and linked to an access node.

Current Windows PC:

- First implementation can infer Access Node from current process/platform.
- It should report `os_family = windows` and `provider_name = windows_non_admin_probe_v1`.

Future Linux mini-server:

- The same endpoint model should support Linux mount paths and device IDs without changing Source Profile/provenance semantics.
- A mini-server may become the primary Access Node for scheduled or always-on intake.

Future Mac:

- The contract should support `/Volumes/...` observed paths and macOS provider evidence without changing endpoint/profile structure.

## 7. Probe Request Contract

Conceptual request:

```json
{
  "source_type": "external_device",
  "observed_path": "E:\\Photos",
  "intended_use": "source_profile_setup",
  "probe_mode": "setup_probe",
  "os_family": "windows",
  "access_node_id": null,
  "access_node_hint": "Chuck Windows PC",
  "provider_name": null,
  "include_raw_evidence": false,
  "redaction_level": "standard",
  "expected_endpoint_evidence": null
}
```

Required fields:

- `source_type`
- `observed_path` for local/external/removable/NAS probe modes
- `probe_mode`

Optional fields:

- `intended_use`
- `os_family`
- `access_node_id`
- `access_node_hint`
- `provider_name`
- `include_raw_evidence`, default false
- `redaction_level`, default standard
- `expected_endpoint_evidence`
- `expected_source_root`

Probe modes:

`setup_probe`:

- Used before enrolling or creating an endpoint-linked Source Profile.
- Gathers enough evidence to classify new/known/ambiguous/unreadable.
- Does not write endpoint identity.

`readiness_probe`:

- Used when showing whether an existing Source Profile appears connected.
- Uses stored expected evidence when available.
- Should produce operator-friendly blockers/warnings.

`run_launch_verification`:

- Used immediately before Source Intake starts.
- Most conservative mode.
- Blocks mismatches, ambiguous identities, missing roots, access denied, credential prompts, and invalid NAS server-only roots.

`diagnostic_probe`:

- Used for Advanced Details/troubleshooting.
- May include more evidence item detail but still no full raw dumps or secrets.

## 10. Windows Provider Design

The first Windows provider should be non-admin and conservative.

First-line evidence methods:

- `.NET DriveInfo` for drive readiness, type, label, filesystem, size/free space.
- `vol <drive>:` for volume serial when available.
- `mountvol <drive>: /L` for volume GUID when available.
- `mountvol` for mounted volume list when needed.
- `fsutil fsinfo drivetype <drive>:` for drive type.
- `fsutil fsinfo volumeinfo <drive>:` as available, with access denied handled gracefully.
- `pnputil /enum-devices /connected /class DiskDrive`
- `pnputil /enum-devices /connected /class Volume`
- `pnputil /enum-devices /connected /class WPD`
- `pnputil /enum-devices /connected /class USB`
- `net use` for mapped drive to UNC mapping.
- `Test-Path` / `Get-Item` equivalent checks for exact filesystem or UNC root supplied by the request.

Optional enrichment, not mandatory:

- `Get-Volume`
- `Get-Disk`
- `Get-Partition`
- `Get-CimInstance`
- `Get-PnpDevice`
- `Get-SmbMapping`
- `wmic path ...`

These were access-denied or unavailable in the 12.63.2 environment and must not be required for v1 readiness.

Avoid:

- Credential-store queries.
- Credential prompts.
- Mounting or unmounting drives.
- Writing marker files.
- Large content scans.
- Full raw command dumps.
- Direct promotion of raw command output to canonical identity.

Access denied handling:

- Return evidence item `command_access_denied`.
- Keep provider status as `completed_with_warnings` if enough other evidence exists.
- Set `safe_to_run = needs_review` or `false` depending on source type and mode.

Unavailable command handling:

- Return evidence item `command_unavailable`.
- Mark capability false.
- Continue with remaining first-line evidence.

Drive-letter mapping:

- Start from exact observed path.
- Determine drive root.
- Gather volume evidence for that root.
- Gather broad PnP evidence.
- Correlate PnP evidence only when evidence is strong enough, such as WPD volume label/root alignment or clear USBSTOR/volume relationship.
- If no reliable drive-to-device join exists, do not pretend it does. Return medium/needs-review when volume evidence is good but device evidence is partial.

Sanitization:

- Mask volume GUIDs, serials, PnP instance IDs, USB identifiers, hostnames, usernames in paths where possible, and server/share identities in Advanced Details.
- Store or return exact source root only because it is operationally required.

## 11. Future Linux / Mini-Server Hook

The normalized contract must support Linux without redesigning Source Profiles.

Likely observed paths:

```text
/mnt/henderson-nas/photos
/media/chuck/ExternalDrive
/srv/photo-sources/archive
```

Likely durable evidence concepts:

- Mount path.
- Filesystem UUID or label.
- Block device identity.
- `/dev/disk/by-uuid/...` or equivalent stable links.
- NAS mount source, such as server/share.
- Readability and mount availability.

Provider capability flags that matter:

- `volume_identity`
- `device_pnp_evidence` or Linux equivalent.
- `drive_to_device_join`
- `network_mapping`
- `network_share_check`
- `mount_source_resolution`

Linux NAS differs from Windows:

- The observed path may be a local mount path, not a UNC path.
- The provider must be able to distinguish local folder under `/mnt` from a mounted NAS share when evidence is available.
- The endpoint should still store NAS server/share identity separately from observed mount path.

No Linux commands are implemented or deeply specified in this milestone.

## 13. Source-Type Behavior

Local:

- Identity should combine Access Node + local volume evidence + selected root path.
- A local source root may be a volume root or folder.
- Path-only legacy profiles may continue to run until explicitly endpoint-enrolled.

External Device:

- Identity should combine observed drive/mount path + volume evidence + device evidence.
- Drive letter alone is never durable identity.
- If volume evidence is strong but device evidence cannot be joined, classify as medium / needs review.

Removable Media:

- Identity should emphasize inserted media/session evidence when available.
- SD/camera cards may have only weak-to-medium evidence.
- Reader device evidence is supporting context, not the media identity by itself.

NAS:

- Identity must distinguish server, share, folder inside share, and observed path.
- Direct UNC share paths are valid if readable.
- Mapped drives are observed paths only and should be resolved to UNC via `net use` when possible.
- Server-only UNC is not a runnable root.
- Do not store NAS credentials.
- Do not enumerate unrelated shares as normal probing.

Cloud:

- Cloud identity remains provider-specific.
- iCloud uses source profile/provider/account/staging/inventory concepts already in the app.
- Do not reduce cloud identity to local filesystem volume evidence.
- Do not probe Apple credentials, sessions, cookies, 2FA, tokens, or provider helpers.

## 14. NAS Path Classification

The probe should classify NAS paths as follows:

| Input shape | Classification | Valid source root? | Typical result |
| --- | --- | --- | --- |
| `\\HENDERSON-NAS` | `nas_server_only` | No | Block with `nas_server_not_runnable` |
| `\\HENDERSON-NAS\Photos` | `nas_share_root` | Yes if readable | Candidate root |
| `\\HENDERSON-NAS\Photos\Family Archive` | `nas_share_folder` | Yes if readable | Candidate root |
| `Z:\Photos` where `Z:` maps to `\\HENDERSON-NAS\Photos` | `mapped_drive_path` plus resolved UNC | Yes if readable and mapping matches | Candidate root, observed path only |
| `\\192.168.1.10\Photos` | `nas_share_root_ip` | Yes if readable | Needs review unless matched to known endpoint |
| `\\NASALIAS\Photos` | `nas_share_root_hostname_alias` | Yes if readable | Needs review unless matched |
| unavailable UNC | `nas_unreachable` | No | Not connected/block |
| access denied | `nas_access_denied` | No | Block |
| credential prompt required | `nas_credential_required` | No | Block |

Specific rule:

```text
\\HENDERSON-NAS is a NAS server endpoint seed.
It is not a runnable Source Root.

\\HENDERSON-NAS\<share> and \\HENDERSON-NAS\<share>\<folder>
are runnable Source Root candidates only if readable.
```

The probe should not call broad share enumeration as normal setup if an exact intended share/root is supplied. Exact-path probing is safer and avoids unnecessary exposure.

## 15. Source Root Candidate Rules

Response fields:

```text
is_valid_source_root_candidate
filesystem_boundary_type
root_reason
```

Boundary types:

```text
local_volume_root
local_folder
external_volume_root
external_folder
removable_media_root
removable_media_folder
nas_server_only
nas_share_root
nas_share_folder
cloud_profile_scope
cloud_staging_path
unknown
```

Local:

- Valid if volume root or folder exists and is readable.
- Root path plus host/volume evidence identifies the source candidate.

External Device:

- Valid if volume root or folder exists/readable and current evidence matches or can become endpoint evidence.
- Invalid if only a drive letter string exists but volume/path evidence is missing.

Removable Media:

- Valid if media root or folder exists/readable and media/volume evidence is present enough.
- Needs review if identity evidence is generic or weak.

NAS:

- Valid if share root or folder inside share exists/readable.
- Invalid if server-only UNC.
- Invalid if access denied, credential required, or unreachable.

Cloud:

- Provider-specific.
- iCloud profile scope and managed staging path should be checked through cloud-specific readiness, not generic volume-only identity.

## 16. Confidence / Match Tier Design

Tiers:

`strong_match`:

- Durable endpoint evidence matches expected evidence.
- Path exists/readable.
- Source-root candidate is valid.
- No contradictory evidence.
- No active conflicting operation.

`medium_needs_review`:

- Important evidence matches but one durable field is missing, unavailable, or changed.
- Safe enough to suggest a source, not safe enough for automatic run launch unless future policy allows.

`weak_manual_confirmation_required`:

- Only label/path/size/filesystem or similarly weak evidence matches.
- Requires explicit operator confirmation or endpoint repair flow.

`mismatch_block`:

- Current observed path maps to different enrolled identity evidence.
- Multiple possible endpoint matches.
- NAS share differs.
- Device/volume evidence contradicts enrolled endpoint.

`unavailable_not_connected`:

- Path missing, drive not ready, share unavailable, access denied, or provider unsupported.

`not_compared`:

- Setup probe without expected endpoint evidence.

Safe-to-run mapping:

| Tier | `safe_to_run` |
| --- | --- |
| `strong_match` | `true` |
| `medium_needs_review` | `needs_review` |
| `weak_manual_confirmation_required` | `needs_review` |
| `mismatch_block` | `false` |
| `unavailable_not_connected` | `false` |
| `not_compared` | `needs_review` for run launch, otherwise not applicable |

For enrolled external/removable/NAS profiles, mismatch must block. Ambiguous matches must block or require an explicit future review/repair path. Drive letter or mount path alone must never be sufficient durable identity.

## 17. Privacy / Redaction Rules

May be returned raw when operationally required:

- Source type.
- Selected source root/folder path.
- Non-secret provider name.
- Managed staging path for cloud sources.
- Readiness state and timestamps.
- High-level source alias.

Mask in normal UI or Advanced Details:

- Hostname.
- Volume GUID.
- Volume serial.
- PnP instance IDs.
- USB VID/PID/serial-like identifiers.
- NAS server/share names if treated as sensitive.
- Usernames inside paths where feasible.

Hash before later storage:

- Host/access-node fingerprint.
- Volume GUID and serial.
- PnP/USB identifiers.
- NAS server/share identity if product decides not to store raw.

Never collect or store:

- NAS passwords.
- Credential-store secrets.
- Apple credentials.
- Tokens.
- Session cookies.
- 2FA codes.
- Cloud provider secrets.
- Full raw command dumps containing sensitive identifiers.

Normal UI should show:

- Connected / Not Connected / Needs Review / Blocked.
- Source type.
- Selected root.
- Clear blocker or next safe action.

Advanced Details may show:

- Provider name/version.
- Masked evidence items.
- Confidence tier.
- Capability limitations.
- Blocker codes.

Logs should exclude raw identifiers and full command output. Log codes, counts, and sanitized summaries only.

## 18. Error / Blocker Codes

Proposed standard codes:

| Code | Meaning |
| --- | --- |
| `path_not_found` | Observed path does not exist. |
| `path_not_readable` | Path exists but cannot be read. |
| `access_denied` | OS denied access to path or evidence. |
| `source_root_invalid` | Path shape is not a valid source root for source type. |
| `nas_server_not_runnable` | NAS server-only path was provided. |
| `nas_share_unknown` | NAS share identity could not be determined. |
| `credential_required` | OS/provider would require credentials or prompt. |
| `provider_unavailable` | Provider cannot run in this environment. |
| `provider_access_denied` | Provider-level evidence collection was denied. |
| `identity_unavailable` | Required identity evidence could not be collected. |
| `identity_mismatch` | Current evidence conflicts with expected endpoint. |
| `identity_ambiguous` | Multiple possible endpoints match. |
| `multiple_matches` | More than one candidate source is plausible. |
| `unsupported_source_type` | Source type is not supported by this provider/service. |
| `unsupported_os_provider` | Requested OS/provider is unsupported. |
| `command_unavailable` | Optional/expected command is missing. |
| `command_access_denied` | Command exists but was denied. |
| `cloud_provider_not_probeable` | Cloud provider must use provider-specific readiness. |
| `raw_evidence_suppressed` | Raw evidence exists but was not returned by privacy policy. |
| `operation_conflict_active` | Another ingestion-related operation is active. |

Future UI should map these codes to clear operator messages and next safe actions.

## 21. Readiness and Run Launch Integration

Future non-cloud readiness:

1. Load Source Profile from `ingestion_sources`.
2. If endpoint-enrolled, load expected endpoint evidence.
3. Probe current observed path or known observations.
4. Combine probe result with existing operation guardrails.
5. Return one readiness result with blockers, warnings, and next actions.

Future run launch verification:

1. Operator starts Run Intake for a non-cloud Source Profile.
2. Backend obtains guardrail lock/checks active operations.
3. Backend runs `run_launch_verification` probe before creating `SourceIntakeRun`.
4. If mismatch/ambiguous/unavailable/invalid, return 409 or 400 with structured probe blockers.
5. If strong match, pass verified current source root to Source Intake.
6. Source Intake performs ingestion and remains the authority for Vault/DB/provenance.

Current architecture seam:

- `backend/app/services/admin/source_intake_execution_service.py` is the eventual point to call run-launch verification before resolving and scanning the source root.
- Do not put raw provider commands inside that service.
- Do not change this behavior until endpoint enrollment exists and the implementation milestone scopes the change.

Legacy path-only profiles:

- Must continue to work until explicitly enrolled/upgraded.
- May show warning: "Path-only profile; source identity not enrolled."
- Should not be silently blocked by endpoint verification that the operator never enrolled.

Mismatch behavior:

- Do not launch Source Intake.
- Do not rewrite `source_root_path`.
- Do not rewrite provenance.
- Do not update endpoint identity silently.
- Future implementation may append a failed observation if a safe schema exists.

## 23. Risks / Tradeoffs

- Windows-only first implementation leaves Linux mini-server and macOS as contract-only until later.
- Non-admin Windows evidence has gaps; Storage/WMI/CIM/PnP APIs may be denied.
- Drive-letter-to-device join may be partial, especially for external HDDs reported as Fixed.
- Volume serial/GUID can be weak or change after reformat/remount.
- PnP identifiers may represent USB bridge hardware rather than bare disk identity.
- Removable media identity may be weak without media/session IDs.
- Optical media remains unvalidated.
- NAS identity is tricky because hostnames, IPs, aliases, mapped drives, and share names can overlap.
- `\\HENDERSON-NAS` server visibility does not prove share/root availability.
- Privacy risk is real: paths, hostnames, serials, PnP IDs, and share names can be sensitive.
- False blocks could frustrate operators if evidence changes benignly.
- False accepts are worse because wrong-source ingestion damages provenance meaning.
- Legacy path-only profile compatibility must be preserved.
- iCloud compatibility must not regress; cloud readiness remains provider-specific.

Tradeoff recommendation:

- Bias toward "Needs Review" or "Blocked" over wrong-source intake for endpoint-enrolled external/removable/NAS profiles.
- Keep path-only legacy behavior until enrollment explicitly raises the safety bar.

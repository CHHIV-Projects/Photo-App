## 4. Current Readiness / Status Findings

Current Source Profile status is lifecycle/status metadata, not source identity readiness.

Current Source Profile summary/detail responses expose:

```text
source_id
source_label
source_type
source_root_path
endpoint_id
profile_status
cloud_provider
acquisition_method
managed_staging_path
run/reference counters
```

The only generic readiness-like check today is path verification:

```text
POST /api/admin/source-profiles/{source_id}/verify-path
```

That endpoint resolves the Source Profile effective path and returns:

```text
path
path_kind
exists
is_directory
checked_at
```

It does not compare durable Source Endpoint identity. It does not use `endpoint_id`. It does not produce a source readiness decision.

iCloud has its own provider-specific readiness endpoint:

```text
GET /api/admin/source-profiles/{source_id}/icloud-readiness
```

That endpoint should remain separate from generic filesystem endpoint readiness.

## 5. Current Source Intake Launch Findings

The Ingestion page currently supports Run Intake for active local/external profiles.

Before opening the Source Intake confirmation modal, the UI:

```text
checks basic run-disabled rules
checks whether Source Intake is already active
calls POST /api/admin/source-profiles/{source_id}/verify-path
requires exists=true and is_directory=true
opens the run confirmation modal
```

After confirmation, the UI calls:

```text
POST /api/admin/source-intake/run
```

The backend launch path currently:

```text
checks cross-operation guardrails
loads the ingestion source
requires source_root_path
resolves the path
requires path exists
requires path is a directory
requires Drop Zone is empty
creates a source_intake_runs row
starts the background Source Intake thread
```

There is no current Source Endpoint identity comparison in Source Intake launch.

The natural future guard insertion point is immediately before the run confirmation flow or immediately before `start_source_intake` is called. The same readiness service should be reused in both contexts.

## 6. Proposed Readiness State Model

The operator model should stay simple:

```text
Check Readiness
Run Intake
```

Readiness should not become a long wizard. The UI should show:

```text
compact readiness badge
plain-language operator message
one recommended next action
Advanced Details for probe/match internals
```

Proposed top-level statuses:

| Status | Label | Meaning | Future Source Intake behavior |
| --- | --- | --- | --- |
| `ready` | Ready | Source is reachable and identity is acceptable for run. | Allow Source Intake. |
| `path_only` | Path-only | No durable endpoint is enrolled, but the path is usable. | Allow Source Intake with warning. |
| `needs_review` | Needs Review | Source is readable, but identity confidence is medium/weak or requires operator confirmation. | Allow only after explicit per-run acknowledgment. |
| `blocked` | Blocked | A hard safety or availability issue exists. | Do not allow Source Intake. |
| `provider_specific` | Provider-specific | Generic readiness does not apply, such as iCloud. | Route to provider-specific workflow. |
| `unknown` | Unknown | Readiness has not been checked or could not be determined. | Prompt operator to check readiness before running. |

Hard blockers should include:

```text
endpoint mismatch
unavailable path
NAS server-only path
unsupported source type
unsafe or ambiguous source condition
inactive/non-runnable profile status
```

Warnings should not become their own primary state unless they affect the run decision.

## 7. Proposed Identity Match Model

Recommended identity match statuses:

| Match Status | Meaning | Readiness Mapping |
| --- | --- | --- |
| `not_enrolled` | Source Profile has no endpoint_id. | `path_only` if path is usable, otherwise `blocked` or `unknown`. |
| `matched` | Current probe matches the linked endpoint. | `ready`. |
| `needs_review` | Current probe is readable but medium/weak or incomplete. | `needs_review`. |
| `mismatch` | Current probe points to a different endpoint identity. | `blocked`. |
| `unavailable` | Path is missing, access denied, or not readable. | `blocked`. |
| `unsupported` | Source type or boundary is unsupported. | `blocked`. |
| `provider_specific` | Generic readiness should not handle this source. | `provider_specific`. |
| `ambiguous` | The system cannot safely identify the source, or evidence conflicts. | `blocked` if unsafe; otherwise `needs_review` only when clearly readable and non-conflicting. |
| `unknown` | No current check has been performed or result is indeterminate. | `unknown`. |

For enrolled profiles, strong automatic match should require:

```text
same endpoint source_type
same durable identity_fingerprint_hash
endpoint not retired
current path is readable
current source root boundary is valid
```

Observed path alone should not be treated as durable identity evidence.

If the same endpoint appears at a different mount/path and the durable fingerprint still matches, readiness should be `ready` or `needs_review` depending on confidence. Drive letters and transient mount paths remain observations, not durable identity.

If an enrolled endpoint has a fingerprint and the current probe fingerprint differs, readiness should be `blocked` with an endpoint mismatch message.

If the fingerprint cannot be collected but the path is readable and no conflict is found, readiness should be `needs_review`, not `ready`.

## 8. Path-Only Profile Behavior

Path-only profiles are Source Profiles where:

```text
endpoint_id = null
```

They must remain valid and runnable for now.

Recommended behavior:

```text
path readable and active profile:
  readiness_status = path_only
  can_run_source_intake = true
  requires_operator_acknowledgment = true in future run confirmation

path missing/unreadable:
  readiness_status = blocked
  can_run_source_intake = false

not checked:
  readiness_status = unknown
  recommended action = Check Readiness
```

Suggested operator copy:

```text
Path-only source identity. This source can run, but durable source identity enrollment is recommended.
```

The UI should suggest enrollment, but not force it before Source Intake.

## 9. Enrolled Local / External / Removable / NAS Behavior

Generic readiness applies to filesystem-backed endpoint types:

```text
local
external_device
removable_media
nas
```

The readiness service should map existing Source Profile types conservatively:

```text
local_folder with normal local path -> local
local_folder with UNC path -> nas
external_drive -> external_device
cloud_export with icloud -> provider_specific
scan_batch / other -> unsupported unless later designed
```

Rules:

```text
same endpoint, same fingerprint, readable path:
  ready

same endpoint, changed path, fingerprint still matches:
  ready or needs_review depending on confidence

readable path, medium/weak identity evidence:
  needs_review

readable path, fingerprint mismatch:
  blocked

path missing, access denied, not directory, or not readable:
  blocked

NAS server-only path:
  blocked

NAS share root or NAS share folder, readable, matching server/share fingerprint:
  ready or needs_review depending on confidence

mapped NAS drive where canonical share evidence is incomplete:
  needs_review unless durable endpoint match can be proven
```

For NAS, endpoint identity should continue to be server plus share. The full folder path remains the Source Profile root and observed path.

## 10. Cloud / iCloud Behavior

Cloud/iCloud remains provider-specific.

Generic filesystem endpoint readiness should not control iCloud. iCloud already has its own readiness/status/prepare/import/resume model.

For iCloud Source Profiles, generic readiness should return:

```text
readiness_status = provider_specific
identity_match_status = provider_specific
can_run_source_intake = false for generic run
recommended_next_action = Use iCloud Intake readiness/workflow
```

Suggested operator copy:

```text
iCloud readiness is handled by iCloud Intake.
```

Future cloud endpoint identity should be designed separately.

## 11. Backend Service/API Design

Add a new service:

```text
SourceProfileReadinessService
```

Recommended location:

```text
backend/app/services/source_identity/readiness_service.py
backend/app/services/source_identity/readiness_schema.py
```

This keeps readiness near source identity while avoiding changes to endpoint enrollment and Source Intake.

Recommended endpoint:

```text
POST /api/admin/source-profiles/{source_id}/check-readiness
```

`POST` is preferred because this performs a live check/probe and may touch slow/removable/NAS paths. It should still be safe and non-destructive.

The service should:

```text
load the Source Profile
resolve the effective path
map Source Profile type to probe source type
call SourceIdentityProbeService with probe_mode=readiness_probe
load linked SourceEndpoint if endpoint_id exists
compare current probe identity with linked endpoint identity
return one operator-facing readiness result
avoid starting Source Intake
avoid writing Vault/assets/provenance/cleanup
avoid mutating Source Profile paths
```

Recommended response fields:

```text
source_profile_id
source_label
source_type
profile_status
cloud_provider
endpoint_id
endpoint_alias
endpoint_source_type
readiness_status
identity_match_status
can_run_source_intake
requires_operator_acknowledgment
hard_block
operator_message
recommended_next_action
warnings
blockers
checked_at
probe_summary
observed_path_summary
access_node_summary
advanced_details
```

Implementation note:

The fingerprint-building logic currently lives inside endpoint enrollment. Readiness should not duplicate that logic. A future implementation should extract the fingerprint helper into a shared source identity utility so enrollment and readiness compare identity the same way.

## 12. UI Integration Design

Minimal first UI implementation should be in the Source Profile details drawer.

Recommended details drawer area:

```text
Source Readiness
  Badge: Ready / Path-only / Needs Review / Blocked / Provider-specific / Unknown
  Message: plain-language result
  Next action: one recommended action
  Button: Check Readiness
  Advanced Details: probe/match/status internals
```

The UI should avoid a 10-12 step workflow. It should not require the operator to walk through enrollment, probe internals, endpoint details, and intake options every time.

Source Profile list rows may later show a compact badge, but the first implementation can keep readiness in details to avoid noisy list polling and expensive probes.

Create Source Profile flow should not auto-run readiness. After enrollment success it may say:

```text
Endpoint enrolled. Check readiness before running intake.
```

Generic Source Intake controls should remain separate from iCloud Intake controls.

The existing wording that says source identity is based on label + type + effective path should be revised in a future UI milestone so it does not conflict with durable endpoint identity. Suggested distinction:

```text
Compatibility Source Identity: label + type + effective path
Durable Source Identity: enrolled endpoint
Readiness: current ability to safely use the source
```

## 13. Run-Launch Guard Design

Future run-launch behavior should be simple.

When the operator clicks Run Source Intake:

```text
1. UI/backend performs check-readiness immediately before launch.
2. If ready, continue to Source Intake confirmation.
3. If path_only, show one warning acknowledgment in the confirmation flow.
4. If needs_review, show one explicit per-run acknowledgment in the confirmation flow.
5. If blocked, stop and show the blocker message.
6. If provider_specific, route to iCloud/provider-specific workflow.
7. If unknown, prompt operator to check readiness before running.
```

Approved future behavior:

```text
ready:
  allow Source Intake

path_only:
  allow Source Intake with warning that durable source identity is recommended

needs_review:
  allow Source Intake only after explicit per-run acknowledgment

blocked:
  do not allow Source Intake

provider_specific:
  do not use generic readiness; route to iCloud/provider-specific workflow

unknown:
  prompt operator to check readiness before running
```

The acknowledgment should be per run. It should not become a permanent broad bypass.

The backend run endpoint should eventually repeat the readiness check close to `start_source_intake` so browser-side state cannot become stale.

## 14. Data Persistence Recommendation

Recommended v1 readiness persistence:

```text
read-only check
no new readiness history table
no Source Profile mutation
no automatic observed-path writes from manual Check Readiness
```

Reason:

Manual readiness checks may be frequent, exploratory, or run against missing/removable/NAS sources. Persisting every check would add noise and create a larger evidence-history problem before the run-launch policy is mature.

Future guarded run launch may persist an observed path when:

```text
endpoint exists
readiness was successful or acknowledged
Source Intake launch actually proceeds
the observed path record model already supports the fields
```

That persistence should be explicitly scoped in the run-launch guard milestone.

## 17. Risks / Open Questions

Resolved product decision:

```text
needs_review should eventually allow Source Intake only after explicit per-run acknowledgment.
```

Remaining risks:

```text
Fingerprint helper reuse:
  Readiness and enrollment must not drift into two different identity comparison algorithms.

Existing source type vocabulary:
  Source Profiles still use legacy values such as local_folder, external_drive, cloud_export, scan_batch, and other.
  Readiness must map these conservatively without a taxonomy migration.

NAS mapped-drive evidence:
  Mapped drive to UNC canonicalization remains limited.
  If share identity cannot be proven, readiness should fall back to needs_review rather than ready.

Endpoint detail exposure:
  Source Profile summary/detail currently exposes only endpoint_id.
  Readiness response should include safe endpoint alias/source type details without exposing secrets.

Stale checks:
  A readiness result can become stale if a removable drive/NAS share changes after the check.
  Future run launch must re-check immediately before starting Source Intake.

Operator overload:
  Advanced probe details are useful for debugging but should stay out of the primary operator path.
```

No blocking open questions remain for the next API/service milestone.

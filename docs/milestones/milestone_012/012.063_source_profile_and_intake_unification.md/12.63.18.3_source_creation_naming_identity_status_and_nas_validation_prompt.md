## Why This Milestone Exists

`12.63.18.2` successfully established the practical Source Creation flow:

- static Create a Source panel
- path-first recognition
- explicit existing-device naming decisions
- duplicate / adoption / reactivation handling
- transactional creation behavior
- operator-confirmed drive-letter-independent recognition

The recent closeout and operator validation also show two remaining usability gaps:

### 1. Generated Source labels are overly long and technical

The created Source label may expose the full endpoint-relative path in an unwieldy way.

Example pattern:

```
External 10 - WD Backup.swstor\...\Pictures\2019-03-13
```

This is technically correct but operator-hostile.

### 2. Identity messaging still feels too technical

The endpoint was successfully recognized with a full v2 Volume GUID fingerprint, but the UI still surfaced internal-style status language such as:

```
medium_needs_review
```

That is not the correct normal operator-facing answer when the identity is effectively strong enough for Source Creation.

### 3. NAS creation behavior needs live user-environment validation

Automated coverage exists, but NAS source creation was not fully live-validated in the coder’s isolated environment.

We should validate the real user environment using the known NAS path patterns.

## Product Decisions Locked for This Milestone

### 1. Source Name vs Source Label

We need a clearer operator-facing Source name.

Current technical label generation based on full endpoint-relative root is acceptable for internal uniqueness, but not ideal for normal display.

For this milestone, use the following conceptual model:

```
Device Name:human-readable endpoint namee.g. External 10, Chuck PC, Henderson NASSource Root:technical endpoint-relative roote.g. Archive\Family PhotosSource Display Name:short operator-facing source name
```

### 2. New Sources Should Get Better Default Display Names

For newly created Sources, the default display name should be shorter and more human-readable than the full relative path.

Preferred default rule:

- If endpoint-relative root is empty:
  - use `Entire device` or `Entire share`
- Otherwise:
  - default to the **final folder name** in the endpoint-relative root
  - if needed for disambiguation, append a short parent context

Examples:

```
Archive\Family Photos-> Family PhotosWD Backup.swstor\hende\Pictures\2019-03-13-> 2019-03-13Dad Files\DadFilesClean1x\Photos\32. RMH Pic\1. Old RMH-> Old RMH
```

If the final folder name is too generic or duplicated within the same device, a slightly richer default is acceptable, such as:

```
32. RMH Pic - Old RMH
```

### 3. Existing Source Labels Are Not Broadly Migrated

Do not rewrite all previously created Source labels in this milestone.

Only newly created Sources need the improved naming behavior.

If a very narrow display-layer improvement can show a cleaner display name without changing the stored label, that is acceptable, but do not perform a risky migration.

### 4. Operator-Facing Identity Status Must Be Simple

For normal Source Creation UI, do not show internal-style wording such as:

```
medium_needs_reviewnot_comparedfingerprint_evidence_medium
```

Normal operator-facing fields should be:

```
Durable Identity:VerifiedNot verifiedProvider-specificUnknown
```

For a full v2 Volume GUID match in Source Creation, normal UI should show:

```
Verified
```

Internal diagnostic fields may remain in Advanced Details.

### 5. Identity Details Still Matter

When identity is verified, the normal result should still show:

```
Identifier TypeIdentifier
```

Examples:

```
Identifier Type: Volume GUIDIdentifier: {...8206}Identifier Type: NAS ShareIdentifier: \\HENDERSON-NAS\Photos
```

The identifier may remain masked/safe where appropriate.

### 6. NAS Must Be Validated Live

This milestone should include real-environment validation of NAS Source Creation using:

- a share-level path
- a deeper folder under that share

Examples based on the user environment:

```
\\HENDERSON-NAS\Photos\\HENDERSON-NAS\Photos\Camera imports
```

If mapped-drive NAS validation is safely possible in the user environment, it may be validated too, but direct UNC validation is the priority.

### 7. iCloud Remains Unchanged

If iCloud is chosen, keep the current provider-specific creation controls.

Do not mix iCloud into the filesystem naming/status polish beyond ensuring consistent Create Source layout.

### 8. Removable Remains Deferred

Removable should remain visible as:

```
Removable — coming later
```

Do not implement Removable in this milestone.

That should be handled in a separate next milestone if we continue the source-creation arc.

## Required Work

### 1. Improve New Source Display Naming

For newly created filesystem Sources:

- generate a cleaner Source display name
- preserve the durable source model:
  - endpoint identity
  - endpoint-relative root
  - observed path
- do not depend on drive letter for naming

Preferred behavior after successful creation:

Show:

```
Device Name:External 10Source Name:2019-03-13Root Relative to Device:WD Backup.swstor\hende\Pictures\2019-03-13Observed Path:E:\WD Backup.swstor\hende\Pictures\2019-03-13
```

Do not force the operator to use the long technical root as the main source name.

If the current schema uses a persisted Source label, you may improve the default label generation for **new Sources only**.

### 2. Improve Create Source Result Display

After successful creation or reuse/adoption/reactivation, the normal result area should present:

```
Source TypeDevice NameSource NameDurable IdentityIdentifier TypeIdentifierRoot Relative to DeviceObserved PathAction Completed
```

Examples of action completed:

```
Created new SourceUsed existing SourceAdopted and linked existing SourceReactivated existing SourceRenamed device and created Source
```

Do not put Endpoint ID or internal IDs in the normal display area.

Those may remain under Advanced Details.

### 3. Simplify Identity Status Wording

Review the current Source Creation API response and UI mapping.

Ensure the normal Create Source UI shows:

- Verified
- Not verified
- Provider-specific
- Unknown

Map strong full-GUID and strong NAS share cases appropriately to `Verified`.

If internal confidence or evidence values remain in API responses, keep them out of the normal operator-facing section.

### 4. Validate and Polish NAS Source Creation

Perform live validation in the actual user environment if possible.

Required scenarios:

#### A. Entire share

Example:

```
\\HENDERSON-NAS\Photos
```

Expected:

- NAS recognized
- endpoint identity = `\\HENDERSON-NAS\Photos`
- endpoint-relative root = empty string
- entire share semantics shown
- source created/reused correctly

#### B. Share subfolder

Example:

```
\\HENDERSON-NAS\Photos\Camera imports
```

Expected:

- same NAS endpoint identity
- relative root = `Camera imports`
- source naming is human-readable
- no duplicate endpoint created

#### C. Existing NAS endpoint reuse

If a NAS endpoint already exists, validate that:

- the existing endpoint is recognized
- Device Name choice is explicit
- same-share different-root creation remains allowed
- exact-root duplicate detection works

### 5. Allow Small Source Creation Polish Only

Small UI or service polish is allowed only if directly needed to support:

- new Source naming
- identity wording
- NAS validation success

Do not opportunistically broaden scope.

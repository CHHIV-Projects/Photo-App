# 9. New Source Selection API

Implement:

POST /api/admin/source-selection/select

## 9.1 Request

The request must contain only:

    {
      "source_profile_id": 90
    }

The backend must derive:

- Source Type;
- Source Endpoint;
- root;
- provider;
- identity method;
- workflow kind;
- current path.

Do not accept or trust frontend-submitted:

- Source Type;
- endpoint ID;
- Source Root;
- observed path;
- endpoint-relative root;
- workflow kind;
- provider identity;
- identity fingerprint.

## 9.2 Response

Normalize into:

    {
      "result": "selected",
      "availability": "available",
      "workflow_kind": "filesystem_source_intake",
      "selected_source_context": {},
      "message": "External 10 - Family Photos is available.",
      "retry_guidance": null,
      "advanced_details": {}
    }

Enums:

    result:
      selected
      not_selected
    
    availability:
      available
      unavailable
      needs_attention
    
    workflow_kind:
      filesystem_source_intake
      icloud_intake
      null

## 9.3 HTTP semantics

Use:

- `200` for normal selected and not-selected business outcomes;
- `404` when Source Profile does not exist;
- `400` for malformed request;
- appropriate server error only for unexpected service failure.

Do not use HTTP conflict responses for normal environmental conditions such as:

- disconnected device;
- wrong disc;
- wrong removable media;
- unavailable NAS;
- expired iCloud session;
- identity timeout.

Return those as normalized business outcomes.

## 9.4 Idempotency

The endpoint must be read-only and idempotent.

Repeated requests with unchanged environment must return equivalent results.

No Source, endpoint, observed path, alias, profile, status, asset, provenance, or Vault record may be written.

# 11. Read-Only Current-Path Resolver

Implement a read-only resolver for modern Sources.

The resolver must not mutate observed-path records.

## 11.1 Modern filesystem rule

Authoritative resolution:

current verified endpoint access path  

+ endpoint_relative_root

Rules:

- empty string means whole endpoint;
- `NULL` means legacy/unresolved;
- a stale `source_root_path` is not durable identity;
- stored observed paths may be candidate access paths but must be verified;
- a changed drive letter must not require Source recreation.

## 11.2 Resolution sources

Use existing read-only provider/probe functionality where practical.

Candidates may include:

- stored observed paths;
- current path from `source_root_path`;
- mounted Windows volume enumeration;
- canonical NAS UNC;
- optical drive enumeration;
- provider-managed iCloud context.

Verify endpoint identity before returning a modern resolved path.

## 11.3 No observed-path persistence

If a new drive letter or access path is found:

- return it ephemerally;
- include it in selected-source context;
- optionally include prior paths under Advanced Details;
- do not create or update observed-path records.

Observed-path persistence is deferred to:

- Source Creation; or
- a later authorized Run Ingestion operation.

# 12. Selection Outcomes

## 12.1 Available

Return `available` when the Source is currently usable and identity/root/provider checks succeed.

Normal successful selection should require no acknowledgment.

## 12.2 Unavailable

Use when the Source is currently absent or the wrong physical/provider resource is present.

Examples:

- external drive disconnected;
- no matching removable media;
- wrong removable media;
- no optical disc;
- wrong optical disc;
- NAS share unreachable;
- identity mismatch;
- local volume unavailable.

## 12.3 Needs attention

Use when the Source exists but safe automatic selection cannot complete.

Examples:

- root missing on a correctly matched endpoint;
- ambiguous legacy identity;
- linked legacy Source with unresolved relative root;
- optical identity timeout;
- incomplete optical fingerprint;
- iCloud authentication/session issue;
- provider configuration mismatch;
- exact Source conflict requiring management;
- unsupported management status;
- unknown readiness condition.

Do not expose internal readiness terms as the primary outcome.

# 14. Local Selection

Identity method:

- Volume GUID fingerprint

Selection behavior:

1. Locate the registered local volume using read-only current-volume evidence.
2. Verify endpoint identity.
3. Resolve current volume root.
4. Append `endpoint_relative_root`.
5. Verify the resulting Source Root exists and is a directory.

Success:

- `available`
- `workflow_kind=filesystem_source_intake`

Failure examples:

- registered local volume missing:
  `unavailable`
- identity mismatch:
  `unavailable`
- volume matches but Source subfolder is missing:
  `needs_attention`

Do not run Source Intake.

---

# 15. External Selection

Identity method:

- Volume GUID fingerprint

Selection behavior:

1. Determine whether the registered external device is connected.
2. Find its current drive letter by identity.
3. Reconstruct the Source Root.
4. Verify root readability.

Required behavior:

- changed drive letter selects automatically;
- old drive letter occupied by a different device must not be trusted;
- no Source recreation is required.

Failure examples:

- device disconnected:
  `unavailable`
- wrong identity at stored drive letter:
  `unavailable`
- correct endpoint but missing relative root:
  `needs_attention`

---

# 16. Removable Selection

Identity method:

- Volume GUID fingerprint

Selection behavior:

1. Enumerate available removable/local volumes read-only.
2. Find the matching medium by durable identity.
3. Reconstruct Source Root.
4. Verify root.

Required behavior:

- same flash drive or SD card at another drive letter selects automatically;
- different media at the same drive letter fails;
- endpoint registered under an existing legacy type retains its registered type;
- do not reclassify endpoints.

Failure examples:

- correct media not inserted:
  `unavailable`
- wrong card/flash drive:
  `unavailable`
- identity matches but Source folder missing:
  `needs_attention`

---

# 17. Optical Selection

Identity method:

- `optical_media_fingerprint_v1`

Selection behavior:

1. Locate readable physical optical media.
2. Compute the complete metadata-only fingerprint.
3. Compare it to the registered endpoint fingerprint.
4. Reconstruct the Source Root.
5. Verify the requested root exists.

Use the established complete optical identity process and maximum timeout of:

300 seconds

Do not use a partial fingerprint.

Normal UI should show automatic progress such as:

`Checking optical disc…`

Do not require another verification button.

Required outcomes:

- matching disc:
  `available`
- no disc:
  `unavailable`
- wrong disc:
  `unavailable`
- timeout:
  `needs_attention`
- incomplete identity:
  `needs_attention`
- matched disc but missing subfolder:
  `needs_attention`

Do not read file contents.

Only the established metadata-only optical manifest enumeration is allowed.

---

# 18. NAS Selection

Identity method:

- canonical server/share identity

Selection behavior:

1. Load the registered NAS endpoint.
2. Derive canonical server/share UNC boundary.
3. Append `endpoint_relative_root`.
4. Verify the UNC Source Root is currently reachable and readable.

Rules:

- direct readable UNC is valid;
- mapped-drive letters are not durable identity;
- mapped-drive evidence may appear under Advanced Details;
- do not require a mapped drive;
- do not create or alter NAS mappings.

Failure examples:

- share unreachable:
  `unavailable`
- share reachable but subfolder missing:
  `needs_attention`
- path does not correspond to registered NAS identity:
  `needs_attention` or `unavailable` according to evidence.

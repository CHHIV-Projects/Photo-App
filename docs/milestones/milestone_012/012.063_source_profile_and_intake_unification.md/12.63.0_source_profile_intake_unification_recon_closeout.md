## 2. Current Behavior Map

### Source Profile Creation

Source Profiles are currently stored in the existing `ingestion_sources` table. The system does not yet have a separate Source Profile table, Source Device table, or Source Endpoint table.

The user-facing Source Profile creation flow lives primarily in the Ingestion tab. The operator enters or chooses:

- Source label.
- Source type: `local_folder`, `external_drive`, `cloud_export`, `scan_batch`, or `other`.
- Profile status.
- Source root path where required.
- Cloud provider where relevant.
- Acquisition method where relevant.
- iCloud account username where relevant.
- Managed staging path where relevant.

Backend-derived or normalized fields include:

- `source_label_normalized`.
- `source_root_path_normalized`.
- Effective path for iCloud, where `managed_staging_path` becomes the operational root.
- Default iCloud managed staging path under the approved iCloud export/staging area.
- Source reference counts and warnings.
- Masked account display fields.

iCloud differs from local/external profiles because the profile represents an iCloud-backed managed staging workflow, not a directly ingested source root. iCloud creation requires cloud-specific metadata and resolves the operational path to controlled local staging.

### Source Profile Editing and Detail Display

Source Profile metadata can be edited after creation, but source identity fields are intentionally constrained:

- Source label can be edited.
- Profile status can be edited.
- Cloud provider, acquisition method, account username, and managed staging path can be edited under service rules.
- Source type is locked.
- Source root path is locked.
- Referenced iCloud managed staging paths are protected from unsafe edits.

The UI already warns that Source Profile changes are not retroactive and do not rewrite prior provenance, source paths, intake reports, or asset history.

The normal UI exposes a large amount of backend detail today: type, root path, managed staging path, cloud provider, acquisition method, account username, reference counts, readiness metadata, report paths, and raw run details. Some of this should move to Advanced Details in future UI simplification.

### Local / External / NAS Intake

Local and external intake currently use direct Source Intake. NAS and removable media are not first-class source types today; they are effectively represented as local/external/other paths depending on how the operator creates the profile.

The current flow is:

1. Create or choose a Source Profile.
2. Verify that the profile has an active local/external source path.
3. Start Source Intake from the Ingestion UI or Admin UI.
4. Backend validates that the source exists and is a directory.
5. Backend rejects the run if Drop Zone is not empty.
6. Source Intake scans the configured root path.
7. Skip-known logic checks existing provenance by source and relative path.
8. Eligible files are staged into Drop Zone.
9. Source Intake writes Vault assets, DB records, and provenance.
10. Reports are written under source intake report storage.

This flow is appropriate for small targeted local/external runs, but it is not yet durable enough for long-running resumable source work. The current local/external run is process-bound and does not have a prepared candidate snapshot or durable chunk ledger.

### iCloud Intake

iCloud Intake is source-profile driven and more durable. The current flow is:

1. Select an active iCloud Source Profile.
2. Refresh / Prepare Next 1000.
3. Metadata inventory scans provider records and updates known/deferred inventory.
4. Prepared candidates are stored in durable prepare tables.
5. Import Next 1000 or Resume Interrupted Import starts or resumes a durable import run.
6. Import advances in bounded chunks.
7. Each chunk performs acquisition into local staging, Source Intake handoff, guarded cleanup dry run/execution when safe, deferred accounting, and status/report updates.
8. Stale/interrupted work can be exposed as resume available without auto-continuing.

iCloud has source-specific requirements that should remain source-specific:

- Cloud acquisition is staging-only.
- The app does not delete remote iCloud assets.
- Cleanup may only delete verified local staging copies.
- Deferred adjusted resources remain policy-deferred.
- Apple credentials, tokens, 2FA codes, cookies, and secrets are not stored.

### Source Intake Handoff

Source Intake remains the ingestion authority for assets entering the Vault. iCloud acquisition and local/external runs both ultimately hand off to Source Intake for Vault, DB, and provenance creation.

The iCloud path has additional acquisition and cleanup machinery before and after Source Intake. The local/external path does not have acquisition or staging cleanup, because the source root itself must never be treated as disposable staging.

### Readiness / Status Handling

iCloud readiness is comparatively rich. It checks source status, cloud provider, managed staging path, source alignment, operation conflicts, cleanup conflicts, and workflow readiness.

Local/external readiness is simpler. It mostly checks that the Source Profile is active, has a valid path, and is allowed to run Source Intake. Source readiness classification for temp/partial/unstable files exists mainly for `cloud_export` intake behavior and is not yet generalized for local/external/NAS.

Operation guardrails already exist across ingestion operations. They block conflicting iCloud acquisition, Source Intake, and cleanup activity. This is a useful shared foundation for future workflow unification.

### Run Reporting

Source Intake writes JSON reports with scanned, skipped-known, selected, deferred/unready, staged, processed, and failure counts. The UI can display recent reports and raw details.

iCloud writes additional routine/import/deferred/cleanup reporting, including durable import run state, chunk ledgers, cleanup safety counters, deferred counts, and safe deferred asset rows.

### Provenance / Source Linkage

Provenance records link assets to:

- `ingestion_source_id`.
- `ingestion_run_id`.
- Denormalized source label.
- Source type.
- Source root path.
- Source path and source relative path.
- Asset hash/source hash context.

This keeps historical provenance explainable, but current identity still depends heavily on label/type/root path matching in the source registry.

## 4. Source Identity Findings

### Where Path Is Used as Identity

`ingestion_sources` currently uses a uniqueness constraint based on:

- `source_label_normalized`
- `source_type`
- `source_root_path_normalized`

`source_root_path_normalized` is produced from a resolved path and lowercased string. On Windows, that means drive letters, mapped paths, UNC spelling, and mounted root strings become part of the source identity.

This is acceptable for controlled iCloud staging because the managed staging path is app-controlled and stable enough for v1. It is fragile for removable media, external drives, and NAS shares.

### Where Label / Name Is Used as Identity

The source label is not purely cosmetic today. It participates in the source registry uniqueness constraint and source matching. The UI treats the Source Profile label as editable and warns that edits are not retroactive.

Because the label participates in lookup identity, a future design should split display alias from durable source/device identity. The current behavior is workable, but a label edit can make future matching and historical reasoning less intuitive.

### Where Source Registry Identity Is Used

`IngestionSource` currently acts as three things at once:

- User-facing Source Profile.
- Backend source registry.
- Compatibility anchor for ingestion runs and provenance.

iCloud durable prepare/import rows use `source_profile_id`, but that is currently an FK to `ingestion_sources`. Future Source Profile / Source Device / Source Endpoint separation will need a compatibility plan for these existing references.

### Where Provenance Stores Source / Path Context

Provenance stores both relational and denormalized context:

- `ingestion_source_id`
- `ingestion_run_id`
- `source_label`
- `source_type`
- `source_root_path`
- `source_path`
- `source_relative_path`

This is good for historical explanation. It also means future source alias changes should not rewrite old provenance. The risk is that the current source identity model may create multiple source rows for the same physical source if path observations change.

### Fragile for External Drives

External drives are fragile because:

- Drive letters can change.
- Drive letters can be reused by different media.
- The same device may be accessed under a different path.
- A renamed root folder can look like a different source.
- Skip-known checks can miss prior assets if they resolve to a different `ingestion_source_id`.

Future identity should treat the observed drive path as an observation, not durable identity by itself.

### Fragile for NAS / Network Shares

NAS shares are fragile because:

- A mapped drive and UNC path can refer to the same share but normalize differently.
- Hostname, IP address, DNS alias, and share spelling can differ.
- User-specific mappings can differ by machine/session.
- Network availability can make readiness intermittent.

Future identity should preserve observed paths but also capture endpoint evidence such as host/share identity, UNC canonicalization where possible, and operator-confirmed profile intent.

### Acceptable for iCloud

iCloud is better isolated because:

- The managed staging path is local and controlled.
- The source profile is provider-specific.
- Acquisition is staging-only.
- Cleanup is limited to verified local staging files.
- Deferred rows track known policy gaps.

The main iCloud source identity risk is historical label/path matching for older acquisition rows that do not carry direct `ingestion_source_id` references.

## 5. Source Profile Creation Unification Findings

### Must Remain Source-Specific

These differences should stay source-specific:

- iCloud account username, masked display, cloud provider, acquisition method, managed staging, and iCloud readiness.
- iCloud metadata inventory and prepared candidate behavior.
- iCloud guarded local staging cleanup.
- Local/external/NAS source root verification.
- Local/external/NAS rule that source roots are never disposable staging.
- Any future NAS endpoint checks and network availability readiness.
- Any future removable media identity evidence.

### Can Share Common UI Language

Source setup can share a common operator grammar:

- Source
- Readiness
- Prepare / Scan
- Import / Intake
- Progress
- Result
- Next Safe Action
- Advanced Details

The UI should feel consistent without forcing every source type into the iCloud backend lifecycle.

### Can Move to Advanced Details

Likely Advanced Details candidates:

- Normalized label.
- Normalized root path.
- Raw managed staging path unless needed for iCloud action.
- Cloud provider/acquisition method for non-cloud sources.
- Masked account username outside cloud detail context.
- Reference counts.
- Internal IDs.
- Report paths.
- Raw report JSON.
- Source alignment diagnostics.
- Operation conflict flags.
- Cleanup manifest fingerprints and low-level counters except when needed for review.

The normal view should focus on readiness, current source, last run, next action, imported/remaining/deferred counts, and clear blocking reasons.

### Needs Backend Design Before UI Changes

Do not make broad UI simplification before defining:

- Source Profile versus Source Device / Endpoint versus Ingestion Source.
- Whether `nas_share` and `removable_media` become explicit source types.
- How targeted subfolder intake is represented.
- Whether source alias is separated from immutable source identity.
- Which identity mismatches block a run versus warn the operator.
- How historical `ingestion_sources` rows migrate or remain as compatibility rows.

## 6. Intake Methodology Unification Findings

### Local / External / NAS Targeted Intake

The product-owner leaning matches the code reality: a Source Profile should usually represent a reusable meaningful top-level source root, while an individual run may scan the whole root or a targeted subfolder beneath it.

This preserves provenance clarity if the selected run path is stored carefully. The future design must decide whether `source_relative_path` remains relative to the profile root or becomes relative to the selected run root. The safer long-term default is to keep profile root as the provenance anchor and record selected subfolder as run context.

Small local/external/NAS runs can continue to use direct Source Intake without durable prepared candidate snapshots.

### iCloud Library-Style Intake

iCloud should remain library-style and durable:

- Inventory refresh.
- Prepared candidates.
- Bounded import.
- Chunk ledger.
- Resume.
- Deferred policy ledger.
- Guarded staging cleanup.

This is appropriate because iCloud is large, provider-backed, slow, and requires staging and cleanup boundaries.

### Shared Workflow Grammar

The workflow grammar should converge around:

- Readiness check.
- Prepare or scan when needed.
- Intake/import action.
- Live progress.
- Clear result summary.
- Next safe action.
- Advanced details.

The implementation behind each step can differ.

### Candidate Preparation Possibilities

Local/external/NAS should not be forced into iCloud-style prepare for every run.

Recommended split:

- Small targeted run: direct Source Intake with preflight and final report.
- Large external/NAS run: optional future prepared snapshot to lock candidate list and support resume.
- Removable/NAS run with unstable identity: read-only identity/readiness probe before intake.
- iCloud: keep current durable prepared candidate model.

### Durable Run / Resume Possibilities

iCloud already has durable import run and chunk state suitable for resume.

Source Intake has a run table and status, but local/external execution remains process-bound. Future durable local/external/NAS resume should be introduced only after source identity/readiness and targeted path semantics are clear.

### Overkill Patterns to Avoid

Avoid applying these iCloud patterns broadly without a concrete need:

- Mandatory prepared snapshots for every local folder.
- Cleanup flows for local/external source roots.
- Deferred policy ledger for normal local files.
- Cloud-style acquisition abstractions for direct local intake.
- Automatic resume/continue after interrupted work.
- Large source scheduler assumptions in the v1 UI.

## 7. Future Scheduling / Background Readiness Assessment

Scheduling is out of scope now, but the next design can preserve the path.

Already useful for future scheduling:

- iCloud durable prepare/import/chunk state.
- Operation guardrail service.
- Source Intake run/status rows.
- Source Profile status and readiness concepts.
- Provenance source linkage.

Still too UI/request-bound:

- Local/external Source Intake process-bound background thread.
- Lack of durable candidate snapshot for large local/external/NAS runs.
- Lack of durable source device/endpoint identity.
- Lack of targeted path run context.
- Limited local/external readiness state.

A future scheduler would need:

- Read-only source readiness checks.
- Durable run state.
- Conflict detection across acquisition, Source Intake, cleanup, and post-processing jobs.
- Clear stale/interrupted handling.
- Candidate preparation for large or unstable sources.
- Explicit operator intent for what source root/subfolder is scheduled.

Near-term choices that help without overbuilding:

- Define Source Profile / Device / Endpoint boundaries now.
- Add read-only identity probes before schema-heavy work.
- Store selected run target path explicitly when targeted intake is added.
- Keep Source Intake as the authority.
- Keep cleanup source-specific and staging-only.

## 8. Risks and Safety Concerns

### Provenance Confusion

Because label/type/path identity is mixed with user-facing Source Profile naming, alias changes and path changes can make historical source reasoning confusing. Provenance itself remains explainable because it snapshots source context, but future matching can diverge.

### Drive Letter Changes

External drive letter changes can cause the same physical source to appear as a new source, miss skip-known history, or make prior provenance harder to connect. Reused drive letters can create wrong-source risk if the operator does not notice.

### NAS Path Normalization

Mapped drives and UNC paths can point to the same NAS share but normalize as different source roots. Hostname aliases and IP-based paths can also fragment identity.

### Wrong-Source / Wrong-Path Intake

Current path validation checks that a path exists and is a directory. It does not prove the durable identity of an external device or NAS endpoint. Future readiness should surface identity mismatch warnings or blocks before intake.

### Schema Migration / Backfill

Splitting Source Profile from Source Device / Endpoint and Ingestion Source will affect:

- `ingestion_sources`.
- `ingestion_runs`.
- `provenance`.
- `source_intake_runs`.
- iCloud prepare/import/chunk tables.
- Deferred asset ledger.
- Existing API payloads and frontend types.

This should be additive and compatibility-first.

### UI Over-Unification

The biggest UI risk is hiding important source-specific differences. iCloud staging cleanup and cloud safety boundaries must remain visible where they matter. Local/external source roots must never be described like disposable staging.

### Breaking Current iCloud Intake

iCloud Intake is currently good enough for v1. The next milestones should avoid changing iCloud mechanics unless necessary for naming, compatibility, or shared readiness grammar.

### Breaking Current Local Source Intake

Local/external Source Intake is the simplest working path. Future changes should keep direct run behavior available for small targeted intake and avoid requiring durable snapshots too early.

## 9. Proposed Implementation Sequence

### 12.63.1 - Unified Source Identity Boundary Design

Goal: Write a design-only milestone that defines Source Profile, Source Device / Endpoint, Ingestion Source / Registry, Observed Path, provenance compatibility, targeted run path semantics, and migration boundaries.

Why next: The code currently uses `ingestion_sources` for multiple concepts. A boundary design is needed before schema or UI changes.

Risk level: Low.

### 12.63.2 - Read-Only Source Identity Probe Recon

Goal: Add or design read-only probes for local folders, external/removable drives, and NAS/network shares. Capture what identity evidence is available without changing schema or intake behavior.

Why next: The project needs facts about what Windows/local/NAS identity evidence can be gathered safely before committing to tables or UI promises.

Risk level: Low to medium, depending on whether implementation is included. Keep first pass read-only.

### 12.63.3 - Source Workflow Readiness and UI Language Design

Goal: Define shared operator grammar and decide what belongs in normal UI versus Advanced Details for each source type.

Why next: The UI can be simplified safely only after identity and readiness terms are stable.

Risk level: Low.

### 12.63.4 - Local / External / NAS Targeted Intake Foundation

Goal: Add per-run selected target path under a Source Profile root, validation that target is within the profile root, and reporting/provenance context for that target.

Why next: This directly supports the product-owner leaning that a Source Profile is a reusable top-level source and runs may target subfolders.

Risk level: Medium.

### 12.63.5 - Source Device / Endpoint Model Foundation

Goal: Add additive schema/model foundations for durable source identity evidence after the design and probe findings are stable.

Why next: Schema should follow the boundary design and real probe evidence, not lead it.

Risk level: Medium to high.

### 12.63.6 - Optional Large Source Prepared Snapshot

Goal: Explore prepared candidate snapshots for large external/NAS runs only, with durable state and explicit resume behavior.

Why next: This should come after targeted intake and identity readiness exist, because candidate snapshots need stable source/run identity.

Risk level: Medium to high.

## 10. Clarification Questions / Product Decisions Needed

1. Should `nas_share` and `removable_media` become explicit source types, or should they remain variants under `external_drive` with endpoint/device metadata?

2. When a future identity probe sees a mismatch, should the first v1 behavior be warning-only, hard block, or operator-confirmed override?

3. For targeted subfolder intake, should provenance `source_relative_path` be relative to the Source Profile root, while the selected subfolder is stored as run context? This seems safest, but it is a product decision because it affects reports and operator language.

4. Should Source Profile display labels remain editable long term, or should the system introduce a separate editable alias while locking the original registry label for compatibility?

5. Should local/external/NAS show a user-visible "Prepare / Scan" step, or should small targeted runs keep a single "Run Intake" action with an automatic preflight summary?

6. For NAS, should v1 avoid storing credentials entirely and rely only on already-mounted/accessible shares?

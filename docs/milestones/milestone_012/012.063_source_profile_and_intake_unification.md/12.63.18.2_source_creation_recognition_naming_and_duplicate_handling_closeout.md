## 3. Final operator flow

For Local, External, and NAS sources, the operator flow is:

1. Select Source Type.
2. Enter Root Path or Mount Point.
3. Press `Identify Location`.
4. Review the recognition result, durable identity, endpoint boundary, relative root, existing device, exact Source matches, warnings, and blockers.
5. For a new endpoint, enter a Device Name. For an existing endpoint, explicitly choose `Use Existing Name`, `Rename Device`, or `Cancel`.
6. Resolve any Source Type mismatch by explicitly continuing with the registered type or cancelling.
7. Review the exact final action, such as create, reuse, reactivate, adopt, or rename plus one of those Source actions.
8. Confirm. The backend recomputes the plan and fingerprint before applying one atomic metadata transaction.

The iCloud selection continues to use its existing provider-specific creation controls.

## 4. Static panel behavior

`Create a Source` is now always visible near the top of the Ingestion page. The collapse button, collapsed state, and expand/collapse behavior were removed. The panel was not replaced with a modal, drawer, or floating action.

## 5. Path-first identification

Filesystem source planning now accepts Source Type and observed path without requiring a Device Name. The UI does not probe on every keystroke. It calls the existing read-only plan endpoint only when the operator presses `Identify Location`.

The planning response now provides a recognition status and title, selected and technically recognized source types, endpoint boundary and relative root, existing endpoint evidence, exact Source matches, final action label, warnings, blockers, and required decisions. Identification performs no source-creation metadata writes.

## 6. Device recognition behavior

Recognition uses the read-only Source Identity Probe and shared durable fingerprint policy.

- UNC paths and mapped paths resolved to UNC are recognized as NAS.
- Local and External Volume GUID evidence is matched across both `local` and `external_device` endpoint categories.
- Strong durable fingerprint matches take precedence over weaker legacy candidates.
- Registered endpoint type, alias, status, durable identifier, and safe identity evidence are surfaced to the operator.
- Exact Source matching evaluates both modern endpoint-relative roots and normalized legacy full roots.
- Readability and path-safety blockers take precedence over duplicate classification.
- Clear removable-media evidence blocks creation rather than silently storing the source as Local or External.

No unrelated drives, shares, or folders are enumerated.

## 7. Device Name behavior

Device Name is not requested before filesystem identification.

For a new endpoint, a non-empty Device Name is required after successful recognition. For an existing endpoint, the stored alias is shown and the operator must choose `Use Existing Name`, `Rename Device`, or `Cancel`. A stored alias is never silently substituted for newly entered text.

When rename is selected, the field is prefilled with the current alias and the UI explains that durable identity, Sources, roots, and history do not change. New alias collisions are rejected using the global normalized alias rule. Case-only renames are permitted for the same endpoint.

## 8. Rename impact-analysis findings

The focused code and schema review found:

- `SourceEndpoint.alias` is current display metadata. Durable identity is anchored by the endpoint record, endpoint UUID, and durable fingerprint, not by the alias.
- `alias_normalized` already has a global uniqueness constraint and is used for collision detection.
- Endpoint aliases are exposed in source-identity, enrollment, readiness, and Source creation displays as current operator-facing names.
- Source Profile labels are independently persisted values. They are not dynamically derived from the endpoint alias.
- Source Intake requests and routing use Source Profile IDs and source configuration, not the endpoint alias as identity.
- Existing ingestion runs, reports, assets, provenance, observed paths, and endpoint-relative roots do not need an alias rewrite.
- Historical provenance contains Source Profile and observed-path context; endpoint identity remains indirectly associated through the Source Profile. Renaming the current endpoint alias must not rewrite that history.
- Endpoint source type participates in matching and has potential readiness, routing, and persisted Source-type implications, so it is not safe to treat as display-only metadata.

Accordingly, only `SourceEndpoint.alias` is renamed. Existing Source Profile labels and historical snapshots remain unchanged.

## 9. Rename implementation and audit behavior

Added the repo-native `source_endpoint_alias_events` table and ORM model with:

- source endpoint ID;
- old alias;
- new alias;
- action source;
- timestamp.

The idempotent source-endpoint schema helper creates the table where needed. A successful rename updates `alias` and `alias_normalized` and writes one audit event with action source `source_creation_confirm` in the same confirmation transaction.

Rename preserves endpoint ID, endpoint UUID, durable fingerprint and version, endpoint type, Source Profile IDs and labels, endpoint-relative roots, observed paths, profile statuses, ingestion history, assets, Vault files, and provenance. A failure in rename or the associated Source action rolls back the entire confirmation. Tests cover identity preservation, global collision rejection, case-only rename, audit creation, and rollback.

## 10. Source Type mismatch behavior

The selected Source Type is treated as the operator expectation; the probe and any registered endpoint establish the technical and persisted endpoint type.

When an existing endpoint is recognized with a different stored type, the plan shows both types and requires an explicit `Continue Using <registered type>` decision or cancellation. Continuing retains the registered endpoint type. Cancelling and all blocked plans write nothing.

For a genuinely new Local or External endpoint, the approved operator category is retained when Windows evidence cannot safely distinguish those categories. Clear NAS and removable evidence overrides that assumption for safety.

## 11. Whether type reclassification was implemented or deferred

Actual reclassification of an existing endpoint was deferred. Endpoint source type contributes to matching and may affect readiness, routing, API behavior, and Source Profile interpretation. This milestone therefore retains the recognized endpoint's existing type and provides explicit continue/cancel behavior. It does not mutate endpoint or Source Profile types.

## 12. Modern exact-Source handling

A modern exact Source is matched by durable endpoint identity plus endpoint-relative root.

- An active exact Source is returned through `Use Existing Source`; no endpoint, Source, or duplicate observed-path row is created.
- An exact Source whose status is literally `inactive` can be reactivated in place.
- The existing Source Profile ID, label, root, history, and provenance remain intact.
- The same endpoint with a different relative root remains eligible for a new Source.

Strong modern endpoint matches are not displaced by weaker legacy endpoint candidates.

## 13. Inactive Source handling

Only the literal profile status `inactive` is eligible for automatic reactivation. Reactivation changes that existing Source to `active` and retains its Source Profile ID. It may add only a safe, required endpoint link or deterministic relative root as part of the same transaction.

Statuses such as `archived`, `test`, and `deprecated` are not auto-reactivated. They block automatic creation and direct the operator to source management.

## 14. Legacy Source adoption

An exact legacy match is found through normalized full-root equality when the Source has no endpoint link or has a legacy `NULL` relative root.

When exactly one eligible legacy Source is selected, `Adopt and Link Existing Source`:

- retains the existing Source Profile ID, label, root, history, and provenance;
- links the verified endpoint;
- writes the endpoint-relative root only when deterministically derived;
- creates no duplicate Source;
- completes in the same transaction as any endpoint reuse, upgrade, rename, observed-path evidence, or reactivation.

An inactive eligible legacy Source can be adopted and reactivated atomically.

## 15. Multiple-match handling

Multiple active or otherwise ambiguous exact Source matches block automatic creation. The plan exposes safe rows for all exact matches and does not silently choose one or permit confirmation to create a third Source.

The approved known-data exception is implemented narrowly: one active, unlinked legacy Source plus one inactive, linked modern duplicate selects the active legacy Source for adoption, surfaces the inactive conflict, and leaves the inactive record unchanged for later management. No broad duplicate repair or canonicalization is performed.

## 16. Overlap handling

Parent/child root overlap is reported as a non-blocking warning. It is not treated as normalized exact equality and does not prevent a legitimate new Source on the same endpoint with a different root. Loose substring matching is not used.

## 17. Whole-device/share behavior

The 12.63.18.1 semantics are preserved:

- empty string means intentionally the entire device or share;
- `NULL` means legacy, unknown, or unresolved;
- a non-empty value means an endpoint-relative folder.

Whole-device and whole-share exact matching therefore distinguishes empty string from `NULL`. A legacy `NULL` root is adopted as an entire endpoint only when endpoint boundary and normalized full path deterministically prove equivalence. The UI identifies entire-device/share plans and warns when the selected root is the Windows system volume.

## 3. Final Source Creation Flow

For Local, External, and NAS:

1. Choose Source Type.
2. Enter Root Path or Mount Point.
3. Identify Location.
4. Review endpoint identity and exact Source matches.
5. Resolve Device Name.
6. For a genuinely new Source, accept or edit Source Name.
7. Review duplicate/canonical Source choices when exact matches exist.
8. Confirm final action.
9. On success, Root Path, Source Name, recognition state, name decisions, duplicate selections, warnings, blockers, and confirmation state clear; selected Source Type and completed result remain.

iCloud keeps its existing provider-specific creation controls. Removable remains disabled.

## 4. Suggested Source Name Behavior

The 12.63.18.3 suggestions remain the default:

- final folder component for non-empty relative roots;
- `Entire device` for entire Local/External endpoint;
- `Entire share` for entire NAS share;
- limited parent context on same-endpoint collision;
- stable fallback suffix only if needed.

The plan response now includes both `suggested_source_name` and final `source_display_name`.

## 5. Manual Source Name Behavior

For `create_new_source`, the UI shows an editable Source Name field after identification. The operator-entered value is sent through plan/confirm as `source_name` and persisted as `IngestionSource.source_label`.

Manual Source Name does not change endpoint identity, endpoint-relative root, observed path, fingerprint, or source type.

Existing, reused, adopted, reactivated, and canonicalized Sources keep their existing labels.

## 6. Source Name Validation and Uniqueness

Validation now:

- trims leading/trailing and repeated whitespace;
- rejects blank names;
- rejects control characters;
- enforces the existing 255-character Source label limit;
- preserves punctuation and spaces;
- does not interpret Source Name as a path.

Uniqueness rule implemented:

- Source Name may repeat across different endpoints/devices.
- New Source Name is blocked when another Source on the same endpoint already has the same normalized label.
- Existing DB uniqueness remains enforced by `source_label_normalized + source_type + source_root_path_normalized`.
- Existing/reused/adopted/reactivated/canonicalized Sources are excluded from rename behavior and retain labels.

On collision, the entered value is retained and the plan can surface a practical alternative such as parent-context naming.

## 10. Duplicate-Review Presentation

Exact Source matches now include:

- Source Name;
- Source Type;
- status;
- source root path;
- endpoint ID and endpoint alias when linked;
- endpoint-relative root;
- modern exact vs legacy exact match kind;
- classification, including linked legacy vs unlinked legacy;
- provenance count;
- ingestion run count;
- Source Intake run count;
- distinct asset count from provenance where available;
- protected-history flag;
- recommendation/allowed action;
- selected/conflict state.

Normal Create Source now shows only a short `Existing Sources for This Location` notice when exact matches exist. The canonical/repair controls are intentionally hidden from the normal operator flow. IDs, detailed technical state, and duplicate/legacy recommendations remain in Advanced Details for a later dedicated management workflow.

## 11. Canonical-Selection Rules

The resolver recommends a canonical Source only when safe:

- one active exact Source with only inactive/no-history duplicates;
- active legacy canonical plus inactive duplicate;
- inactive single exact Source when reactivation is safe;
- explicit selected canonical Source when noncanonical active duplicates are selected for no-history inactivation.

Ambiguous cases remain blocked, including multiple active Sources without selected canonical/no-history resolution or any duplicate with protected history selected for inactivation.

## 12. Adoption Behavior

Unlinked legacy exact Sources may be adopted when safe:

- Source Profile ID is retained;
- label is retained;
- root is retained;
- endpoint link is populated;
- deterministic endpoint-relative root is populated;
- ingestion runs, Source Intake runs, provenance, assets, and history are preserved.

## 13. Reactivation Behavior

Only literal `inactive` status is eligible for automatic reactivation.

Supported combined actions:

- Reactivate Existing Source for inactive modern exact Source.
- Adopt and Reactivate Existing Source for inactive unlinked legacy Source.
- Canonicalize and Reactivate Existing Source for inactive linked legacy Source.

Archived, test, deprecated, and other management statuses remain blocked for management review.

## 14. No-History Duplicate Inactivation

Explicit duplicate inactivation is supported only when the noncanonical duplicate:

- is an exact-root match;
- is active;
- has zero provenance rows;
- has zero distinct provenance assets;
- has zero ingestion runs;
- has zero Source Intake runs;
- is explicitly selected by the operator;
- is not the selected canonical Source.

Confirm performs inactivation in the same transaction as the canonical Source action. No Source is deleted, merged, or reassigned.

This capability remains backend-supported but is not exposed as a normal Create Source control after UX review. It should be surfaced later through a deliberate Source management / duplicate repair workflow if needed.

## 15. Ambiguous Duplicate Behavior

Ambiguous duplicate groups remain blocked when:

- canonical choice is unclear;
- more than one active Source has protected history;
- a selected duplicate has protected history;
- selected canonical Source no longer matches the exact location;
- selected duplicate no longer matches exact location;
- management statuses such as archived/test/deprecated are present.

## 18. Transactions and Rollback

Confirm recomputes the plan and validates fingerprint, Source Name, selected canonical Source, selected duplicate IDs, statuses, reference counts, and blockers before mutation.

One transaction may include:

- endpoint creation/reuse/rename;
- endpoint legacy fingerprint upgrade;
- new Source creation;
- unlinked legacy adoption;
- linked legacy canonicalization;
- Source reactivation;
- no-history duplicate inactivation;
- observed-path evidence.

Any exception rolls back the full confirmation. Tests cover rollback-sensitive rename and duplicate inactivation protections.

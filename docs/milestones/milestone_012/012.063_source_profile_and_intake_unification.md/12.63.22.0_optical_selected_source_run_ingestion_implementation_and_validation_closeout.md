# 12.63.22.0 Optical Selected-Source Run Ingestion Implementation and Validation Closeout

## Final Milestone Classification

Selected-source Optical dispatch and readiness integration are implemented and fail closed when media identity cannot be verified. Automated validation passed. - selected-source Optical dispatch implemented;
- Optical generic readiness integration implemented;
- launch-time media revalidation implemented;
- existing filesystem Source Intake reused;
- automated safety behavior validated;

Do not describe Optical ingestion as fully operational or fully accepted in the operator environment.

The implemented code remains valuable and safe because it:

- requires complete `optical_media_fingerprint_v1` evidence;

- blocks swapped, missing, unreadable, unverified, or mismatched media;

- reuses the existing Source Intake pipeline;
- adds no Optical-specific ingestion engine;
- adds no ripping, conversion, decryption, writing, or automatic eject;
- adds no new persistence;
- leaves Vault and provenance semantics unchanged.

## Implementation Details

### Backend dispatch

`backend/app/services/admin/run_ingestion_dispatch_service.py`

- Removed the prior normal-workflow block that always returned `optical_not_enabled`.
- Added Optical to the enabled filesystem friendly-source set.
- Added Optical launch-time validation before Source Intake starts.
- Reused Source Selection revalidation and the existing Optical fingerprint version constant.
- Did not duplicate the Optical fingerprint algorithm in dispatch.

Optical launch now requires:

- active Source Profile;
- active linked Source Endpoint;
- endpoint type `optical_media`;
- complete current fingerprint metadata using `optical_media_fingerprint_v1`;
- selected-source context identity status `matched`;
- selected-source context durable identity status `verified`;
- backend-derived readable runtime Source Root;
- endpoint-relative-root containment within the current media root;
- no path traversal;
- no stale endpoint selection;
- no active operation conflict.

### Generic readiness integration

`backend/app/services/source_identity/readiness_service.py`

- Added current-format `optical_media` to generic Source Profile readiness.
- Routed Optical readiness through the existing Optical probe path.
- Required complete current `optical_media_fingerprint_v1` evidence.
- Required exact fingerprint match.
- Preserved fail-closed behavior for incomplete, weak, mismatched, or unavailable Optical evidence.
- Treated provider-realistic `safe_to_run="not_applicable"` as acceptable only when an exact strong Optical fingerprint match exists.
- Kept `safe_to_run="needs_review"` insufficient for Optical launch.

### Source Selection unavailable classification

`backend/app/services/source_identity/source_selection_service.py`

- Classified `optical_drive_unverified`, `no_readable_optical_media_inserted`, and `blank_or_unreadable_optical_media` as unavailable conditions rather than generic identity mismatch fallthrough.
- This improves operator messaging while preserving exact-match enforcement.

### Frontend Step 3

`frontend/src/components/IngestionView.tsx`

- Removed the Optical-only Step 3 disabled message.
- Current-format Optical selections can show the same Filesystem Source Intake Step 3 tile as Local, External, Removable, and NAS.
- The button still routes through backend dispatch, which performs authoritative launch-time revalidation.

## Consolidated Operator-Test History

Chronological operator-test sequence:

1. Optical Step 3 was initially enabled.
2. Generic readiness still rejected `optical_media`.
3. Readiness was corrected so Optical uses its existing probe and requires exact current fingerprint evidence.
4. The operator then reached the Optical Filesystem Source Intake tile.
5. Launch was still blocked because current media identity evidence did not reliably match or could not be generated.
6. Read-only investigation produced two distinct findings:
   - at one point, stored and current `optical_media_fingerprint_v1` hashes differed for the operator's test media;
   - at another point, `E:\` was filesystem-readable but Windows metadata did not verify it as an Optical drive, producing `optical_drive_unverified` and no current fingerprint.
7. No live Optical Source Intake occurred.

These two physical-environment findings are not proven to have one cause.

### Unresolved Physical Optical Identity Findings

#### A. Windows Optical-drive recognition

- The path was readable.
- The provider could not verify the drive as Optical.
- The application correctly reports this as unavailable/needs attention.
- The application must not treat any readable drive as Optical merely to bypass this condition.

#### B. Fingerprint repeatability

- Stored and current `optical_media_fingerprint_v1` values differed during one investigation.
- The reason for the difference is not yet known.
- Possible causes require evidence-based investigation.
- It is not yet proven that the algorithm itself is defective.
- Exact matching must not be weakened in 12.63.22.0.

## 3. Current Optical Identity Architecture

Optical uses the normal Source identity stack:

- Windows provider probes the observed root as `optical_media`.
- The provider verifies the path is an Optical drive and physical media, enumerates a metadata-only manifest, and emits `optical_media_fingerprint_present`.
- Source Creation persists the fingerprint on `source_endpoints.identity_fingerprint_hash` with version `optical_media_fingerprint_v1`.
- Source Selection re-probes candidate paths and compares the current fingerprint with the stored endpoint fingerprint.
- Generic readiness re-probes the configured/effective path and requires an exact current Optical fingerprint match.
- Run Ingestion dispatch revalidates Source Selection and blocks unless the selected Optical identity is matched and verified.

The current architecture intentionally fails closed when the inserted media fingerprint does not match the enrolled endpoint fingerprint.

## 5. Windows Optical-Drive Recognition Findings

The Windows non-admin provider uses PowerShell/CIM-backed metadata through `WindowsSourceIdentityProbeProvider._collect_optical_metadata()` and `_collect_optical_media_evidence()`.

Relevant evidence:

- `Win32_LogicalDisk` / logical-drive metadata:
  - drive type normalized to `cd-rom`;
  - filesystem type;
  - volume label;
  - volume serial;
  - total size;
  - free space.
- `Win32_CDROMDrive` / CD-ROM metadata:
  - drive letter;
  - media-loaded state;
  - media type;
  - drive name;
  - PNP device ID.
- Physical/virtual classification:
  - `_optical_physical_status()` returns `physical` when the PNP ID or drive name contains supported physical CD/DVD/Blu-ray indicators such as `USBSTOR\CDROM`, `IDE\CDROM`, or `SCSI\CDROM`;
  - virtual-drive hints block as `virtual_optical_drive_not_supported`;
  - missing or ambiguous physical evidence blocks as `optical_drive_unverified`.

`optical_drive_unverified` can occur in either of these cases:

- Windows does not provide a drive type for the selected path.
- Windows reports a CD-ROM drive type but the provider cannot verify it as a supported physical Optical device.

During this recon, Codex and backend API context both observed the current `E:\` disc as:

- `drive_type`: `cd-rom`
- `filesystem_type`: `UDF`
- `media_loaded`: `true`
- `media_type`: `DVD Writer`
- physical status: `physical`
- blockers: none

The earlier `optical_drive_unverified` observation was not reproduced during this recon. It remains bounded as an intermittent Windows recognition/context/timing issue, not the cause of the current acceptance failure.

## 6. Fingerprint Definition

`optical_media_fingerprint_v1` hashes this payload from `_optical_fingerprint_payload()`:

- `algorithm`: `optical_media_fingerprint_v1`
- `disc_metadata`
  - `filesystem_type`, normalized/casefolded
  - `volume_label`, normalized/casefolded or `null`
  - `volume_serial`, normalized/casefolded
  - `total_size`
  - `used_size`, computed as `total_size - free_space`
- `manifest`
  - sorted metadata entries
  - `file_count`
  - `directory_count`
  - `timestamps_included`

Each manifest entry includes:

- lowercased endpoint-relative path with `\` separators;
- `entry_type`: `directory`, `file`, or `other`;
- `file_size` for files;
- `last_write_time_ns` from Python `stat_result.st_mtime_ns` when available.

Manifest traversal is deterministic in code:

- directories are scanned with `os.scandir`;
- child directories are sorted by normalized path;
- final entries are sorted by `(relative_path, entry_type)`;
- root names are uppercased and sorted;
- the manifest is scanned twice before fingerprinting;
- timestamps are included only when the two scans match exactly and every entry has `last_write_time_ns`.

Serialization uses the shared stable JSON hashing helper in `identity_fingerprint.py`.

## 13. Root Cause Classification

Primary classification: **C. Unstable metadata included in v1**.

Evidence:

- same-mount probes were deterministic;
- app restart did not change the live hash;
- Optical recognition succeeded in all recon probes;
- manifest entries, counts, file sizes, and timestamps stayed stable;
- Windows-reported free space / computed used size changed after device-level eject/reappearance;
- v1 includes `used_size`;
- excluding `used_size` produced a stable diagnostic variant across the observed states.

Secondary bounded classification: **F. Inconclusive environmental issue** for the earlier `optical_drive_unverified` observation only.

That recognition failure was not reproduced during this recon, and current evidence does not show it caused the fingerprint mismatch.

## 14. Fingerprint Version Recommendation

Recommendation: **Option 3 — Introduce versioned v2**.

Reason: `optical_media_fingerprint_v1` includes `used_size`, which is derived from Windows `free_space`. For this Optical/UDF test disc, that value changed across device/media lifecycle state without any observed change to the file manifest. Because v1’s stored hashes already include that field, changing v1 in place would silently alter the meaning of existing v1 endpoint identities.

Design-level v2 direction:

- keep exact-match semantics;
- keep versioned hash storage;
- keep metadata-only probing;
- keep deterministic JSON serialization;
- keep filesystem type, volume serial/label where present, total size if proven stable, manifest paths, entry types, and file sizes;
- exclude Windows-reported `free_space` and computed `used_size`;
- strongly consider excluding timestamps or treating timestamp use as a separate evidence policy unless cross-mount stability is proven;
- preserve v1 endpoints as v1, but do not auto-migrate them silently;
- require re-enrollment or an explicit safe upgrade path for existing v1 Optical Sources;
- continue blocking v1 mismatches until upgraded/re-enrolled.

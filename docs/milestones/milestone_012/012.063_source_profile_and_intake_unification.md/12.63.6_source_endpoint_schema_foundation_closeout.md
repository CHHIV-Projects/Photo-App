## 5. Migration Summary

The prompt requested a migration, but this repo does not currently use Alembic. Per user approval, the migration-equivalent work was implemented using the existing repo-native pattern:

```text
new SQLAlchemy models
new idempotent ensure_*_schema helper
startup wiring in backend/app/main.py
in-memory SQLite tests
```

The new helper is:

```text
backend/app/services/source_endpoint_schema.py
ensure_source_endpoint_schema(db_session)
```

It is additive and non-destructive:

- Creates the three new endpoint/access-node tables if missing.
- Adds nullable `ingestion_sources.endpoint_id` if missing.
- Adds `ix_ingestion_sources_endpoint_id` if missing.
- Adds the `ingestion_sources.endpoint_id` FK on PostgreSQL where it can be added cleanly.
- Skips risky SQLite table rebuilds.
- Performs no data backfill.
- Does not populate endpoint rows.
- Does not modify existing `ingestion_sources` values.

## 7. Privacy / Evidence Storage Summary

The schema is designed for sanitized evidence only.

JSON-like fields are stored as `Text`, matching current project patterns:

```text
capabilities_json
evidence_summary_json
blockers_json
warnings_json
```

These fields are intended for sanitized summaries and structured codes only. The schema does not require or introduce storage for:

```text
NAS passwords
credential-store secrets
Apple credentials
cloud tokens
session cookies
2FA codes
raw command dumps
raw USB/PnP dumps
raw environment dumps
source media
Vault files
```

The tests use fake/sanitized fixture identifiers only.

## 11. Risks / Known Limitations

- Schema exists but no enrollment workflow exists yet.
- Schema exists but no readiness integration exists yet.
- Schema exists but no run-launch verification exists yet.
- Legacy path-only profiles remain unchanged.
- `ingestion_sources.endpoint_id` remains nullable and unpopulated.
- NAS exact access must be validated by the runtime access context that will perform future intake.
- Linux/macOS Access Node support is schema-ready but no Linux/macOS probe provider is implemented.
- SQLite does not receive a risky rebuilt-table FK constraint for legacy `ingestion_sources`; PostgreSQL receives the FK when the helper can add it cleanly.
- Endpoint source type/status/confidence values are stored as strings, not DB enums/check constraints, to preserve flexibility until enrollment/readiness behavior is designed.

## 12. Recommended Next Milestone

Recommended next milestone:

```text
12.63.7_source_endpoint_enrollment_service_design_prompt.md
```

Reason:

The schema foundation is now present and intentionally inert. The next useful step is to design endpoint enrollment before adding any write behavior, admin API, readiness integration, or Source Profile linking workflow.

Recommended design focus:

- How a probe result becomes an endpoint candidate.
- How immutable aliases are chosen and normalized.
- How duplicate endpoint detection should work.
- How NAS server/share/folder identity should be stored or masked.
- How `ingestion_sources.endpoint_id` should be linked during enrollment.
- How to avoid partial endpoint/profile rows if enrollment is canceled.

## 13. Product Decisions Still Needed

1. Should NAS server/share names be stored raw, masked, hashed, or both raw-for-display and hash-for-match?

2. Should endpoint aliases remain globally unique forever, or should a future historical-alias/rename workflow be designed?

3. Which identity evidence combinations are enough to auto-match an existing endpoint versus require operator review?

4. Should endpoint enrollment create the Source Profile in the same transaction, or should endpoint creation and profile linking remain separate explicit steps?

5. Should medium-confidence external/removable/NAS evidence ever allow run launch after one-time operator confirmation, or always require reviewed enrollment/repair?

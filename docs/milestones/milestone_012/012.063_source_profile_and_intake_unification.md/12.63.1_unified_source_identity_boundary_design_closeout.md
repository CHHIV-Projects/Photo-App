- Observed Path

## 2. Executive Design Summary

The recommended v1 source identity model is:

```text
Durable Source Endpoint
  = the enrolled source identity anchor
  = source type + durable identity evidence + immutable alias + observed path history

Source ID / Source Profile
  = the runnable intake unit
  = durable endpoint + selected root/folder + intake settings + lifecycle state

Observed Path
  = where the source was reachable for setup or a specific run
  = not durable identity

Ingestion Source / Source Registry
  = current compatibility layer used by Source Intake, iCloud Intake, reports, and provenance
```

The smallest safe future implementation path is additive:

1. Keep `ingestion_sources.id` as the current operational Source ID / Source Profile ID.
2. Add durable endpoint identity beside `ingestion_sources`, not in place of it.
3. Add observed path history as append-only evidence.
4. Link new endpoint identity to current Source Profiles when confidence is high.
5. Keep existing provenance source/path/run semantics intact.
6. Use endpoint verification during readiness and run launch for enrolled non-cloud sources.

This keeps current iCloud and local Source Intake behavior stable while giving the system a stronger identity anchor than label/type/path.

## 3. Concept Definitions

### Durable Source Endpoint

What it is:

The durable identity anchor for the thing the user intends to ingest from. It represents a local computer/volume context, external device, removable media item/session, NAS/share endpoint, or cloud account/library.

Who sees it:

Both user and system see it, but at different levels. The user sees the immutable alias and high-level type. The system stores durable identity evidence and observed path history.

Mutable or immutable:

- Immutable: source type, enrolled alias for v1, original durable identity anchor.
- Append-only or carefully amended: identity evidence observations, confidence, observed path history.
- Mutable only through explicit future repair flow: corrected identity evidence or endpoint merge/split, if ever designed.

Examples:

- `Chuck External Drive 1`
- `Chuck Desktop Local C Volume`
- `Synology Photos Share`
- `Family DVD 2004-01`
- `Chuck iCloud Library`

Existing approximation:

`backend/app/models/ingestion_source.py` approximates this today through `source_label`, `source_type`, `source_root_path`, `cloud_provider`, `managed_staging_path`, and `account_username`, but it currently mixes endpoint identity, runnable profile, and compatibility registry behavior.

Future direction:

Create a durable endpoint layer or endpoint-linked fields beside `ingestion_sources`. It should capture source type, immutable alias, durable identity evidence, identity confidence, and observed path history. Do not treat drive letters, mapped paths, or labels as sufficient durable identity.

### Source ID / Source Profile

What it is:

The runnable unit the operator selects for intake. It is a durable endpoint plus a selected source root/folder plus intake settings and lifecycle state.

Who sees it:

Both user and system. The user chooses and runs it. The system uses it to resolve the current source path, run readiness checks, launch Source Intake, and record provenance.

Mutable or immutable:

- Immutable or locked after creation for v1: endpoint link and selected root/folder.
- Mutable: lifecycle/status and non-identity intake settings.
- Alias: derived from the endpoint alias plus root label; do not design casual renaming for v1.

Examples:

- `Chuck External Drive 1 - Entire Drive`
- `Chuck External Drive 1 - Photos`
- `Chuck External Drive 1 - Scans`
- `Synology Photos Share - Family Archive`
- `Chuck Desktop Local C Volume - Desktop`

Existing approximation:

`ingestion_sources.id` is the current operational Source Profile ID. iCloud prepare/import tables also use `source_profile_id` as a foreign key to `ingestion_sources`.

Future direction:

For the smallest safe path, keep `ingestion_sources.id` as the compatibility Source ID / Source Profile ID and add endpoint identity beside it. A separate `source_profiles` table can be considered later only if `ingestion_sources` becomes too limiting.

### Source Root

What it is:

The selected root/folder within the durable endpoint that a Source Profile scans. Intake scans this root and its subfolders.

Who sees it:

Both user and system. The user chooses it during profile creation. The system stores it as the stable root for relative path and skip-known behavior.

Mutable or immutable:

For v1, treat it as immutable after Source Profile creation. If the root was wrong, archive/deprecate/test the Source Profile and create a corrected one.

Examples:

- Local: `C:\Photos`
- External Device: `\` or `\Photos` relative to the detected device
- Removable Media: `\DCIM` or disc root
- NAS: `\Photos` relative to the known share
- Cloud: managed staging root or cloud provider library scope, depending on provider workflow

Existing approximation:

`source_root_path` and `source_root_path_normalized` in `ingestion_sources`, plus `source_root_path` snapshots in `ingestion_runs`, `source_intake_runs`, and `provenance`.

Future direction:

Store source root as endpoint-relative where possible. For local sources, the root may remain path-like because local folder identity is inherently host/volume/path based. Preserve `source_relative_path` under the selected Source Profile root.

### Observed Path

What it is:

The path used to access the source at setup time or run time. It is an observation, not durable identity.

Who sees it:

Both user and system. The user may select it. The system records it, probes it, verifies it, and uses it to resolve the current run path.

Mutable or immutable:

Append-only history. Individual observations should not be treated as durable identity. They may be marked last seen, verified, failed, or superseded.

Examples:

- `D:\`
- `E:\`
- `Z:\`
- `\\Synology\Photos`
- `\\192.168.1.10\Photos`
- `C:\Users\Chuck\Desktop`

Existing approximation:

`source_root_path` is often doing observed-path work today. This is the root weakness for external drive and NAS identity.

Future direction:

Store observed path history separately from durable endpoint identity. Before an enrolled external/removable run, verify that the current observed path maps to the enrolled durable identity.

### Ingestion Source / Source Registry

What it is:

The existing backend compatibility record used by Source Intake, iCloud Intake, ingestion runs, and provenance.

Who sees it:

Primarily system and Advanced Details. It should become less visible in normal operator UI.

Mutable or immutable:

Today it is partially editable. Future work should treat it as compatibility plumbing and avoid exposing it as the primary user identity.

Examples:

- Existing row in `ingestion_sources`
- Current Source Profile ID used by `/api/admin/source-profiles`
- Compatibility source ID used by Source Intake and provenance

Existing approximation:

This is exactly `backend/app/models/ingestion_source.py`.

Future direction:

Keep it during transition. Add endpoint linkage rather than replacing it. Avoid breaking existing references from iCloud prepare/import rows, source intake runs, ingestion runs, and provenance.

### Intake Run

What it is:

A specific execution attempt against a Source ID / Source Profile. It resolves an observed/current path, verifies readiness, scans the selected root, and records results.

Who sees it:

Both user and system. The user sees status and summary. The system records detailed counts, paths, reports, and run metadata.

Mutable or immutable:

Run records should be append-only after completion except for status/progress while running and controlled stale/interrupted recovery fields.

Examples:

- A local Source Intake run from `C:\Photos`
- An external drive intake run after the drive is detected as `E:\`
- An iCloud import run/chunk sequence

Existing approximation:

- `ingestion_runs`
- `source_intake_runs`
- `icloud_intake_import_runs`
- `icloud_intake_import_chunks`

Future direction:

Add observed path and durable endpoint verification result to run context. For local/external/removable/NAS, direct Source Intake remains the v1 execution path unless a future large-source milestone adds prepared snapshots.

### Provenance

What it is:

The historical explanation of where an asset came from, during which run, from which source root, and at which source path/relative path.

Who sees it:

Both user and system. Users may see summarized source/path history. The system uses it for lineage, skip-known behavior, cleanup safety, source review, and future source-aware workflows.

Mutable or immutable:

Historical provenance should not be casually rewritten. Future durable endpoint links should be additive.

Examples:

- Asset came from Source Profile `Chuck External Drive 1 - Photos`
- In ingestion run `123`
- From source root `\Photos`
- At relative path `2020\IMG_0001.JPG`
- Observed during that run at `E:\Photos\2020\IMG_0001.JPG`

Existing approximation:

`backend/app/models/provenance.py` links to `ingestion_source_id`, `ingestion_run_id`, and stores denormalized source label/type/root/path/relative path fields.

Future direction:

Preserve source/path/run semantics and add durable endpoint/profile identity references when available. Leave historical provenance explainable even if it cannot be confidently linked to a new endpoint.

## 4. Source Type Design

### Local

What the user selects:

A folder/path on the current computer, such as `C:\Photos` or the user Desktop.

Identity evidence to capture:

- Host/computer identity, using non-secret evidence.
- Volume identity if reliably available.
- Filesystem/volume serial or UUID if reliably available.
- Selected local root path.
- Observed path history.

Observed path meaning:

The direct local path currently used to access the root.

Source root meaning:

The selected folder path on the local host/volume. For local sources, the path remains more meaningful than it does for removable/external sources.

Readiness should verify:

- Source Profile is active.
- Host/volume evidence matches where available.
- Root path exists and is a directory.
- Root is readable.
- No conflicting ingestion operation is running.
- Drop Zone state is safe for Source Intake.

Should block a run:

- Path missing.
- Path not a directory.
- Access denied.
- Identity mismatch where reliable host/volume evidence exists.
- Conflicting operation.
- Unsafe Drop Zone state.

Source-specific behavior:

Local has no acquisition step and no cleanup of source root. It should use direct Source Intake for v1.

### External Device

What the user selects:

An observed path such as `D:\`, `E:\`, or a folder under a mounted external drive.

Identity evidence to capture:

- Device serial if reliably available.
- USB VID/PID where useful.
- Volume serial number.
- Filesystem UUID or volume GUID where available.
- Volume label and capacity as secondary evidence, not sufficient alone.
- Observed path history.

Observed path meaning:

The drive letter or mount path where the device appeared for setup or a run.

Source root meaning:

The root/folder selected on the external device, stored endpoint-relative where possible, such as `\`, `\Photos`, or `\Scans`.

Readiness should verify:

- The device is connected.
- The current observed path maps to the enrolled durable endpoint identity.
- The selected root exists on that device.
- The root is readable.
- No conflicting operation is running.

Should block a run:

- Device not connected.
- Current path maps to a different device.
- Durable identity cannot be read with enough confidence.
- Multiple candidate devices match ambiguously.
- Selected root is missing or unreadable.
- Conflicting operation.

Source-specific behavior:

The system should eventually auto-discover the current drive letter when possible. The user should not normally need to re-enter the drive letter every run.

### Removable Media

What the user selects:

A drive/path representing inserted media, such as an optical disc, inserted media session, or future media-card treatment if designed that way.

Identity evidence to capture:

- Media/session/content identity where available.
- Optical disc/session metadata where available.
- Filesystem serial/UUID where available.
- Volume label and content fingerprint as supporting evidence.
- Reader device evidence only as context, not source identity.

Observed path meaning:

The current drive letter/path through which the inserted media is accessible.

Source root meaning:

The selected folder/root on the inserted media, such as disc root or `\DCIM`.

Readiness should verify:

- Media is inserted.
- The inserted media matches the enrolled media identity.
- The selected root exists and is readable.
- No conflicting operation is running.

Should block a run:

- No media inserted.
- Reader is present but media identity differs.
- Media identity cannot be read with enough confidence.
- Selected root is missing.
- Access/read errors.

Source-specific behavior:

The reader device is not the source identity. If future SD/camera card behavior treats cards as media rather than devices, it should follow this model.

### NAS

What the user selects:

A mapped drive or UNC path, such as `Z:\`, `\\Synology\Photos`, or `\\192.168.1.10\Photos`.

Identity evidence to capture:

- Canonical UNC server/share where available.
- Mapped drive to UNC resolution where available.
- Server name, share name, and non-secret network identity evidence.
- NAS/share/volume identifier if reliably available.
- Observed path history, including mapped drive and UNC variants.

Observed path meaning:

The current mapped drive or UNC path used to access the share.

Source root meaning:

The selected folder/root within the share, such as share root or a folder below it.

Readiness should verify:

- Share is reachable through an observed path.
- Mapped drive or UNC resolves to the enrolled endpoint/share identity.
- Selected root exists and is readable.
- No credentials are required from Photo Organizer.
- No conflicting operation is running.

Should block a run:

- Share unavailable.
- Mapped drive points to a different share.
- UNC/server/share identity mismatch.
- Identity is ambiguous.
- Root missing or unreadable.
- Operating system prompts for credentials that Photo Organizer should not store.

Source-specific behavior:

Photo Organizer should not store NAS usernames or passwords for v1. It should rely on already-accessible operating system shares.

### Cloud

What the user selects:

A cloud source profile. iCloud exists now; OneDrive, Google Drive, Dropbox, or export-style providers may come later.

Identity evidence to capture:

- Provider.
- Non-secret account/library identifier where available.
- Managed staging path for provider acquisition.
- Provider/library remote identity evidence where available.
- Observed local staging path history.

Observed path meaning:

For iCloud today, the observed local path is the managed staging path. Provider-side identity and helper/session state are not ordinary filesystem observed paths.

Source root meaning:

For iCloud today, the runnable scope is the iCloud library/profile plus managed staging path. Cloud providers may have provider-specific root/library/folder semantics later.

Readiness should verify:

- Source Profile is active.
- Provider and acquisition method are supported.
- Non-secret account/profile metadata is present.
- Managed staging path is under the approved root.
- Staging path aligns with the selected profile.
- Provider/session status is sufficient where safely knowable.
- Operation guardrails are clear.

Should block a run:

- Unsupported cloud profile.
- Missing or unsafe staging path.
- Source registration/path mismatch.
- Provider/session not ready.
- Conflicting acquisition, Source Intake, or cleanup operation.

Source-specific behavior:

Cloud may retain Prepare / Import because provider, download, staging, retry, resume, deferred policy, and cleanup complexity are real.

## 5. Endpoint Enrollment Design

### Common Enrollment Flow

1. User chooses source type.
2. User provides an observed path or cloud provider/account context.
3. System performs a read-only identity probe.
4. System decides whether the durable endpoint is new, known, ambiguous, or unreadable.
5. If new, user assigns an immutable alias.
6. If known, user is routed toward the existing endpoint.
7. User selects a source root/folder on the endpoint.
8. System creates the runnable Source ID / Source Profile.
9. No records are created if the user cancels before confirmation.

### New Endpoint Enrollment

If the identity probe finds no matching known endpoint:

- Show source type.
- Show safe user-facing identity summary.
- Ask for immutable alias.
- Ask for root/folder selection.
- Create endpoint plus Source ID / Source Profile after confirmation.

The alias should be globally unique enough for user clarity. The design should avoid two different endpoints with the same alias.

### Known Endpoint Detected During Setup

If the identity probe matches an existing endpoint:

- Show the existing immutable alias.
- Do not allow creation of a duplicate endpoint alias.
- Offer:
  - use existing Source ID / Source Profile if matching root exists,
  - add a new root under the known endpoint,
  - cancel.

### Attempted Duplicate Alias

If the endpoint identity is known but the user tries to create a new alias, block that path and explain that this device/share/media is already enrolled.

If the endpoint identity is new but the alias is already used by another endpoint, require a different alias to prevent provenance and operator confusion.

### Adding a New Root to an Existing Endpoint

The user can intentionally create multiple Source IDs / Profiles under one endpoint:

```text
Endpoint: Chuck External Drive 1
Profiles:
  Chuck External Drive 1 - Entire Drive
  Chuck External Drive 1 - Photos
  Chuck External Drive 1 - Scans
```

Before creating a new Source Profile, the system should check whether the same endpoint/root already exists and route the user to the existing Source Profile when possible.

### Cancel Behavior

Canceling endpoint enrollment or root/profile creation should leave no partial endpoint/profile rows unless a future workflow explicitly designs a draft state. For v1, avoid draft complexity.

### External Device Enrollment

1. User selects `D:\`, `E:\`, or a folder under an observed drive path.
2. System probes durable device/volume identity.
3. System checks for known endpoint identity.
4. If new, user assigns immutable alias.
5. User selects root/folder on the device.
6. System creates Source ID / Source Profile.

### Removable Media Enrollment

1. User selects the drive/path for inserted media.
2. System probes media/session/content identity.
3. Reader device identity is recorded only as context, not durable source identity.
4. If the media identity is new, user assigns immutable alias.
5. User selects root/folder.
6. System creates Source ID / Source Profile.

### NAS Enrollment

1. User selects a mapped drive or UNC path.
2. System resolves mapped path to UNC/share identity where possible.
3. System probes non-secret endpoint/share identity.
4. System checks for known endpoint/share.
5. If new, user assigns immutable alias.
6. User selects root/folder under the share.
7. System creates Source ID / Source Profile.

No NAS credentials should be stored by Photo Organizer for v1.

### Local Enrollment

1. User selects local folder/root.
2. System probes host, volume, and path evidence where available.
3. System treats local path as meaningful but still records observed path and identity evidence.
4. If new, user assigns immutable alias or accepts a suggested one.
5. System creates Source ID / Source Profile for the selected local root.

## 6. Source ID / Source Profile Design

A runnable Source ID / Source Profile is:

```text
durable source endpoint
+ selected source root/folder
+ source type
+ lifecycle/status
+ intake settings
+ last run summary
+ future scheduling suitability
```

Recommended display name:

```text
endpoint alias + root label
```

Examples:

```text
Endpoint Alias: Chuck External Drive 1
Root: \
Display: Chuck External Drive 1 - Entire Drive

Endpoint Alias: Chuck External Drive 1
Root: \Photos
Display: Chuck External Drive 1 - Photos

Endpoint Alias: Synology Photos Share
Root: \Family Archive
Display: Synology Photos Share - Family Archive

Endpoint Alias: Chuck Desktop Local C Volume
Root: \Users\Chuck\Desktop
Display: Chuck Desktop Local C Volume - Desktop
```

Design rules:

- Endpoint alias is immutable for v1.
- Root/folder is locked after Source Profile creation.
- Lifecycle/status can change without rewriting provenance.
- Intake settings can be edited if they do not change identity.
- Last run summary is derived from run/report state.
- A profile can later become the schedulable unit, but scheduling is not implemented now.

Compatibility rule:

For the first additive implementation, `ingestion_sources.id` should remain the operational Source ID / Source Profile ID. Existing APIs, iCloud source_profile_id references, Source Intake, reports, and provenance can keep working while endpoint identity is linked beside it.

## 7. Observed Path Resolution Design

### Setup-Time Use

At setup, observed path is the input that lets the system probe identity. It should be recorded with:

- Raw observed path.
- Normalized/canonical path where safely available.
- Source type.
- Probe time.
- Probe host/environment.
- Identity evidence snapshot.
- Probe result.

### Storage

Observed paths should be stored as history, not as the endpoint identity itself. Multiple observations may exist for the same endpoint:

```text
D:\
E:\
Z:\
\\Synology\Photos
\\192.168.1.10\Photos
```

### Why History Is Useful

Observed path history supports:

- Auto-discovery of current mount path.
- Operator explanation.
- Readiness diagnostics.
- Wrong-path blocking.
- NAS mapped drive versus UNC reconciliation.
- Future scheduling decisions.

### Run-Time Resolution

Before every run:

1. Load Source ID / Source Profile.
2. Load linked durable endpoint identity.
3. Resolve current observed path.
4. Probe current identity.
5. Verify identity matches endpoint.
6. Verify selected root exists under current path.
7. Launch Source Intake only after readiness passes.

### Auto-Discovery

External devices:

- Scan mounted volumes where safe and read-only.
- Match identity evidence to enrolled endpoint.
- If exactly one match is found, derive current root path from that mount.

Removable media:

- Detect inserted media through accessible drives.
- Match media/session/content identity.

NAS:

- Try last known UNC and mapped observations.
- Resolve mapped drives to UNC where possible.
- Do not prompt for or store credentials.

Local:

- Use configured local path and host/volume evidence.
- If path is unavailable, block as missing/not connected.

Cloud:

- Use cloud provider readiness and managed staging path rules.

### When User Must Provide a New Observed Path

The user should provide or select a new observed path when:

- Auto-discovery cannot find the source.
- Multiple possible matches exist.
- NAS path has changed and no known observation works.
- Identity cannot be probed from prior observations.
- User is adding a new root under a known endpoint.

### Safe Failure Behavior

If the old observed path points to a different device/media/share:

- Block the run.
- Do not update source identity.
- Do not run Source Intake.
- Show a clear wrong-source warning.
- Record the failed observation as diagnostic evidence if safe.

If identity cannot be read:

- External Device and Removable Media: block or mark Needs Review.
- NAS: block or mark Needs Review unless endpoint/share identity can be safely inferred.
- Local: block if root missing or unreadable; if path exists but identity evidence is partially unavailable, use a conservative Needs Review state depending on future probe findings.

If multiple possible matches exist:

- Block and require operator selection/review.

## 8. Provenance Compatibility Design

Future provenance should still answer:

```text
What asset came from which source, during which run, from which source root, at what source path / relative path?
```

Existing useful fields should remain:

- `asset_sha256`
- `ingestion_source_id`
- `ingestion_run_id`
- `source_label`
- `source_type`
- `source_root_path`
- `source_path`
- `source_relative_path`

Recommended additive future links:

- Durable endpoint/source identity reference.
- Source Profile reference if it ever differs from `ingestion_source_id`.
- Observed path used for the run.
- Identity verification result for the run.
- Selected source root snapshot.
- Endpoint alias snapshot.

Historical provenance:

- Do not rewrite source paths or labels casually.
- Leave historical rows explainable as they are.
- Optionally backfill nullable endpoint/profile references only when confidence is high.
- Preserve historical aliases/labels as snapshots.
- Do not require all historical provenance to be perfectly linked before new intake can work.

Relative path rule:

`source_relative_path` should remain relative to the selected Source ID / Source Profile root. This keeps folder/subfolder behavior intuitive:

```text
Endpoint: Chuck External Drive 1
Profile Root: \Photos
Observed Path: E:\Photos
Asset Path: E:\Photos\2020\IMG_0001.JPG
Relative Path: 2020\IMG_0001.JPG
```

Observed path is run/access evidence. It should not replace source root or relative path semantics.

## 9. Current `ingestion_sources` Compatibility Strategy

Current reality:

`ingestion_sources` acts as:

1. User-facing Source Profile.
2. Backend source registry.
3. Compatibility anchor for Source Intake, iCloud Intake, ingestion runs, and provenance.

Recommended transition:

### Phase 1 - Keep `ingestion_sources` Stable

Do not replace `ingestion_sources` first. Keep:

- Existing IDs.
- Existing iCloud `source_profile_id` references.
- Existing Source Intake launch behavior.
- Existing provenance and run references.
- Existing reports.

### Phase 2 - Add Endpoint Identity Beside It

Add a durable endpoint identity layer or endpoint-linked fields beside `ingestion_sources`.

For a first schema implementation, the safest likely shape is:

```text
source_endpoints
source_endpoint_observed_paths
nullable endpoint link from ingestion_sources
```

This is a design direction, not an implemented schema commitment.

### Phase 3 - Enroll or Link Existing Profiles

Existing profiles can remain legacy/path-based until enrolled or confidently linked.

For legacy local/external rows:

- Do not force immediate migration.
- Offer a probe/enroll flow later.
- Preserve current behavior until the profile is upgraded.

For iCloud:

- Link to a Cloud endpoint only if useful.
- Do not rework iCloud mechanics.
- Keep `source_profile_id` stable as the current `ingestion_sources.id`.

### Phase 4 - Resolve Current Path at Run Time

For endpoint-linked non-cloud profiles:

- Resolve current observed path from endpoint identity.
- Verify match before Source Intake.
- Pass the resolved path to existing Source Intake.
- Keep the same `ingestion_source_id` for skip-known/provenance continuity.

### Phase 5 - Consider a Separate Source Profile Table Later

Only consider a new first-class `source_profiles` table after endpoint probing and compatibility needs are proven. A premature replacement would create unnecessary iCloud and Source Intake risk.

References requiring compatibility support:

- `provenance.ingestion_source_id`
- `ingestion_runs.ingestion_source_id`
- `source_intake_runs.ingestion_source_id`
- `icloud_intake_prepare_runs.source_profile_id`
- `icloud_intake_prepared_candidates.source_profile_id`
- `icloud_intake_import_runs.source_profile_id`
- `icloud_intake_import_chunks.source_profile_id`
- `source_profile_deferred_assets.source_profile_id`
- Source Profile API payloads and frontend types
- Source Intake reports and ingestion manifests

Smallest safe additive path:

1. Probe first.
2. Add endpoint identity only after probe evidence is understood.
3. Keep `ingestion_sources` as the compatibility Source/Profile row.
4. Add nullable endpoint linkage.
5. Move normal UI away from registry internals.

## 10. Intake Workflow Design

### Common UI Grammar

All source types should use the same user-facing grammar:

```text
Source
Readiness
Action
Progress
Result
Next Safe Action
Advanced Details
```

### Non-Cloud v1 Workflow

For Local, External Device, Removable Media, and NAS:

```text
Check Readiness
Run Intake
Show Result
```

Readiness should show:

- Source connected/found.
- Identity verified where applicable.
- Selected root exists.
- Access/readability.
- Operation conflicts.
- Drop Zone safety.
- Last run summary.

Run Intake should continue to use Source Intake as the ingestion authority.

Do not require mandatory prepared candidate snapshots for v1 non-cloud intake. Direct Source Intake is still appropriate for small and targeted runs.

### Cloud Workflow

For iCloud and similar cloud sources where provider/staging/resume/cleanup complexity exists:

```text
Prepare
Import
Show Result
```

iCloud should keep:

- Refresh / Prepare Next 1000.
- Exact prepared candidate set.
- Import Next 1000.
- Durable import/chunk ledger.
- Explicit resume.
- Deferred policy handling.
- Guarded local staging cleanup.

### Advanced Details

Advanced Details should contain:

- Endpoint ID and identity evidence.
- Observed path history.
- Compatibility `ingestion_source_id`.
- Normalized paths/labels.
- Internal run IDs.
- Report paths.
- Raw blocker/conflict details.
- Cleanup counters for cloud staging.
- Provider diagnostics.

### Deferred Large-Source Resume Work

Large external/NAS sources may eventually benefit from:

- Candidate scan/preparation.
- Exact candidate snapshot.
- Chunked run ledger.
- Resume after interruption.

That should be a future milestone after identity/readiness and targeted root semantics are implemented.

## 11. Future Scheduling Implications

Scheduling is out of scope now.

This model supports future scheduling because Source ID / Source Profile is the runnable unit:

```text
Source Profile = endpoint + root + settings + lifecycle
```

Multiple roots under one endpoint support automation cleanly:

```text
Endpoint: Synology Photos Share
Profiles:
  Synology Photos Share - Family Archive
  Synology Photos Share - Scans
  Synology Photos Share - Imports
```

A future scheduler would need to verify before running:

- Source Profile is active and schedule-enabled.
- Durable endpoint is available.
- Current observed path matches enrolled identity.
- Selected root exists.
- No conflicting acquisition/intake/cleanup/post-processing job is active.
- Cloud provider/session is ready where applicable.
- Prior run is not stuck in a state requiring review.

State that should prevent scheduled runs:

- Not connected.
- Identity mismatch.
- Ambiguous identity match.
- Needs Review.
- Source inactive/archived/deprecated.
- Conflicting operation active.
- Drop Zone unsafe.
- Cloud session unavailable.
- Prior interrupted run requiring explicit operator resume.

If source is disconnected or identity mismatch occurs:

- Do not auto-run.
- Record blocked/skipped scheduler result.
- Surface Next Safe Action to operator.
- Do not modify source identity automatically.

Future fields/settings that may be useful:

- Schedule enabled.
- Cadence/window.
- Max run size/time.
- Last scheduled attempt/result.
- Last successful run.
- Retry policy.
- Preferred observed path.
- Require operator confirmation after identity change.
- Identity confidence threshold.

Do not implement scheduling now.

## 12. Risks / Tradeoffs

### Schema Complexity

Adding endpoint and observed path history introduces new relationships. The risk is manageable if added beside `ingestion_sources` rather than replacing it.

### Migration / Backfill Risk

Historical rows may not have enough evidence to link confidently to endpoints. Backfill should be optional, nullable, and confidence-based. Do not block future intake on perfect historical linking.

### UI Confusion

The user should not need to understand endpoint IDs, registry IDs, normalized paths, and observed paths in normal flow. These belong in Advanced Details.

### Alias Immutability Limitations

Immutable aliases prevent casual provenance confusion but can be inconvenient if the user chooses a poor name. For v1, that is an acceptable tradeoff. A future historical-alias or rename-everywhere workflow can be designed separately.

### Device Identity Reliability

Windows may expose different identifiers depending on filesystem, device type, permissions, USB bridge, or driver. This is why the next milestone should probe read-only evidence before schema commitments.

### NAS Path Ambiguity

Mapped drives, UNC paths, IP addresses, hostnames, DNS aliases, and share renames can all point to similar storage. NAS identity may require confidence scoring and operator confirmation.

### Removable Media Identity Uncertainty

Optical media and removable cards may expose weak or inconsistent identity evidence. Content fingerprinting may be needed as supporting evidence but should be designed carefully to avoid expensive scans.

### iCloud Compatibility Risk

iCloud already uses `source_profile_id` references to `ingestion_sources`. Replacing Source Profile identity too early could break durable import, deferred ledger, cleanup, and report behavior.

### Local Source Intake Regression Risk

Local Source Intake currently works with direct path validation. Endpoint verification should be introduced only for enrolled/upgraded profiles and should not break legacy path-based profiles immediately.

### Privacy / Sensitivity

Device serials, host names, network share names, and account identifiers may be sensitive. The probe and future schema should avoid secrets and store only necessary non-secret identity evidence.

### Wrong-Source Safety

The main safety benefit is preventing wrong-device or wrong-share intake. The main risk is false blocks if identity evidence is weak. The next probe milestone should determine realistic confidence behavior.

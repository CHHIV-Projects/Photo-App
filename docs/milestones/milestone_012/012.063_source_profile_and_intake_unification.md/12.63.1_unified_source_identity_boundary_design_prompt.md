## Background / Context

Milestone `12.63.0` completed reconnaissance of the current Source Profile, Source Intake, iCloud Intake, source registry, provenance, readiness, cleanup, and UI workflow surfaces.

Key 12.63.0 findings:

```text
- Source Profiles are currently stored in the existing ingestion_sources table.
- There is no separate Source Profile table, Source Device table, or Source Endpoint table today.
- ingestion_sources currently acts as:
  1. user-facing Source Profile,
  2. backend source registry,
  3. compatibility anchor for ingestion runs and provenance.
- Current identity depends too heavily on source label, source type, and normalized source root path.
- Drive letters, mapped paths, UNC spellings, and mounted root strings can become part of source identity.
- Provenance is already source/path/run based and generally explainable.
- Future work should strengthen the source identity anchor without rewriting provenance semantics.
```

Current product direction:

```text
iCloud Intake is good enough for v1.0.
Do not rework iCloud mechanics unless necessary for naming, compatibility, or shared readiness language.
The next product area is external/local/NAS/removable/cloud source identity and intake clarity.
```

## Product Decisions Already Locked for This Milestone

Do not reopen these unless code reality proves they are impossible or unsafe.

### 1. Source Types

Use this top-level source type model for v1 design:

```text
Local
External Device
Removable Media
NAS
Cloud
```

Definitions:

```text
Local
= a folder/path on the current computer, such as C:\Photos or the user Desktop.
Mac support may come later, but current design is Windows-first.

External Device
= physically connected storage whose device/volume is the durable source identity,
such as an external HDD, external SSD, or thumb drive.

Removable Media
= inserted media where the media/session/content identity is durable,
not the reader device. Examples include CD, DVD, Blu-ray, or similar inserted media.
If camera cards or SD cards are later treated as media rather than devices,
the design should explain that path.

NAS
= networked storage/share, such as a Synology share or other SMB/network share.

Cloud
= cloud-backed source. iCloud exists now; OneDrive, Google Drive, Dropbox, or others may come later.
```

The UI should not expose unnecessary low-level subtypes unless they are needed for diagnostics or safety.

### 2. Durable Endpoint and Alias

A durable source endpoint is enrolled once.

A durable source endpoint includes:

```text
source type
durable identity evidence
immutable user-facing alias
observed path history
```

The alias is central to user understanding and provenance clarity.

For v1 design, treat the alias as immutable after enrollment.

Do not design a casual rename workflow. A future rename-everywhere or historical-alias workflow can be designed separately if needed.

### 3. Source ID / Source Profile

A Source ID / Source Profile is the runnable source unit.

A Source ID / Source Profile should be modeled conceptually as:

```text
durable source endpoint
+ selected root/folder
+ source type
+ intake settings / lifecycle state
```

One durable endpoint may have multiple Source IDs / Source Profiles if the user intentionally creates multiple roots/workflows on the same endpoint.

Example:

```text
Durable Endpoint:
  Alias: Chuck External Drive 1
  Durable identity: ABC123

Source IDs / Profiles:
  Chuck External Drive 1 — Entire Drive
    Root: \

  Chuck External Drive 1 — Photos
    Root: \Photos

  Chuck External Drive 1 — Scans
    Root: \Scans
```

The system should not allow accidental creation of a second alias for the same durable endpoint identity.

If a user probes a path and the durable endpoint is already known, the design should route them toward:

```text
use existing Source ID / Source Profile
add a new root under the known endpoint
cancel
```

not toward creating a duplicate endpoint alias.

### 4. Source Root and Folder Behavior

For Local, External Device, Removable Media, and NAS sources, the user chooses a meaningful source root/folder.

The intake run scans that root and its subfolders.

Do not design every subfolder as its own Source Profile by default.

Do not design a required iCloud-style Prepare / Scan step for non-cloud v1 intake.

Examples:

```text
Local:
  C:\Photos

Local:
  C:\Users\Chuck\Desktop

External Device:
  D:\

External Device:
  D:\Photos

NAS:
  \\Synology\Photos
```

For v1, local/external/removable/NAS workflow should generally be:

```text
Check Readiness
Run Intake
Show Result
```

Cloud may retain prepare/import because cloud has provider, download, staging, retry, resume, and cleanup complexity.

### 5. Observed Path

An observed path is the access path used to locate or run a source at a particular moment.

Examples:

```text
D:\
E:\
C:\Photos
Z:\
\\Synology\Photos
\\192.168.1.10\Photos
```

For setup/enrollment, the user may need to provide the observed path so the system can probe the durable source identity.

After enrollment, the observed path is not durable identity.

For External Device and Removable Media runs, every run should verify that the currently observed path maps to the enrolled durable endpoint/media identity before proceeding.

If the durable identity does not match, the run should fail/block safely.

For External Device sources, the system should eventually be able to find the device automatically when possible. The user should not normally need to re-enter the drive letter on every run if the system can discover the enrolled identity. If the device cannot be found, the source should show Not Connected / Blocked / Needs Review.

### 6. Provenance

The intended provenance change is additive.

Do not redesign folder/subfolder provenance semantics.

Existing provenance behavior should remain:

```text
asset came from a source
during an ingestion run
from a source root
at a source path / relative path
with folder/subfolder context preserved
```

The source anchor should become stronger by adding durable endpoint/source identity.

For future design:

```text
Drive letters, mapped paths, UNC variants, and mount paths
= observed access paths for a run

Durable endpoint/device/media/share/cloud identity
= stable source anchor

Source root/folder
= selected root for a runnable Source ID / Source Profile

Relative path
= file path under the selected source root, preserving subfolder structure
```

Do not casually rewrite existing provenance.

Historical provenance must remain explainable.

### 7. NAS Credentials

For v1, Photo Organizer should not store NAS credentials.

NAS sources should rely on shares already accessible to the operating system.

Photo Organizer may store non-secret path, endpoint, readiness, and identity evidence. It must not store NAS usernames/passwords unless a future milestone explicitly designs credential handling.

### 8. Source Intake and Cloud Boundary

Source Intake remains the ingestion authority.

Cloud acquisition remains staging-only.

Local, External Device, Removable Media, and NAS source roots are not disposable staging and must never be treated like iCloud staging cleanup targets.

No cleanup behavior should be added for non-cloud source roots in this design.

### 3. Endpoint Enrollment Flow

Design the conceptual enrollment flow.

Include at least:

```text
new endpoint enrollment
known endpoint detected during setup
attempted duplicate alias
adding a new root to an existing endpoint
cancel behavior
```

For External Device, include:

```text
user selects D:\ or another observed path
system probes durable identity
system detects whether identity is new or known
user assigns immutable alias only if endpoint is new
user adds root/folder to create Source ID / Source Profile
```

For Removable Media, include:

```text
user selects drive/path
system identifies inserted media/session/content where possible
reader device is not treated as source identity
media identity is treated as source identity
```

For NAS, include:

```text
user selects mapped drive or UNC path
system should prefer endpoint/share identity where available
mapped drive or UNC path is observed path
no credentials stored by Photo Organizer for v1
```

For Local, include:

```text
user selects local folder/root
identity may include host/computer, volume, and root path
path remains more meaningful than for removable/external devices
```

### 4. Source ID / Source Profile Creation Flow


```text

```

Explain whether the user-facing display name should be:


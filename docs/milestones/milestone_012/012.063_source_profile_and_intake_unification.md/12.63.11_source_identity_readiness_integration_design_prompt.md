## Product Direction

Endpoint enrollment is now possible and validated for local and NAS paths.

The next product question is:

```text
When an operator wants to run Source Intake for a Source Profile, how should Photo Organizer decide whether the source is ready and safe to run?
```

The desired direction is:

```text
Path-only profiles remain valid for now.
Enrolled endpoint profiles get stronger readiness checks.
Readiness should be understandable to a non-programmer operator.
Run-launch safety should eventually re-check endpoint identity immediately before Source Intake starts.
Cloud/iCloud remains provider-specific and should not be forced into generic filesystem endpoint readiness.
```

---

## Key Product Decisions to Design

### 1. Path-Only Profiles Remain Valid

Existing Source Profiles with:

```text
endpoint_id = null
```

must remain runnable for now.

They may show a warning such as:

```text
Path-only source identity. Durable source identity enrollment is recommended.
```

But they should not be blocked solely because they are not enrolled.

### 2. Enrolled Profiles Should Be Checked Against Endpoint Identity

For Source Profiles with:

```text
endpoint_id != null
```

readiness should eventually compare the currently observed source path against the enrolled endpoint identity.

Examples:

```text
Ready:
  current probe matches enrolled endpoint

Needs Review:
  source is readable but match confidence is medium/weak

Blocked:
  source path is unavailable
  source path points to a different endpoint
  source path is NAS server-only
  source type is unsupported
```

### 3. Readiness Is Not the Same as Enrollment

Enrollment answers:

```text
What is this source?
```

Readiness answers:

```text
Can this runtime safely use this source now?
```

The design should keep those concepts separate.

### 4. Readiness Is Not the Same as Source Intake

Readiness should not run Source Intake.

Readiness may probe paths, inspect safe metadata, compare endpoint identity, and report status.

It must not:

```text
copy files
write Vault files
create asset records
run cleanup
delete source files
```

### 5. Run-Launch Guard Should Be a Future Final Check

Design how a future Source Intake launch should be guarded.

Example future rule:

```text
Immediately before Source Intake starts, re-check readiness.
If endpoint mismatch or source unavailable, block run launch.
If path-only profile, allow legacy run with warning.
If enrolled endpoint matches, allow run.
```

Do not implement this yet.

### 6. Cloud/iCloud Remains Provider-Specific

Generic filesystem endpoint readiness should not control iCloud.

iCloud already has its own prepare/import/resume/status model.

The design should explicitly say:

```text
cloud_export / iCloud uses provider-specific readiness
generic endpoint readiness is not used for iCloud yet
future cloud endpoint identity should be designed separately
```

### 7. Operator Copy Should Be Simple

The UI should prefer states like:

```text
Ready
Needs Review
Blocked
Unknown
Resume Available
Path-only
Enrolled
Endpoint Mismatch
Source Not Found
```

Avoid exposing raw probe terms as primary labels.

Advanced details may include:

```text
probe_status
match_status
identity_confidence
filesystem_boundary_type
endpoint_id
observed_path_id
access_node
blocker codes
warning codes
```

Preserve:

```text
Source Intake remains the ingestion authority.
Readiness must not import files.
Readiness must not write Vault files.
Readiness must not delete source files.
Readiness must not delete staging files.
Readiness must not rewrite provenance.
Readiness must not change iCloud Intake.

Endpoint alias remains immutable for v1.
```

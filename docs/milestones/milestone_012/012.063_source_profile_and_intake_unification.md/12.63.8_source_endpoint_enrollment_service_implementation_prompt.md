## Goal

Implement the backend Source Endpoint Enrollment service.

This milestone should implement the explicit two-phase enrollment flow designed in `12.63.7`:

```text
1. Plan: read-only enrollment candidate and match analysis.
2. Confirm: explicit operator-confirmed write transaction.
```

The implementation should allow Photo Organizer to create durable `SourceEndpoint` rows, create/update an `AccessNode`, create a `SourceEndpointObservedPath` row, and link an existing `ingestion_sources` Source Profile through nullable `ingestion_sources.endpoint_id`.

This is the first milestone that may write endpoint enrollment data.

The write behavior must be explicit, backend-only, transactional, tested, and isolated from Source Intake.

## Product Decisions Locked for This Milestone

### 1. Enrollment Is Explicit

Do not auto-enroll from probe results.

A plan may recommend enrollment, but confirm must be a separate explicit call.

### 2. Use Existing Source Profiles First

For this implementation milestone, focus on enrolling/linking an **existing** `ingestion_sources` row.

Allowed:

```text
existing Source Profile + new endpoint
existing Source Profile + existing endpoint
same endpoint + existing different Source Profile root
```

Do not implement new Source Profile creation inside enrollment confirm unless current code makes this trivially safe and you stop to ask first.

Rationale:

```text
This milestone should create real endpoint enrollment behavior without also expanding Source Profile creation semantics.
```

### 3. `ingestion_sources` Remains Operational Source Profile

Current `ingestion_sources.id` remains the operational Source ID / Source Profile ID.

Enrollment may populate:

```text
ingestion_sources.endpoint_id
```

but must not replace, rename, or reinterpret `ingestion_sources`.

### 4. Existing Path-Only Profiles Remain Valid

Existing profiles with:

```text
endpoint_id = null
```

must continue to work.

Do not block Source Intake because a profile is not endpoint-enrolled.

Do not add readiness warnings unless explicitly scoped in this milestone, which it is not.

### 5. Endpoint Alias Is Immutable for v1

Implement alias creation and normalization.

Do not implement alias editing.

Alias must be unique by normalized form.

### 6. Medium-Confidence Enrollment Is Allowed With Explicit Review

A medium-confidence probe result may be enrollable if:

```text
the source root is valid
the path is readable
there are no blocking conditions
the operator explicitly confirms
```

But enrollment must not authorize automatic Source Intake run launch.

### 7. NAS Endpoint Boundary

For NAS v1:

```text
Endpoint identity should generally represent server + share.
Source Profile root represents share root or folder inside share.
Observed path records the exact UNC or mounted path used by the Access Node.
```

Examples:

```text
Endpoint:
\\HENDERSON-NAS\Photos

Source Profile root:
\\HENDERSON-NAS\Photos\Camera imports

Observed path:
\\HENDERSON-NAS\Photos\Camera imports from Chuck Windows PC
```

### 8. No Probe API Persistence

Do not make:

```text
POST /api/admin/source-identity/probe
```

write endpoint, observed path, or profile-link rows.

Enrollment persistence belongs only in the new explicit confirm flow.

### 9. No Source Intake Integration

Do not make Source Intake use endpoint_id yet.

Do not add run-launch verification.

Do not change ingestion execution behavior.

## Required Behavior

### 1. Plan Is Read-Only

The plan operation must not write:

```text
SourceEndpoint
AccessNode
SourceEndpointObservedPath
ingestion_sources.endpoint_id
database rows of any other kind
source files
Vault files
```

It may query existing endpoints, access nodes, source profiles, and run the read-only probe service.

### 2. Confirm Is the Only Write Path

Confirm may write:

```text
AccessNode, if needed
SourceEndpoint, if creating new endpoint
SourceEndpointObservedPath
ingestion_sources.endpoint_id
```

Confirm must not write:

```text
Source Intake rows
Asset rows
Provenance rows
Vault files
source files
cleanup state
iCloud acquisition state
frontend state
```

### 3. Confirm Must Be Atomic

Use one DB transaction for the enrollment writes.

If any required write fails, rollback all enrollment writes.

Examples:

```text
alias conflict after revalidation -> no writes
source profile missing -> no writes
source profile already linked unexpectedly -> no writes
observed path insert fails -> rollback endpoint/profile link
endpoint creation fails -> no profile link
operator confirmation missing -> no writes
```

### 4. Confirm Must Revalidate Critical Assumptions

Before writing, confirm should revalidate:

```text
operator_confirmed = true
source_profile_id exists
source_profile endpoint_id is null or matches selected endpoint, depending flow
alias still available if creating new endpoint
selected existing endpoint still exists if linking
probe/source root is still readable and enrollable
plan is not stale, if plan fingerprints/expiry are implemented
```

### 5. Existing Linked Profiles

If `ingestion_sources.endpoint_id` is already populated:

```text
same endpoint + same requested link -> return already linked / completed or needs_review, but do not duplicate observed path blindly
different endpoint -> block with source_profile_already_linked or source_profile_endpoint_mismatch
```

Do not silently overwrite endpoint links.

### 6. Candidate Must Be Enrollable

Do not enroll:

```text
nas_server_only
cloud generic probe
blocked probe result
unavailable probe result
unsupported provider
invalid source root
path not readable
access denied
identity mismatch
ambiguous durable match without selected endpoint and explicit review
```

Allow reviewed enrollment for:

```text
completed medium_needs_review results
completed_with_warnings if warnings are not enrollment-blocking
```

### 7. Duplicate Detection

Implement practical v1 duplicate detection:

Strong duplicate:

```text
same source_type + same identity_fingerprint_hash
```

Alias conflict:

```text
same alias_normalized
```

Medium possible match:

```text
same source_type + overlapping partial fingerprint/evidence if available
same NAS server/share hash when full fingerprint is not strong
```

If medium matching is too complex for this first implementation, implement strong fingerprint + alias conflict now and document medium matching as future work.

Do not treat observed path alone as durable duplicate evidence.

### 8. Identity Fingerprint v1

Implement:

```text
identity_fingerprint_version = source_endpoint_fingerprint_v1
```

Implement a practical deterministic hash from sanitized canonical evidence.

Must not hash secrets.

Must not use raw command dumps.

Source-type guidance:

Local:

```text
source_type + access-node/host hash + volume evidence + normalized root anchor
```

External/removable:

```text
source_type + available volume/device/media evidence summary
```

NAS:

```text
source_type + canonical server + share
```

Cloud:

```text
generic cloud not enrollable in this milestone
```

If source-type evidence is incomplete, fingerprint may still be created with lower confidence, but the plan should require review.

### 9. NAS Enrollment Behavior

For NAS:

```text
\\HENDERSON-NAS
```

must not enroll.

It should remain:

```text
nas_server_only
nas_server_not_runnable
```

For:

```text
\\HENDERSON-NAS\Photos
\\HENDERSON-NAS\Photos\Camera imports
```

if readable:

```text
endpoint candidate identity should be server + share
Source Profile root should remain the configured folder/root
observed path should be the exact path
```

Do not store credentials.

Do not enumerate unrelated shares.

Do not require mapped drive letters.

### 10. Observed Path Recording

On confirm, create one initial `SourceEndpointObservedPath` row.

Populate:

```text
source_endpoint_id
access_node_id
observed_path
normalized_observed_path
filesystem_boundary_type
source_root_candidate_path
is_valid_source_root_candidate
probe_provider_name
probe_provider_version
probe_status
confidence_tier
match_status
safe_to_run
blockers_json
warnings_json
evidence_summary_json
first_seen_at
last_seen_at
last_success_at, if successful/readable
```

Use sanitized JSON/text values.

Do not store raw command dumps.

Do not append duplicate identical rows if the profile is already linked and the same observation exists, unless current schema/testing makes dedupe too expensive. Prefer no duplicate rows for idempotent confirm.

### 11. Access Node Handling

Confirm should create or reuse an AccessNode.

Practical v1 behavior:

```text
Use access node info from probe response.
If access_node_uuid is available, reuse by UUID.
If not, derive stable-ish access_node_uuid from sanitized host/provider/os evidence.
If still unavailable, create a deterministic local/current access node identity for tests.
```

Avoid raw host dumps.

### 12. Alias Normalization

Implement helper:

```text
normalize_endpoint_alias(alias: str) -> str
```

Behavior:

```text
trim leading/trailing whitespace
collapse repeated whitespace
casefold/lowercase
reject empty alias
reject control characters
limit length to model constraint
```

Do not over-normalize punctuation.

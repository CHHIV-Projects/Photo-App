## Goal

Implement the first backend-only, read-only Source Identity Probe service.

This milestone should create the application-level probe service and the first Windows non-admin provider:

```text
SourceIdentityProbeService
windows_non_admin_probe_v1
```

The service should accept a probe request, collect safe read-only evidence, normalize the result, classify source-root validity, apply privacy masking, and return a structured probe response.

This is the first implementation step after the 12.63.3 design.

## Background / Context

Milestone `12.63.0` found that current Source Profiles are stored in `ingestion_sources`, and that `ingestion_sources` currently mixes:

```text
user-facing Source Profile
backend source registry
compatibility anchor for Source Intake, iCloud Intake, reports, and provenance
```

Milestone `12.63.1` defined the desired source identity model:

```text
Durable Source Endpoint
  = source type + durable identity evidence + immutable alias + observed path history

Source ID / Source Profile
  = durable endpoint + selected root/folder + intake settings + lifecycle state

Observed Path
  = where the source is reachable at setup or run time
  = not durable identity

Ingestion Source / Source Registry
  = existing compatibility layer used by Source Intake, iCloud Intake, reports, and provenance
```

Milestone `12.63.2` performed Windows evidence reconnaissance and found useful non-admin evidence through:

```text
DriveInfo-style path/drive checks
vol
mountvol
fsutil
pnputil
net use
Test-Path / Get-Item equivalents
```

It also found that several richer APIs were access-denied or unavailable in the current environment:

```text
Get-Volume
Get-Disk
Get-Partition
Get-CimInstance
Get-PnpDevice
Get-SmbMapping
wmic path
```

Milestone `12.63.3` designed the probe service/API contract and recommended this milestone as the first implementation:

```text
12.63.4_source_identity_probe_service_read_only_implementation_prompt.md
```

Expected 12.63.4 implementation posture:

```text

read-only only
no schema writes
no Source Profile creation changes
no Source Intake launch changes
no UI changes
no provenance changes
no iCloud changes
no cleanup changes

```

## Product Decisions Locked for This Milestone

Do not reopen these unless implementation reality proves they are unsafe.

### 1. Source Types

Implement probe-level source types as internal probe schema values:

```text
local
external_device
removable_media
nas
cloud
```

These are probe-level values only.

Do **not** change the existing `ingestion_sources.source_type` model or frontend Source Profile type options in this milestone.

### 2. Source Root Rules

For Local, External Device, and Removable Media:

```text
A Source Root may be a readable volume/media root, such as F:\,
or any readable folder below it.
```

For NAS:

```text
A Source Root must be a share or folder inside a share.

\\HENDERSON-NAS is a NAS server endpoint seed only.
It is not a runnable Source Root.

\\HENDERSON-NAS\<share> may be a runnable share root if readable.
\\HENDERSON-NAS\<share>\<folder> may be a runnable folder root if readable.
```

For Cloud:

```text
Cloud remains provider-specific.
The generic filesystem probe should not try to validate cloud credentials or sessions.
```

### 3. Access Node / Probe Provider

Implement contract support for:

```text
Access Node
Probe Provider
os_family
provider_name
provider_version
provider capabilities
```

Only Windows provider implementation is required now.

Future Linux mini-server and macOS support should be represented by contract hooks only, not implemented.

### 4. Read-Only Behavior

The probe may inspect paths and run safe read-only OS commands.

The probe must not:

```text
write marker files
copy files
delete files
move files
stage files
mount drives
unmount drives
change drive letters
query credential stores for secrets
prompt for credentials
run Source Intake
run iCloud acquisition
run cleanup
write DB rows
```

### 5. Medium Confidence and Run Safety

For this milestone, do not auto-run anything.

But the response should classify `safe_to_run` as:

```text
true
false
needs_review
not_applicable
```

Medium-confidence external/removable matches should generally be:

```text

```

until future endpoint enrollment/repair policy exists.

### 6. Legacy Profiles

Do not change behavior of legacy path-only profiles.

This milestone does not integrate with Source Profile creation or Source Intake launch.

### 7. Raw Diagnostic Evidence

Do not return full raw command output from the service or API.

Return structured, sanitized evidence items only.

## Required Provider Behavior

### Provider Selection

Implement provider selection in the service.

Rules:

```text
If os_family is omitted or unknown, infer from runtime platform.
If runtime platform is Windows, use windows_non_admin_probe_v1.
If os_family is windows, use windows_non_admin_probe_v1.
If os_family is linux or macos, return unsupported_provider for now.
If provider_name is supplied but unsupported, return unsupported_provider.
```

Do not attempt Linux/macOS shell commands.

### Windows Provider Commands / Evidence Sources

The Windows provider may use read-only methods based on 12.63.2.

First-line evidence:

```text
Python stdlib path checks
platform/os information
subprocess calls with timeouts to safe read-only commands:
  vol
  mountvol
  fsutil fsinfo drivetype
  fsutil fsinfo volumeinfo
  pnputil /enum-devices /connected /class DiskDrive
  pnputil /enum-devices /connected /class Volume
  pnputil /enum-devices /connected /class WPD
  pnputil /enum-devices /connected /class USB
  net use
```

For exact NAS paths:

```text
Test existence/readability of the exact requested path only.
Do not enumerate unrelated shares as normal behavior.
Do not run broad share enumeration unless explicitly diagnostic and safe.
```

Implementation caution:

```text
All subprocess execution must use a bounded timeout.
All command inputs derived from observed_path must be validated/sanitized.
Do not pass arbitrary user path text into shell commands unsafely.
Prefer argument lists over shell=True.
Handle command not found, access denied, timeout, and non-zero exit gracefully.
```

### Commands That Must Not Be Required

Do not require these for successful provider operation:

```text
Get-Volume
Get-Disk
Get-Partition
Get-CimInstance
Get-PnpDevice
Get-SmbMapping
wmic path
```

These may be optional future enrichment only. They should not be used in first implementation unless there is a strong reason and tests prove graceful access-denied handling.

### Command Output

Do not return full raw command output.

Parse or summarize into evidence items.

For example:

```text
volume_serial_present = true
volume_guid_present = true
drive_type = removable
pnputil_usb_evidence_present = true
net_use_mapping_present = false
```

instead of raw output.

## Source-Type-Specific Behavior

### Local

For source type `local`:

Valid roots:

```text
C:\
C:\Photos
C:\Users\Chuck\Desktop
```

Classification:

```text
local_volume_root
local_folder
```

Evidence:

```text
host evidence
volume evidence
path evidence
```

Rules:

```text
If path exists and is readable, candidate can be valid.
If path missing, block/unavailable.
C:\ is technically valid but may receive a warning because broad system-drive scans may be noisy.
```

### External Device

For source type `external_device`:

Valid roots:

```text
F:\
F:\Photos
```

Classification:

```text
external_volume_root
external_folder
```

Evidence:

```text
volume evidence
device evidence where available
path evidence
```

Rules:

```text
Drive letter alone is not durable identity.
If volume evidence exists but device join is partial, classify as medium_needs_review.
If path missing or unreadable, block/unavailable.
```

### Removable Media

For source type `removable_media`:

Valid roots:

```text
H:\
H:\DCIM
```

Classification:

```text
removable_media_root
removable_media_folder
```

Evidence:

```text
media evidence if available
volume evidence
reader/device context as supporting evidence
path evidence
```

Rules:

```text
Reader device is not the durable source by itself.
SD/camera cards may produce weak or medium evidence.
Weak/generic evidence should classify as needs_review.
```

### NAS

For source type `nas`:

Valid roots:

```text
\\HENDERSON-NAS\Photos
\\HENDERSON-NAS\Photos\Family Archive
```

Invalid runnable root:

```text
\\HENDERSON-NAS
```

Classification:

```text
nas_server_only
nas_share_root
nas_share_folder
```

Rules:

```text
Server-only UNC path is not a valid Source Root.
Server-only path should return blocker nas_server_not_runnable.
Share path or folder inside share may be valid if readable.
Mapped drive paths are observed paths only; if net use reveals a UNC mapping, include that as network_share_evidence.
Do not store or request NAS credentials.
Do not enumerate unrelated shares during normal probe.
```

### Cloud

For source type `cloud`:

Generic probe behavior:

```text
Return cloud_provider_not_probeable or not_applicable for generic filesystem identity.
Do not probe credentials, sessions, cookies, 2FA, or provider helper state.
Do not change iCloud behavior.
```

The response should explain that cloud sources use provider-specific readiness.

## Implementation Guidance

### Command Runner

Use a command runner abstraction for Windows provider.

Recommended behavior:

```text
timeout per command
capture stdout/stderr
return structured command result
do not raise on non-zero exit by default
sanitize output before conversion to evidence
allow fake command runner in tests
```

Avoid direct subprocess calls scattered across business logic.

### Path Handling

Validate and normalize observed paths.

For Windows:

```text
Detect drive-root style paths such as F:\
Detect folders below drive roots such as F:\Photos
Detect UNC server-only paths such as \\HENDERSON-NAS
Detect UNC share roots such as \\HENDERSON-NAS\Photos
Detect UNC share folders such as \\HENDERSON-NAS\Photos\Family Archive
```

Be careful with escaping in tests and code.

### No Shell Injection

Do not pass arbitrary user path strings into shell commands unsafely.

For commands requiring a drive letter, derive and validate the drive root first.

For NAS exact path checks, use safe filesystem/path APIs where practical.

### Graceful Degradation

The provider should return useful results even when some evidence is unavailable.

Examples:

```text
volume evidence present but PnP unavailable -> medium_needs_review
path exists but identity unavailable -> needs_review or warning
command access denied -> completed_with_warnings, not crash
unsupported OS -> unsupported_provider, not crash
```

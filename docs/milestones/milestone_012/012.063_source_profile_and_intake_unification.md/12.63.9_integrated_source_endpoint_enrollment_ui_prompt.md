## Goal

Integrate Source Endpoint enrollment into the existing **Create Source Profile** workflow on the **Ingestion** page.

The current Ingestion page already has a `Create Source Profile` button and modal with source type-specific fields. This milestone should extend that existing workflow rather than adding a disconnected endpoint-enrollment page or large standalone panel.

The operator should be able to create a Source Profile and, when appropriate, enroll durable source identity as part of that same guided flow.

This milestone should use the backend enrollment endpoints implemented in `12.63.8`:

```text
POST /api/admin/source-endpoints/enrollment/plan
POST /api/admin/source-endpoints/enrollment/confirm
```

The backend currently enrolls an **existing** Source Profile by `source_profile_id`. Therefore, the UI may technically need to:

```text
1. Create the Source Profile.
2. Use the newly created Source Profile id to run enrollment plan.
3. Show the plan result.
4. Confirm enrollment if the operator explicitly approves.
```

But to the operator, this should feel like one integrated Create Source Profile workflow.

## Product Decisions Locked for This Milestone

### 1. Enrollment Belongs in the Existing Create Source Profile Flow

Do not implement endpoint enrollment as the main workflow in a separate panel.

The primary flow should be integrated into the Create Source Profile modal.

A small secondary action for already-created profiles is also allowed:

```text
Source Identity: Not enrolled
[Enroll Identity]
```

But the main new-user flow should be:

```text
Create Source Profile + optional endpoint identity enrollment
```

### 2. Enrollment Is Optional

Do not make endpoint enrollment mandatory.

The operator must still be able to create a Source Profile without enrolling endpoint identity.

Acceptable UI options:

```text
Create Profile
Create Profile and Enroll Source Identity
```

or:

```text
[ ] Enroll durable source identity after creating this profile
```

### 3. Enrollment Is Explicit

The UI must not auto-enroll silently.

The operator must explicitly confirm enrollment after reviewing the plan result.

### 4. Backend Requires Existing Source Profile

The backend confirm flow links an existing `source_profile_id`.

Therefore, for the integrated create workflow, the UI may need to:

```text
create the Source Profile first
then run /source-endpoints/enrollment/plan
then display the plan
then call /source-endpoints/enrollment/confirm after explicit confirmation
```

This is acceptable, but the modal should present it as one guided workflow.

### 5. Do Not Change Source Intake Behavior

Do not run Source Intake after profile creation.

Do not run Source Intake after endpoint enrollment.

Do not change Source Intake buttons or behavior.

Do not make endpoint enrollment a prerequisite for Source Intake.

### 6. Cloud/iCloud Uses Provider-Specific Identity

For `Cloud Export / iCloud`, do not use generic filesystem endpoint enrollment.

The cloud-specific fields should continue to show as they do now.

The generic Source Identity enrollment section should either be hidden or display a note:

```text
Cloud sources use provider-specific identity and staging. Generic filesystem endpoint enrollment is not available for this source type yet.
```

Do not change iCloud behavior.

### 7. Path-Only Profiles Remain Valid

Existing profiles with:

```text
endpoint_id = null
```

remain valid.

The UI may show:

```text
Source Identity: Not enrolled
```

but must not imply that the profile is broken.

### 8. Alias Is Required for New Endpoint

When the backend plan says:

```text
endpoint_action = create_new_endpoint
```

the UI must require an endpoint alias before confirm.

When the backend plan says:

```text
endpoint_action = link_existing_endpoint
```

alias should not be required because the existing endpoint alias is immutable.

### 9. Review Requirements Must Be Acknowledged

If the backend returns review requirements such as:

```text
medium_confidence_requires_review
weak_evidence_requires_manual_confirmation
```

the UI must require explicit review acknowledgment before confirm.

### 10. Blockers Must Block Confirm

If the plan returns blockers or a blocked status, the Confirm Enrollment button must be disabled.

## Desired Integrated Modal Flow

### Step 1 — Fill Out Source Profile Fields

The operator opens the existing Create Source Profile modal and fills current fields.

Examples:

For local:

```text
Source Label
Source Type = Local Folder
Profile Status
Source Root Path
```

For cloud/iCloud:

```text
Source Label
Source Type = Cloud Export / iCloud
Profile Status
Cloud Provider
Acquisition Method
Account Username
Managed Staging Path
```

Do not regress existing modal behavior.

### Step 2 — Show Source Identity Section for Supported Non-Cloud Types

For supported filesystem-backed types, show a Source Identity section.

Example:

```text
Source Identity

[ ] Enroll durable source identity after creating this profile

Endpoint alias
[ Chuck PC Pictures ]

This helps Photo Organizer recognize the same source later even if the drive letter or mount path changes.
```

For unsupported or cloud source types, hide the section or show a short explanatory note.

### Step 3 — Create Profile

When the operator submits:

If enrollment is not selected:

```text
create Source Profile normally
close modal or show existing success behavior
do not call enrollment endpoints
```

If enrollment is selected:

```text
create Source Profile first
retain the new source_profile_id
continue to enrollment plan step
```

Do not run Source Intake.

### Step 4 — Run Enrollment Plan

The UI calls:

```text
POST /api/admin/source-endpoints/enrollment/plan
```

The request should include:

```text
source_profile_id
probe_request built from the newly created or selected Source Profile
proposed_alias, if entered
```

If building a probe request from the selected Source Profile is ambiguous, block the enrollment step with a clear message rather than guessing.

### Step 5 — Display Plan Result

Display plan result in the same modal or immediate follow-up section.

Show:

```text
plan_status
endpoint_action
source_profile_action
endpoint candidate source type
candidate alias suggestions
proposed alias / alias_normalized
filesystem boundary type
observed path
identity confidence
possible matches, if any
required confirmations
blockers
warnings
```

Use readable labels.

Do not dump raw JSON in normal UI.

Advanced details may show:

```text
plan_fingerprint
filesystem_boundary_type
identity_confidence
blocker codes
warning codes
```

### Step 6 — Alias / Existing Endpoint Choice

For new endpoint:

```text
show alias input
pre-fill from alias suggestion or original user entry
require non-empty alias
```

For existing endpoint link:

```text
show selected existing endpoint summary if response includes it
do not require alias
```

If backend returns alias conflict:

```text
disable confirm
show clear alias conflict message
```

### Step 7 — Review Acknowledgment

If required confirmations are present, show checkbox:

```text
I reviewed the warnings and want to enroll this source endpoint.
```

Only enable confirm when checked.

### Step 8 — Confirm Enrollment

The operator clicks:

```text
Confirm Enrollment
```

The UI calls:

```text
POST /api/admin/source-endpoints/enrollment/confirm
```

Confirm request should include:

```text
source_profile_id
original probe_request
plan_fingerprint
confirmed_alias, if creating new endpoint
selected_existing_endpoint_id, if linking existing endpoint
operator_confirmed = true
operator_review_acknowledged = true when required
```

### Step 9 — Result Display

On success, show:

```text
Endpoint enrolled.
Endpoint id, if returned.
Observed path id, if returned.
Created endpoint vs linked existing endpoint.
Source Intake behavior is unchanged.
```

Refresh source profile data if the current UI has a safe way to do that.

On failure, show:

```text
clear error message
blocker/warning codes
safe next action
```

Do not hide backend errors that are needed for operator action, but avoid dumping raw JSON in normal UI.

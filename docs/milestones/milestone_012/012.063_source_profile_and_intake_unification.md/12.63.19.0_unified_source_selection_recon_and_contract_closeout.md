## 5. Current readiness workflow

Generic Source Profile readiness is currently launch-oriented, not selection-oriented.

`SourceProfileReadinessService.check_readiness`:

- loads an `IngestionSource` by ID;
- derives an effective path from `source_root_path`, or iCloud managed staging path;
- maps the profile source type to a probe source type;
- probes that effective path;
- compares the probe fingerprint to the linked endpoint when present;
- returns `ready`, `path_only`, `needs_review`, `blocked`, `provider_specific`, or `unknown`;
- exposes `can_run_source_intake` and `requires_operator_acknowledgment`.

Important current limitation: the service probes the stored effective path. For modern filesystem Sources, Source Selection must instead resolve a current endpoint access path and combine it with `endpoint_relative_root`. A stale stored drive-letter path must not be treated as durable identity.

Important current gap: `_map_source_type` handles local, external, removable, NAS, and cloud/provider-specific cases, but it does not map `optical_media`; current generic readiness treats Optical as unsupported.

## 6. Current identity-verification workflow

Identity verification is implemented through the source identity probe stack and Source Creation plan/confirm path.

Current durable identity evidence:

- Local, External, and Removable use Volume GUID fingerprint evidence.
- NAS uses canonical server/share identity.
- Optical uses `optical_media_fingerprint_v1`, computed from complete metadata-only manifest enumeration.
- iCloud uses provider-specific profile/account/staging checks, not filesystem probing.

Source Creation writes endpoint and observed-path metadata during confirm. Source Selection must reuse the same provider/probe logic in read-only mode and must not call creation confirm, endpoint enrollment confirm, or any repair path.

## 7. Current path-resolution workflow

Current path resolution is split and not yet suitable as a final selection contract.

- `SourceProfileDetail.effective_path` uses `source_root_path` or `managed_staging_path`.
- `verify_source_profile_path` checks existence of that stored effective path only.
- generic readiness probes the same stored effective path.
- Source Intake launch uses `source.source_root_path`; it also has a legacy `backend/storage` fallback that can update `source_root_path` during launch.
- Source Creation can derive endpoint boundary and `endpoint_relative_root`, but that derivation happens from an operator-supplied observed path during creation, not from a stored profile during selection.

Final Source Selection therefore needs a new read-only endpoint-current-path resolver. It should use existing probe/provider logic, but not the stored absolute path as the primary modern filesystem source of truth.

## 8. Current iCloud selection/readiness workflow

iCloud is already provider-specific.

`get_icloud_source_readiness` checks:

- profile type and active status;
- account username presence;
- managed staging path presence;
- approved iCloud exports root;
- managed staging path and source root alignment against expected acquisition path;
- source registration alignment;
- latest matching acquisition and auth error state;
- operation conflicts across acquisition, Source Intake, and cleanup.

This service can be composed behind Select Source, but its output must be normalized to the same selection response shape as filesystem Sources. Select Source must not run acquisition, historical refresh, import, Source Intake, or cleanup.

## 11. Final selector hierarchy

Final Step 2 hierarchy:

```text
Source Type -> Device -> Source -> read-only Source Root -> Select Source
```

No root dropdown should exist. A Source Profile defines exactly one endpoint-relative root or provider-managed scope. Source Root is displayed, not chosen.

Source Type list rule: omit source types with no eligible active Sources.

Device list rule: after Source Type is selected, show only devices/endpoints with at least one eligible active Source of that type.

Source list rule: after Device is selected, show eligible Source Profiles on that device.

## 12. Final eligible-Source rules

Normal selector includes:

- active modern filesystem Sources with endpoint links;
- active iCloud provider Sources;
- active legacy path-only Sources only when strict compatibility checks can make them safe;
- active ambiguous Sources may appear, but selecting them returns `needs_attention` rather than silently hiding them.

Normal selector excludes:

- inactive profiles;
- archived profiles;
- deprecated profiles;
- test profiles;
- validation profiles when represented as inactive or test records;
- endpoints with no eligible active Sources;
- retired endpoints;
- Advanced / Legacy source types unless they are specifically handled as safe active path-only compatibility Sources.

There is no structured `validation` status today. The contract assumes validation Sources are marked inactive or test. Do not add broad label heuristics for validation records without a separate management decision.

## 16. Source Root display contract

- NAS: display canonical UNC root when available;

## 17. Select Source orchestration contract

Select Source must perform one read-only orchestration:

1. Load Source Profile by ID.
2. Verify profile eligibility.
3. Load linked Source Endpoint when present.
4. Derive friendly Source Type.
5. Resolve current endpoint access path for modern filesystem Sources.
6. Combine current endpoint access path with `endpoint_relative_root`.
7. Probe the resolved Source Root or boundary as required.
8. Compare durable identity evidence to the endpoint fingerprint.
9. Verify Source Root readability/existence.
10. Run iCloud provider-specific readiness for iCloud.
11. Normalize result to `available`, `unavailable`, or `needs_attention`.
12. Return a selected-source context and workflow kind.

No Source Intake, iCloud acquisition, iCloud import, cleanup, Source Creation, endpoint enrollment, observed-path persistence, profile mutation, or repair action may occur.

## 18. Readiness-to-selection status mapping

| Current internal state | Selection availability | Notes |
| --- | --- | --- |
| `ready` + identity matched | `available` | Normal success. |
| `path_only` | `available` only under strict active legacy compatibility; otherwise `needs_attention` | No routine acknowledgment. |
| `needs_review` | `needs_attention` | Selection should not depend on operator acknowledgment. |
| `blocked` + unavailable path/media | `unavailable` | Clear retry guidance. |
| `blocked` + ambiguous/conflict/unsupported | `needs_attention` | Management or repair guidance. |
| `provider_specific` iCloud | map through iCloud readiness | Do not show provider_specific to the operator. |
| `unknown` | `needs_attention` | Selection cannot prove availability. |

Current launch-specific `can_run_source_intake` and `requires_operator_acknowledgment` should not be exposed as normal selection fields.

## 19. Local behavior

Identity method: Volume GUID fingerprint.

Selection behavior:

- locate the registered local volume through read-only mounted-volume enumeration or equivalent provider evidence;
- verify fingerprint match;
- combine current volume root with `endpoint_relative_root`;
- verify the resolved Source Root exists and is a directory.

Success result: `available`, workflow kind `filesystem_source_intake`.

Failure examples:

- local volume not found: `unavailable`;
- identity mismatch: `unavailable`;
- root missing on matched volume: `needs_attention` with root-specific guidance.

## 20. External behavior

Identity method: Volume GUID fingerprint.

Selection behavior:

- determine whether the registered external drive is connected;
- find the current drive letter or mount path by identity, not by stored path;
- reconstruct the Source Root with `endpoint_relative_root`;
- verify readability.

Drive-letter changes must not require Source recreation.

Failure examples:

- device disconnected: `unavailable`;
- another device at the old drive letter: `unavailable` identity mismatch;
- matched device but missing root: `needs_attention`.

## 21. Removable behavior

Identity method: Volume GUID fingerprint for the inserted flash drive or memory card volume.

Selection behavior:

- detect the currently inserted matching media by Volume GUID;
- reconstruct root from current drive letter plus `endpoint_relative_root`;
- verify the root.

Failure examples:

- no matching media inserted: `unavailable`;
- wrong media using expected drive letter: `unavailable` identity mismatch;
- matched media but missing folder: `needs_attention`.

## 22. Optical behavior

Identity method: `optical_media_fingerprint_v1` from complete metadata-only manifest.

Selection behavior:

- probe readable physical optical media;
- compute the complete optical fingerprint with the existing 300 second timeout;
- compare with the registered endpoint fingerprint;
- reconstruct root from current optical drive root plus `endpoint_relative_root`;
- verify root exists.

Timeout behavior: return `not_selected` with `availability=needs_attention`, one clear message, retry guidance, and no writes.

Failure examples:

- no disc inserted: `unavailable`;
- wrong disc: `unavailable`;
- fingerprint timeout or incomplete identity: `needs_attention`;
- matched disc but missing subfolder: `needs_attention`.

## 23. NAS behavior

Identity method: canonical NAS server/share identity.

Selection behavior:

- use the registered UNC server/share as durable endpoint boundary;
- combine it with `endpoint_relative_root`;
- verify UNC/root availability;
- do not treat mapped drive letters as durable identity.

Direct readable UNC remains valid. If a mapped drive exists, it may appear in Advanced Details as access evidence but should not replace canonical NAS identity.

Failure examples:

- share unavailable: `unavailable`;
- subfolder missing: `needs_attention`;
- path readable but does not correspond to registered share: `unavailable` or `needs_attention` depending on evidence.

## 24. iCloud behavior

iCloud must differ internally while staying consistent in the UI.

Selection behavior:

- load the iCloud Source Profile;
- verify active profile status;
- verify account username and provider fields;
- run iCloud readiness checks for managed staging path, approved root, path alignment, source registration, auth state, recent acquisition evidence, and operation conflicts;
- return `workflow_kind=icloud_intake` when selectable.

Mapping:

- iCloud readiness `ready`: `available`;
- readiness `warning` with only benign warnings such as no recent acquisition or missing safe staging folder: `available` or `needs_attention` based on whether Step 3 can safely present next actions;
- auth required, session expired, path mismatch, source registration mismatch, approved root blocked, active operation conflict: `needs_attention`.

Selection must not authenticate, acquire, refresh inventory, import, run Source Intake, create staging folders, or clean up files.

## 25. Modern Source Root resolution

Authoritative modern filesystem resolution:

```text
current verified endpoint access path + endpoint_relative_root
```

Rules:

- `endpoint_relative_root = ""` means the whole device/share/medium/disc.
- `endpoint_relative_root = NULL` means legacy or unresolved, not whole endpoint.
- `source_root_path` is compatibility/last-known path for modern Sources; it is not durable identity.
- Source Root is displayed read-only.
- If identity matches but the relative root no longer exists, selection returns `needs_attention`.
- If a path is readable but identity does not match, selection returns `unavailable` and writes nothing.

## 26. Legacy Source compatibility

Active path-only legacy Sources may appear under synthetic Device `Legacy source`.

Strict safe compatibility conditions for `available`:

- profile status is active;
- no endpoint is linked;
- `endpoint_relative_root` is `NULL`;
- stored `source_root_path` exists and is a readable directory;
- generic probe reports a supported source type with no blockers;
- no exact active conflict or management status conflict is known for that same normalized root;
- the profile is not known validation/test/deprecated/archived metadata.

If any condition is not met, selection returns `needs_attention`. It should suggest Create Source or future source management repair, not silently migrate or hide the Source.

Linked legacy Sources with `endpoint_id` present and `endpoint_relative_root = NULL` are not modern whole-endpoint Sources. If root derivation is not deterministic at selection time, return `needs_attention` and defer repair to `SRC-ID-006`.

## 27. Read-only versus metadata-write decision

Final decision: Source Selection must remain read-only.

If selection discovers a new current drive letter, mount path, or optical access path for an existing endpoint, it should return that path ephemerally in `selected_source_context` and Advanced Details.

Observed-path persistence is deferred to Run Ingestion or an existing explicitly authorized metadata-write path. Selection must not create or update `SourceEndpointObservedPath` records.

Rationale: selection is a UI availability decision. Persisting path evidence is useful, but not necessary to tell the operator whether the Source is currently selectable. Keeping selection read-only prevents hidden metadata churn and keeps Step 2 distinct from creation/repair/run actions.

## 30. Proposed API endpoint and schemas

Recommended endpoint:

```text
POST /api/admin/source-selection/select
```

Request:

```json
{
  "source_profile_id": 90
}
```

Response shape:

```json
{
  "result": "selected",
  "availability": "available",
  "workflow_kind": "filesystem_source_intake",
  "selected_source_context": {},
  "message": "External 10 - 2019-03-13 is available.",
  "retry_guidance": null,
  "advanced_details": {}
}
```

Response enum recommendations:

```text
result: selected | not_selected
availability: available | unavailable | needs_attention
workflow_kind: filesystem_source_intake | icloud_intake | null
```

HTTP semantics:

- `200` for normal selected and not-selected business outcomes.
- `404` when the Source Profile ID does not exist.
- `400` for malformed request.
- Avoid `409` for ordinary availability or active-operation conflicts during selection; map those to `needs_attention` unless the request itself cannot be evaluated.

Idempotency: repeat calls with unchanged environment return equivalent results and write nothing.

Timeouts: optical identity timeout returns `result=not_selected`, `availability=needs_attention`, and no writes.

Cancellation: client abort should cancel the request where framework/runtime allows; no cleanup mutation is required because selection is read-only.

## 32. Normal failure UI

Failure preserves the selected dropdown values and shows one actionable reason.

Examples:

- Local: `The registered local volume or Source Root is unavailable.`
- External: `External 10 is not currently connected. Connect the device and select the Source again.`
- Removable: `The inserted removable media does not match this Source. Insert the correct media and try again.`
- Optical: `The registered optical disc is not inserted.`
- NAS: `The NAS share is unavailable. Check the NAS connection and try again.`
- iCloud: `The iCloud session requires attention before this Source can be selected.`
- Legacy: `This legacy Source needs identity review before it can be selected.`

Detailed probe evidence, attempted paths, internal states, and IDs belong in Advanced Details.

## 33. Warning/acknowledgment policy

No routine acknowledgments in Source Selection.

Policy:

- identity match: proceed automatically;
- identity mismatch: fail selection;
- unavailable path/media/share/disc: fail selection;
- wrong removable media or optical disc: fail selection;
- provider session problem: needs attention;
- overlap warnings: do not block ordinary selection of an already-created Source;
- endpoint type mismatch from legacy records: preserve registered identity and put technical details in Advanced Details when safe;
- ambiguous legacy identity: needs attention;
- destructive or run-specific acknowledgment: defer to Step 3.

Do not preserve acknowledgments solely because current readiness or run launch has them.

## 34. Advanced Details policy

Advanced Details may include:

- Source Profile ID and endpoint ID;
- endpoint fingerprint version and confidence tier;
- probe status, evidence categories, warning/blocker codes;
- attempted paths and current resolved endpoint path;
- legacy compatibility reason;
- iCloud readiness raw statuses and blocking codes;
- optical manifest timeout/incomplete identity details;

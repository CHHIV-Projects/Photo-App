## 5. Prior Source Selection contract carried forward

Source Selection is the Step 2 authority. A successful selection returns:

- `workflow_kind="filesystem_source_intake"` for filesystem-like sources.
- `workflow_kind="icloud_intake"` for iCloud sources.
- `selected_source_context`, including selected profile, endpoint, resolved/display root data, identity status, availability, provider context where applicable, and an optional `selection_fingerprint`.

Source Selection is a handoff context, not permanent authorization to run ingestion later.

## 6. Source Selection implementation status

The current implementation lives in:

- `backend/app/services/source_identity/source_selection_service.py`
- `backend/app/services/source_identity/source_selection_schema.py`
- `backend/app/api/admin.py`

The frontend caller is:

- `frontend/src/components/IngestionView.tsx`
- `frontend/src/lib/api.ts`

The API request is intentionally narrow: `SourceSelectionRequest` accepts only `source_profile_id` and forbids extra fields.

## 7. Source Selection runtime limitation relevant to Step 3

Source Selection can resolve a current endpoint path, including changed-drive scenarios, and returns that path ephemerally in the selection context.

The existing filesystem Source Intake launch path does not currently consume that selected/resolved path. It revalidates readiness and then uses the stored `IngestionSource.source_root_path`.

That gap is the main reason Step 3 should not be implemented as a frontend-only call to the existing Source Intake API.

## 14. Backend filesystem execution entry point

The existing filesystem launch service is:

- `backend/app/services/admin/source_intake_execution_service.py`
- function `start_source_intake(...)`

It is exposed by:

- `POST /api/admin/source-intake/run`
- schema `SourceIntakeRunRequest`

It starts the existing ingestion pipeline in a background thread and writes a `SourceIntakeRun` record.

## 15. Backend filesystem readiness enforcement

`start_source_intake(...)` calls `SourceProfileReadinessService.check_readiness(...)` and `_enforce_readiness_for_launch(...)`.

Important status behavior:

- `ready`: allowed.
- `path_only` or `needs_review`: allowed only with required acknowledgment.
- `provider_specific`: blocked with guidance to use iCloud Intake.
- `blocked` or `unknown`: blocked.

This readiness gate should be preserved.

## 16. Backend filesystem path behavior

After readiness enforcement, `start_source_intake(...)` currently resolves:

```text
source.source_root_path
```

It does not accept or derive an authoritative runtime root from `selected_source_context.resolved_source_root`.

For changed-drive or endpoint-relative-root cases, Step 3 needs a narrow backend bridge so execution uses a freshly revalidated root, not a stale stored drive-letter path.

## 17. Backend filesystem pipeline authority

The existing pipeline remains the authority for filesystem ingestion:

- `backend/app/services/ingestion/pipeline_orchestrator.py`

It owns scanning, known-file skipping, Drop Zone staging, Vault writes, database ingestion, provenance, duplicate handling, deferred/unready files, and Drop Zone cleanup.

Step 3 should not duplicate this logic.

## 18. Backend filesystem status, stop, and report behavior

- `get_source_intake_run_status(...)`

## 19. Backend iCloud readiness authority

It checks Source Profile metadata, managed staging path alignment, approved root constraints, authentication state inferred from recent runs, operation conflicts, and source-registration status.

Source Selection delegates iCloud selection decisions to this readiness path.

## 20. Backend iCloud intake authority

It currently covers active iCloud acquisition, source intake, and iCloud cleanup operations.

Step 3 should reuse this guardrail and should not introduce a parallel concurrency model.

## 25. Source Selection handoff fields

The Step 3 frontend needs only the selected result already returned by Source Selection:

- `source_profile_id`
- `source_endpoint_id`
- `source_type`
- `device_label`
- `source_name`
- `resolved_source_root`
- `resolved_endpoint_path`
- `root_display`
- `availability`
- `workflow_kind`
- `provider_context`
- `selection_fingerprint`

The backend must not trust these fields as execution truth without revalidation.

## 26. API request contract for Step 3

The recommended Step 3 run request should be minimal:

- `source_profile_id`
- source-specific run options
- optional `selection_fingerprint`

It should not accept arbitrary client-supplied workflow kind, filesystem path, endpoint identity, durable identifier, provider context, or cloud state.

## 27. Runtime revalidation contract

Immediately before starting any run, the backend should:

1. Load the current Source Profile.
2. Re-run Source Selection or a shared authoritative resolver.
3. Confirm `result="selected"` and `availability="available"`.
4. Confirm `workflow_kind` is still present and supported.
5. Confirm source/profile status is still runnable.
6. Compare the optional `selection_fingerprint` and return a stale-selection response if it changed.
7. Dispatch only according to the backend revalidated workflow kind.

## 28. Stale selection contract

If the selected source changes between Step 2 and Step 3, the backend should block execution and tell the frontend to reselect the Source.

Examples:

- drive removed
- different media inserted
- endpoint identity changed
- profile deactivated
- iCloud auth/readiness changed to blocking
- optional selection fingerprint mismatch

## 29. Filesystem run contract

For `workflow_kind="filesystem_source_intake"`, Step 3 should reuse the existing Source Intake execution service and pipeline.

Required narrow implementation change:

- Provide a safe way for the run service to use the backend-revalidated current source root for modern endpoint-linked sources, or factor Source Intake launch through a shared runtime-root resolver.

This must not bypass readiness acknowledgment, guardrails, pipeline authority, or Source Intake reports.

## 30. iCloud run contract

For `workflow_kind="icloud_intake"`, Step 3 should reuse the current iCloud historical/intake routine.

The selected-source iCloud tile should be driven by `source_profile_id` from Source Selection, not by a second iCloud Source Profile picker.

The tile can expose the existing phases truthfully:

- prepare/refresh inventory when needed
- import/resume when prepared candidates exist
- advance/import chunks using existing service behavior
- show deferred/needs-policy, cleanup, and report status from existing responses

## 31. Source-driven tile: no source selected

When no Source is selected, Step 3 should not display an active Run Ingestion action.

It should show a neutral message: select and verify a Source first.

## 32. Source-driven tile: filesystem selected

When Source Selection returns `filesystem_source_intake`, Step 3 should display a Filesystem Source Intake tile.

Minimum normal controls:

- selected Source summary
- Run Ingestion
- optional total limit
- optional batch size
- required readiness acknowledgment only when backend revalidation says it is needed

## 33. Source-driven tile: iCloud selected

When Source Selection returns `icloud_intake`, Step 3 should display an iCloud Intake tile.

Minimum normal controls:

- selected iCloud Source summary
- current auth/readiness/status
- prepare/import/resume action according to current routine state
- target logical asset count only where the existing service supports it
- deferred/needs-policy summary
- report link/path

## 34. Source-driven tile: unavailable or needs attention

If Source Selection does not return a selected/available source with a workflow kind, Step 3 should not display an active run action.

It should show the reason and the next safe action returned by Source Selection/readiness.

## 35. Selection changed behavior

If the operator changes Source Type, Device, Source, or re-runs Select Source, the Step 3 tile should reset to the latest selected context.

Any stale previous run options should be treated as UI-local only and not as authorization.

## 36. Active run behavior

While a run is active, Source Selection controls should be locked or disabled enough to prevent the displayed selected source from diverging from the active operation.

The operator should be able to stop/cancel through the run tile where existing stop support exists.

## 39. Stop contract: filesystem

Filesystem Source Intake already supports cooperative stop through:

- `POST /api/admin/source-intake/run/stop`
- `request_source_intake_stop(...)`

Step 3 should display that same stop behavior and status.

## 40. Stop contract: iCloud

Current normal iCloud import progress is chunked. Step 3 should preserve existing semantics:

- do not start a new chunk when stopping/paused/interrupted
- allow resume when the existing service reports resume is available
- do not invent cloud deletion or unsafe cleanup behavior

If a precise stop endpoint is missing for a specific iCloud phase, the UI should label the phase truthfully rather than implying instant cancellation.

## 41. Completion contract: filesystem

Filesystem completion should show the existing Source Intake terminal summary and report path.

Completion means the Source Intake run reached a terminal state. It does not mean every file in the source was imported unless the report says source complete.

## 42. Completion contract: iCloud

iCloud completion should distinguish:

- prepare complete
- import chunk complete
- import run complete
- deferred/needs-policy remaining
- cleanup performed or not performed
- local staging status

The UI should not compress these into a misleading single “done” state.

## 43. Error contract

Errors should be mapped from existing service responses and should preserve the next safe action.

Examples:

- source no longer available: reselect source
- stale selection fingerprint: reselect source
- iCloud auth required: re-authenticate outside Photo Organizer
- local staging not clean: complete intake/cleanup recovery first
- readiness acknowledgment required: show explicit acknowledgment
- operation conflict: wait/stop active operation first

## 44. Resume and recovery contract

Step 3 should expose resume/recovery only when the existing backend service reports it is valid.

It should not create a separate resume model.

Relevant existing iCloud support includes:

- `resume_icloud_intake_import(...)`
- `advance_icloud_intake_import(...)`
- cleanup recovery behavior inside the iCloud historical routine service

## 45. Reporting contract

Step 3 should link to or display existing reports rather than create a new reporting format in the first implementation.

Existing report sources:

- Source Intake report JSONs
- iCloud routine/import reports
- iCloud cleanup reports
- iCloud deferred/needs-policy summaries

## 46. Concurrency contract

The first implementation should reuse `protected_ingestion_operation_start(...)` and the existing guardrail snapshot.

Do not allow simultaneous filesystem Source Intake, iCloud acquisition, or iCloud cleanup operations that existing guardrails already classify as conflicting.

iCloud import chunk execution should continue using its existing active-child-operation checks.

## 47. New persistence decision

No new selected-source persistence is recommended.

Reason:

- Source Selection is deliberately read-only and ephemeral.
- Existing run tables already record actual execution.
- A persisted selected-source record would risk becoming stale and would duplicate Source Profile/endpoint/run state.

If implementation later needs auditability, the run record can store a copy of the revalidated context, but that is run evidence, not selection authority.

## 49. Local source contract

Local Source Selection should resolve the source root read-only and Step 3 should revalidate before execution.

For local sources, the existing Source Intake pipeline can be reused directly once the selected-source bridge is in place.

## 50. External drive contract

External drives must be run by durable endpoint identity plus endpoint-relative root, not by a stale stored drive letter.

The selected-source bridge must pass or resolve the current root at execution time.

## 51. Removable media contract

Removable media should behave like external drives with stricter review/acknowledgment when evidence is weaker.

If runtime revalidation returns `needs_review`, Step 3 may proceed only with an explicit acknowledgment and only if the backend allows launch.

## 52. NAS contract

NAS selection uses canonical network/share identity, not mapped-drive letters as durable identity.

The first Step 3 implementation should not claim broad NAS coverage unless it adds focused execution tests for NAS selected-source revalidation and run launch.

## 53. Optical media contract

Optical selection exists, but normal execution should remain blocked for now because the generic readiness/run-launch mapping does not currently classify `optical_media` as runnable.

Optical Source Intake should be a later, explicit implementation/validation item if desired.

## 54. Legacy source contract

Legacy path-only compatibility is acceptable only when Source Selection determines the path is safe and no stronger endpoint match/conflict exists.

Step 3 should show this as a compatibility/needs-review case, not as a durable identity success.

## 56. iCloud tile action model

Current iCloud semantics do not cleanly support one magical one-click “Run Ingestion” that safely coordinates all phases without preserving the prepare/import/resume distinctions.

The normal iCloud tile can still have a primary action, but the label/action should reflect the current state:

- `Prepare Next 1000` when no prepared inventory is available.
- `Import Next 1000` when candidates are prepared.
- `Resume Interrupted Import` when resume is required.
- `Continue Import` or equivalent when advancing chunks.

This keeps the UI simple without lying about the backend state machine.

It should not remain as a competing normal way to bypass Source Selection.

## 59. iCloud acquisition/detail controls recommendation

## 60. Admin/internal controls recommendation

## 61. Option A assessment — frontend tile dispatch to existing APIs

Option A is not sufficient by itself.

It is tempting because existing APIs already run Source Intake and iCloud intake, but it leaves the frontend responsible for workflow choice and cannot safely bridge the changed-drive/resolved-root gap for filesystem sources.

It also makes stale selection handling weaker because the frontend would be dispatching from cached selected context.

## 62. Option B assessment — thin backend dispatch endpoint

Option B is the recommended direction.

The endpoint should:

- accept `source_profile_id`, run options, and optional `selection_fingerprint`;
- re-run Source Selection or a shared resolver;
- decide workflow kind server-side;
- call existing filesystem or iCloud services;
- return normalized launch/status metadata for the tile.

This is the smallest architecture that satisfies safety and operator clarity.

## 63. Option C assessment — separate iCloud orchestration wrapper

Option C is not recommended as the first normal Step 3 solution.

The current iCloud historical/intake routine already has a service model, statuses, resume behavior, chunking, cleanup accounting, and reports.

A new wrapper risks duplicating orchestration that already exists. Use it only later if normal iCloud UX proves impossible to express through the existing routine.

## 64. Selected implementation direction

Implement 12.63.20.1 as a thin selected-source Step 3 integration:

1. Add a backend selected-source run/dispatch path.
2. Revalidate current Source Selection server-side immediately before launch.
3. Reuse the existing filesystem Source Intake service/pipeline with a narrow resolved-root bridge.
4. Reuse existing iCloud historical/intake services.
5. Replace the placeholder with a source-specific tile.
6. Keep legacy/admin controls available outside the normal happy path.

## 65. Why this is the simplest viable architecture

It reuses existing authorities:

- Source Selection for Step 2 availability and workflow classification.
- Source Intake for filesystem ingestion.
- iCloud readiness and historical/intake services for iCloud.
- Existing cleanup, stop, status, and report mechanisms.

It adds only the missing seam: safe selected-source dispatch and runtime revalidation.

## 66. Explicit out-of-scope confirmation

The following are out of scope for the implementation that should follow this closeout:

- broad new workflow framework
- new selected-source persistence table
- duplicate ingestion pipeline
- duplicate iCloud orchestration engine
- cloud deletion
- automatic NAS/Optical broadening without explicit execution validation
- replacing Source Intake as the ingestion authority
- allowing frontend-submitted arbitrary paths or workflow kinds

## 67. Blockers identified

The primary implementation blocker is the filesystem selected-root gap:

- Source Selection can return the current resolved root.
- Existing Source Intake launch uses the stored source root.

This must be corrected with a narrow backend bridge before changed-drive Step 3 execution can be called safe.

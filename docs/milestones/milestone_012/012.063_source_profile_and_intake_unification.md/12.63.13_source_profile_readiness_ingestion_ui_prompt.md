## Goal

Add Source Profile readiness UI to the **Ingestion** page using the backend readiness API implemented in `12.63.12`.

This milestone should add an operator-facing readiness display and manual check action for Source Profiles.

The operator model should remain simple:

```text
Check Readiness
Run Intake
```

Do not create a multi-step readiness wizard.

Do not implement Source Intake run-launch guard yet.

Do not change Source Intake launch behavior yet.

## Product Direction

Readiness UI should help the operator understand:

```text
Is this source usable right now?
Is this source path-only, enrolled, blocked, or provider-specific?
What is the next safe action?
```

It should not turn the Ingestion page into a technical probe console.

The primary UI should show:

```text
compact readiness badge
plain-language operator message
one recommended next action
Check Readiness button
Advanced Details for technical probe/match internals
```

Keep Source Intake controls separate for now.

---

## Product Decisions Locked for This Milestone

### 1. UI Only for Readiness Display and Check

Implement frontend/API-client support for the readiness endpoint.

Do not change backend readiness logic unless a small bug is found.

### 2. No Run-Launch Guard Yet

Do not modify `Run Source Intake` behavior.

Do not add run confirmation acknowledgments yet.

Do not block or allow Source Intake based on the new readiness UI yet.

That belongs to a later milestone.

### 3. Details Drawer Is the Primary Home

Add the readiness UI to the Source Profile details drawer on the Ingestion page.

Do not add expensive readiness polling to every list row.

Do not check readiness automatically for every source profile.

### 4. Manual Check

Add a button such as:

```text
Check Readiness
```

The button should call:

```text
POST /api/admin/source-profiles/{source_id}/check-readiness
```

The result should display in the details drawer.

### 5. Keep It Simple

Avoid a long workflow.

The UI should not require the operator to step through probe internals, endpoint details, warnings, and advanced fields unless they expand Advanced Details.

### 6. iCloud / Cloud Remains Provider-Specific

For `provider_specific` readiness, show clear copy such as:

```text
iCloud readiness is handled by iCloud Intake.
```

Do not add generic readiness to the iCloud workflow.

Do not change iCloud Intake UI or behavior.

### 7. Path-Only Remains Valid

For `path_only`, show that the source can run but durable source identity enrollment is recommended.

Do not imply the source is broken.

Suggested copy:

```text
Path-only source. This can run, but durable source identity enrollment is recommended.
```

### 8. Needs Review Is Not a Hard Block Yet

For `needs_review`, show a warning-style status and message.

Do not add the future run-launch acknowledgment yet.

Suggested copy:

```text
Needs review before relying on durable source identity.
```

### 9. Blocked Means Fix Before Running

For `blocked`, show clear blocker messages and recommended next action.

Do not change the actual Run Intake button behavior in this milestone, but the readiness display should make the condition clear.

## Button Behavior

### Before Check

```text
Status: Unknown
Message: Readiness has not been checked.
Recommended action: Check readiness before running intake.
```

Button:

```text
Check Readiness
```

### During Check

Show loading state:

```text
Checking readiness...
```

Disable repeated clicks while request is in flight.

### After Success

Display returned readiness result.

Allow the operator to click again to refresh readiness.

Button label may become:

```text
Recheck Readiness
```

### After Error

Show a clear error message.

Do not leave the UI stuck in loading state.

Do not hide the existing Source Profile details.

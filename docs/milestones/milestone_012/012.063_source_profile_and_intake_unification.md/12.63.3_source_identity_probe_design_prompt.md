## Goal

Design the app-level read-only Source Identity Probe service and API contract.

This milestone should define how Photo Organizer will eventually probe a user-selected source path, normalize OS-specific identity evidence, classify confidence, redact sensitive values, and return a safe result for future Source Profile enrollment and readiness checks.

This is a design-only milestone.

Do not implement the probe service.  
Do not edit code, schema, UI, tests, migrations, runtime data, Source Intake behavior, iCloud behavior, cleanup behavior, or provenance behavior.

The output should be a closeout that can directly guide a future implementation milestone.

## Background / Context

Milestone `12.63.0` found that current Source Profiles are stored in `ingestion_sources`, and that `ingestion_sources` currently mixes:

```text
user-facing Source Profile
backend source registry
compatibility anchor for Source Intake, iCloud Intake, reports, and provenance
```

Milestone `12.63.1` defined the desired identity model:

```text
Durable Source Endpoint
  = source type + durable identity evidence + immutable alias + observed path history

Source ID / Source Profile
  = durable endpoint + selected root/folder + intake settings + lifecycle state

Observed Path
  = where the source is reachable at setup or run time
  = not durable identity

Ingestion Source / Source Registry
  = existing compatibility layer used by Source Intake, iCloud Intake, reports, and provenance
```

Milestone `12.63.2` performed Windows read-only reconnaissance and found:

```text
- Useful non-admin Windows evidence is available through:
  DriveInfo, vol, mountvol, fsutil, pnputil, net use, Test-Path / Get-Item.

- Several richer Windows APIs were access-denied in the current shell:
  Get-Volume, Get-Disk, Get-Partition, Get-CimInstance, Get-PnpDevice, Get-SmbMapping.

- External device identity appears feasible at medium confidence using volume identity plus PnP evidence.

- Removable media identity is weaker, especially for SD cards and untested optical media.

- NAS server \\HENDERSON-NAS was observable, but shares were not listable due to access denied.
  The NAS server alone is not a runnable Source Root.
  A NAS Source Root requires a share or folder inside a share, such as \\HENDERSON-NAS\Photos.

- Cloud should remain provider-specific and should not be reduced to filesystem probing.
```

This milestone should turn those findings into a precise app-level design.

## Product Decisions Already Locked

Do not reopen these unless code reality or safety concerns make them impossible.

### 1. Source Types

Use this v1 source type model:

```text
Local
External Device
Removable Media
NAS
Cloud
```

Definitions:

```text
Local
= folder/path on the current computer.

External Device
= physically connected storage whose device/volume is the durable source identity,
such as external HDD, external SSD, or thumb drive.

Removable Media
= inserted media where the media/session/content identity is durable,
not the reader device. Examples include CD, DVD, Blu-ray, SD/camera card when Windows evidence treats it as inserted media, or similar removable media.

NAS
= networked storage/share, such as a Synology SMB share or other network share.

Cloud
= provider-backed source. iCloud exists now; OneDrive, Google Drive, Dropbox, or others may come later.
```

### 2. Source Roots

For Local, External Device, and Removable Media:

```text
The Source Root may be the whole readable volume root, such as F:\,
or any folder below it.
```

Examples:

```text
Local:
C:\Photos

External Device:
F:\

External Device:
F:\Photos

Removable Media:
H:\

Removable Media:
H:\DCIM
```

For NAS:

```text
The Source Root must be a share or folder inside a share.
The NAS server alone is not a runnable Source Root.
```

Valid NAS examples:

```text
\\HENDERSON-NAS\Photos
\\HENDERSON-NAS\Photos\Family Archive
```

Not a runnable NAS Source Root:

```text
\\HENDERSON-NAS
```

For Cloud:

```text
Cloud remains provider-specific.
Do not force cloud into the same filesystem probe model as local/external/removable/NAS.
```

### 3. Access Node and OS Provider

The source identity architecture must be source-agnostic but access-node-aware.

Define and use this concept:

```text
Access Node
= the computer/environment performing the source probe and intake run.
```

Examples:

```text
Chuck Windows PC
Future Linux mini-server
Future Mac
```

Define and use this concept:

```text
Probe Provider
= the OS-specific implementation used by an Access Node to gather source evidence.
```

Examples:

```text
windows_non_admin_probe_v1
future_linux_probe_v1
future_macos_probe_v1
```

Product rule:

```text
The first implemented probe provider may be Windows-only, but the probe service contract must be OS-provider-based so future Linux mini-server or macOS providers can be added without redesigning Source Profiles, Source Endpoints, provenance, readiness, or Source Intake.
```

### 4. Durable Source Identity vs Observed Path

A durable source is not the drive letter or mount path.

Examples:

```text
Same external drive on Windows:
F:\

Same external drive on future Linux mini-server:
/media/chuck/ChuckExternalDrive

Same NAS share on Windows:
\\HENDERSON-NAS\Photos

Same NAS share on Linux:
/mnt/henderson-nas/photos
```

The model should be:

```text
Durable Source Endpoint
= what source is this?

Access Node
= what machine is trying to access it?

Observed Path
= where that source appears from that machine right now?

Probe Provider
= how that operating system verifies the source identity?
```

### 5. Provenance

Do not redesign provenance.

Provenance remains source/path/run based.

The future change is additive:

```text
add durable endpoint/source identity linkage
add observed path/run evidence where useful
do not casually rewrite historical provenance
```

### 6. Current Compatibility Layer

Do not replace `ingestion_sources` yet.

For now, assume:

```text
ingestion_sources.id remains the current operational Source ID / Source Profile ID.
```

Future endpoint identity should be added beside it, not in place of it.

### 7. Non-Cloud Intake Workflow

For Local / External Device / Removable Media / NAS, preserve the intended v1 workflow:

```text
Check Readiness
Run Intake
Show Result
```

Do not introduce mandatory iCloud-style Prepare / Import for non-cloud sources.

### 8. Cloud Boundary

Do not change iCloud.

Do not probe cloud credentials, sessions, cookies, 2FA, or provider helpers.

Cloud remains provider-specific.

### 10. Source-Type-Specific Probe Behavior

Design how the probe response should differ by source type.

For Local:

```text

```

For External Device:

```text

```

For Removable Media:

```text

```

For NAS:



### 11. NAS Design Detail

The NAS part must explicitly reflect this product rule:

```text
\\HENDERSON-NAS is a NAS server endpoint seed.

A runnable NAS Source Root must be a share or folder inside a share:
\\HENDERSON-NAS\<share>
\\HENDERSON-NAS\<share>\<folder>
```


### 12. Source Root Classification

```text

External Device:

Removable Media:
Media root or folder is valid if readable and media identity is present enough.

NAS:
Share root or folder inside share is valid if readable.
Server-only path is not valid.

Cloud:
Provider-specific.
```

The response should include:


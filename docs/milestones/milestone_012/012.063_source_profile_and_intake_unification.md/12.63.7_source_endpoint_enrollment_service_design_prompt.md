## Goal

Design the future Source Endpoint Enrollment service.

This milestone should define how Photo Organizer will convert a read-only Source Identity Probe result into a durable Source Endpoint and link that endpoint to an operational Source Profile / `ingestion_sources` row.

This is a design-only milestone.

Do not implement endpoint enrollment.

Do not add write APIs.

Do not change Source Profile creation behavior.

Do not change Source Intake run-launch behavior.

Do not change readiness behavior.

Do not change frontend UI.

Do not write endpoint rows.

Do not write observed path rows.

Do not backfill existing profiles.

The output should be a closeout that can directly guide a future implementation milestone.

## Background / Context

Milestone `12.63.0` found that current Source Profiles are stored in `ingestion_sources`, and that `ingestion_sources` currently mixes:

```text
user-facing Source Profile
backend source registry
compatibility anchor for Source Intake, iCloud Intake, reports, and provenance
```

Milestone `12.63.1` defined the durable source identity model:

```text
Durable Source Endpoint
  = source type + durable identity evidence + immutable alias + observed path history

Source ID / Source Profile
  = durable endpoint + selected root/folder + intake settings + lifecycle state

Observed Path
  = where the source is reachable from a specific Access Node at setup or run time
  = not durable identity

Ingestion Source / Source Registry
  = existing compatibility layer used by Source Intake, iCloud Intake, reports, and provenance
```

Milestone `12.63.3` designed the Source Identity Probe service contract.

Milestone `12.63.4` implemented the backend read-only probe service/API.

Milestone `12.63.5` validated the read-only service/API against real current paths. It confirmed that:

```text
\\HENDERSON-NAS\Photos\Camera imports
```

is readable from the user's normal project terminal context and that access depends on the runtime process/access context.

Milestone `12.63.6` added the additive schema foundation:

```text

source_endpoints
source_endpoint_observed_paths
ingestion_sources.endpoint_id nullable link
ensure_source_endpoint_schema(db_session)
```

`12.63.6` intentionally did not implement enrollment, readiness integration, Source Profile behavior changes, Source Intake changes, probe persistence, frontend changes, or data backfill.

The recommended next milestone from `12.63.6` was:

## Product Decisions Already Locked

Use these as design assumptions unless implementation reality makes them unsafe.

### 1. Enrollment Must Be Explicit

Endpoint enrollment should happen only after an operator confirms it.

Do not design silent auto-enrollment from probe results.

A probe result can produce an endpoint candidate, but it should not automatically create endpoint/profile rows without explicit confirmation.

### 2. `ingestion_sources` Remains Operational Source Profile

Current `ingestion_sources.id` remains the operational Source ID / Source Profile ID.

Enrollment may eventually populate:

```text
ingestion_sources.endpoint_id
```

but should not replace or rename `ingestion_sources`.

Existing path-only profiles must remain valid.

### 3. Endpoint Alias Is Immutable for v1

Endpoint alias should be chosen carefully at enrollment time.

For v1:

```text
Endpoint alias is immutable.
Endpoint alias_normalized should remain unique.
Alias repair/rename is a future explicit workflow.
```

Do not design casual alias editing.

### 4. Auto-Match Requires Strong Evidence

Only strong evidence should auto-match an existing endpoint.

Medium-confidence evidence should require operator review.

Weak evidence should require manual confirmation or block, depending on flow.

### 5. Medium-Confidence Runs Should Not Auto-Run Yet

Endpoint enrollment design may allow a reviewed endpoint to be created from medium-confidence evidence, but future run-launch policy should remain conservative.

Do not design automatic Source Intake run launch from medium-confidence evidence.

### 6. NAS Identity Needs Both Operational Path and Safe Evidence

For NAS, the app may need to store raw operational source root path where required to run.

But identity evidence should be masked/hashed/sanitized where possible.

Design should distinguish:

```text
operational path needed for access
display alias
matching fingerprint/evidence
observed path history
sanitized evidence summaries
```

### 7. Access Context Matters

A path can be readable in one process/access context and blocked in another.

Design enrollment and readiness around this rule:

```text
The Access Node / runtime process that will perform future intake must be able to read the exact source root.
```

### 8. Cloud Is Provider-Specific

Do not force cloud enrollment through the same generic filesystem model.

iCloud and future cloud providers may create or link endpoints through provider-specific identity/readiness flows.

### 2. Enrollment Flow Types

Design the major future flows.

At minimum include:

#### A. New Source Profile + New Endpoint

Example:

```text
Operator selects E:\Photos
Probe returns endpoint candidate
Operator chooses alias
System creates SourceEndpoint
System creates or links ingestion_sources row
System records observed path
```

#### B. Existing Path-Only Source Profile + New Endpoint

Example:

```text
Existing ingestion_sources row has source_root_path but endpoint_id is null
Operator checks readiness/probe
Operator confirms enrollment
System creates endpoint
System links ingestion_sources.endpoint_id
System records observed path
```

#### C. Existing Source Profile + Existing Endpoint

Example:

```text
Probe evidence strongly matches existing endpoint
Operator confirms linking
System links ingestion_sources.endpoint_id
System records observed path
```

#### D. Probe Matches Existing Endpoint but Different Source Root

Example:

```text
Same external drive or NAS share
Different selected root/folder
May be valid as a separate Source Profile under same endpoint
```

Design how endpoint vs Source Profile root should be separated.

#### E. Duplicate / Ambiguous Endpoint Candidate

Example:

```text
Probe evidence could match more than one endpoint
System must require review and avoid automatic linking
```

#### F. Enrollment Canceled

Design what happens if the operator cancels before confirmation.

Expected:

```text
No endpoint row.
No Source Profile link.
No observed path row.
No partial enrollment.
```

### 4. Alias Design

Include:

```text

```

Do not over-engineer alias normalization; recommend a practical v1 approach.

### 5. Source Root vs Endpoint Identity

Design exactly where source root belongs.

Clarify:

```text
SourceEndpoint = durable device/share/cloud identity
ingestion_sources = operational Source Profile and selected root/folder/settings
SourceEndpointObservedPath = where endpoint/source root was observed from an Access Node
```

Examples:

External drive:

```text
Endpoint = physical external drive / volume identity
Source Profile root = F:\Photos or endpoint-relative \Photos
Observed path = F:\Photos from Chuck Windows PC
```

NAS:

```text
Endpoint = NAS server/share identity, possibly with selected folder depending design choice
Source Profile root = \\HENDERSON-NAS\Photos\Camera imports
Observed path = \\HENDERSON-NAS\Photos\Camera imports from Chuck Windows PC
```

Design whether a NAS endpoint should represent:

```text
server
server + share
server + share + folder
```

Recommended default:

```text
NAS endpoint should generally represent server + share.
Source Profile should represent selected folder/root within that share.
Observed path should record the exact UNC folder used by the access node.
```

But evaluate whether current schema supports that cleanly.

### 6. NAS Storage / Privacy Design

Resolve or recommend the NAS storage approach.

Design should answer:

```text
What raw NAS values must be stored to run?
What hashed/masked values should be stored for identity matching?
What appears in normal UI?
What appears in Advanced Details?
What belongs in evidence_summary_json?
What should never be stored?
```

Recommended posture to evaluate:

```text
Store operational NAS root path in ingestion_sources.source_root_path because it is needed to run.
Store endpoint alias raw because it is user-facing.
Store endpoint identity evidence as sanitized summary + hash/fingerprint.
Store observed path raw only where operationally necessary.
Mask/share-hash details in evidence summaries.
Never store credentials.
```

Design how this should work for:

```text
\\HENDERSON-NAS\Photos
\\HENDERSON-NAS\Photos\Camera imports
mapped drive paths
future Linux NAS mount path
```

### 8. Duplicate / Existing Endpoint Detection

Design endpoint matching behavior.

For each source type, define:

```text
strong match
medium possible match
weak/manual match
mismatch
ambiguous match
```

Examples:

```text
same fingerprint hash = strong candidate
same alias_normalized = alias conflict
same NAS server/share hash = possible same endpoint
same volume serial but missing device evidence = medium
same observed path only = weak, not durable
```

Design what the enrollment service should do:

```text
auto-select existing endpoint
show possible existing endpoints
block ambiguous linking
allow operator to create new endpoint despite possible match, if safe
require explicit confirmation
```

Be conservative.

### 9. Transaction / Rollback Design

Design transaction boundaries.

Answer:

```text
Should endpoint creation and ingestion_sources endpoint linking happen in one transaction?
What rows are created together?
What happens if alias conflict occurs?
What happens if Source Profile creation fails?
What happens if observed path insert fails?
What happens if user cancels?
How do we avoid orphan endpoints?
How do we avoid partially linked profiles?
```

Recommended principle:

```text
When an operator confirms enrollment that creates an endpoint and links a Source Profile, those writes should be atomic.
```

Design whether observed path insertion is inside the same transaction or can be retried separately.

### 10. Existing Source Profile Compatibility

Design how existing path-only profiles behave.

Rules:

```text
Existing profiles remain valid with endpoint_id = null.
No automatic backfill.
No mandatory enrollment in this milestone.
No Source Intake blocking merely because endpoint_id is null.
```

Future UI/readiness may warn:

```text
Path-only profile; source identity not enrolled.
```

Design how the future enrollment flow should link them safely.

### 14. Observed Path Recording Design

Design how observed path records should be created later.

Use existing table:

```text

```

Design when to write:

```text

on successful future readiness check
on successful future run-launch verification
on meaningful state change
```

Avoid noise:

```text

Use update/current-state plus event/history pattern if needed later.
```

The design should recommend whether this table is current-state, history, or hybrid.

Given current schema includes `first_seen_at`, `last_seen_at`, and `last_success_at`, likely design:

```text
one row per endpoint + access node + normalized observed path + source root candidate, updated over time
future separate event history only if needed
```

But evaluate and recommend.

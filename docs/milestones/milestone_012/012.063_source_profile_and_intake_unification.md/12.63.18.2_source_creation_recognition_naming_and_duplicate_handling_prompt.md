# 1. Goal

Finish the normal Source Creation interaction for Local, External, and NAS sources.

This milestone is limited to:

- the static Create a Source panel;
- path-first device recognition;
- safe Device Name handling;
- endpoint type mismatch handling;
- exact-root duplicate prevention;
- existing Source reuse, reactivation, or legacy adoption;
- safe endpoint rename support, subject to a required impact analysis.

Do not redesign Source Selection.

Do not change readiness, Source Intake, iCloud Intake, provenance, Vault behavior, cleanup, or runtime drive-letter resolution.

Milestone 12.63.18.1 established the intended durable model:

Source = Durable Endpoint Identity + Endpoint-Relative Root

This milestone must make the operator-facing creation flow use that model correctly.

# 2. Current Defects to Correct

The 12.63.18.1 implementation correctly added:

- endpoint-relative-root persistence;
- full Volume GUID fingerprinting;
- atomic source creation;
- existing endpoint reuse;
- whole-device/share semantics.

However, manual use exposed two defects.

## 2.1 Silent Device Name substitution

The operator entered a new Device Name, but the recognized endpoint already had the leftover validation alias:

TEST 12.63.18 Local Valid

The application silently reused that alias and completed creation.

The operator was not given a clear choice to:

- reuse the existing name;
- rename the recognized device;
- cancel.

That behavior must be corrected.

## 2.2 Exact-root legacy duplicate

An active, unlinked legacy Source already existed for:

C:\Users\chhen\OneDrive\Desktop\Exif provanace

The new creation service searched only Sources already linked to the recognized endpoint. It did not detect the existing unlinked legacy Source with the same normalized root.

It created a second active Source Profile for the same exact root.

That behavior must be corrected.

# 5. Exact Non-iCloud Operator Flow

## Step 1 — Choose Source Type

Choices:

- Local
- External
- NAS
- iCloud
- Removable — coming later

Local, External, and NAS use the filesystem recognition flow.

iCloud uses its current provider-specific controls.

Removable remains disabled in this milestone.

## Step 2 — Enter Root Path or Mount Point

Examples:

Local:

C:\Users\chhen\Pictures

External:

E:\Photos

Entire External device:

E:\

NAS folder:

\\HENDERSON-NAS\Photos\Family

Entire NAS share:

\\HENDERSON-NAS\Photos

The operator supplies the full currently accessible location once.

## Step 3 — Identify Location

Provide a deliberate button such as:

Identify Location

Do not probe on every keystroke.

When pressed, perform a focused, read-only probe of the entered path.

Do not broadly scan unrelated PC drives or network resources.

The probe must determine:

- whether the path is readable;
- actual technical source type;
- durable endpoint identity;
- endpoint boundary;
- endpoint-relative root;
- current observed path;
- whether the endpoint is already registered;
- whether the exact Source already exists;
- whether a legacy unlinked Source exists at the same normalized full root;
- whether other Sources overlap this root.

No database writes occur during identification.

## Step 4 — Show Recognition Result

Show one of these clear states:

- New device identified
- Existing device recognized
- Existing device recognized with a different stored type
- Existing exact Source found
- Existing inactive Source found
- Existing unlinked legacy Source found
- Multiple conflicting Source matches
- Device identity needs review
- Location blocked or unreadable

The recognition result must be visible before any creation or rename occurs.

## Step 5 — Resolve Device Name

### New endpoint

Show:

Device Name

as free-form user input.

The name is required before creation.

### Existing recognized endpoint

Show:

Recognized Device:
<existing endpoint alias>

Then provide explicit choices:

- Use Existing Name
- Rename Device
- Cancel

Do not silently replace newly entered text with the existing alias.

Do not create a second endpoint merely because the operator prefers another name.

### Rename Device

When Rename Device is selected:

- show an editable text field prefilled with the existing alias;
- require a non-empty replacement name;
- show that the durable identity will not change;
- require explicit confirmation as part of the final action.

Suggested copy:

Renaming changes the display name for this recognized device. Its durable identity, Sources, roots, and history will not change.

# 6. Required Rename Impact Analysis

Before implementing endpoint rename, perform a focused code and schema investigation.

Inspect every use of:

- SourceEndpoint.alias;
- Source Profile label;
- Source Profile summaries;
- Source selectors and dropdowns;
- readiness result displays;
- Source Intake request construction;
- intake reports;
- run-history displays;
- provenance fields and snapshots;
- audit/event logs;
- search and filtering;
- API response schemas;
- any uniqueness constraints involving aliases.

Document findings before modifying rename behavior.

## Expected identity rule

The intended rule is:

Endpoint alias = mutable display metadata

Stable endpoint identity = endpoint record + durable fingerprint

Renaming must not change:

- endpoint ID;
- Volume GUID fingerprint;
- NAS fingerprint;
- Source Profile IDs;
- endpoint-relative roots;
- observed paths;
- active/inactive status;
- ingestion runs;
- assets;
- Vault files;
- historical provenance;
- acquisition or intake behavior.

## Historical data

Do not rewrite historical provenance or historical run reports merely because the current endpoint alias changes.

Historical records may retain the Device Name recorded when the event occurred.

## Current Source labels

Determine whether current Source labels are:

- dynamically derived from endpoint alias and relative root; or
- persisted copies.

If labels are dynamically derived, current displays should naturally use the renamed endpoint alias.

If labels are persisted, update current Source display labels only when the investigation proves that:

- they are current mutable display metadata;
- no identity or historical semantics depend on them;
- the update can be narrow, transactional, and audited.

If this cannot be proven safely, stop and ask before implementing profile-label changes. The endpoint alias may still be renamed, but do not perform an unbounded downstream rewrite.

## Audit

A successful rename must record at least:

- endpoint ID;
- old alias;
- new alias;
- timestamp;
- action source or operator context where supported.

Use the existing audit/event pattern if one exists.

Do not build a broad new audit framework solely for this milestone.

# 7. Source Type Recognition and Mismatch

The selected Source Type is an operator expectation.

The probe determines the technical path/device reality.

Examples:

- UNC path is NAS.
- Mapped drive resolving to UNC is NAS.
- Local Windows drive path may be Local or External based on the registered endpoint/category and available evidence.

## Existing recognized endpoint

When an endpoint already exists, retain its stored Source Type by default.

If the operator selected a different type, show:

This device is already registered as <existing type>.

Provide:

- Continue Using <existing type>
- Cancel

The UI may switch the selected type to the recognized existing type after confirmation.

## Optional type reclassification

Perform a short impact review of changing an existing endpoint’s Source Type.

If Source Type is clearly only mutable display/grouping metadata and changing it has no identity, routing, readiness, intake, or provenance consequence, an explicit Change Category option may be implemented.

If changing type affects or may affect:

- provider routing;
- endpoint matching;
- readiness;
- intake behavior;
- API dispatch;
- provenance meaning;
- migration logic;
- persisted Source Profile types;

then defer actual reclassification.

Do not let deferred type reclassification block the rest of this milestone.

Document the result in the closeout.

The default safe behavior is:

- retain the recognized endpoint’s existing type;
- explain the mismatch;
- continue or cancel.

# 8. Duplicate and Existing-Source Detection

Identification must search across both modern and legacy Source Profiles.

## 8.1 Modern exact match

Match using:

- durable endpoint identity;
- endpoint-relative root.

The empty endpoint-relative root means the entire device/share.

## 8.2 Legacy exact-path match

Also search Source Profiles that:

- have no endpoint link; or
- have `endpoint_relative_root = NULL`;

using normalized full root-path equality.

Path matching must use the project’s existing safe normalization rules.

Do not use loose substring matching.

## 8.3 Required result classifications

### Exact active Source exists

Do not create another Source.

Show:

This Source already exists.

Provide:

- Use Existing Source
- Cancel

Returning the existing Source must be idempotent and create no rows.

### Exact inactive Source exists

Do not create another Source.

Show:

This Source already exists but is inactive.

Provide:

- Reactivate Existing Source
- Keep Inactive / Cancel

Reactivation should update only the existing Source’s active status and any safe required endpoint linkage.

### Exactly one unlinked legacy Source exists

Do not create a duplicate.

Show:

An existing legacy Source was found for this exact location.

Provide:

- Adopt and Link Existing Source
- Cancel

Adoption must:

- retain the existing Source Profile ID;
- link it to the verified endpoint;
- populate endpoint-relative root only when deterministically derived;
- preserve the original source root;
- preserve ingestion/provenance relationships;
- avoid creating a second Source.

Adoption must be transactional.

If the legacy Source has prior ingestion history, do not rewrite historical provenance.

### Multiple exact Sources exist

Block automatic creation.

Show:

Multiple existing Sources match this exact location. Review is required before continuing.

Do not silently choose one.

### Same endpoint, different root

Allow creation of a new Source.

### Overlapping but non-identical roots

Show a non-blocking overlap warning.

Do not classify ordinary parent/child overlap as an exact duplicate.

# 10. Transactional Requirements

The existing plan/confirm architecture should remain the basis of this workflow.

Extend it rather than creating a competing creation path.

The plan operation remains read-only.

The confirm operation must recompute and validate the plan fingerprint.

Where applicable, confirm must perform these actions in one transaction:

- create or reuse endpoint;
- rename endpoint;
- create Source;
- reactivate Source;
- adopt/link legacy Source;
- populate deterministic endpoint-relative root;
- write observed-path evidence;
- write narrow audit information.

Any failure must roll back all changes from that confirmation.

No partial rename, link, reactivation, or Source creation is acceptable.

# 12. Whole Device and Whole Share

Preserve 12.63.18.1 semantics:

- empty string = intentionally entire device/share;
- `NULL` = legacy, unknown, or unresolved;
- non-empty value = endpoint-relative folder.

Examples:

External whole device:

E:\

Endpoint-relative root:

""

NAS whole share:

\\HENDERSON-NAS\Photos

Endpoint-relative root:

""

Exact duplicate detection must distinguish:

- empty string;
- `NULL`;
- non-empty relative root.

A deterministic legacy whole-device/share match may be adopted only when the endpoint boundary and full normalized path prove the equivalence.

# 19. Stop Conditions

Stop and ask before proceeding if:

- endpoint alias is used as durable identity;
- renaming requires rewriting historical provenance;
- renaming requires a broad migration;
- profile-label updates have uncertain identity or historical effects;
- legacy adoption cannot preserve the original Source Profile ID;
- exact-root matching cannot distinguish legitimate roots safely;
- Source Type reclassification affects routing or ingestion and cannot be safely isolated;
- the implementation requires changing Source Intake or readiness;
- the plan/confirm transaction cannot atomically protect rename/adoption/reactivation.

Actual Source Type reclassification may be deferred without stopping the rest of the milestone.

# 1. Goal

Enable Source Creation for removable filesystem media:

- USB thumb drives
- USB flash drives
- SD cards
- microSD cards mounted through an adapter or card reader

Reuse the existing durable Source Endpoint, Source Profile, Observed Path, and Source Creation plan/confirm architecture.

The inserted flash drive or memory card is the durable endpoint.

The following are not identity:

- drive letter
- USB port
- card-reader hardware
- computer
- current mount point
- operator-entered Media Name
- operator-entered Source Name

Optical media is explicitly excluded and will be handled in a separate milestone.

# 5. Durable Identity Model

## 5.1 Endpoint identity

For USB flash and SD media, durable identity must use the full Windows Volume GUID through the existing v2 identity process.

The normal UI should show:

- Durable Identity: `Verified`
- Identifier Type: `Volume GUID`
- Identifier: the existing safe masked identifier

The full Volume GUID may be used in memory to compute the durable identity fingerprint.

Do not expose the full sensitive/raw identifier in the normal UI or logs.

## 5.2 Identity belongs to the mounted medium

The endpoint represents the mounted flash volume or memory-card volume.

Required semantics:

- Same USB flash drive in another USB port:
  same endpoint.
- Same USB flash drive with a different drive letter:
  same endpoint.
- Same SD card placed into another card reader:
  same endpoint when Windows reports the same Volume GUID.
- Different SD card in the same reader:
  different endpoint.
- Different flash drive using the same drive letter later:
  different endpoint.
- Reformatting media may produce a new Volume GUID:
  treating it as a new endpoint is acceptable.
- Volume label changes:
  identity remains unchanged when Volume GUID remains unchanged.
- Media Name changes:
  identity remains unchanged.
- Source Name changes:
  identity remains unchanged.

## 5.3 Volume-level limitation

For this milestone, identity is volume-level rather than physical-device-level.

If one physical removable device contains multiple mounted filesystem volumes, each mounted Volume GUID may be treated as a separate Source Endpoint.

Document this limitation clearly in the closeout.

Do not add physical-device merging or serial-number identity in this milestone.

# 6. Classification and Safety Rules

Automatic removable-media classification is not always perfectly reliable on Windows.

Some USB flash devices may report themselves as fixed disks.

Do not use unreliable heuristics such as:

- storage capacity
- volume label
- folder names
- drive-letter range
- manufacturer text alone

## 6.1 Operator-selected category

`Removable` is an explicit operator-selected source category.

The probe must still verify that the selected path points to a safe local mounted filesystem volume.

## 6.2 Required evidence

A new Removable endpoint may proceed when:

- the path resolves to a local mounted filesystem volume;
- a full Volume GUID is available;
- the volume is not a network/UNC path;
- the volume is not an optical drive;
- the volume is not the active Windows system volume;
- the probe does not reliably identify it as an HDD or SSD;
- evidence supports removable, USB flash, SD, memory-card, or equivalent media; or
- evidence is ambiguous but safely compatible with removable media and the operator explicitly acknowledges the ambiguity.

Reuse the existing needs-review or mismatch-acknowledgment mechanism where practical.

Do not invent an unrelated second acknowledgment framework.

## 6.3 Reliable mismatch

When reliable evidence identifies the medium as a USB HDD or USB SSD:

- do not create a new Removable endpoint;
- explain that the location appears to be External storage;
- direct the operator to choose `External`.

When reliable evidence identifies an internal/system disk:

- block Removable creation;
- direct the operator to choose `Local`.

## 6.4 Ambiguous USB evidence

When the path is:

- local;
- non-optical;
- non-network;
- not the system volume;
- backed by a full Volume GUID;
- connected through USB or a card-reader-style interface;
- but Windows reports ambiguous fixed/removable evidence;

allow a needs-review plan with explicit operator acknowledgment.

The warning should explain:

    Windows could not conclusively classify this medium.
    Continue only if this is a USB flash drive or memory card.
    USB HDDs and SSDs should be registered as External.

## 6.5 Existing endpoint takes precedence

If the Volume GUID already matches an existing endpoint:

- reuse the existing endpoint;
- do not create another endpoint under Removable;
- retain the endpoint’s registered Source Type;
- show a type-mismatch notice when the selected category differs;
- require the existing acknowledgment where appropriate;
- do not automatically reclassify the endpoint.

Examples:

- A flash drive previously registered as External remains External.
- An endpoint previously registered as Removable remains Removable.
- A Volume GUID already registered as Local must not receive a duplicate Removable endpoint.

Durable identity takes precedence over the newly selected category.

# 7. Explicitly Unsupported Paths

## 7.1 Optical

If the selected path is an optical drive:

- block Source Creation;

- show:
  
    Optical media is not supported yet.
    Support for data CDs, DVDs, and Blu-ray discs will be added separately.

Do not treat the optical drive’s Volume GUID, drive letter, or hardware as removable-media identity.

Do not create an endpoint.

## 7.2 Empty card reader or removable slot

If Windows exposes a removable/card-reader drive letter but no media is inserted:

- block identification;

- show:
  
    No readable media is inserted.

Do not create an endpoint or Source Profile.

## 7.3 NAS or UNC

If the operator chooses Removable and enters:

- a UNC path;
- a mapped network location that resolves to NAS;
- a network provider path;

block or redirect through the existing NAS classification workflow.

Do not probe it as a removable volume.

## 7.4 System/internal volume

Do not permit the current Windows system volume to be registered as Removable.

Use Local instead.

## 7.5 Unreadable or unavailable media

If the selected media is unavailable, unmounted, unreadable, or removed during plan/confirm:

- block confirmation;
- retain operator input;
- write nothing;
- report that the medium must be reinserted and identified again.

# 9. Whole-Medium and Subfolder Roots

## 9.1 Whole medium

Example:

    E:\

Persist:

    endpoint_relative_root = ""

Suggested Source Name:

    Entire device

Normal UI may use the more context-appropriate wording:

    Entire medium

Only change the persisted suggestion from `Entire device` to `Entire medium` if doing so is narrow and does not destabilize Local/External behavior.

Otherwise retain the existing persisted default and use contextual UI wording.

Document the final decision in the closeout.

## 9.2 Subfolder

Example:

    E:\DCIM\Camera

Persist:

    endpoint_relative_root = "DCIM\Camera"

Suggested Source Name:

    Camera

The operator may replace the suggested Source Name before confirmation.

## 9.3 Multiple roots

The same removable endpoint may have multiple intentional Source Profiles with different roots.

Examples:

    Entire medium
    DCIM
    Scanned Photos
    Family Archive

Same endpoint + same exact relative root must reuse the existing Source.

Same endpoint + different relative root is a legitimate separate Source.

Parent/child roots should show the existing overlap warning.

1. Choose `Removable`.
2. Enter Root Path or Mount Point.
3. Select `Identify Location`.
4. Probe the mounted medium read-only.

   - Source Type
   - Media Name
   - Source Name
   - Durable Identity
   - Identifier Type

   - Root Relative to Media
   - Current Observed Path

   - final action

7. Enter or confirm Source Name for a genuinely new Source.
8. Acknowledge ambiguous classification only when required.
9. Confirm.
10. On success:
    - clear Root Path or Mount Point;
    - clear recognition and naming state;
    - preserve selected Source Type;
    - preserve completed result.

# 15. Media Replacement Safety

A removable drive letter may point to a different medium later.

Confirm must not trust only the submitted path or drive letter.

Before mutation, confirm must recompute durable identity from the currently inserted volume.

Required cases:

## Same media, same drive letter

Proceed when the plan remains valid.

## Same media, different drive letter

A new plan should recognize the existing endpoint and record the new observed path.

## Different media, same drive letter

The prior plan fingerprint must fail.

Do not create or update records using the stale plan.

Show:

    The inserted media changed after identification.
    Identify the location again.

## Media removed before confirm

Block and write nothing.

# 22. Manual Validation

Manual validation must not scan or ingest media contents.

## 22.1 General boundaries

Allowed:

- read-only root/path probe;
- Volume GUID lookup;
- drive/media classification lookup;
- Source Creation plan;
- explicitly authorized Source Creation metadata confirmation;
- Source Profile visibility check.

Not allowed:

- Source Intake;
- recursive media scan;
- file hashing;
- file copying;
- file movement;
- file deletion;
- formatting;
- drive-letter reassignment;
- mount changes;
- eject commands;
- writing test files to the medium.

## 22.2 USB flash validation

When a safe USB flash drive is available and its path is explicitly identified:

Validate:

- Removable can identify it.
- Durable identity is Verified.
- Identifier Type is Volume GUID.
- whole-medium or selected subfolder root is correct.
- Media Name is editable for new endpoint.
- Source Name is editable for new Source.
- confirm creates/reuses correct endpoint and Source.
- completed result remains.
- path clears after success.
- no files are read recursively or modified.

## 22.3 SD validation

When an SD or microSD card is available and its path is explicitly identified:

Validate the same behavior as USB flash.

If practical without changing mounts or reader configuration, record whether probe evidence identifies SD/card-reader characteristics.

Do not require the operator to move the card between readers during this milestone.

## 22.4 Repeat-plan validation

For any confirmed validation medium:

- run a second read-only plan for the same root;
- confirm the existing endpoint and exact Source are recognized;
- confirm no duplicate endpoint or Source would be created.

## 22.5 Validation metadata

Any newly created validation Source must:

- use a clearly recognizable validation Source Name;
- be marked inactive after validation;
- remain in the database rather than being deleted;
- have no Source Intake run.

Record:

- Source Profile ID
- endpoint ID
- observed-path ID
- Media/Device Name
- Source Name
- Volume GUID identifier type
- identity status
- final inactive status

Do not modify existing real Sources unless separately authorized.

## 22.6 Hardware unavailable

If no USB flash drive or SD card is available:

- do not substitute an External HDD/SSD;
- complete automated tests;
- validate UI/API plan behavior with mocks/fixtures;

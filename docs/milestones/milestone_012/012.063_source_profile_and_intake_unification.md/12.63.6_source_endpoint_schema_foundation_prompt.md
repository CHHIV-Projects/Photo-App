## Goal

Add the first additive database/model foundation for durable source endpoints, access nodes, and observed path history.

This milestone should create the schema foundation needed for future Source Profile enrollment and source identity readiness, while keeping all current ingestion behavior unchanged.

This is a schema/model foundation milestone only.

## Background / Context

Milestone `12.63.0` found that current Source Profiles are stored in `ingestion_sources`, and that `ingestion_sources` currently mixes:

```text
user-facing Source Profile
backend source registry
compatibility anchor for Source Intake, iCloud Intake, reports, and provenance
```

Milestone `12.63.1` defined the durable source identity model:

```text
Durable Source Endpoint
  = source type + durable identity evidence + immutable alias + observed path history

Source ID / Source Profile
  = durable endpoint + selected root/folder + intake settings + lifecycle state

Observed Path
  = where the source is reachable from a specific Access Node at setup or run time
  = not durable identity

Ingestion Source / Source Registry
  = existing compatibility layer used by Source Intake, iCloud Intake, reports, and provenance
```

Milestone `12.63.2` gathered Windows source identity evidence.

Milestone `12.63.3` designed the Source Identity Probe service contract with Access Node / Probe Provider hooks.

Milestone `12.63.4` implemented the backend read-only Source Identity Probe service and Windows provider.

Milestone `12.63.5` validated the read-only service/API against real local, external, removable, NAS, cloud, and unsupported provider cases.

Important `12.63.5` result:

```text
\\HENDERSON-NAS\Photos\Camera imports
```

was confirmed as readable and valid from the user's normal project terminal context. The earlier `access_denied` result was due to the Codex sandbox access context, not a probe-service bug and not a UNC escaping bug.

## Product Decisions Locked for This Milestone

### 1. Additive Only

This milestone must be additive.

Allowed:

```text
new models
new tables
new indexes
new nullable foreign keys
new migration
model tests
migration/schema tests
safe compatibility tests
```

Not allowed:

```text
data backfill
mandatory endpoint enrollment
Source Profile behavior changes
Source Intake launch changes
readiness integration
frontend UI changes
provenance rewrite
iCloud behavior changes
cleanup behavior changes
probe API persistence
```

### 2. `ingestion_sources` Remains Stable

Current `ingestion_sources.id` remains the operational Source ID / Source Profile ID.

Do not replace it.

Do not rename it.

Do not change existing uniqueness rules unless absolutely required and approved.

Do not change existing Source Profile creation/edit behavior.

A nullable endpoint linkage may be added beside it, but existing rows must remain valid with no endpoint.

### 3. Source Endpoint Alias Is Immutable for v1

A durable source endpoint has an immutable user-facing alias for v1.

Schema should support this, but no alias editing workflow should be implemented.

Endpoint aliases should be globally unique or at least constrained strongly enough to avoid operator confusion.

Preferred:

```text
source_endpoints.alias_normalized unique
```

If a different constraint is safer in current DB conventions, explain in closeout.

### 4. Source Types

Endpoint source type values should support:

```text
local
external_device
removable_media
nas
cloud
```

These are durable endpoint source types.

Do not change existing `ingestion_sources.source_type` options in this milestone.

### 5. Access Node Is a First-Class Future Concept

An Access Node is the computer/runtime environment performing source probing and future intake.

Examples:

```text
Chuck Windows PC
future Linux mini-server
future Mac
```

Observed paths are access-node-specific.

The same durable endpoint may appear as different observed paths on different access nodes.

### 6. Observed Path History Is Append-Only Conceptually

Observed paths are evidence.

They are not durable identity by themselves.

Schema should support append-only observed path records, but this milestone should not automatically write observations from the probe API.

### 7. NAS Rule

For NAS:

```text
\\HENDERSON-NAS
```

is a server endpoint seed, not a runnable Source Root.

A runnable NAS Source Root must be a share or folder inside a share, such as:

```text
\\HENDERSON-NAS\Photos
\\HENDERSON-NAS\Photos\Camera imports
```

The schema should allow NAS endpoint/share identity and observed access paths without requiring mapped drive letters.

### 8. Privacy / Raw Evidence

Do not store raw command dumps.

Do not store credentials.

Do not store tokens, cookies, 2FA codes, or secret material.

Schema should be designed for sanitized/masked/hashed identity evidence summaries only.

## Required Tables / Fields

Exact names may be adjusted for project conventions, but the schema must preserve these meanings.

### 1. `access_nodes`

Purpose:

Represents the machine/runtime environment that observed or may observe a source.

Recommended fields:

```text
id
node_uuid or access_node_uuid
label
os_family
provider_name
provider_version
host_fingerprint_hash
host_fingerprint_masked
capabilities_json
status
last_seen_at
created_at
updated_at
```

Recommended constraints/indexes:

```text
unique node_uuid / access_node_uuid
index os_family
index status
```

Notes:

```text
host_fingerprint_hash should be nullable.
host_fingerprint_masked should be nullable.
capabilities_json should contain sanitized capability summaries only.
No secrets.
No raw environment dumps.
```

Status values may be simple strings for now, such as:

```text
active
inactive
retired
```

Do not implement lifecycle behavior yet.

### 2. `source_endpoints`

Purpose:

Represents the durable source identity anchor.

Recommended fields:

```text
id
endpoint_uuid
source_type
alias
alias_normalized
status
identity_fingerprint_hash
identity_fingerprint_version
identity_confidence
evidence_summary_json
created_from_access_node_id
created_at
updated_at
retired_at
```

Recommended constraints/indexes:

```text
unique endpoint_uuid
unique alias_normalized
index source_type
index status
index identity_fingerprint_hash
foreign key created_from_access_node_id -> access_nodes.id, nullable
```

Source type values should support:

```text
local
external_device
removable_media
nas
cloud
```

Status values may be:

```text
active
needs_review
retired
```

Identity confidence values may reuse or align with probe confidence tiers where helpful:

```text
strong_match
medium_needs_review
weak_manual_confirmation_required
unavailable_not_connected
unknown
```

Notes:

```text
alias is immutable by product decision, but do not implement edit blocking workflow here unless model-level constants make that natural.
identity_fingerprint_hash should store hashed/sanitized durable identity, not raw serials or command output.
evidence_summary_json must be sanitized.
Do not store NAS credentials, cloud secrets, tokens, cookies, or raw command dumps.
```

### 3. `source_endpoint_observed_paths`

Purpose:

Records where an endpoint has been observed from a particular Access Node.

Recommended fields:

```text
id
source_endpoint_id
access_node_id
observed_path
normalized_observed_path
filesystem_boundary_type
source_root_candidate_path
is_valid_source_root_candidate
probe_provider_name
probe_provider_version
probe_status
confidence_tier
match_status
safe_to_run
blockers_json
warnings_json
evidence_summary_json
first_seen_at
last_seen_at
last_success_at
created_at
updated_at
```

Recommended constraints/indexes:

```text
foreign key source_endpoint_id -> source_endpoints.id
foreign key access_node_id -> access_nodes.id
index source_endpoint_id
index access_node_id
index normalized_observed_path
index filesystem_boundary_type
index probe_status
```

Notes:

```text
observed_path is operationally necessary but sensitive.
Do not store raw command dumps.
Do not store credentials.
blockers_json / warnings_json should contain structured codes only.
evidence_summary_json should be sanitized.
This table supports future append-only observation history, but this milestone does not automatically write observations.
```

### 4. Nullable Link From `ingestion_sources`

Add nullable endpoint linkage to the existing `ingestion_sources` table.

Recommended field:

```text
endpoint_id nullable foreign key -> source_endpoints.id
```

Optional fields only if low-risk and clearly useful:

```text
endpoint_relative_root
endpoint_root_label
endpoint_link_status
```

Default recommendation:

```text
Add only endpoint_id unless current code structure makes one additional nullable root/link-status field clearly useful.
```

Do not require endpoint_id for existing or future rows yet.

Do not change Source Profile creation behavior.

Do not auto-populate endpoint_id.

Do not alter existing `source_label`, `source_type`, `source_root_path`, or existing path normalization behavior.

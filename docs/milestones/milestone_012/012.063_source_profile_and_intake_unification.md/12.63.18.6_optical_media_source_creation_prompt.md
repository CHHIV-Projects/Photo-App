# 1. Goal

Enable Source Creation for supported optical data media on Windows:

- data CDs;
- data DVDs;
- data Blu-ray discs;
- finalized optical discs containing normal readable files and folders.

Reuse the existing:

- Source Endpoint;
- Source Profile;
- Observed Path;
- Source Creation plan/confirm;
- endpoint alias;
- editable Source Name;
- exact Source recognition;
- form-reset;
- durable identity display;

architecture.

The durable endpoint must represent the inserted disc.

The following must not be treated as durable Source identity:

- optical drive hardware;
- optical reader serial number;
- drive letter;
- computer;
- SATA or USB port;
- current mount point;
- Disc Name;
- Source Name.

The same disc inserted in another compatible optical drive should resolve to the same Source Endpoint whenever the selected identity evidence supports that conclusion.

A different disc inserted into the same optical drive must resolve to a different Source Endpoint.

Use these user-facing Source categories:

## Local

Internal computer storage.

## External

Externally attached HDD or SSD storage.

## Removable

USB flash drives, SD cards, and microSD cards.

## Optical

Supported data CDs, DVDs, and Blu-ray discs.

## NAS

Network shares.

## Cloud

iCloud and future cloud providers.

Do not implement Optical as a subtype of:

- Local;
- External;
- Removable.

# 3. Supported Optical Scope

## 3.1 Supported

Target ordinary mounted data discs containing a readable filesystem and normal files/folders.

Potential supported examples include:

- ISO 9660 data CD;
- Joliet data CD;
- UDF data CD/DVD/Blu-ray;
- finalized recordable data disc;
- read-only photo archive disc;
- data disc created by normal backup or disc-authoring software.

Actual filesystem support must follow what Windows can mount and enumerate safely.

## 3.2 Explicitly unsupported

Do not support:

- audio CDs;
- commercial movie DVDs;
- commercial Blu-ray movie discs;
- copy-protected media;
- encrypted media requiring additional credentials or software;
- blank discs;
- unformatted discs;
- unreadable discs;
- damaged discs that cannot be enumerated consistently;
- discs that expose no normal mounted filesystem;
- disc writing, burning, formatting, finalization, or erasure;
- optical-disc image files such as `.iso` mounted from a local file, unless reconnaissance proves they can be distinguished safely from physical optical media and the user later authorizes that scope.

Do not add media-player, ripping, transcoding, decryption, or copy-protection bypass behavior.

# 6. Optical Identity Principle

The Source Endpoint represents the inserted disc.

Required semantics:

- Same disc, same drive:
  same endpoint.
- Same disc, different drive letter:
  same endpoint.
- Same disc, different compatible optical drive:
  same endpoint when the identity evidence is stable across readers.
- Different disc, same drive:
  different endpoint.
- Empty optical drive:
  no endpoint.
- Disc removed before confirm:
  confirmation blocked.
- Disc replaced before confirm:
  confirmation blocked.
- Disc label renamed while content and strong identity remain the same:
  identity should remain the same when technically possible.
- Rewritable or multisession disc content changes:
  treating the changed visible media state as a new logical endpoint is acceptable for v1.

Drive letter is current Observed Path evidence only.

# 7. Identity Evidence Strategy

## 7.1 Preferred strong media-specific identifier

First investigate whether Windows exposes an inserted-media-specific identifier that is:

- stable across removal and reinsertion;
- stable across drive-letter changes;
- independent of optical-drive hardware;
- stable across compatible optical readers;
- sufficiently collision-resistant.

Examples of evidence to investigate include:

- volume serial;
- object unique identifier;
- filesystem volume identifier;
- disc/session identifier;
- UDF or ISO volume descriptors;
- media creation identifier;
- other Windows optical-media properties.

Do not assume an OS value is durable merely because it is available.

Prove its semantics through code inspection, controlled tests, or live read-only validation.

## 7.2 Metadata-only optical media fingerprint

If no single OS-provided identifier is sufficiently strong, implement a versioned deterministic logical-media fingerprint.

Suggested internal identifier type:

    Optical media fingerprint v1

The fingerprint may combine available stable inserted-media evidence such as:

- normalized filesystem type;
- normalized volume label;
- volume serial or volume identifier;
- media/session descriptor;
- volume creation timestamp when stable;
- total visible capacity or used bytes;
- complete metadata-only directory manifest;
- file and directory counts.

The complete metadata-only directory manifest may include:

- normalized relative path;
- entry type: file or directory;
- file size;
- stable filesystem timestamp when available;
- other stable read-only filesystem attributes proven useful.

The manifest must:

- use paths relative to the disc root;
- exclude the drive letter;
- exclude optical-drive identity;
- normalize separators;
- normalize path comparison consistently;
- sort deterministically;
- avoid unstable access timestamps;
- avoid Windows mount-specific metadata;
- be hashed using SHA-256 or the project’s equivalent strong hash.

## 7.3 No file-content hashing during Source Creation

Source Creation must not:

- open every file for content hashing;
- calculate ingestion SHA256 hashes;
- parse EXIF;
- create previews;
- inspect media streams;
- copy files.

A recursive metadata-only directory enumeration is authorized solely when necessary to establish optical media identity.

It must read directory entries and filesystem metadata only.

It is not Source Intake.

## 7.4 Complete enumeration required

Do not create a durable identity from a partial directory manifest.

If enumeration:

- times out;
- encounters unresolved access failures;
- becomes inconsistent;
- loses the disc;
- returns only a partial result;

block creation and write nothing.

Do not silently fall back to a weak label/capacity identity.

## 7.5 Identity algorithm versioning

Persist enough information to distinguish the identity algorithm version.

Examples:

- `optical_media_fingerprint_v1`;
- evidence version;
- safe media summary;
- fingerprint hash.

Do not persist the full directory manifest unless the existing architecture has a clear safe reason to do so.

Prefer persisting:

- final fingerprint;
- algorithm version;
- safe entry counts;
- safe filesystem/media summary;
- observed path evidence.

Do not persist raw credentials, file contents, or unnecessary complete path inventories.

# 8. Logical Identity Limitation

The milestone may implement logical media identity rather than guaranteed physical-disc identity.

When two separately manufactured or burned discs contain identical:

- filesystem descriptors;
- labels;
- directory structures;
- filenames;
- sizes;
- timestamps;
- media metadata;

they may produce the same logical fingerprint.

For v1, this may be accepted as the same logical optical endpoint when no reliable physical media serial exists.

Document this limitation clearly.

Do not add an operator-generated random salt merely to force identical discs into different durable identities.

Disc Name remains display metadata and must not become identity.

A later parking-lot item may address physical-copy provenance if that becomes necessary.

# 9. Optical Media Changes

## 9.1 Rewritable media

For CD-RW, DVD-RW, BD-RE, or other rewritable media:

- fingerprint the currently visible finalized filesystem state;
- if content changes and the fingerprint changes, treating it as a new endpoint is acceptable;
- do not attempt to mutate or synchronize the prior endpoint;
- do not write to the disc.

## 9.2 Multisession media

For multisession discs:

- fingerprint the complete filesystem state Windows currently exposes;
- later sessions that change the visible manifest may produce a new identity;
- document this behavior.

Do not attempt low-level session reconstruction unless existing safe Windows APIs already provide it narrowly.

# 10. Classification and Blocking Rules

## 10.1 Optical drive with supported data disc

Allow Optical planning when:

- the selected path resolves to an optical drive;
- readable data media is inserted;
- Windows exposes a mounted filesystem root;
- the filesystem can be enumerated read-only;
- strong logical media identity can be calculated.

## 10.2 Empty optical drive

When the optical drive exists but no readable disc is inserted, block with:

    No readable optical media is inserted.

Create no endpoint, Source Profile, or observed-path record.

## 10.3 Audio CD

When the inserted media is an audio CD without a normal supported mounted data filesystem, block with:

    Audio CDs are not supported.

Do not expose ripping or track-copy controls.

## 10.4 Movie DVD or Blu-ray

When the media is recognized as commercial or movie-oriented DVD/Blu-ray content rather than a normal supported data archive, block with:

    Movie DVDs and Blu-ray discs are not supported.

Do not inspect, decrypt, rip, or bypass copy protection.

## 10.5 Blank, damaged, or unreadable media

Use accurate messages:

- `No readable optical media is inserted.`
- `The optical disc is blank or unformatted.`
- `The optical disc could not be read consistently.`
- `The optical disc does not expose a supported data filesystem.`

Do not create identity records.

## 10.6 Non-optical path selected as Optical

When the operator selects Optical but the path resolves to:

- Local;
- External;
- Removable;
- NAS;
- Cloud;
- virtual filesystem;
- unsupported mount;

block and direct the operator to the correct Source Type.

Do not create an Optical endpoint from non-optical media.

## 10.7 Existing endpoint precedence

If strong inserted-media identity matches an existing endpoint:

- reuse that endpoint;
- preserve its registered Source Type;
- do not create a second endpoint;
- do not automatically reclassify it.

If the matching endpoint is registered under an unexpected type due to legacy data:

- show the mismatch;
- preserve the registered type;
- avoid inline repair;
- refer technical conflicts to `SRC-ID-006` where appropriate.

Hard safety blockers still win over endpoint reuse.

# 26. Manual Validation

Manual validation must use only safe data discs.

## 26.1 Required boundaries

Allowed:

- optical-drive detection;
- inserted-media detection;
- filesystem and volume metadata lookup;
- read-only directory metadata enumeration;
- Source Creation plan;
- explicitly authorized Source Creation metadata confirmation;
- Source Profile visibility check;
- disc removal/reinsertion test;
- second-disc replacement test when available.

Not allowed:

- Source Intake;
- file-content hashing;
- EXIF extraction;
- preview creation;
- file copying;
- disc ripping;
- media playback;
- decryption;
- source file modification;
- disc writing;
- disc formatting;
- disc finalization;
- eject commands;
- drive-letter changes;
- mount changes.

## 26.2 Hardware/path authorization

Do not guess an optical drive path.

Use an exact path provided by the operator or clearly discovered through read-only reconnaissance.

Do not confirm Source Creation against a real disc until:

- the disc is confirmed to be a safe ordinary data disc;
- the path is known;
- metadata-only validation is appropriate.

Plan-only validation is acceptable by default.

## 26.3 Empty-drive validation

When an empty optical drive is available:

- verify the drive is recognized as Optical;
- verify no endpoint or Source is created;
- verify `No readable optical media is inserted.`

## 26.4 Supported data-disc validation

When a safe data disc is available:

Validate:

- Optical identifies the disc;
- Durable Identity is Verified;
- identifier belongs to the disc or logical media state;
- whole-disc or subfolder root is correct;
- Disc Name is editable for a new endpoint;
- Source Name is editable for a new Source;
- no file contents are read;
- no media files are modified.

## 26.5 Reinsert validation

When practical:

1. Run a plan for the disc.
2. Remove the disc manually.
3. Reinsert the same disc.
4. Run a new plan.
5. Verify the same endpoint identity is recognized.

Do not automate eject.

## 26.6 Different-disc validation

When two safe data discs are available:

- plan disc A;
- replace it manually with disc B in the same drive;
- verify disc B has a different identity;
- verify a stale disc A confirmation would fail.

Do not require two discs if only one is available.

## 26.7 Different-drive validation

When two compatible optical drives are available:

- insert the same safe disc into each drive;
- verify endpoint identity remains the same.

Do not require purchase or installation of another optical drive.

# 28. Stop Conditions

Stop and ask before proceeding if:

- available identity evidence belongs to the optical drive rather than the inserted disc;
- no strong inserted-media or logical-media identity can be produced;
- stable identity would require reading and hashing all file contents;
- the directory manifest cannot be enumerated completely and safely;
- the identity cannot distinguish different ordinary discs reliably enough;
- Optical requires physical drive serial identity;
- adding Optical requires destructive schema migration;
- Source Creation would need a parallel API or endpoint registry;
- Local, External, Removable, NAS, or iCloud behavior must materially change;
- Source Intake or readiness must be broadened;
- Windows cannot reliably distinguish empty drive from unreadable media;
- commercial media detection would require parsing, playback, decryption, or circumvention;
- confirm cannot detect disc removal or replacement;
- manual validation could modify the disc;
- full logical fingerprinting is operationally impractical and no safe alternative exists.

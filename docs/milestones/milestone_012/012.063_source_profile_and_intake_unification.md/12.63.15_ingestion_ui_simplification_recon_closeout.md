## 4. Current Pain Points

The current page has several operator confusion points:

```text
The long Source Profile registry table dominates the page, even though the desired workflow is source-focused.
iCloud appears both in the standalone iCloud Intake panel and in the generic Source Profile table.
Generic Run Intake controls are still near iCloud profiles, even though generic iCloud launch is blocked.
The retired guided iCloud generic Source Intake handoff still appears in the iCloud details drawer as a normal-looking section.
Technical columns such as acquisition method, managed staging path, masked username, first seen, and reference counts are always visible in the main table.
Readiness, durable identity, paths/staging, iCloud readiness, acquisition, cleanup, and run history are split into many sections.
Operator-facing next action is not visually dominant because audit information and counters compete for attention.
Test, deprecated, archived, inactive, and legacy source profiles can clutter the operator view through the status filter.
Source type labels are still internal/backend-oriented: local_folder, external_drive, cloud_export, scan_batch, other.
NAS is inferred from UNC path and is not yet presented as a clear operator-facing source type.
The Create Source Profile drawer mixes source creation, cloud staging fields, endpoint enrollment planning, endpoint matching, and status management.
Audit/history data is valuable but scattered across the registry table, active run panels, report summary, details drawer, iCloud panel, and raw report details.
```

The page is safe, but it makes the operator parse implementation details before choosing the next action.

## 5. Proposed Simplified Information Architecture

Recommended future structure:

```text
Ingestion Workbench

Top controls:
  Create Source Profile
  Source Type selector
  Source selector/search
  Refresh

Main panel:
  one selected source workflow

Secondary:
  Advanced / Manage Sources
```

The top-level mental model should be:

```text
1. Pick source type.
2. Pick source.
3. Work in one source-specific panel.
```

The design should avoid a long visible wizard. The primary surface should show:

```text
current source
current status/readiness
one or two primary actions
latest result
advanced details when needed
```

Filesystem-backed source action model:

```text
Check Readiness
Run Intake
```

iCloud source action model:

```text
Refresh / Prepare
Import / Resume
```

## 6. Source Type Selector Design

Approved long-term operator-facing source type vocabulary:

```text
Local
External
Removable
NAS
iCloud
```

Recommended mapping for current internal values:

```text
local_folder + non-UNC path -> Local
local_folder + UNC path -> NAS
external_drive -> External
future removable_media or removable endpoint evidence -> Removable
cloud_export + iCloud/cloud_provider=icloud/acquisition_method=icloudpd -> iCloud
cloud_export + other cloud providers -> Advanced / Provider-specific until designed
scan_batch -> Advanced / Legacy / Unsupported
other -> Advanced / Legacy / Unsupported
```

Approved product decisions:

```text
scan_batch and other should not be normal first-class operator choices.
Show scan_batch and other only under Advanced / Legacy / Unsupported unless or until their product meaning is clarified.
Include Removable in the design, but implementation may hide it, disable it, or show it as coming later until the backend model supports it.
```

Do not implement a persisted source type migration as part of this design. Presentation can map current internal values into friendlier categories.

## 7. Source Selector Design

The main source selector should default to active sources only.

Approved product decision:

```text
Inactive, archived, test, deprecated, and legacy sources should be behind an Advanced / Show inactive or legacy sources toggle.
```

Recommended source selector display fields:

```text
source label
operator-facing source type
short path/provider hint
status badge
readiness/latest status summary when available
```

Recommended selector behavior:

```text
filter by selected source type
search by source label and path/provider hint
default to active sources
show non-active/test/legacy sources only with advanced toggle
preserve the selected source when refresh does not invalidate it
show an empty state with Create Source Profile when no active source exists for the selected type
```

Avoid using the full source registry as the primary selection surface.

Keep Create Source Profile available from the top of the Ingestion Workbench.

```text
Local:
  source label
  root path
  optional durable source identity enrollment

External:
  source label
  current mount/path
  optional durable source identity enrollment

Removable:
  source label
  current mount/path
  coming-later or disabled until backend support exists

NAS:
  source label
  UNC/share path
  optional durable source identity enrollment
  clarify server/share identity vs profile root folder

iCloud:
  source label
  masked account username
  managed staging path
  provider-specific workflow note

```

Recommended copy distinctions:

```text
source label = operator-facing name
source path = current observed path or profile root
endpoint alias = durable source identity label
managed staging path = provider-managed local staging for iCloud
```

Post-create behavior recommendations:

```text
For filesystem sources, offer Check Readiness after create.
For enrolled filesystem sources, show durable identity result and then offer Check Readiness.
For iCloud sources, route to iCloud Intake status/prepare workflow.
```

Do not make source creation a 10-12 step wizard.

## 15. Risks / Open Questions

Resolved product decisions from this recon:

```text
Retired guided iCloud generic Source Intake handoff:
  remove it from normal iCloud details view in future UI implementation
  route all iCloud action to newer iCloud Intake
  keep only Advanced / Legacy notes if needed

Source selector default:
  active sources only
  inactive/archived/test/deprecated/legacy behind Advanced / Show inactive or legacy sources

scan_batch and other:
  Advanced / Legacy / Unsupported only

Removable:
  include in long-term vocabulary
  hide, disable, or show as coming later until backend support exists

Overall design:
  source-focused workbench
  one selected source workflow
  long registry moved to Advanced / Manage Sources
```

Remaining risks:

```text
Source type presentation could drift from backend readiness/enrollment mapping if helper logic is duplicated in multiple frontend places.
NAS is currently inferred from UNC path; the UI must avoid implying a persisted NAS source type exists before it does.
Removable support is product-approved as vocabulary, but backend identity modeling is not yet complete.
Moving registry actions could hide useful admin information if Advanced / Manage Sources is too buried.
iCloud details contain older acquisition/handoff concepts; removing them must not affect the true chunked iCloud Intake workflow.
Readiness snapshots can become stale after source paths, removable devices, NAS availability, or endpoint evidence changes.
Test/reference profiles in the dev DB may still appear unless the active-only default and advanced toggle are implemented carefully.
```

Open implementation questions for future prompts:

```text
Should the source type selector be tabs, segmented buttons, or a dropdown?
Should the selected source workflow be a persistent panel or a drawer?
How much latest-run history should be visible before expanding Run History?
Should source search include paths by default, or only after typing?
Should Advanced / Manage Sources be a drawer, collapsible section, or separate route?
When should Removable become a real backend-supported source category?
```

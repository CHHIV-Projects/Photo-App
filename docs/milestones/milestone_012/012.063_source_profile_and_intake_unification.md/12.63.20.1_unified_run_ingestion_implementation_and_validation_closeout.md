## 3. Final operator workflow

Normal workflow is now:

1. Choose source type.
2. Choose device and Source Profile.
3. Select Source.
4. Step 3 presents the backend-determined action for the selected source.

For filesystem sources, Step 3 launches Source Intake through the new dispatch endpoint after backend Source Selection revalidation.

For iCloud sources, Step 3 embeds the iCloud intake panel in selected-source mode and uses the dispatch endpoint to prepare, start, resume, or advance the existing iCloud historical/intake routine.

For NAS and Optical sources, Step 3 explains that the source is not runnable in this milestone and does not expose an active ingestion action.

## 4. Architecture

The implementation follows the recon roadmap:

- Source Selection remains the Step 2 authority.
- Source Selection output is treated as a handoff context, not permanent authorization.
- Run Ingestion revalidates Source Selection on the backend at action time.
- The backend dispatch service is the workflow authority.
- Existing ingestion engines remain authoritative for actual ingestion behavior.

New backend dispatch service:

- `backend/app/services/admin/run_ingestion_dispatch_service.py`
- `RunIngestionDispatchService.dispatch(...)`

New backend API route:

- `POST /api/admin/run-ingestion/dispatch`

The route is guarded with the existing ingestion operation guardrail wrapper and returns a normalized dispatch response.

## 5. Filesystem integration

Filesystem Step 3 dispatch reuses:

- `backend/app/services/admin/source_intake_execution_service.py`

The existing filesystem pipeline remains the authority for scanning, skipping known files, staging, Vault writes, provenance, duplicate handling, deferred files, and cleanup.

- `RunIngestionDispatchResponse`

Response includes:

- normalized result
- backend-determined workflow kind
- normalized action
- source profile ID
- optional underlying run ID
- status/next action/message
- sanitized workflow payload

## 14. Post-closeout operator observation — legacy Flash Qlik removable mismatch

After closeout drafting, the operator selected:

- Source Type: `Removable`
- Device: `Validation Flash D`
- Source: `Flash Qlik`

The UI showed Source Selection as selected and available:

- Friendly Source Type: `Removable`
- Workflow: `Filesystem Source Intake`
- Device identity: `matched`
- Resolved source root: `D:\`

However, the Step 3 filesystem tile also showed this warning:

```text
This Source Profile type is not supported by generic readiness. Use a supported local, external, removable, or NAS Source Profile.
```

Read-only API evidence for `Flash Qlik` showed:

```json
{
  "source_label": "Flash Qlik",
  "source_type": "other",
  "endpoint_id": 9,
  "endpoint_source_type": "removable_media",
  "source_root_path": "D:\\"
}
```

Interpretation:

- `Removable` is the user-facing UI label.
- `removable` is the frontend/operator category.
- `removable_media` is the canonical backend/probe/endpoint type.
- `other` is a legacy or compatibility Source Profile type from earlier milestone iterations.

The observed problem is not the UI label `Removable` versus backend type `removable_media`; those are expected translations for the same practical source class. The problem is that this Source Profile has split legacy/current identity:

```text
Source Profile source_type: other
Linked Endpoint source_type: removable_media
UI friendly type: Removable
```

Source Selection treated the matched endpoint identity as removable and selected the source. The older generic readiness gate keyed off the persisted Source Profile `source_type="other"` and rejected it.

Classification:

- `Flash Qlik` / operator-referenced Source 56 is obsolete legacy/test data for this milestone.
- This shape is not produced by the completed normal Create Source workflow.
- The mismatch exposed a legacy-data incompatibility, not a current workflow defect.
- No compatibility code, migration, backfill, or Source repair was implemented.
- Legacy Source 56 is outside current-format acceptance and may be retired or cleaned up separately if desired.

No code changes were made for this observation.

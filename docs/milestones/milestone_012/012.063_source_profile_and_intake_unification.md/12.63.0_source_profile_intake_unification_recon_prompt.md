## Goal

Perform a reconnaissance-only review of the current Source Profile creation and ingestion/intake workflows, with special attention to how local, external drive, removable media, NAS/network share, and iCloud source workflows can be unified where appropriate.

## Background / Context

The project has completed the major iCloud Intake arc through milestone `12.62.29.3`.

Current direction:

```text
iCloud Intake is good enough for v1.0.
iCloud performance optimization is parked.
The next major product area is external/local/NAS source identity and intake workflow redesign.
```

The next phase should focus on:

```text
1. Source Profile creation and identity clarity
2. Ingestion / intake methodology and workflow clarity
3. External/local/NAS source identity that does not depend on drive letters alone
4. A shared user-facing workflow grammar across source types
5. v1.0 operator clarity and safety
```

The project owner has clarified that there are two related but distinct things to unify as much as practical:

```text
1. Source Profile creation
2. Ingestion methodology
```

These do not need to be identical across source types, but the look, feel, language, and operator flow should be similar where possible.

Important product expectation:

Local, external drive, removable media, and NAS/network ingestion will often be smaller and more targeted than iCloud. These workflows are expected to be based on:

```text
source + selected folder/root/path
```

rather than treating the provider/library as one very large single set the way iCloud does.

Future enhancement note:

Scheduled/background ingestion is a far-future enhancement. Do not implement scheduling now. However, the future design should not make scheduled/background source processing harder later.

### Shared Workflow Grammar, Not Forced Backend Uniformity

A key purpose of this reconnaissance is to distinguish:

```text
shared operator grammar
```

from:

```text
shared backend mechanics
```

iCloud, local folders, external drives, removable media, and NAS/network shares should feel similar in user-facing language and workflow where practical, but they should not be forced into one backend path if their safety, identity, acquisition, or intake requirements differ.

### Source Identity Design Split

During reconnaissance, evaluate current behavior against this conceptual split:

```text
Source Profile = user-facing intent, alias, configuration, and workflow container
Source Device / Endpoint = durable machine-readable identity evidence
Ingestion Source / Registry = existing backend run/provenance linkage and compatibility layer
Observed Path = current mount/path/root observation for a particular run, not durable identity by itself
```

Drive letters, mapped paths, UNC variants, and transient mount paths should be treated as observations unless future design proves they are safe identity components.

### v1 Scope Caution

For v1, avoid overbuilding the full identity model prematurely.

A likely safe sequence is:

```text
1. Design Source Profile / Device / Endpoint / Provenance boundaries.
2. Add read-only source identity probes for local/external/NAS sources.
3. Simplify UI readiness and source workflow language.
4. Add schema/model foundations only after the design is stable.
```

The closeout should confirm or challenge this sequence based on code reality.

### Product Decision to Evaluate

Please evaluate this product question during reconnaissance:

```text

Product-owner leaning: A Source Profile should usually represent a reusable, user-meaningful top-level source root, such as C:\Photos, the user Desktop, an external drive root such as D:\, or a NAS share/folder. Each intake run may scan the whole profile root or, where useful, a targeted subfolder beneath that root. Do not assume every subfolder should become its own Source Profile.

A narrower folder should become its own Source Profile only when it represents a distinct durable source, workflow, owner, device/share boundary, or long-term scheduled intake target.
```

Current product-owner leaning is that local/external/NAS ingestion will usually be targeted by source plus selected folder/root/path, and may often involve smaller loads than iCloud. The closeout should explain how each option would affect Source Profiles, provenance, intake runs, UI clarity, and future scheduled/background processing.

## 3. Final Optical Product Definition

Optical means a readable, ordinary data CD/DVD/Blu-ray filesystem exposed by a physical optical drive.

The Source Endpoint represents the inserted disc's logical media state, not the optical reader.

The Source Profile represents the endpoint plus a root on that disc.

## 4. Internal Source Type Value

- operator-facing create category: `optical`
- backend/internal endpoint type: `optical_media`
- persisted Source Profile type: `optical_media`

## 5. Supported Optical Media

Supported by design and automated coverage:

- finalized readable data CDs;
- finalized readable data DVDs;
- finalized readable data Blu-rays;
- CD-R/CD-RW/DVD/Blu-ray variants when they expose an ordinary data filesystem.

Live validation used a CD-RW data disc at `E:\`.

## 6. Unsupported Optical Media

Unsupported and blocked:

- empty optical drives;
- audio CDs;
- movie DVD/Blu-ray structures when detected from safe root-level names;
- blank/unformatted/unreadable discs;
- virtual optical drives and mounted disc images when detected;
- unsupported or incomplete identity evidence;
- identity enumeration timeout.

## 7. Final Source Creation Flow

Optical uses the normal Source Creation flow:

1. Choose `Optical`.
2. Enter a drive-root or subfolder path such as `E:\`.
3. Select `Identify Location`.
4. Review Disc Name, Source Name, durable identity, root, exact Source state, and final action.
5. Confirm when the plan is ready.
6. Confirm recomputes the plan and fingerprint before metadata writes.

## 8. Optical Drive Versus Inserted-Disc Model

The optical drive is access hardware only.

Excluded from endpoint identity:

- drive letter;
- absolute mounted path;
- optical reader name;
- optical reader PnP/device ID;
- port, host, or access-node details;
- Disc Name;
- Source Name.

The drive identity is used only to verify that the selected path is a supported physical optical drive.

## 9. Durable Identity Implementation

Windows did not provide a proven inserted-disc identity that could replace logical fingerprinting.

Implemented fallback:

- `optical_media_fingerprint_v1`

The provider produces durable `media_evidence` item:

- code: `optical_media_fingerprint_present`
- durability: `durable`
- fingerprint version: `optical_media_fingerprint_v1`
- normal identifier type: `Optical media fingerprint`

## 10. Identity Algorithm and Version

Algorithm: `optical_media_fingerprint_v1`

Hash: SHA-256 via the project's versioned fingerprint helper.

Persisted/stored endpoint fields:

- final fingerprint hash;
- fingerprint version;
- safe evidence summary.

The complete manifest listing is used to compute the hash but is not persisted.

## 11. OS-Provided Media Evidence

The Windows provider uses read-only non-admin evidence:

- `Win32_LogicalDisk` drive type, filesystem, volume serial, size, and free space;
- `Win32_CDROMDrive` media-loaded state, media type, drive name, and PnP hint for physical/virtual classification;
- ordinary filesystem path readability;
- metadata-only directory enumeration.

`Get-Volume` was deliberately not used in the final Optical metadata command because it took about 40 seconds on this workstation and reported `FileSystemType = Unknown` despite the disc exposing a readable `UDF` filesystem through `Win32_LogicalDisk` and `fsutil`.

## 12. Metadata-Only Manifest Behavior

The manifest is complete, deterministic, and metadata-only.

Included fields:

- normalized relative path;
- entry type;
- file size for files;
- stable last-write timestamp only when two repeated enumerations match;
- file count;
- directory count;
- timestamp inclusion flag.

Excluded fields:

- drive letter;
- absolute mounted path;
- optical drive identity;
- access timestamps;
- mount timestamps;
- enumeration order;
- file contents;
- EXIF/media metadata;
- preview data;
- ingestion hashes.

The default hard timeout for complete optical identity enumeration is 300 seconds. Timeout blocks Source Creation and writes no fingerprint.

## 13. Logical Versus Physical Identity Limitation

The fingerprint identifies the complete visible logical filesystem state, not a hidden physical disc serial.

Known limitation:

- two separately produced discs with exactly identical stable metadata and manifest can produce the same logical identity.

This limitation is accepted for this milestone and documented in code/test behavior.

- same logical disc in another mocked optical drive reuses the same fingerprint;
- different manifest produces a different fingerprint.

## 19. Exact Source Reuse

Exact Source reuse uses existing Source Creation behavior.

Automated tests cover:

- subfolder Source on same disc creates a distinct Source;
- same endpoint with different root remains allowed.

## 20. Empty-Drive Behavior

When Windows clearly reports an optical drive with no media loaded, the provider blocks with:

`No readable optical media is inserted.`

Automated provider coverage verifies this message and avoids the generic `path_not_found` message.

No live empty-drive validation was performed because the available drive contained the approved CD-RW data disc.

## 21. Audio CD Behavior

Audio CDs block only when combined evidence shows no ordinary data filesystem and audio/CDDA-style evidence is present.

Automated provider coverage verifies `audio_cd_not_supported`.

The live `E:\` disc was not classified as audio because it exposed an ordinary readable filesystem and `Win32_LogicalDisk` reported `UDF`.

## 22. Movie-Disc Behavior

Movie-oriented structures block from safe root-level metadata-only names.

Currently recognized root signals include:

- `VIDEO_TS`
- `BDMV`
- `AACS`

`CERTIFICATE` alone is not treated as conclusive.

No files are opened or parsed for movie detection.

## 23. Blank/Unreadable-Disc Behavior

Blank, unreadable, unsupported-filesystem, and incomplete-identity cases block without fingerprint persistence.

The provider uses the most specific blocker available instead of reusing the empty-drive message for unreadable media.

## 24. Rewritable and Multisession Behavior

Rewritable and multisession discs are supported only when the currently visible logical filesystem can be completely enumerated.

If the visible manifest changes between repeated enumeration, Source Creation blocks with incomplete identity evidence.

## 25. Disc Removal/Replacement Safety

Confirm recomputes the plan and plan fingerprint before writing metadata.

If the disc is removed or replaced between plan and confirm:

- the recomputed fingerprint or source-root evidence changes;
- the plan fingerprint no longer matches;
- confirmation blocks and writes nothing.

## 26. Drive-Letter Change Behavior

Drive letter is excluded from `optical_media_fingerprint_v1`.

Automated provider coverage verifies same logical media at a different drive letter has the same fingerprint.

Observed paths remain access-node evidence only.

## 27. Different-Drive Behavior

Optical drive identity is excluded from `optical_media_fingerprint_v1`.

Automated provider coverage verifies a different mocked optical drive with the same logical media has the same fingerprint.

No live second optical drive was available.

## 28. Form-Reset Behavior

Optical uses the existing Create Source success behavior.

On successful creation:

- path clears;
- Disc Name and Source Name inputs clear;
- recognition state clears;
- selected Source Type remains selected;
- completed result remains visible.

Blocked and failed operations preserve operator input.

# Milestone 12.63.7 - Source Endpoint Enrollment Service Design Closeout

## 1. Scope Completed

Completed a design-only milestone for future Source Endpoint enrollment.

This closeout defines how a future implementation should convert a read-only `SourceIdentityProbeResponse` into:

- an endpoint candidate
- an enrollment plan
- an explicit operator-confirmed enrollment transaction
- a durable `SourceEndpoint`
- a nullable `ingestion_sources.endpoint_id` link
- a `SourceEndpointObservedPath` record

No code, schema, tests, runtime data, endpoint rows, observed path rows, Source Profile behavior, Source Intake behavior, iCloud behavior, cleanup behavior, provenance behavior, or frontend UI was changed.

## 3. Executive Design Summary

Endpoint enrollment should be a two-phase, operator-confirmed workflow:

```text
1. Plan: read-only candidate and match analysis.
2. Confirm: future explicit write transaction.
```

The planning phase should accept a fresh probe result or run a probe internally, build an endpoint candidate, evaluate duplicate/existing endpoint matches, validate alias availability, and describe exactly what would be created or linked. It must not write endpoint rows, observed path rows, or `ingestion_sources.endpoint_id`.

The confirmation phase should be the only future write step. It should require explicit operator confirmation, revalidate that the probe/source root is still readable in the current runtime access context, and then atomically create or link:

```text
SourceEndpoint
ingestion_sources.endpoint_id
SourceEndpointObservedPath
```

For v1, endpoint enrollment is opt-in. Existing path-only Source Profiles remain valid and must not be blocked merely because `endpoint_id` is null.

Strong durable evidence may select an existing endpoint candidate automatically for review, but the operator still confirms the link. Medium-confidence evidence may allow reviewed enrollment, but must not authorize automatic Source Intake run launch. Weak evidence should remain manual review or blocked, depending on source type and blockers.

## 4. Core Enrollment Concepts

Endpoint Candidate:

A safe, non-persistent interpretation of a probe result. It contains source type, source root candidate, access node summary, provider identity, confidence, fingerprint candidate, sanitized evidence summary, blockers, warnings, alias suggestions, and possible endpoint matches.

Enrollment Request:

The operator or UI request to plan enrollment. It includes the source type, observed path or source profile id, intended flow, optional alias, optional source profile fields, and probe result or request data.

Enrollment Plan:

A read-only response describing whether enrollment is possible, what would be created or linked, duplicate matches, alias conflicts, required confirmations, and blocking/reviewable errors.

Enrollment Confirmation:

The explicit operator approval to execute a previously planned write. It should include the plan id or plan fingerprint, selected alias, target source profile id or source profile create payload, selected existing endpoint id if applicable, and a confirmation phrase/flag.

Enrollment Transaction:

The atomic future DB transaction that creates or links the endpoint, links the Source Profile, and records the initial observed path. If any required write fails, all writes roll back.

Endpoint Link:

The nullable link from `ingestion_sources.endpoint_id` to `source_endpoints.id`. It does not replace `ingestion_sources.id` as operational Source ID / Source Profile ID.

Observed Path Record:

A record in `source_endpoint_observed_paths` showing where an endpoint/root was observed from a specific Access Node, with sanitized probe status, confidence, blockers, warnings, and timestamps.

Duplicate Endpoint Match:

A candidate match to an existing endpoint. Strong matches are based on durable fingerprint/evidence. Medium matches require review. Observed path alone is weak and must not create a durable match by itself.

Ambiguous Endpoint Match:

Multiple plausible endpoints match the candidate. Ambiguity must block automatic linking and require review.

Enrollment Cancel / Abort:

The operator stops before confirmation, or planning returns blocked. No endpoint, Source Profile link, or observed path row is written.

Endpoint Repair / Relink:

Future-only flow for changing a wrong link, repairing evidence, merging/splitting endpoints, or dealing with aliases chosen poorly. Not part of v1 enrollment implementation.

## 5. Enrollment Flow Design

New Source Profile + New Endpoint:

1. Operator selects a path such as `E:\Photos`.
2. System runs source identity probe.
3. Plan confirms the path is readable and root candidate is valid.
4. Plan finds no strong existing endpoint match.
5. Operator chooses a globally unique immutable alias.
6. Confirm creates `SourceEndpoint`.
7. Confirm creates or gets the `ingestion_sources` row.
8. Confirm links `ingestion_sources.endpoint_id`.
9. Confirm records the observed path.

Existing Path-Only Source Profile + New Endpoint:

1. Existing `ingestion_sources` row has `endpoint_id = null`.
2. Operator runs readiness/probe for the existing configured root.
3. Plan builds a candidate from the probe and the existing profile.
4. Plan finds no strong existing endpoint match.
5. Operator confirms alias and enrollment.
6. Confirm creates endpoint, links the existing source profile, and records observed path.

Existing Source Profile + Existing Endpoint:

1. Existing profile is endpoint-null or needs relinking.
2. Probe evidence strongly matches one existing endpoint.
3. Plan recommends linking to that endpoint.
4. Operator confirms.
5. Confirm links `ingestion_sources.endpoint_id` and records observed path.

Same Endpoint + Different Source Profile Root:

1. Probe matches an existing endpoint, such as the same external drive or NAS share.
2. Selected root differs, such as `\Photos` versus `\Scans`.
3. Plan treats this as a new or existing Source Profile under the same endpoint, not as a duplicate endpoint.
4. Confirm links the new/existing Source Profile to the endpoint and records the root-specific observed path.

Duplicate / Ambiguous Endpoint Candidate:

1. Plan finds same alias, same fingerprint, or multiple possible durable matches.
2. Strong same-fingerprint match should route to existing endpoint linking.
3. Alias conflict without fingerprint match blocks new endpoint creation until alias changes.
4. Multiple durable candidates block automatic linking and require operator review.

Enrollment Canceled:

Cancel before confirm writes nothing:

```text
no endpoint row
no Source Profile row/link
no observed path row
no partial enrollment state
```

Candidate construction should start from `SourceIdentityProbeResponse`.

Required candidate inputs:

```text

observed_path

source_root_candidate.filesystem_boundary_type
access_node_summary
provider_name
provider_version
confidence_tier
match_status
safe_to_run
identity_fingerprint_candidate
evidence_summary
blockers
warnings
```

Derived candidate fields:

```text
enrollment_status
enrollment_blockers
review_reasons
alias_suggestions
endpoint_fingerprint_input_summary
possible_endpoint_matches
target_source_profile_action
confirmation_requirements
plan_fingerprint
plan_expires_at
```

Enrollability rules:

Eligible:

```text
probe_status = completed
probe_status = completed_with_warnings, if no enrollment-blocking blocker
confidence_tier = medium_needs_review, with explicit review
filesystem_boundary_type = local_volume_root/local_folder/external_volume_root/external_folder/removable_media_root/removable_media_folder/nas_share_root/nas_share_folder
is_valid_source_root_candidate = true
path readable in the runtime context that will perform future intake
```

Not eligible:

```text
probe_status = blocked
probe_status = unavailable
probe_status = unsupported_provider
probe_status = provider_error
filesystem_boundary_type = nas_server_only
filesystem_boundary_type = cloud_profile_scope through generic filesystem flow
is_valid_source_root_candidate = false
path not readable
access denied
identity mismatch
ambiguous durable match without review path
```

Generic cloud probe responses should not enroll through this filesystem endpoint flow. Cloud providers need provider-specific enrollment later.

## 7. Alias Design

Alias rules:

```text
alias is required for endpoint creation
alias_normalized is required
alias_normalized is globally unique
alias is immutable for v1
alias edit/repair is future-only
```

Practical v1 normalization:

```text
trim leading/trailing whitespace
collapse repeated internal whitespace to one space
casefold/lowercase for comparison
preserve ordinary punctuation in display alias
normalize punctuation only enough to avoid invisible/duplicate whitespace confusion
reject empty normalized alias
```

Alias validation:

```text
1 to 255 characters after trimming
not only punctuation
no path separators-only alias
no control characters
no exact normalized conflict with existing endpoint
```

Alias suggestions should be helpful but never automatic final truth:

```text
Chuck Windows Laptop C Drive
Family Photos External Drive
HENDERSON-NAS Photos Share
Camera Imports NAS Folder
iCloud Chuck Library
```

Alias conflict handling:

```text
same alias_normalized and same strong endpoint match -> suggest linking existing endpoint
same alias_normalized and different/unknown endpoint evidence -> block and ask for different alias
medium possible duplicate -> show possible match and require review
```

Operator-facing message examples:

```text
Alias is required.
This endpoint alias is already used. Choose a different alias or link the existing endpoint.
Endpoint aliases are immutable in this version. Choose a name that will remain clear in provenance.
```

## 8. Source Root vs Endpoint Identity Design

SourceEndpoint:

The durable identity anchor: physical/local volume context, external/removable device identity, NAS server/share identity, or future cloud library/account identity. It stores alias, fingerprint hash/version, identity confidence, and sanitized evidence summary.

`ingestion_sources` Source Profile:

The operational runnable Source Profile. It stores selected root/folder/path, type/settings/lifecycle, and remains the compatibility anchor for Source Intake, iCloud Intake, reports, and provenance.

SourceEndpointObservedPath:

The access-node-specific observation of where the endpoint/root was reachable when probed, enrolled, or verified.

External drive example:

```text
Endpoint = physical external drive / volume identity
Source Profile root = E:\Photos or endpoint-relative \Photos
Observed path = E:\Photos from Chuck Windows PC
```

NAS example:

```text
Endpoint = \\HENDERSON-NAS\Photos share identity
Source Profile root = \\HENDERSON-NAS\Photos\Camera imports
Observed path = \\HENDERSON-NAS\Photos\Camera imports from Chuck Windows PC
```

Recommended NAS boundary:

```text
NAS endpoint = server + share
Source Profile = selected share root or folder inside share
Observed path = exact UNC or mounted path used by the Access Node
```

This keeps one endpoint for the durable share and allows multiple Source Profiles under that share.

## 9. NAS Storage / Privacy Design

Recommended v1 posture:

```text
store operational NAS root path in ingestion_sources.source_root_path when needed to run
store endpoint alias raw because it is user-facing
store endpoint identity_fingerprint_hash from canonical server/share evidence
store evidence_summary_json as sanitized/masked/high-level summary
store observed_path raw only because it is operationally necessary for readiness/run context
never store NAS credentials
```

Normal UI should show:

```text
endpoint alias
source profile label/root label
readiness state
high-level source type
```

Advanced Details may show:

```text
configured operational path
observed path
filesystem boundary type
masked host/share evidence
probe provider/status/confidence
```

Evidence summaries should store codes and masked/hash hints, not raw command output:

```text
network_share_evidence = present
server_display = HENDERSON-NAS, if product accepts raw display
share_display = Photos, if product accepts raw display
server_share_hash = sha256(...)
path_evidence = readable
```

Recommended product answer for v1:

Use both raw operational path where required to run and hash-for-match evidence for endpoint identity. NAS server/share names may appear in normal UI if they are part of the operator-chosen path/alias, but raw command dumps and credentials must never be stored.

Mapped drive paths:

```text
Z:\Camera imports is observed path
resolved \\HENDERSON-NAS\Photos\Camera imports is canonical operational path when available
endpoint identity remains server + share, not drive letter
```

Future Linux NAS mount:

```text
/mnt/photos/camera-imports is observed path
mount/source evidence should resolve to server/share when provider can do so
endpoint identity remains server + share
```

## 10. Identity Fingerprint Design

Fingerprint goals:

```text
stable enough to match the same endpoint
source-type specific
versioned
hashes durable evidence instead of storing raw secrets
never based on drive letter alone
```

Recommended algorithm label:

```text
source_endpoint_fingerprint_v1
```

Local:

Use access node identity plus volume/path evidence where local folder identity is host-bound:

```text
source_type
access_node_uuid or host_fingerprint_hash
volume_guid/serial hash when available
normalized selected root or root anchor hash
```

External device:

Use strongest available durable device/volume evidence:

```text
source_type
volume_guid hash
volume_serial hash
device/pnp evidence hash when available
filesystem label hash if available
```

Removable media:

Use media/volume evidence and keep confidence conservative:

```text
source_type
volume/media serial hash when available
filesystem id hash
optional label hash
```

NAS:

Use canonical server/share identity, not selected folder:

```text
source_type = nas
canonical server name or address hash
canonical share name hash
optional provider/mount evidence hash
```

Cloud:

Generic cloud is out of scope for this enrollment service. Future provider-specific flow may use provider/library/account non-secret identifiers and should not store tokens or session material.

Missing fields:

```text
strong_match requires fingerprint hash
medium_needs_review may use partial durable evidence
weak/manual cannot rely on observed path alone
unavailable evidence blocks automatic match
```

## 11. Duplicate / Existing Endpoint Detection

Strong match:

```text
same identity_fingerprint_hash and source_type
or future provider-specific durable id match
```

Action:

```text
recommend existing endpoint
operator confirms link
do not create duplicate endpoint
```

Medium possible match:

```text
same NAS server/share hash with missing secondary evidence
same volume serial but missing device evidence
same endpoint alias family but no fingerprint match
same observed path plus partial durable evidence
```

Action:

```text
needs review
show possible endpoints
allow link only after explicit confirmation
do not auto-run intake from medium evidence
```

Weak/manual match:

```text
same observed path only
same display label only
same drive letter only
same folder name only
```

Action:

```text
not durable enough
require manual confirmation or new endpoint alias
```

Mismatch:

```text
fingerprint conflicts with selected existing endpoint
NAS share differs
device/volume evidence contradicts endpoint
source type differs incompatibly
```

Action:

```text
block linking
recommend repair/relink flow later
```

Ambiguous:

```text
more than one strong or medium candidate
conflicting fingerprint/evidence signals
multiple endpoint rows share partial evidence
```

Action:

```text
block automatic linking
require operator review
do not create/link without explicit selected endpoint and confirmation
```

Creating a new endpoint despite a possible match should be allowed only when evidence is not strong, the alias is unique, and the operator confirms that this is a distinct source.

## 12. Transaction / Rollback Design

Future confirm should use one DB transaction for:

```text
create SourceEndpoint, if new
create or get AccessNode, if needed
create or get ingestion_sources row, if new Source Profile flow
set ingestion_sources.endpoint_id
create or update SourceEndpointObservedPath
```

If any required operation fails, the transaction rolls back.

Failure behavior:

```text
alias conflict -> no writes
Source Profile creation failure -> no endpoint write remains
observed path write failure -> rollback endpoint/profile link
source profile already linked to different endpoint -> block unless future repair flow
stale plan/runtime path no longer readable -> no writes
operator cancel -> no writes
```

Confirm should revalidate critical plan assumptions before writing:

```text
alias still available
target source profile still exists/unlinked or linked as expected
selected endpoint still exists if linking existing
probe/source root still readable in current runtime access context
plan has not expired
```

Observed path write should be inside the same transaction for initial enrollment because it is the audit trail for why the endpoint/profile link was made.

## 13. Existing Source Profile Compatibility

Existing Source Profiles remain valid with:

```text
ingestion_sources.endpoint_id = null
```

No automatic backfill should run.

No Source Intake operation should be blocked merely because endpoint identity has not been enrolled.

Future UI/readiness may show a non-blocking warning:

```text
Path-only profile; source identity is not enrolled.
```

Future opt-in enrollment for existing profiles should:

```text
load current Source Profile
probe its effective path in the runtime context
build an enrollment plan
require operator confirmation
link endpoint_id only after successful confirm
preserve source_label/source_type/source_root_path history
```

If a path-only profile has historical provenance, enrollment should be additive. It must not rewrite provenance or reinterpret old runs unless a later backfill/review milestone explicitly scopes that work.

## 14. Enrollment Service Boundary

Recommended future service location:

```text
backend/app/services/source_identity/enrollment_service.py
```

Reason:

Enrollment is logically part of source identity, and it consumes `SourceIdentityProbeResponse` while writing `SourceEndpoint` tables.

Recommended supporting schema module:

```text
backend/app/services/source_identity/enrollment_schema.py
```

Responsibilities:

```text
build endpoint candidate from probe response
validate enrollment request
normalize and validate aliases
check alias uniqueness
build fingerprint input summaries
check duplicate/existing endpoint candidates
build read-only enrollment plan
execute future explicit enrollment transaction
record initial observed path during confirm
link ingestion_sources.endpoint_id during confirm
```

Non-responsibilities:

```text
run Source Intake
write Vault files
rewrite provenance
authenticate NAS or cloud providers
mount or unmount drives
store credentials
edit immutable aliases
repair/merge/split endpoints
persist probe API results outside confirmed enrollment
```

Access node resolver:

Future implementation likely needs a small helper to resolve or create the current Access Node. It should use sanitized host/runtime evidence and avoid raw environment dumps.

## 17. Observed Path Recording Design

Recommended v1 strategy:

```text
hybrid current-state observation table
one row per endpoint + access node + normalized observed path + source root candidate
update first_seen_at/last_seen_at/last_success_at over time
avoid duplicate rows for identical repeated observations
add separate event history only if future audit needs it
```

Write observed path records later on:

```text
confirmed enrollment
successful future readiness check
successful future run-launch verification
meaningful state change, such as path changed or confidence changed
```

Do not write on every read-only probe. The existing `/api/admin/source-identity/probe` endpoint should remain read-only unless a future milestone explicitly scopes persistence.

For failed observations, future design can either:

```text
update the existing row with latest failed status and warnings
or write separate endpoint observation events
```

For v1 enrollment, write the initial observed path only on confirm.

## 21. Product Decisions Recommended for v1

1. NAS server/share names:

Recommended v1 answer:

Store raw operational paths where required to run, store user-facing alias raw, and store durable matching evidence as versioned hashes plus sanitized summaries. Do not store credentials or raw command dumps. Allow raw server/share display in Advanced Details when it is already part of the operator-configured path.

2. Endpoint alias permanence:

Recommended v1 answer:

Keep aliases globally unique and immutable. Design future historical-alias/rename workflow separately if needed.

3. Auto-match evidence:

Recommended v1 answer:

Only same source type plus same versioned `identity_fingerprint_hash` is strong enough to auto-select an existing endpoint candidate. Partial evidence is medium and requires review. Observed path, drive letter, or label alone is weak and never durable enough.

4. Endpoint and Source Profile transaction:

Recommended v1 answer:

Confirmed enrollment should create/link endpoint, Source Profile, and observed path in one transaction. Planning remains read-only.

5. Medium-confidence run launch:

Recommended v1 answer:

Medium-confidence evidence may allow reviewed enrollment, but should not permit automatic run launch. Future endpoint-enrolled run launch should require fresh readiness/run verification and either strong match or explicit review policy.

## 22. Risks / Known Limitations

Endpoint over-merge:

Two distinct sources could be linked if fingerprint inputs are too broad, especially NAS aliases/IPs or reused removable media labels.

Endpoint under-merge:

The same source could create multiple endpoints if evidence varies by access node, USB bridge, NAS hostname, or OS provider.

NAS identity ambiguity:

Hostnames, IP addresses, aliases, mapped drives, and mounted paths can point to the same share. Conservative review is required.

Medium-confidence evidence:

Useful for enrollment review, but unsafe for automatic run launch.

Alias immutability inconvenience:

A poor alias may be inconvenient. Keep immutable for v1 and design repair/rename later.

Linux/macOS access-node differences:

Future providers may observe the same endpoint through different paths and evidence. Schema supports this, but providers do not yet exist.

Legacy profile compatibility:

Path-only profiles must continue working. UI should avoid making endpoint enrollment feel mandatory until run verification is mature.

Partial enrollment risk:

Mitigated by transaction design and no writes on cancel.

Privacy risk:

NAS/server/share and host evidence can be sensitive. Store operational paths only when needed, use hashes/sanitized summaries for matching, and never store credentials or raw dumps.

Runtime access context risk:

A path readable in one terminal may be blocked in another process. Confirm should use the runtime context that will perform future intake.

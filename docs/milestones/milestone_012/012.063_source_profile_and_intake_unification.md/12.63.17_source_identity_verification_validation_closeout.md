## 3. Source Type UI Summary

Local is shown as `Local / NAS Folder` and persists as `local_folder`.

External is shown as `External` and persists as `external_drive`.

NAS is explicitly accounted for by using `Local / NAS Folder` with a UNC path. The details/workbench classify UNC local-folder profiles as NAS.

iCloud is shown as `iCloud / Cloud Export` and remains provider-specific.

Removable is shown as disabled / coming later. The backend probe model has `removable_media`, but persisted Source Profile types do not currently support a clean removable value, so no unsupported backend value is silently invented.

Advanced / legacy profiles remain available as `Advanced / Scan Batch` and `Advanced / Other`.

## 4. Verification Policy

Verified:

```text
Local/External/Removable: readable source root plus durable mountvol Volume GUID evidence.
NAS: readable UNC share/root/folder plus parsed UNC server/share identity.
```

Not verified:

```text
Readable path with no strong durable identifier.
Path-only, medium, weak, supporting-only, unavailable, or blocked evidence.
NAS server-only path.
```

Provider-specific:

```text
iCloud/cloud_export and generic cloud probe results.
```

Unknown:

```text
Not checked, unsupported without a probe, or unable to evaluate.
```

Endpoint ID alone never yields `Verified`.

## 5. Evidence Captured

Local:

```text
mountvol <drive> /L Volume GUID is strong when source root is readable.
Volume serial, drive type, host, and command results remain supporting/advanced evidence.
```

External:

```text
mountvol <drive> /L Volume GUID is strong when source root is readable.
Volume serial, drive type, and PnP evidence remain supporting unless a future provider safely links them more strongly.
```

Removable:

```text
Probe source type exists, but persisted Source Profile type support is not ready.
Policy matches External when a removable profile can be safely represented.
Not manually tested in this milestone.
```

NAS:

```text
UNC server/share is strong durable identity when the share/root/folder path is readable.
The selected folder remains the Source Profile observed/runnable path.
```

iCloud:

```text
Provider-specific identity. Generic filesystem endpoint verification does not apply.
```

## 6. Windows Probe Findings

The misleading command warning was caused by truncating command display to the first four arguments. For example, `cmd /c fsutil fsinfo drivetype C:` could be shown as only `cmd /c fsutil fsinfo`.

Fixed:

```text
Read-only command warnings now include the full safe command argument summary.
```

Volume GUID findings:

```text
mountvol <drive> /L is read-only and produced a masked Volume GUID during validation.
Volume GUID evidence is now classified as durable.
```

fsutil findings:

```text
fsutil warnings can still occur under non-admin/runtime constraints.
They are treated as warnings, not proof of failure, when stronger mountvol GUID evidence is available.
Transient command warnings no longer invalidate an otherwise identical reviewed enrollment plan.
```

Observed manual warnings:

```text
Local validation: command_access_denied
External validation: command_timeout
NAS validation: none
```

## 9. Source Label vs Endpoint Alias Clarification

Current implementation:

```text
Source Label remains the operator-facing source name.
Endpoint Alias still exists for endpoint records, but defaults from Source Label.
Source Root remains the current observed/runnable path.
```

Recommended product language:

```text
Source Name: user-facing workflow name.
Durable Identity: machine-readable source/device/share identity evidence.
Source Root: current path or UNC folder used to run intake.
```

Post-closeout NAS UI observation:

```text
Creating additional NAS Source Profiles with new labels and deeper root paths under
\\HENDERSON-NAS\Photos showed an Enrollment Plan state of "Duplicate Match."

This is expected under the current NAS durable identity policy because NAS endpoint
identity is server + share, not the deeper folder. A Source Profile rooted at:

\\HENDERSON-NAS\Photos\Dad Files\...

matches the existing NAS endpoint for:

\\HENDERSON-NAS\Photos

The full configured folder still remains the Source Profile's observed/runnable root.
```

Operator impact:

```text
This is not a duplicate Source Profile error. It means a matching NAS share endpoint
already exists and should be selected/linked.

The current UI wording is confusing because "Duplicate Match" reads like a problem.
Future UI should say something closer to "Existing NAS share endpoint found" and show
the durable share identity, e.g. \\HENDERSON-NAS\Photos.
```

External comparison:

```text
The operator did not observe the same behavior during similar External source testing.
The known reason in this validation environment is that the NAS test endpoint already
existed from 12.63.10, while the External test path did not have an equivalent
successfully linked matching endpoint at the time of testing.

Product note: External endpoint duplicate matching is also volume-identity based when
a durable Volume GUID endpoint exists. Future UI should explain this similarly if
multiple External Source Profiles intentionally share the same physical/logical volume.
```

## 14. Risks / Known Limitations

Removable persisted Source Profile support is still absent.

`fsutil` evidence remains best-effort under non-admin Windows constraints. This is acceptable because `mountvol <drive> /L` provides the strong Volume GUID evidence used for Verified.

Local and External are verified at the volume level plus source root scope. They do not yet prove a specific physical USB device instance beyond the volume identity.

Browser UI validation was not performed in this turn.

Initial live Create Source Profile testing exposed a false blocked confirm when a bounded `fsutil` timeout appeared in the reviewed plan but not in the recomputed confirm plan. This was fixed with a regression test.

NAS duplicate-match wording remains a UI/product limitation. The behavior is technically
consistent with server/share identity, but normal operators need clearer language and
preferably auto-selection when there is exactly one strong NAS endpoint match.

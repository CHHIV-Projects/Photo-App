# 12.63.2 Read-Only Source Identity Probe Recon Closeout

## 1. Scope Completed

This read-only reconnaissance inspected what source identity evidence is available on the current Windows development environment for future Source Profile / Source Endpoint work.

Inspected:

- Local host/local volume evidence.
- Ready local/removable/external drives currently visible as `C:`, `D:`, `E:`, and `H:`.
- Additional visible but unavailable `G:` filesystem drive/slot.
- USB drive in `D:`.
- External HDD in `E:`.
- SD card in `H:`.
- Network/NAS mapping visibility.
- Cloud source identity boundary conceptually only.
- Current code integration points for source profiles, Source Intake launch, readiness, provenance, and UI/API payloads.

No code, schema, frontend, tests, migrations, scripts, runtime data, Source Intake, iCloud acquisition, cleanup, DB writes, file copies, file deletion, drive-letter changes, mount/unmount actions, or credential/session probes were performed.

## 2. Executive Findings

Available non-admin evidence:

- Host identity is available from environment variables, but should be treated as privacy-sensitive.
- Drive letters and basic readiness are available through PowerShell/.NET and `fsutil`.
- Volume label, filesystem, drive type, size/free space, and readiness are available through `.NET DriveInfo`.
- Volume serial numbers are available for ready drives through `vol` and, for some drives, `fsutil fsinfo volumeinfo`.
- Volume GUIDs are available for ready mounted drives through `mountvol`.
- Connected disk-device and USB/PnP evidence is available through `pnputil` without elevation.
- `pnputil` can show DiskDrive, Volume, WPD, and USB class devices, including USBSTOR instance IDs, VID/PID-like USB identifiers, and device descriptions.

Weak or unavailable evidence in this shell:

- `Get-Volume`, `Get-Disk`, and `Get-Partition` were access-denied.
- `Get-CimInstance` and `wmic path` for Win32 logical disk, disk drive, partition, association, and CD-ROM classes were access-denied.
- `Get-PnpDevice` was access-denied.
- `Get-SmbMapping` was access-denied.
- `net use` showed no mapped network drives.
- `\\HENDERSON-NAS` was supplied and probed. The server endpoint produced an access-denied response to share enumeration, so a NAS server endpoint is observable, but no share/root path was confirmed.
- No optical/removable disc media was available for direct testing.
- Non-admin commands did not produce a clean built-in join from drive letter to partition to physical disk serial.

Most important conclusion:

The first app-level probe should be designed around non-admin evidence that actually worked:

```text
DriveInfo + vol + mountvol + fsutil drivetype/volumeinfo + pnputil
```

Storage/WMI/CIM evidence may be useful as optional enrichment later, but should not be required for v1 readiness because it was blocked in the current operating shell.

Source types ready for first implementation design:

- Local: yes, using host + volume + selected root path.
- External Device: yes, but first pass should use volume identity plus PnP evidence and a Needs Review tier when physical mapping is incomplete.
- Removable Media / SD card: partially; SD card evidence exists, but durable media identity is weaker than external HDD/USB identity.
- Cloud: yes conceptually; keep separate from local probe design.

Source types needing more investigation:

- NAS: `\\HENDERSON-NAS` is observable as a server endpoint, but shares were not listable without access, no mapped drive exists, and a runnable Source Profile still needs an intended `\\server\share` or folder path.
- Optical media: no inserted optical media was available; media/session identity remains unvalidated.

## 4. Local Evidence Findings

Local evidence observed:

- Host/computer identity is available from environment variables.
- `C:` is ready and identified as a fixed NTFS drive.
- `C:` has a volume label, volume serial number, and `mountvol` volume GUID.
- `C:\` exists and is basically readable.
- Example local paths such as `C:\Photos` and the current user Desktop path were not present in this environment during the probe.
- `fsutil fsinfo volumeinfo C:` returned access denied even though `.NET DriveInfo`, `vol C:`, and `mountvol C: /L` worked.

Recommendation:

Local identity should be:

```text
host identity + local volume identity + selected root path
```

Local source identity should not be volume-only. `C:\Photos` and Desktop on the same machine/volume must be distinguishable by selected root path. The selected root path remains meaningful for local sources, while host/volume evidence helps detect unexpected machine/volume changes.

Stable enough to be useful:

- Host identity, if stored carefully.
- Volume GUID from `mountvol`.
- Volume serial from `vol`.
- Filesystem and fixed/removable type as supporting evidence.
- Selected root path.

Too volatile or insufficient alone:

- Drive letter alone.
- User-entered label alone.
- Free space.
- Volume label alone.
- Host name alone.

Storage recommendation:

- Store host identity hashed or as a stable internal fingerprint.
- Store volume GUID and volume serial hashed or encrypted/masked if treated as sensitive.
- Store selected root path raw because it is operationally required, but show it in normal UI only where useful.

## 5. External Device Evidence Findings

Drives tested:

- `D:` user-described USB drive.
- `E:` user-described external HDD.

Observed for `D:`:

- Ready.
- Reported as Removable by `.NET DriveInfo` and `fsutil`.
- FAT filesystem.
- No volume label.
- Volume serial present.
- `mountvol` volume GUID present.
- `pnputil` DiskDrive and Volume/WPD evidence present for a Generic Flash Disk.
- `pnputil` USB class evidence shows USB mass storage VID/PID-style evidence and a serial-like instance identifier.

Observed for `E:`:

- Ready.
- Reported as Fixed by `.NET DriveInfo` and `fsutil`, despite being an external HDD.
- exFAT filesystem.
- Volume label present.
- Volume serial present.
- `mountvol` volume GUID present.
- `pnputil` DiskDrive and USB class evidence present for the external HDD.
- `pnputil` WPD evidence includes the device/volume display label.

Can Windows map drive letter to partition to disk to device identity?

- In this non-admin shell, not through `Get-Disk`, `Get-Partition`, `Get-CimInstance`, `wmic path`, or `Get-PnpDevice`; all were denied or unavailable.
- `pnputil` exposes device identity evidence, but the raw command output does not provide a clean direct drive-letter-to-disk join.
- `WPD` entries can sometimes bridge the gap:
  - `D:` appeared directly as a WPD device description tied to a USBSTOR instance.
  - `E:` appeared by volume/device label, which can be correlated but should not be treated as a guaranteed join.

Auto-discovery feasibility:

- Feasible at medium confidence using volume GUID/serial plus `pnputil` device evidence.
- Stronger if a future probe can reliably join current drive letter to PnP/USBSTOR instance ID.
- Without that join, auto-discovery should fall back to Needs Review when multiple devices have similar labels/sizes/filesystems or when only volume evidence matches.

Likely durable identifiers:

- PnP USBSTOR/USB instance identifiers, with privacy masking.
- Volume GUID.
- Volume serial.

Supporting identifiers:

- Volume label.
- Filesystem.
- Drive type.
- Size/capacity.
- USB VID/PID/product/manufacturer descriptions.

Evidence sufficient for auto-match:

- Same volume GUID and volume serial, plus compatible filesystem/size, and no conflicting PnP evidence.
- Or same PnP USBSTOR instance plus matching volume evidence.

Evidence requiring Needs Review:

- Only label/size/filesystem match.
- Volume serial match but volume GUID changed.
- Device appears through PnP but volume evidence cannot be read.
- External HDD appears as Fixed and cannot be differentiated from local fixed disks except by PnP/label evidence.

Evidence that should block:

- Observed drive letter resolves to a different stored volume GUID/serial.
- PnP device evidence contradicts enrolled endpoint.
- Multiple possible matches.
- Path unavailable or access denied.

## 6. Removable Media Evidence Findings

Drive tested:

- `H:` user-described SD card.

Observed for `H:`:

- Ready.
- Reported as Removable by `.NET DriveInfo` and `fsutil`.
- FAT32 filesystem.
- Volume label present.
- Volume serial present.
- `mountvol` volume GUID present.
- `pnputil` DiskDrive evidence reports an SDHC Card device.
- `pnputil` USB evidence separately reports a Realtek card reader device.
- `pnputil` WPD evidence reports the SD card label/volume.

Can Windows distinguish reader device from inserted media?

- Partially, yes, through `pnputil`:
  - The reader is visible as a USB card reader device.
  - The inserted media/volume is visible separately as an SDHC Card / WPD volume.
- The evidence did not include a strong card-native serial or media/session ID in the non-admin output.

Can durable media identity be read without scanning content?

- For this SD card, only weak-to-medium media evidence was visible: volume label, filesystem, volume serial, volume GUID, size, and SDHC/PnP description.
- The observed volume serial looked generic/default-like, so it should not be trusted alone.

Would SD/camera cards behave as External Device or Removable Media?

For this environment, SD cards behave more like Removable Media:

- Windows reports `H:` as Removable.
- Reader device and inserted media evidence are separable at the PnP description level.
- Durable media identity is weaker than external HDD/USB mass storage identity.

Recommended v1 posture:

- Treat SD/camera cards as Removable Media when they are reported as Removable and reader/media are separable.
- Use volume GUID/serial/label/filesystem/size as a medium or weak match.
- Require operator confirmation if evidence is generic, missing, or changed.

Optical media:

- No optical media/drive was visible through non-admin `DriveInfo`.
- `Get-CimInstance Win32_CDROMDrive` was access-denied.
- `wmic cdrom` alias was unavailable.

Safe follow-up commands if optical media is later available:

```powershell
[System.IO.DriveInfo]::GetDrives()
cmd /c fsutil fsinfo drivetype <drive>:
cmd /c vol <drive>:
cmd /c mountvol <drive>: /L
cmd /c pnputil /enum-devices /connected /class CDROM
cmd /c pnputil /enum-devices /connected /class Volume
```

Do not perform large content hashing for v1. A shallow disc/session evidence probe should come before any content-fingerprint design.

## 7. NAS Evidence Findings

NAS/mapped drive evidence in this run:

- `net use` reported no mapped network drives.
- `Get-PSDrive -PSProvider FileSystem` showed only local/removable drive roots, no `DisplayRoot` network mapping.
- `Get-SmbMapping` was access-denied.
- `\\HENDERSON-NAS` was supplied as a NAS server endpoint.
- `Test-Path "\\HENDERSON-NAS"` returned `False`.
- `cmd /c net view \\HENDERSON-NAS` returned `System error 5 has occurred. Access is denied.`
- No share path such as `\\HENDERSON-NAS\<share>` was supplied, and no NAS share contents were enumerated.

Can mapped drives be resolved to UNC?

- Not validated because no mapped drive was present.
- `net use` should be the first non-admin source for mapped letter to UNC resolution when mappings exist.
- `Get-SmbMapping` may not be reliable in the app context because it was access-denied here.

Can `\\server\share` and `\\ip-address\share` be reconciled?

- Not validated to the share level in this run.
- `\\HENDERSON-NAS` is enough to identify the intended NAS server endpoint for discussion, but it is not enough to identify a runnable source root.
- A future NAS validation should compare mapped drive from `net use`, direct UNC share path, IP-based UNC share path, DNS/hostname aliases, reachability/readability, and operator-confirmed equivalence.

What non-secret endpoint/share evidence is available?

- NAS server identity: `\\HENDERSON-NAS` is user-supplied and observable enough for Windows to return an access-denied enumeration result.
- NAS share identity: not available. Share names were not visible without access, and no intended share path was supplied.
- Source root/folder within a share: not available. A runnable profile needs at least `\\HENDERSON-NAS\<share>` or a folder below that share.
- Observed access path: server-only UNC endpoint, with no mapped drive and no share path.
- Expected v1 evidence should remain non-secret: canonical UNC server/share if accessible, mapped drive letter when present, provider path, reachability/readability, and optional server/share name hash.

Mounted versus not mounted:

- If the NAS is mounted to a drive letter, `net use` can usually expose the drive-letter to UNC-share relationship, making normalization easier.
- If the NAS is not mounted, a direct UNC share path can still be valid. The app should not require a mapped drive if `\\server\share` is readable and confirmed.
- `\\HENDERSON-NAS` alone is sufficient as a server endpoint seed, but not as a Source Profile root.

Should block a run:

- Configured mapped drive missing when the enrolled profile depends on that mapped letter.
- Configured UNC share/root unavailable.
- Observed path resolves to a different share than enrolled.
- Access denied or OS credential prompt required.
- Multiple possible matches.

Safe follow-up commands when NAS is available:

```powershell
net use
Get-PSDrive -PSProvider FileSystem
Test-Path "\\HENDERSON-NAS\<share>"
Get-Item "\\HENDERSON-NAS\<share>"
```

Avoid credential-store queries, do not mount the NAS as part of probing, do not collect usernames/passwords, and do not enumerate unrelated shares.

## 9. Identity Confidence Proposal

### Common Tiers

Strong match:

- Durable endpoint evidence matches exactly.
- Observed path is reachable.
- Selected root exists and is readable.
- No conflicting operation is active.
- No contradictory evidence appears.

Medium match / Needs Review:

- Important evidence matches, but one durable field is missing or changed.
- Evidence is enough to suggest the source, but not enough to auto-run safely.

Weak match / Manual Confirmation Required:

- Only label/path/size/filesystem evidence matches.
- Durable IDs are unavailable.
- Evidence may be generic.

Mismatch / Block:

- Observed path maps to a different enrolled endpoint.
- Volume GUID/serial or PnP evidence conflicts.
- Multiple candidate endpoints match.

Unavailable / Not Connected:

- Path does not exist.
- Drive slot visible but not ready.
- Access denied.
- Share unavailable.

### Local

Strong:

- Host identity, volume GUID/serial, and selected root path match.

Medium / Needs Review:

- Host and root match but volume evidence cannot be read.

Weak:

- Only path string exists.

Block:

- Root missing, unreadable, or host/volume evidence contradicts enrolled local source.

### External Device

Strong:

- PnP USBSTOR/USB evidence and volume GUID/serial match.

Medium / Needs Review:

- Volume GUID/serial match but PnP evidence cannot be joined to drive letter.
- PnP evidence suggests the device but volume evidence changed.

Weak:

- Only label/size/filesystem match.

Block:

- Current observed path has different volume/PnP evidence from enrolled endpoint.

### Removable Media

Strong:

- Media/session identifier exists and matches, if future probes can obtain one.

Medium / Needs Review:

- Volume GUID/serial/label/filesystem/size match and media is present.

Weak:

- Generic/default-looking volume serial or label-only match.

Block:

- Reader present but inserted media evidence differs.

### NAS

Strong:

- Mapped drive or UNC resolves to same canonical server/share identity and root exists.

Medium / Needs Review:

- Hostname/IP alias appears likely but unconfirmed.

Weak:

- Path exists but canonical share identity cannot be established.

Block:

- Share unavailable, different share, access denied, credential prompt, or multiple matches.

### Cloud

Strong:

- Provider/account/library profile and staging path align with app-managed Source Profile.

Medium:

- Non-secret account/profile metadata present but provider session unknown.

Block:

- Unsafe staging path, unsupported provider, missing required profile metadata, or conflicting operation.

## 10. Observed Path Resolution Proposal

Setup-time probe:

1. User selects source type and observed path.
2. Probe using non-admin evidence first:
   - `DriveInfo`
   - `vol`
   - `mountvol`
   - `fsutil fsinfo drivetype`
   - `fsutil fsinfo volumeinfo` when available
   - `pnputil`
   - `net use` for mapped drives
   - `Test-Path` / `Get-Item` for an exact UNC share/root when supplied
3. Classify evidence by type.
4. Determine whether endpoint is new, known, ambiguous, or unreadable.
5. Store only after operator confirmation in a future implementation.

Run-time auto-discovery:

- Local: verify configured path, host, volume, selected root.
- External: scan visible ready drives and match volume/PnP evidence.
- Removable: scan ready removable drives and match media/volume evidence.
- NAS: check the stored observed UNC share/root or mapped path. If a mapped drive is used, resolve it through `net use`. If a direct UNC path is used, probe the exact `\\server\share` or selected folder path. Treat server-only paths such as `\\HENDERSON-NAS` as endpoint seeds, not runnable roots.
- Cloud: use cloud-specific readiness and managed staging checks.

Fallback when auto-discovery fails:

- Show Not Connected or Needs Review.
- Let the operator provide/select a new observed path.
- Probe the new path before any run.
- Do not update endpoint identity silently.

Wrong-device/wrong-share handling:

- Block run.
- Report mismatch.
- Do not launch Source Intake.
- Do not update Source Profile root.
- Record failed observation only if future schema supports safe diagnostic history.

Multiple-match handling:

- Block.
- Require operator selection.
- Prefer no automatic match over wrong-source intake.

Identity-unreadable handling:

- Local: allow only if path/root exists and the profile is legacy/path-only; enrolled endpoint profiles should Needs Review.
- External/removable: Needs Review or block, depending on previous confidence and risk.
- NAS: Needs Review if reachable but identity cannot be reconciled, or if only a server endpoint is known and the intended share/root is missing.
- Cloud: use provider-specific readiness.

## 11. Privacy / Storage Recommendations

Store raw:

- Source type.
- Selected source root/folder, because it is operationally required.
- Non-secret provider name.
- Managed staging path for cloud sources.
- Readiness state and timestamps.

Store hashed or encrypted/masked:

- Host/computer identity.
- Volume GUID.
- Volume serial.
- PnP instance IDs.
- USB VID/PID/serial-like identifiers.
- NAS server/share identity if considered sensitive.

Store summarized:

- Drive type.
- Filesystem.
- Capacity bucket or exact size if needed for matching.
- Label presence.
- Manufacturer/product family if useful.

Show in normal UI:

- Source alias.
- Source type.
- Readiness state.
- Connected / Not Connected / Needs Review.
- Selected root/folder.
- Clear blocking reason.

Show only in Advanced Details:

- Masked volume serial/GUID.
- Masked PnP IDs.
- Masked host identity.
- Observed path history.
- Evidence confidence tier.
- Raw blocker codes.

Never store/log:

- NAS passwords.
- Credential-store secrets.
- Apple credentials.
- Tokens.
- Session cookies.
- 2FA codes.
- Full command outputs containing sensitive IDs.

## 13. Risks / Gaps

- Device serial availability: physical serials are not available through the non-admin Storage/WMI paths tested.
- USB bridge behavior: external HDDs may expose bridge/product IDs rather than bare drive serials.
- Drive classification: external HDD `E:` appeared as Fixed, so drive type alone cannot distinguish internal versus external.
- Volume serial collisions: FAT/FAT32/exFAT volume serials may be weak, generic, or change on reformat.
- Volume GUID persistence: useful, but may change after reformat or OS remount history changes.
- PnP association gap: `pnputil` exposes disk and volume/WPD evidence but not a guaranteed normalized drive-letter join in raw output.
- NAS ambiguity: no mapped NAS was present, `\\HENDERSON-NAS` share enumeration was access-denied, and richer SMB mapping APIs were denied.
- NAS share gap: server identity, share identity, source root/folder, and observed access path must be stored as distinct concepts; server-only UNC is not a sufficient runnable root.
- NAS aliases: hostname/IP/share aliases remain unvalidated.
- Removable media weak identity: SD card evidence is likely medium/weak without content/session identity.
- Optical media unavailable: no disc/session evidence validated.
- Permissions: many useful Windows APIs were access-denied in the current shell.
- Privacy: host names, paths, PnP IDs, volume serials, and share names should be treated as sensitive operational evidence.
- Windows-version differences: `wmic` aliases were unavailable and future machines may differ.
- Future mini-server/Linux differences: this Windows probe does not answer Linux/Ubuntu/NAS mount identity.
- Legacy path-only profiles: future endpoint verification should not break existing profiles until explicitly enrolled/upgraded.

## NAS UNC Addendum - `\\HENDERSON-NAS`

The NAS is not currently mounted to a Windows drive letter. `net use` showed no mapped network entries, and `Get-PSDrive -PSProvider FileSystem` showed only local/removable roots.

`\\HENDERSON-NAS` is usable as a NAS server endpoint identifier for discussion and future probing, but it is not a complete source root. `cmd /c net view \\HENDERSON-NAS` returned access denied, so share enumeration is blocked from the current shell. This should be treated as a permission boundary, not as evidence that no shares exist.

The distinction for the next design step:

- NAS server identity: `\\HENDERSON-NAS`.
- NAS share identity: unknown.
- Source root/folder within a share: unknown.
- Observed access path: server-only UNC endpoint, with no mapped drive.

If the NAS is mounted later, the probe should use `net use` to resolve the mapped letter back to its UNC share. If it remains unmounted, the probe can still work from a direct UNC path, but it needs the intended share/root, for example `\\HENDERSON-NAS\<share>` or a folder below that share. The safe next validation, once the intended share is known, is a read-only exact-path check against that share/root without mapping the drive, storing credentials, or enumerating unrelated shares.

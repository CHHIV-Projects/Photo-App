# 1. Goal

Perform the final reconnaissance and design lock for Step 2 of the unified ingestion workflow:

1. Create Source
2. Select Source
3. Run Ingestion

This milestone is reconnaissance and contract design only.

Do not implement Source Selection in this milestone.

The intended operator workflow is:

Choose Source Type  
→ Choose Device  
→ Choose Source  
→ Review Source Root  
→ Select Source  
→ System automatically verifies identity, resolves the current path, checks availability/readiness, and determines the correct ingestion workflow  
→ Step 3 becomes available

The normal operator must not separately press buttons such as:

- Check Readiness
- Verify Source
- Check Identity
- Resolve Path
- Load Profile
- Refresh Source
- Confirm routine identity warnings
- Perform provider-specific technical checks

Those operations must be automatically coordinated by the future `Select Source` action.

The final Source Selection experience should return one of two practical outcomes:

- Source selected and available
- Source not available, with a clear actionable reason

Technical evidence may remain under Advanced Details.

No Source Intake or iCloud Intake may run during Source Selection.

# 4. Current Durable Source Model

Preserve the established model:

## Source Endpoint

Durable device, share, disc, mounted medium, or provider identity.

Examples:

- Local Volume GUID
- External Volume GUID
- Removable Volume GUID
- Optical logical-media fingerprint
- NAS server/share identity
- iCloud provider/account identity

## Source Profile

Source Endpoint + endpoint-relative root + Source settings.

The existing `ingestion_sources.id` remains the Source Profile ID.

## Observed Path

Current or historical access-path evidence.

Examples:

- `C:\`
- `E:\`
- `F:\Photos`
- `\\HENDERSON-NAS\Photos`
- current optical-drive path

Observed Path is not durable identity.

## Device Name

Operator-facing Source Endpoint alias.

Contextual labels may include:

- Device Name
- Media Name
- Disc Name

## Source Name

Operator-facing Source Profile label.

## Source Root

The root belonging to the Source Profile.

For modern filesystem Sources:

Current endpoint access path + endpoint-relative root

The Source Root must not be user-editable during Source Selection.

The intended hierarchy is:

Source Type  
→ Device  
→ Source  
→ read-only Source Root

Show Source Types represented by selectable Source Profiles.

## Device list

## Source list

After selecting Device, show eligible Source Profiles associated with that endpoint.

Use Source Name as the primary label.

## Root display

After selecting Source, show its root read-only.

Do not require a separate root dropdown when Source Profile already determines the root.

Investigate whether any current data model case legitimately allows one Source Profile to have multiple roots. If not, explicitly reject a root dropdown in the final contract.

# 7. Eligibility Rules

The normal Source Selector should prioritize ordinary usable Sources.

Analyze and recommend precise rules for:

- active Source Profiles;
- inactive Source Profiles;
- archived Source Profiles;
- test/validation Source Profiles;
- deprecated Source Profiles;
- provider-specific Sources;
- legacy path-only Sources;
- linked legacy Sources with `endpoint_relative_root = NULL`;
- Sources involved in exact-match conflicts;
- endpoints with no active Sources.

Preferred normal behavior:

- show active Sources;
- exclude inactive validation Sources;
- exclude archived/deprecated/test management records;
- preserve compatibility for legitimate active legacy Sources where safe;
- do not silently hide a real active Source merely because it predates the new model;
- return `Needs attention` when an active legacy Source cannot be resolved safely;
- do not expose duplicate-repair controls in Source Selection.

Document the final recommended eligibility matrix.

Do not implement `SRC-ID-006`.

# 8. Automatic Select Source Contract

The future `Select Source` action must automatically coordinate the checks currently spread across readiness, identity, path, provider, and profile controls.

At minimum, investigate how it should:

1. Load the selected Source Profile.
2. Confirm the Source status is eligible.
3. Load the associated Source Endpoint.
4. Determine the Source Type.
5. Verify durable identity where applicable.
6. Locate or resolve the currently available endpoint path.
7. Combine the endpoint path with `endpoint_relative_root`.
8. Verify that the Source Root is currently available.
9. Perform provider-specific checks for iCloud.
10. Determine the ingestion workflow for Step 3.
11. Return a selected-source context.
12. Return an actionable failure when selection cannot complete.

Do not require the operator to understand or invoke the individual checks.

# 11. Source-Type Resolution Requirements

Define the automatic behavior for every supported Source Type.

## 11.1 Local

Selection should determine:

- registered durable volume identity;
- current readable volume path;
- current Source Root;
- root availability;
- identity match.

A changed path or mount should not establish a new Source.

## 11.2 External

Selection should determine:

- whether the registered external device is connected;
- whether the durable Volume GUID matches;
- its current drive letter or mount path;
- the reconstructed Source Root;
- root readability.

A changed drive letter must not require Source recreation.

## 11.3 Removable

Selection should determine:

- whether the correct flash drive or memory card is inserted;
- whether Volume GUID matches;
- the current drive letter;
- the Source Root;
- root readability.

A different removable medium using the same drive letter must fail selection.

## 11.4 Optical

Selection should determine:

- whether a readable optical disc is inserted;
- whether the disc’s logical optical fingerprint matches;
- whether the expected Source Root exists;
- whether the correct disc remains present.

The optical drive alone is not sufficient.

A different disc in the same drive must fail selection.

## 11.5 NAS

Selection should determine:

- registered NAS server/share endpoint;
- current UNC availability;
- Source subfolder/root availability;
- identity and path consistency.

Mapped-drive letters must not replace canonical NAS identity.

A direct readable UNC path remains valid.

## 11.6 iCloud

Selection should use provider-specific checks.

Investigate how Select Source should automatically determine:

- correct Source Profile/account;
- provider identity;
- authentication/session state;
- managed staging alignment;
- whether the iCloud workflow can be shown in Step 3.

Do not force iCloud through filesystem Volume GUID logic.

Do not run acquisition, inventory refresh, Source Intake, or cleanup.

The normal result should still be:

- Available; or
- Needs attention with a clear action.

# 18. Warning and Acknowledgment Policy

The intended Source Selection experience should not require acknowledgments for routine successful cases.

Analyze every current acknowledgment and classify it as:

- safe to automate;
- impossible to automate;
- should become a hard actionable failure;
- management/debug-only;
- required at Run Ingestion rather than selection.

Preferred rules:

- identity match:
  proceed automatically;
- identity mismatch:
  fail selection;
- unavailable path:
  fail selection;
- wrong removable medium:
  fail selection;
- wrong optical disc:
  fail selection;
- provider session problem:
  fail selection with guidance;
- overlap warnings:
  do not block ordinary selection of an already-created Source;
- endpoint type mismatch caused by legacy records:
  preserve registered identity and surface technical details only when safe;
- ambiguous legacy identity:
  fail with management guidance;
- destructive or run-specific acknowledgment:
  defer to Step 3.

Do not preserve acknowledgments merely because the current UI has them.

# 23. Stop Conditions

Stop and report before recommending implementation if:

- selection requires Source Intake execution;
- selection requires broad readiness redesign;
- a current path cannot be resolved without mutating identity records;
- existing providers cannot be composed safely;
- a Source Profile does not contain enough information to derive its endpoint/root;
- iCloud cannot fit the unified selection result contract;
- Optical selection requires reading file contents;
- Removable selection cannot distinguish changed media;
- NAS selection requires drive-letter identity;
- active legacy Sources would be silently abandoned;
- Step 3 requires a fundamentally different Source model;
- retiring the current controls would remove required safety behavior;
- a new persistent selection table appears necessary;
- multiple implementation milestones are clearly required.

Do not invent a workaround in the reconnaissance milestone.

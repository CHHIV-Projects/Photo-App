## 3. Protocol V1 Contract

`backend/app/windows_helper_shared/protocol.py` defines:

- `PROTOCOL_VERSION = 1`;
- `HelperCapabilityIdentity`;
- versioned collector and capability declarations;
- `HelperProbeRequest` and `HelperProbeResponse`;
- explicit Source-type, probe-mode, result-status, and error-code enums;
- opaque UUID correlation/request and intended Access-Node binding fields;
- normalized identity evidence and fingerprint summaries;
- strict unknown-field rejection through Pydantic `extra="forbid"`;
- bounded strings and lists;
- fail-closed version/capability compatibility helpers;
- deterministic canonical serialization and SHA-256 digest helpers.

The contract intentionally contains no transport, endpoint URL, socket, authentication, credential, token, command-execution, upload, Linux receiving path, Vault path, database path, inventory, candidate, hash-request, transfer, chunk, resume, or acquisition-state field.

The protocol wire models are separate from backend `SourceIdentityProbeResponse`. The wire contract carries normalized, bounded evidence without backend timestamps or flexible raw evidence structures.

## 4. Provider-Native Path Contract

`backend/app/windows_helper_shared/paths.py` freezes these terms:

```text
provider_native_root
provider_native_relative_path
provider_native_full_path
```

All three are Windows-native strings. The contract:

- accepts absolute drive and exact UNC server/share roots;
- normalizes separators with `ntpath`, never POSIX path functions;
- reconstructs full path from root plus relative path;
- compares Windows paths case-insensitively for containment and canonical digests;
- rejects parent traversal, cross-drive/cross-share escape, drive-relative roots, device-namespace roots, absolute relative paths, alternate-data-stream syntax, reserved device names, control characters, and ambiguous trailing dot/space components;
- never converts a Windows path into a Linux path.

The Linux runtime/receiving path concept is absent from protocol v1.

## 5. Extracted Windows Identity Collectors

The former monolithic backend provider implementation is now the canonical backend-neutral `WindowsIdentityCollector` in `backend/app/windows_helper_shared/identity/windows.py`. It consumes an observational `IdentityCollectionRequest` and returns an `IdentityCollectionResult` made only from shared models.

Windows command execution, path probing, mapped-drive resolution, Optical manifest reading, parsing, normalization, masking, evidence classification, and safety observations are inside that shared collector. Endpoint comparison authority is not.

### Local

Local collection preserves:

- Windows root/folder classification;
- read-only existence/readability evidence;
- volume GUID and serial collection;
- strong v2 volume GUID fingerprint inputs;
- system-volume and storage metadata behavior;
- broad system-drive warning behavior;
- no PowerShell storage query when a sufficient Local mountvol GUID is already available.

### External

External collection preserves:

- volume GUID as durable identity evidence;
- serial, bus, media, partition, disk, and physical-disk supporting evidence;
- partial/non-admin drive-to-device limitations;
- masked raw identifiers;
- observational confidence behavior without Endpoint matching.

### Removable

Removable collection preserves:

- volume and storage evidence;
- removable/card-reader classification;
- system-disk exclusion;
- empty-slot/no-readable-media blockers;
- ambiguous or insufficient device evidence handling.

Drive letter remains an observed path only. Golden tests prove the same GUID at another letter produces the same v2 fingerprint and a different GUID at the same letter produces a different fingerprint.

### Windows NAS

Current parity is preserved:

- mapped drive resolution to canonical UNC evidence;
- canonical server/share identity;
- mapped drive rejected as Local;
- unresolved mapped NAS blocked with a safe UNC action;
- server-only NAS root blocked as non-runnable;
- no change to the accepted Mounted NAS preference where Linux already has direct access.

### Optical

Optical v2 behavior remains unchanged:

- physical-device requirement and virtual-drive rejection;
- empty/unreadable, audio, movie-disc, timeout, and incomplete-evidence blockers;
- complete metadata-only manifest collection;
- double-observation stability behavior;
- timestamp, drive-letter, reader-hardware, free-space, and used-size exclusions already accepted by v2;
- stable disc fingerprint and changed-manifest fingerprint divergence;
- no Optical writes and no live hardware requirement.

## 8. Protocol Version / Capability Behavior

Protocol version 1 is explicit in every capability/probe message. Any other protocol version raises `ProtocolCompatibilityError` through the compatibility helper and fails Pydantic message validation.

Capability identity requires:

- Helper version;
- Windows platform;
- unique supported Source types;
- unique collector names and versions;
- every advertised Source type to be backed by a collector;
- unique named capability versions.

An exact required capability/version mismatch fails closed. There is no silent downgrade and no upgrade negotiation or transport behavior yet.

## 9. Canonicalization / Digest Behavior

Canonical messages use:

```text
domain: photo-organizer-windows-helper-protocol-v1
encoding: UTF-8 JSON
JSON keys: sorted
separators: compact
digest: SHA-256 with sha256: prefix
```

Machine-authority fields, message type, and protocol version are included. Windows paths are normalized case-insensitively. Capability/source-type/evidence collections are deterministically sorted where order is not semantic.

Human detail, display/masked text, root-reason prose, and volatile timestamps are excluded from the response digest. A different durable fingerprint changes the digest. Two messages with different human detail or equivalent Windows path case/capability order retain the same digest.

## 10. Redaction / Error Contract

Machine decisions use closed enums such as:

```text
success
unavailable
identity_ambiguous
identity_mismatch
invalid_root
unsupported
probe_failed
```

`MachineIssue` permits only a stable code, optional normalized evidence code, bounded redacted detail, and bounded next action. Unknown fields are rejected. There is no field for credentials, tokens, environment values, commands, stdout, stderr, raw PowerShell output, or arbitrary payloads.

The extracted collector retains established masking and generic command-failure messages. Existing regression tests prove raw serials, GUIDs, command strings, and optional command output are not exposed in public probe responses.

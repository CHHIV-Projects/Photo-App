## 2. Existing UX / Architecture Audit

The accepted architecture already contains the correct underlying conceptual layers:

1. `AccessNode` identifies a machine/runtime that can provide access.
2. `SourceEndpoint` identifies a durable physical or logical Source device.
3. `IngestionSource` is the durable Source Profile and carries the bounded endpoint-relative root.
4. provider-specific readiness resolves current access and Runtime Root.
5. common Source Intake remains the ingestion authority after provider acquisition.

The current UI exposes too much of layers 1 and 4 during ordinary Source setup. `IngestionView` presents `Access location`, `This server`, and `Windows device`; `WindowsSourceCreation` always asks for a Windows computer, Source device name, exact Windows folder, and Profile name; and Windows enrollment is labeled `Add / Pair Windows Device`. These controls accurately reflect implementation history but conflate computer registration, Source-device identity, and current access routing.

The Source Selector is structurally sound: it already groups by Source Type, Endpoint-derived device label, and Profile. Provider routing is derived from durable bindings through `provider_kind`, not merely from labels or path appearance. The redesign can therefore simplify presentation without replacing Source Endpoint/Profile, Windows Helper, Mounted Source Provider, iCloud, or common Source Intake.

## 3. User-Facing Concept Model

The controlling user-facing model is:

```text
COMPUTER
Who may Photo Organizer communicate with?

SOURCE DEVICE / ENDPOINT
What durable physical or logical device supplies the photos?

SOURCE PROFILE
What bounded folder/root on that device is configured?

INGESTION
Which saved Profile should run now?
```

Normal users should see computers only when registering Windows access, choosing among multiple computers for a Local Source, or resolving an exceptional portable-device route ambiguity. They should not need to understand AccessNode, Helper transport, Linux namespace slots, broker paths, mount propagation, or acquisition receiving paths.

The normal Source Types should be:

- Local;
- External;
- Removable;
- Server;
- NAS;
- iCloud;
- Optical, visibly deferred or omitted from actionable choices until supported.

## 4. Windows Computer Registration

Use the user-facing term `Register Computer`. Keep `pairing` as an internal security/protocol term.

The simplest v1 placement is a compact `Computers` or `Manage Computers` control near the Ingestion page's `Add Source` control. When a user chooses Local and no registered Windows computer exists, the form should link to or open the same registration flow as a prerequisite. Registration should not be repeated inside every External or Removable Source form.

The accepted 12.66.9 mechanism remains suitable:

- user supplies an immutable friendly computer name;
- the UI prepares a one-time authorization;
- the user runs the bounded command against the already-installed Helper;
- the Helper retains its hidden pairing-code prompt;
- AccessNode ID plus authenticated credential remain authority;
- registration creates no Source Endpoint or Profile by itself.

Helper 0.5.1 capability/heartbeat identity has no hostname field. Automatic hostname suggestion would therefore require a Helper/protocol change. It is optional and is not justified for 12.66.9.2. Retain the user-entered friendly name and park hostname suggestion as a usability enhancement.

Existing normal-flow duplicate protection remains bounded to known AccessNode IDs and case-insensitive aliases. Helper 0.5.1 has no independent physical-computer fingerprint; intentionally re-pairing the same physical computer under a wholly different alias cannot be detected strongly. That limitation does not justify a new machine-fingerprint system in 12.66.9.2.

## 5. Local Source Definition

User-facing definition:

```text
Local = storage physically local to a registered Windows computer.
```

Desired v1 presentation:

```text
one registered Windows computer
→ one supported Local Endpoint
→ zero or more Local Source Profiles
```

The Local Endpoint may correspond to one approved local volume on that computer. Multiple folders on that same volume are Profiles beneath the same Endpoint; they must not create additional Endpoints.

The durable identity reality is narrower than the presentation: Windows Local identity is currently a Volume GUID v2 fingerprint, not a computer fingerprint. This is an important and accepted safety boundary. The UI may describe Local as “this registered computer,” but implementation must continue proving and containing the selected folder on the enrolled volume.

## 6. Local Endpoint / Profile Invariant

The current schema does not enforce one Local Endpoint per Windows AccessNode. `SourceEndpoint` has uniqueness for endpoint UUID and normalized alias, while `created_from_access_node_id` is an ordinary nullable foreign key. `SourceEndpointObservedPath` permits an Endpoint to have AccessNode-specific observations. Current Source creation matches Local, External, and Removable Endpoints globally by durable fingerprint and can therefore create another Local Endpoint for a different internal volume observed by the same computer.

The bounded v1 invariant should be enforced in the Windows Local creation service, without weakening the volume fingerprint:

- find active Local Endpoints observed by the selected registered computer;
- zero matches: permit creation only after the existing strong volume-identity and containment checks pass;
- exactly one match with the same durable volume fingerprint: reuse that Endpoint and create/reuse the bounded Profile;
- exactly one Local Endpoint but a different internal-volume fingerprint: block with a clear “additional local volumes are not supported in v1” result;
- multiple active Local Endpoints: fail closed for operator review rather than choosing or rewriting one.

A broad database constraint on `created_from_access_node_id + source_type` is not recommended: `created_from_access_node_id` records creation provenance, while observed paths represent current routing, and portable endpoints may be observed elsewhere. A service-level invariant over active Windows observations is the cleaner bounded v1 rule. Focused tests must cover same-volume reuse, different-volume denial, and ambiguous historical state.

Existing Endpoint 2 (`Chuck_Notebook`) and Profiles 3 and 4 are already the compatible shape: one volume-backed Local Endpoint with multiple bounded Profiles. They must remain unchanged.

If multiple internal physical volumes are required later, the clean future option is to expose multiple durable volume-backed Local devices beneath one computer while preserving one Endpoint per physical volume. It would be misleading and unsafe to force several physical volumes into one Endpoint or to replace Volume GUID identity with a computer alias.

## 7. External Source Identity Across Computers

The durable model already supports AccessNode-independent External identity in its important parts:

- Volume GUID v2 supplies the durable device fingerprint;
- matching is global by fingerprint rather than scoped to one AccessNode;
- `SourceEndpointObservedPath` can associate one Endpoint with observations from multiple AccessNodes;
- drive letter is runtime evidence only;
- current mounted-volume resolution requires exactly one matching volume and detects a different device at the historical letter.

The current blocker is routing, not identity. `windows_helper_profile_binding()` currently collects all active Windows AccessNodes that have ever observed the Endpoint and requires the total to equal one. Two observations make the binding ambiguous even if only one Helper is online.

12.66.9.2 should resolve routes as follows:

- exactly one online, paired, active Helper observes the fingerprint: select that route automatically;
- zero online matches: keep the Endpoint/Profile visible and report `Device not connected` or `Computer not available` as appropriate;
- more than one online matching route: fail closed on automatic routing and expose an exceptional route/computer selector;
- never create another Endpoint merely because another registered computer observes the same fingerprint.

The backend must remain authoritative. The exceptional selector chooses among already verified routes; it does not choose device identity.

## 8. Removable Source Identity Across Computers

Removable uses the same Volume GUID v2 fingerprint, observed-path model, mounted-volume observation, and exactly-one-device resolution as External. It therefore has the same partial portability support and the same current AccessNode-binding limitation.

Apply the identical route policy:

- one online matching Helper route: automatic;
- none: visible but unavailable;
- multiple: fail closed and request an exceptional route choice;
- same device on another computer: reuse the Endpoint and Profiles;
- different device at the same drive letter: identity mismatch and no automatic reuse.

Normal Create Source and Source Selector flows should focus on the removable device alias and Profile, not the observing computer.

## 9. Server Source Type

Add `Server` as a presentation type over the accepted Mounted Linux Local provider.

For v1:

```text
Server = storage local to the machine hosting this Photo Organizer installation.
```

Do not add a persisted `server` Endpoint or Profile type. Existing durable values should remain:

- Endpoint `source_type = local`;
- Profile `source_type = local_folder`;
- provider kind derived as `mounted`;
- stored Linux location and filesystem UUID evidence unchanged.

Frontend/backend presentation mapping should classify `provider_kind = mounted` plus Endpoint type `local` as `Server`, while `provider_kind = windows_helper` plus Endpoint type `local` remains `Local`.

The only configured server-local location today is `linux-local-server-photos`, displayed as `Server Photos`, with fixed host/runtime slots and a strong filesystem UUID. This is a deliberate safety boundary, even if its singularity is historically hard-coded. v1 should use explicitly configured/admin-approved roots; it should not browse the host filesystem or discover arbitrary roots.

Supporting additional server-local roots later is feasible by generalizing the protected location registry and namespace/configuration tooling while retaining explicit approval, stable slots, filesystem identity, and containment. It is not required for 12.66.9.2.

## 11. NAS Current Architecture

The current Mounted NAS path is a safe, accepted, single-share implementation:

- location ID: `linux-nas-photo-organizer`;
- display name: `Photo Organizer NAS`;
- canonical CIFS source: `//192.168.1.171/PhotoOrganizer`;
- authoritative target: `/mnt/nas/photo-organizer`;
- namespace slot: `/mnt/photo-organizer-sources/nas/photo-organizer`;
- runtime slot: `/app/sources/nas/photo-organizer`.

Generic elements already present:

- protected config contains a bounded `locations` list;
- broker requests address a `location_id` and contained relative root;
- application schemas can return multiple browser-safe locations;
- Endpoint/Profile creation, readiness, selection, and relative-root containment are location-driven;
- broker config validation already bounds the list to at most 64 unique location IDs and enforces fixed namespace prefixes.

Single-NAS hard-coding remains in:

- the example/protected configuration generator;
- namespace script constants and one-slot lifecycle;
- broker canonical-source constant and exact validator;
- broker NAS fingerprint parts;
- application provider invariant requiring the one canonical CIFS source;
- broker health checker expecting exactly the current Local and NAS IDs;
- focused systemd/namespace/broker tests.

Current NAS Endpoint identity represents a configured server/share tuple, not a NAS appliance independent of its network address. The fingerprint is derived from `nas + 192.168.1.171 + photoorganizer`; an IP change changes identity even if the appliance/share is otherwise the same.

## 12. Second-NAS Behavior Today

A second NAS cannot be added safely through configuration alone today.

- Adding another config row would pass the outer list shape only if its fields were structurally valid, but broker validation rejects any NAS canonical source other than the one fixed share.
- The namespace script manages exactly one NAS authority and one NAS slot.
- The config generator emits exactly one fixed NAS row.
- The broker verifier and Linux provider require the fixed canonical source.
- The health checker expects exactly two total locations.

Therefore, a second NAS is rejected rather than silently accepted or merely hidden. Hard-coding another share into parallel constants would repeat the limitation and is not an acceptable product model.

## 13. Multi-NAS Options

### A. One administratively configured NAS, cleaner UI

Pros:

- smallest 12.66.9.2 scope;
- preserves fully validated mount, namespace, broker, identity, and rollback behavior;
- no new credential or discovery surface.

Cons:

- cannot add a second NAS without code/host-tool changes;
- remains deployment-specific rather than a general enrollment model.

### B. Multiple explicitly registered NAS/share locations

Pros:

- supplies the necessary generalized product foundation;
- keeps registration intentional and authenticated;
- supports multiple appliances and multiple shares per appliance;
- avoids making network discovery an authority.

Cons:

- requires a protected durable NAS/share registry;
- requires per-location authority mounts and namespace slots;
- requires generalized activation, rollback, validation, health checks, and credential handling;
- requires a stable appliance/share identity design that does not use IP alone.

### C. Discovery-assisted explicit registration

Pros:

- best matches the desired user workflow;
- reduces manual hostname/address entry;
- can present candidate appliances and shares before explicit registration.

Cons:

- discovery coverage varies by network and NAS configuration;
- mDNS, WS-Discovery, or NetBIOS results are hints, not durable identity or proof of access;
- share enumeration may require authentication and must not expose credentials;
- larger security, timeout, duplicate-detection, and test surface.

Recommendation: retain A only for 12.66.9.2, then implement a separate 12.66.9.3 whose authoritative core is B and whose bounded convenience layer is C. This yields the desired eventual product flow without coupling mount authority to discovery.

## 14. NAS Discovery Options

Discovery should be opt-in, bounded, read-only, and advisory. Plausible candidate mechanisms include:

- mDNS/DNS-SD advertising SMB service;
- WS-Discovery where enabled;
- NetBIOS/SMB host discovery where available;
- direct user entry of hostname/address when discovery is absent.

Do not rely on legacy broadcast browsing, unbounded subnet scanning, display name, hostname, or IP address as durable authority. Discovery returns candidates only. Registration must still:

1. identify/select an appliance candidate or accept explicit host input;
2. authenticate through protected host-side handling;
3. identify/select a share;
4. obtain and persist an application-generated registered NAS ID plus verified appliance/share evidence;
5. create a unique protected authority mount and stable namespace slot;
6. verify exact source, filesystem type, uniqueness, major/minor relationship, propagation, and containment;
7. create/reuse Endpoint/Profile only through the existing plan/confirm model.

Identity independent of IP needs more than the current canonical UNC string. 12.66.9.3 should investigate a stable SMB server/appliance identifier (for example a server GUID where reliably obtainable), normalized share identity, and an application-generated registration UUID. The generated registration ID should bind to verified evidence; it must not permit a different appliance at the same address to inherit identity silently.

Feasibility is good for explicit multi-location registration because the application/broker schemas already use `location_id` lists. Discovery is also feasible as a convenience layer, but its protocols and reliable server-identity evidence require a dedicated reconnaissance/implementation gate and heterogeneous-NAS testing.

## 20. Source Selector Design

Preserve the routine hierarchy:

```text

→ Source device / Endpoint alias
→ Source Profile
```

Recommended labels and examples:

- Local → `Chuck_Notebook` → `Family Photos`;
- External → `Family Archive Drive` → `Scanned Archive`;

- Server → `Photo Organizer Server` or approved server-location alias → `Server Photos`;

## 21. Disconnected / Offline Behavior

Configured Endpoints and Profiles remain visible when unavailable.

| Condition | Selector state | Action state |
|---|---|---|
| registered Local computer offline | keep computer/Profiles visible; `Computer not available` | Run disabled |
| Local supported volume unavailable | keep Profile visible; `Local storage not available` | Run disabled |
| External/Removable disconnected | keep Endpoint/Profiles visible; `Device not connected` | Run disabled |
| no online Helper route for portable device | keep visible; `Device not connected` or `Computer not available` | Run disabled |
| multiple online routes | keep visible; `Choose access computer` exceptional state | automatic Run disabled until exact route selected |
| Server location unavailable | keep visible; `Server location not available` | Run disabled |
| NAS unavailable | keep visible; `NAS not available` | Run disabled |
| iCloud action required | keep visible with existing provider-specific status | Run disabled until provider readiness passes |

Temporary loss of access must never require Source recreation or durable identity rewriting.

## 26. 12.66.9.2 Implementation Scope

Recommended bounded implementation scope:

1. Replace the permanently expanded Create Source form with `+ Add Source` and add a small `Manage/Register Computers` entry.
2. Rename normal-user pairing language to `Register Computer` while retaining the existing pairing protocol/API authority.
3. Add `Server` to frontend/operator presentation and map it to existing Mounted Linux Local creation, selector, readiness, and workbench behavior.
4. Remove normal `Access Location`, `This server`, and `Windows device` controls.
5. Refactor provider-specific creation forms to the field matrix in section 19.
6. For Local, omit/preselect the computer when exactly one exists; select only when multiple; enforce one supported active Local Endpoint per Windows AccessNode without weakening Volume GUID matching.
7. For External/Removable, present devices rather than computers; reuse fingerprint matches globally across AccessNodes.
8. Change Helper profile routing to choose exactly one online matching AccessNode, report unavailable for zero, and fail closed for multiple.
9. Add the exceptional multi-route selector only for the multiple-online-route state.
10. Preserve configured-but-offline Sources in Source Selector with provider-specific unavailable labels and disabled Run.
11. Keep raw paths and implementation details in Details, not primary labels.
12. Retain current single configured NAS and simplify only its UI label/form.
13. Preserve iCloud and keep Optical explicitly deferred.
14. Add focused backend/frontend tests for classification, Local invariant, route resolution, disconnected visibility, durable-data compatibility, and removal of normal Access Location.

Out of scope for 12.66.9.2:

- Helper rebuild or hostname protocol change;
- new physical-computer fingerprint;
- multiple internal Local volumes;
- new persisted `server` type;
- generalized NAS registry, discovery, credential, mount, or namespace changes;
- Optical implementation;
- ingestion-engine or provenance redesign.

## 27. Possible 12.66.9.3 NAS Scope

Create a separate generalized NAS milestone with explicit pre-implementation design gates. Recommended scope:

1. define registered NAS appliance, share/location, and Profile concepts without replacing Endpoint/Profile;
2. define a durable NAS identity independent of IP alone, including duplicate and changed-appliance behavior;
3. define protected credential storage/rotation and ensure secrets never enter frontend responses, repository files, logs, or Endpoint evidence;
4. generalize the protected location registry for multiple NAS appliances/shares;
5. allocate deterministic unique authority targets, namespace slots, runtime slots, and location IDs;
6. generalize namespace activation, exact mount validation, propagation, rollback, systemd ordering/retry, and health checks for N locations;
7. preserve fail-closed behavior for wrong, missing, duplicate, stacked, or ambiguous mounts;
8. implement multiple explicit registrations as the authoritative minimum;
9. add bounded advisory discovery with direct-entry fallback;
10. validate one appliance with multiple shares and at least two distinct appliances, including IP change and same-IP/different-appliance rejection cases;
11. preserve the current Synology registration and all existing Profile history without re-enrollment unless a separately approved migration is proven necessary;
12. provide explicit admin removal/retirement semantics that do not delete Source history or Source data.

Discovery protocol choice and stable SMB appliance evidence should be resolved early in 12.66.9.3 reconnaissance. They should not be guessed inside a UI implementation patch.

## 28. Risks / Open Decisions

Product decisions required to compose 12.66.9.2 are resolved. Remaining implementation risks are bounded:

- Local's user-facing “computer” concept must not obscure its volume-backed durable identity.
- A service-level one-Local-Endpoint invariant needs careful handling of ambiguous pre-existing rows and concurrent creation.
- Portable route selection must filter for paired, active, online Helpers and must not treat stale observations as active routes.
- Exceptional explicit route selection must be bound to the already matched Endpoint and request, not accepted as identity input.
- `Server` classification must use durable provider metadata, not label/path heuristics.
- The current single NAS fingerprint changes with IP and must not be generalized by simply copying its constants.
- Discovery may be incomplete on real networks; explicit registration must always remain available.
- Stronger Windows physical-computer identity, multiple Local physical volumes, and hostname suggestion remain future enhancements.

No escalation condition was found.

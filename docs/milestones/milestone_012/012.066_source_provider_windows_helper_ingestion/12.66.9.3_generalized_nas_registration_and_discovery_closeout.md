## 4. Generalized NAS Registration Model

The implementation adds durable NAS appliance, share, and immutable pending-registration records. Registration is two phase: the browser creates a secret-free bounded request, then the tracked root installer validates and activates it. Registration remains separate from Source Profile creation.

## 5. NAS Appliance Identity

Each appliance receives an application-generated immutable UUID. A twice-probed SMB2 ServerGuid digest is retained as verified appliance evidence beneath that UUID. Network address alone is not durable identity. A matching appliance may support a controlled address update; conflicting evidence fails closed.

## 6. Share / Location Identity

Each explicitly registered share receives its own immutable share UUID and deterministic `location_id`, authority path, namespace slot, runtime slot, credential target, and systemd unit names. One appliance may own multiple registered shares, and each share maps to one Source Endpoint with zero or more Profiles.

## 7. Stable Identity Evidence

Share identity combines the registered appliance identity and normalized registered share contract. Raw ServerGuid and credentials are not exposed through normal browser APIs or Source evidence.

## 9. Discovery Design

Discovery is bounded, optional, and advisory. It uses the already-installed mDNS/Avahi path and does not scan subnets or ports. Live discovery returned one candidate, `HENDERSON-NAS` at `henderson-nas.local`, with a sanitized address hint. Discovery created no registration, credential, mount, pending request, Endpoint, or Profile.

## 10. Manual Registration Fallback

Manual hostname/IP and share-name entry remains available regardless of discovery results. The browser never supplies host paths, unit paths, credential paths, or shell fragments.

## 11. Share Discovery / Selection

V1 supports explicit manual share-name registration. It does not enumerate inaccessible administrative/system shares. Safe share discovery is not required for registration and was not added.

## 12. Credential Handling

NAS credentials remain terminal-only and hidden. A new registration's root installer writes a generated per-share credential file under the protected credential directory with restrictive metadata. Credentials never enter the pending database record, browser/backend request, repository, command-line arguments, Source identity, or logs. Existing credential content and metadata were unchanged.

## 13. Privileged Host Boundary

The normal backend remains non-root and has no mount authority. Product Owner-executed tracked code performs bounded registration installation. Host targets are generated from validated registration data. The installer validates fixed roots, protected state, identity, ownership/mode, and exact unit contracts and rolls back on failure.

## 14. Authority Mount Allocation

New registrations receive deterministic authority paths beneath `/mnt/nas/photo-organizer-<share-token>` and generated mount/automount units. The accepted existing authority remains `/mnt/nas/photo-organizer`; it was neither replaced nor metadata-mutated.

## 15. Generalized Source Namespace

The base namespace service now prepares only the shared namespace foundation. A per-location template service, `photo-organizer-source-nas@.service`, activates and verifies individual NAS namespace slots. The namespace script validates exact source, target, CIFS type, major/minor relationship, uniqueness, and propagation without stacking or repairing ambiguous mounts.

## 16. Startup / Recovery

The base namespace and broker remain enabled. Each registered NAS location has an independent enabled template instance. Transient location failures are retryable at the location service; strict configuration or identity conflicts fail closed.

## 17. Per-Location Failure Isolation

Broker protocol v2 represents each protected location independently. Ordinary unavailability blocks only that location while healthy Local/Server/NAS locations remain serviceable. Unsafe global configuration, duplicate identifiers, or conflicting protected definitions still fail the relevant authority closed.

## 18. Source Endpoint / Profile Compatibility

Existing Endpoint 1 and Profile 2 remain linked. Profile 2 finished live validation with `readiness_status=ready`, `identity_match_status=matched`, and `can_run_source_intake=true`. Source Profile creation/reuse continues through the accepted durable Endpoint/Profile flow.

## 19. Register NAS UX

The NAS Add Source panel lists registered locations and their independent availability. It provides bounded discovery and manual registration. Preparing registration produces an immutable, expiring, secret-free request and an exact operator command; credentials are not requested in the browser.

## 20. Add Source NAS UX

After registration, the user selects a registered NAS location and supplies an optional bounded folder plus Profile name. Registration and Profile creation remain visibly separate operations.

## 21. Source Selector

The existing NAS remains presented as NAS, not Server or raw Linux mount implementation. Existing Sources remain selectable through the accepted workbench architecture.

## 22. Unavailable / Identity-Conflict Behavior

Unavailable registered locations remain visible with a blocked/unavailable status. A different appliance at a known address, wrong share, duplicate mount, conflicting location, or ambiguous identity fails closed and cannot silently inherit existing Source identity.

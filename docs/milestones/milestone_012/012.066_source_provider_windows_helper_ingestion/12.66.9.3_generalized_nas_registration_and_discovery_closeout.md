## 4. Generalized NAS Registration Model

The implementation adds durable NAS appliance, share, and immutable pending-registration records. Registration is two phase: the browser creates a secret-free bounded request, then the tracked root installer validates and activates it. Registration remains separate from Source Profile creation.

## 5. NAS Appliance Identity

Each appliance receives an application-generated immutable UUID. A twice-probed SMB2 ServerGuid digest is retained as verified appliance evidence beneath that UUID. Network address alone is not durable identity. A matching appliance may support a controlled address update; conflicting evidence fails closed.

## 6. Share / Location Identity

Each explicitly registered share receives its own immutable share UUID and deterministic `location_id`, authority path, namespace slot, runtime slot, credential target, and systemd unit names. One appliance may own multiple registered shares, and each share maps to one Source Endpoint with zero or more Profiles.

## 11. Share Discovery / Selection

## 12. Credential Handling

NAS credentials remain terminal-only and hidden. A new registration's root installer writes a generated per-share credential file under the protected credential directory with restrictive metadata. Credentials never enter the pending database record, browser/backend request, repository, command-line arguments, Source identity, or logs. Existing credential content and metadata were unchanged.

## 13. Privileged Host Boundary

The normal backend remains non-root and has no mount authority. Product Owner-executed tracked code performs bounded registration installation. Host targets are generated from validated registration data. The installer validates fixed roots, protected state, identity, ownership/mode, and exact unit contracts and rolls back on failure.

## 14. Authority Mount Allocation

## 15. Generalized Source Namespace

The base namespace service now prepares only the shared namespace foundation. A per-location template service, `photo-organizer-source-nas@.service`, activates and verifies individual NAS namespace slots. The namespace script validates exact source, target, CIFS type, major/minor relationship, uniqueness, and propagation without stacking or repairing ambiguous mounts.

## 16. Startup / Recovery

The base namespace and broker remain enabled. Each registered NAS location has an independent enabled template instance. Transient location failures are retryable at the location service; strict configuration or identity conflicts fail closed. The broker uses `RuntimeDirectoryPreserve=restart` so its directory bind mount remains stable for the Development backend across broker restarts. A bounded activation opens only the exact registered authority directory, suppresses directory output, and then repeats strict mount-table validation.

## 17. Per-Location Failure Isolation

Broker protocol v2 represents each protected location independently. Ordinary unavailability blocks only that location while healthy Local/Server/NAS locations remain serviceable. Unsafe global configuration, duplicate identifiers, or conflicting protected definitions still fail the relevant authority closed.

### Registration API failures and recurrence protection

During live registration, the installer twice surfaced the user-visible message `Photo Organizer registration API request failed`. The identical outer message covered separate causes:

1. The first attempt used an incorrect NAS username. The installer failed safely, removed the attempted protected artifacts, preserved the existing registered NAS state, and archived bounded rollback evidence. This was an input/authentication failure rather than an application API defect.
2. That attempt also exposed a broker lifecycle defect: restarting the broker replaced the systemd runtime-directory inode while the Development backend retained a bind mount to the old directory. The backend therefore could not reach the new broker socket when the installer called the registration-completion API. The broker unit now uses `RuntimeDirectoryPreserve=restart`, and host validation proves that the directory inode and backend socket path remain usable across a broker restart.
3. The next attempt exposed an automount activation defect: metadata inspection with `stat` did not reliably activate the newly generated systemd automount. The namespace service therefore had not reached its required ready state when API completion was attempted. The namespace implementation now performs one bounded, output-suppressed directory open against only the exact registered authority, immediately revalidates the authoritative CIFS and namespace mount-table identity, and fails closed on wrong or ambiguous evidence. The installer also requires the per-location namespace unit to report `active/exited/success` with exit status zero before it restarts the broker or calls the completion API.

Focused regression coverage locks runtime-directory preservation, exact bounded automount activation, strict post-activation mount identity, namespace readiness before broker/API completion, and rollback on failure. The successful third attempt then proved the corrected sequence end to end: protected registry update, authority automount, Source namespace activation, broker visibility, and registration API completion all passed.

The installer’s outer failure text remains intentionally secret-safe but is still generic. It does not expose whether a failure arose from authentication, namespace readiness, broker connectivity, or API completion. The protected rollback evidence and stage-specific gates preserve diagnosis, but a future usability improvement could return a bounded non-secret failure code or stage name without exposing credentials or protected paths. This remaining presentation limitation does not undo the recurrence protections above.

### Defect discovered

The first Source Profile created beneath a newly registered NAS share displayed a generic editable `Device Name` field. That presentation incorrectly suggested that the operator needed to name another physical device even though the registered NAS share/location already supplied the durable Source Endpoint boundary and its accepted display name. It also allowed a browser or direct API client to propose a label that could diverge from the registered location name.

### Correction implemented

The bounded correction makes the registered NAS share `display_name` authoritative when its exact registered `location_id`, fingerprint hash, and fingerprint version match the live probe and no Source Endpoint exists yet. The planner now automatically chooses `create_new`, supplies that location name as the Endpoint alias, and performs the normal global alias-conflict check. A caller-supplied conflicting label cannot override the registered location name.

The review UI now presents the value as read-only `NAS Location Name` with an explanation that it comes from the registered NAS location. The same terminology is used in the completion result. The create action no longer waits for a redundant editable Device Name. If the share is already linked to an Endpoint, the existing immutable Endpoint alias remains authoritative and is not renamed or rewritten.

For the live `ExternalDrives` state, Endpoint 7 already has the accepted alias `External Drives Copies`; the correction preserves it. The automatic first-Profile behavior applies to later registered NAS locations as well.

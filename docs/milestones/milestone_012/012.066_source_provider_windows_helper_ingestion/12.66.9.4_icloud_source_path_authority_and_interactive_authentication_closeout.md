## 2. Purpose / Accepted Prior State

This milestone corrected two accepted iCloud gaps: browser ownership of an environment-specific staging path and dependence on terminal-driven iCloud authentication. It preserved the accepted provider architecture:

```text
iCloud provider/account
→ iCloud Source Profile
→ Linux provider authentication/acquisition and managed staging
→ common Source Intake
→ Asset / Vault / Provenance
```

It did not add a second ingestion engine, a Windows Helper dependency for iCloud, a password vault, or a new durable cloud identity model.

## 3. Existing iCloud Architecture Audit

The audit found that iCloud Source creation, readiness, exact selection, acquisition, cleanup, and Source Intake already existed, but runtime ownership was split across historical Windows assumptions and the Linux application. The browser generated a relative-looking path, readiness reconstructed another expected root, and the provider adapters retained Windows-local executable/auth-directory fallbacks. The migrated Development backend was already configured with `EXPORTS_ICLOUD_PATH=/app/storage/exports/icloud`, but not every seam treated that configuration as authoritative.

The accepted correction makes the Linux Development backend the iCloud execution owner. iCloud acquisition still terminates in the existing common Source Intake and retains the selected Source Profile ID, normal Asset/Vault behavior, Provenance, duplicate handling, and cleanup.

## 4. Canonical Path Defect

The original browser-created Profile 13 persisted `/storage/exports/icloud/chuck_iphone`, while the backend runtime required `/app/storage/exports/icloud/chuck_iphone`. Selection correctly failed closed with `PATH_MISMATCH`, `SOURCE_ROOT_MISMATCH`, and `SOURCE_REGISTRATION_MISMATCH`; however, creation should never have persisted that immediately invalid contract.

The defect was systemic path-authority drift: a client, backend service, readiness service, and provider adapter each held enough path knowledge to disagree after the Windows-to-Linux migration.

## 5. Backend Path Authority

`icloud_path_service.py` is now the canonical authority. It derives:

```text
configured EXPORTS_ICLOUD_PATH / deterministic sanitized immutable Source-name component
```

The implementation preserves custom runtime roots such as `/app/storage`, rejects a noncanonical client override, prevents traversal outside the configured root, rejects symbolic-link substitution at the root or final canonical path, and fails before durable persistence when the contract is unsafe. A staging-path collision fails closed unless the request is exact idempotent reuse of the same account/Profile contract.

The iCloud Source name and account identity are immutable after creation in this bounded v1 implementation so a cosmetic rename cannot silently change the runtime path key.

## 6. Frontend Creation Contract

The normal UI no longer constructs or submits a runtime staging path. It submits product-level values only: Source name, account identifier, provider, and acquisition method. The former editable field now states that the path is managed automatically by Photo Organizer. The successful creation result may display the backend-derived path as read-only evidence.

The same correction was applied to both ordinary Add Source and the advanced Source editor creation flow. Runtime container or host paths are not browser authority.

Readiness, selection, exact-selection acquisition, and ordinary acquisition resolve the same configured authority. Creation also establishes the managed staging directory through the backend. Run dispatch idempotently ensures the same canonical directory again before preparing or importing, so a missing-but-safe directory is an operational condition rather than an identity repair procedure.

## 10. Authentication Reconnaissance

The bounded reconnaissance established:

- iCloud should execute in the Linux backend, not Windows Helper 0.5.2;
- the required provider exposes the programmatic `pyicloud_ipd` seam;
- authentication can use a fixed isolated helper process and bounded structured messages rather than a terminal or PTY;
- provider cookies/session artifacts are the only required persistent authentication state;
- password and MFA values can remain ephemeral and can travel over the helper's private standard input rather than command-line arguments;
- the provider exposes modern two-factor, legacy verification, expired-session, unavailable-provider, failed-login, and authenticated states that can be normalized safely; and
- acquisition does not need to start as a side effect of authentication.

No unrestricted shell, browser terminal, iframe, or raw provider transcript was introduced.

The exact reviewed source dependency is pinned to upstream commit `879c561240d993d748ddb4546f935090502b16d3` and archive SHA-256 `9b2df95f8286827dd142c396f3b82cb64cb542cd5bb41adf222a954ad27ea74d`.

## 12. Authentication Integration Choice

The implementation uses the preferred programmatic-provider option behind a defensive fixed-command subprocess boundary:

- fixed Python executable and fixed helper script;
- no browser-supplied executable, command, path, or arguments;
- bounded line-delimited JSON request/response protocol;
- provider stderr discarded and provider stdout suppressed except for the bounded response;
- allowlisted state and message validation;
- bounded response size and timeout; and
- process termination on completion, cancellation, expiry, invalid response, or timeout.

This isolates the provider dependency from the main backend environment while retaining structured application-owned UX.

## 13. Authentication Session Model

Interactive authentication sessions are in-memory, short-lived, and tied to an exact Source Profile and normalized account. The default TTL is 600 seconds. A duplicate start for the same Source reuses the bounded session; another active session for the same account is rejected; cross-Source session use fails closed. The provider process exists only while required for password-to-MFA continuity and is terminated at every terminal boundary.

No authentication-session database table was added. A backend restart invalidates an in-progress dialog session but preserves provider cookie/session state.

## 14. Secret Handling

Apple passwords and MFA codes are accepted only by the bounded authentication endpoints, passed to the fixed provider helper over private standard input, cleared from application/helper references as practical, and never included in the subprocess command line. They are not written to the database, Source Profile, files, environment, reports, logs, API responses, frontend persistence, or this closeout.

Only protected provider cookies/session artifacts persist. Normal responses contain a masked account hint, bounded state, safe message, retryability, Source ID, session ID, and expiry. Provider exception details are defensively mapped; protected auth-root paths are redacted from captured provider output.

## 15. Structured Authentication-Required State

Readiness now performs a real provider-session probe when core path/registration checks pass. It returns bounded states including `authenticated`, `authentication_required`, `session_expired`, `authentication_failed`, and `provider_unavailable`. Selection exposes safe blocking reason codes rather than asking the browser to parse provider text.

The probe neither downloads media nor starts acquisition, Source Intake, or staging content mutation.

## 36. Known Limitations / Deferred Work

### iCloud/runtime limitations

- In-memory authentication orchestration is process-local. A backend restart cancels the active modal session, although protected provider cookies persist. A multi-replica deployment would require a shared lease/session coordinator.
- The run worker is currently an in-process Development thread backed by a durable database ledger. A backend restart leaves a resumable durable run; automatic cross-process continuation would require a durable job queue/lease before multi-replica or always-on Production use.
- Apple may lock or throttle an account during authentication. This milestone safely reports a detected lock but cannot determine why Apple imposed it. Future hardening may add an application retry delay/attempt budget without storing credentials.
- Parent iCloud import reports and child Source Intake reports remain separate artifacts. The UI mapping correction is safe, but a future typed report-reference contract would be stronger than passing raw filesystem-like report strings.
- The exact accepted historical non-repeat failure remains deferred unchanged.
- Existing frontend hook/image and Browserslist-age warnings remain pre-existing and nonblocking.

### Windows-to-Linux and Helper systemic observations

- Paths must remain typed by authority: a Windows absolute source path, a Source-relative folder, a Helper transfer token/path, and a Linux managed staging path are different domains. Direct string reuse across those domains caused both the earlier External-folder HTTP 500 and this iCloud `/storage` versus `/app/storage` defect. Every provider should derive runtime paths at the process that owns that filesystem and reject foreign absolute paths with a bounded 4xx response.
- The previously observed Windows External creation defect accepted `E:\...` in a field that required a device-relative folder and surfaced HTTP 500. Using a relative folder succeeded, but frontend validation and bounded backend error translation remain required in 12.66.9.5.
- The previously observed Windows Helper review limit blocked a Source containing more than 100 items, while canonical ingestion is designed around up to 1,000 logical candidates in internal 100-item chunks. Helper discovery/transport must not impose a whole-Source UI cap. It should provide bounded paging/continuation or staged transfer while the backend remains the durable run/chunk authority.
- A browser or custom-URI Helper launch must establish access only; it should not orchestrate a long ingestion job. The iCloud corrections reinforce the general rule that long work, retries, progress, and completion belong to durable backend state, not a React loop, open HTTP request, drive letter, or live Helper process.
- Windows Helper remains appropriate for Windows filesystem access and physical-device evidence. It is intentionally not part of iCloud authentication/acquisition, NAS access, or Linux runtime-path derivation.
- Provider executables installed in virtual environments must be invoked through the venv launcher without resolving it to the base interpreter. The defect found here can affect any isolated provider/tool integration that relies on launcher-relative site-packages.
- Report consumers should exchange durable report IDs/types rather than arbitrary paths. The wrapper/canonical mismatch found here could recur in Windows or NAS workflows that compose child runs into a parent operation.

The Windows folder-contract and Helper `>100` reconciliation remain explicitly assigned to 12.66.9.5 and were not silently changed here.

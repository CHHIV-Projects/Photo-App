# 10. Acquisition State Machine

Use an explicit fail-closed state machine.

Conceptually:

Run:

planned
→ active
→ completed

with terminal alternatives such as:

failed
cancelled

Item:

pending
→ transferring
→ verifying
→ ready

with terminal/repairable alternatives such as:

failed

Exact names may follow repository conventions.

Rules:

- `ready` means Linux independently verified the complete object;
- failed integrity must never become ready;
- state cannot move backward through ordinary API calls;
- a repeated valid finalize is idempotent;
- conflicting completion fails closed.

Do not make Helper-operation state the durable acquisition truth.

The existing `windows_helper_operations` table remains control transport.

`SourceAcquisitionRun/Item` become acquisition truth.

# 18. Chunk Integrity

Each chunk must include a SHA-256 digest calculated by the Helper over that exact chunk.

Linux must independently calculate SHA-256 over the received chunk before committing it to the partial file.

If digests differ:

→ reject chunk
→ do not advance committed offset
→ item does not become ready

Do not trust Helper-provided chunk digest without Linux verification.

---

# 19. Resume / Idempotency

Resume must survive:

- lost HTTP response;
- Helper process restart;
- SSH tunnel restart;
- expired transport operation.

The durable acquisition item survives these control-channel events.

Linux remains authoritative for the committed receiving offset.

On resume:

Helper
→ requests item status
→ receives committed offset
→ seeks Source file to exact offset
→ continues

Do not rely only on Helper-local state for resume.

### Repeated chunk

If a request is repeated for bytes that Linux has already committed:

- verify that the already-present bytes for that exact range match the supplied chunk digest;
- if they match, return idempotent already-committed success;
- if they differ, fail closed.

A separate durable per-chunk database table is not required if safe idempotency can be proven from the partial file and acquisition-item state.

Do not introduce one unless necessary; if it becomes necessary, report why.

# 23. Receiving Filesystem Safety

# 24. Linux Independent Final Verification

After all expected bytes are committed:

1. ensure partial size exactly equals expected candidate size;
2. Linux re-read/hash the complete partial file;
3. calculate full SHA-256 independently;
4. compare with Helper-reported full Source SHA-256;
5. ensure Helper's pre/post Source-stat evidence remained stable;
6. ensure item still refers to the same authorized Source identity.

Only then may the item become `ready`.

Linux-verified SHA-256 becomes durable acquisition evidence.

Do not use the Helper's SHA as the sole authority.

---

# 25. Source Mutation During Read

The Helper must capture appropriate candidate evidence immediately before and after the complete read.

If the Source file changes materially during acquisition, including relevant:

- size;
- modification/stat evidence;
- stable file identity where available,

then:

→ fail item
→ do not promote partial file to ready
→ retain/report safe evidence
→ require fresh inventory/acquisition selection

Do not treat the transferred bytes as the reviewed inventory candidate when the Source changed during the operation.

---

# 26. Atomic Partial → Ready Publication

After Linux verification succeeds:

- fsync/flush the completed partial file as appropriate;
- publish using same-filesystem atomic rename/replace semantics;
- ensure destination does not already contain a conflicting object;
- durably update item state to `ready`.

Do not copy from partial to ready if an atomic same-filesystem rename is available.

A crash must not produce a database `ready` item pointing at an incomplete file.

On restart, reconciliation must safely identify:

- transferring partial;
- verified/promoted ready;
- inconsistent/conflicting state.

Do not silently delete inconsistent evidence.

---

# 27. Helper Full-File SHA

The Helper may compute SHA-256 incrementally while reading the Source.

On resume, it may safely re-read prior Source bytes if necessary to reconstruct its hash state.

Do not invent a serialized cryptographic internal-state format solely to optimize resume.

Correctness is more important than avoiding a bounded re-read.

The final Helper Source SHA is evidence to compare with Linux's independently calculated SHA.

# 28. Receiving Quota / Disk Safety

Recheck sufficiently to prevent a run from blindly filling the filesystem.

A disk-space failure must fail safely without promoting an incomplete object.

The 1-GiB value is a V1 safety reserve, not a user-facing product quota.

5. CHUNK BUFFERING / SERIALIZATION — APPROVED

Use the proposed bounded implementation:

1 MiB

maximum accepted:
4 MiB

Linux may buffer at most the enforced bounded chunk before committing it.

For each chunk:

receive bounded bytes
→ independently compute Linux SHA-256
→ verify supplied chunk digest
→ acquire/hold appropriate acquisition-item serialization/row lock
→ verify exact expected offset/state
→ write exact range
→ flush/fsync as appropriate
→ only then advance durable committed offset

A failed digest must not modify the partial file or advance the offset.

Do not accept partial-overlap writes as an ordinary resume mechanism.

6. CRASH ORDERING — APPROVED

Use filesystem-first, database-second ordering.

Chunk:

write exact bytes
→ flush/fsync as appropriate
→ database committed_offset advances

Final publication:

verify complete partial
→ fsync
→ atomic no-overwrite partial → ready publication
→ verify published state
→ database item becomes `ready`

Database state must never claim data durability before the corresponding filesystem state exists.

Reconciliation must safely handle cases where the filesystem is ahead of the database because a crash occurred between those two steps.

Do not silently discard such evidence.

A database `ready` item pointing to an absent/incomplete ready object is a hard inconsistency and must fail closed.

7. LOST RESPONSE / IDEMPOTENT CHUNK RETRY — APPROVED

For a repeated exact already-committed range:

- locate the exact committed range in the partial file;
- independently hash that stored range;
- compare it to the repeated request's chunk digest;
- if identical, return idempotent already-committed success without rewriting/advancing;
- if different, fail closed.

Partial overlap with committed state is not accepted as normal retry behavior.

Conflicting bytes are a hard integrity failure.

Linux committed offset remains authoritative.

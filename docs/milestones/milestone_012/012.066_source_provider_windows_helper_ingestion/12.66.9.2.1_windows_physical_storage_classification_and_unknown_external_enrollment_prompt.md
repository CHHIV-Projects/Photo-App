# Milestone 12.66.9.2.1 — Windows Physical Storage Classification and Unknown External Enrollment

## Purpose

Complete the remaining Windows External ingestion capability gap discovered during 12.66.9.2.

12.66.9.2 UX work is accepted and must remain intact.

The remaining problem is narrow but important:

Helper 0.5.1 can safely recognize an already-enrolled External device by its durable Volume GUID fingerprint, but it cannot safely determine whether a previously unknown Windows `fixed` volume is:

- a physical external HDD/SSD;
- an internal physical disk;
- virtual/cloud-backed storage such as Google Drive;
- another unsupported storage presentation.

12.66.9.2 therefore correctly fails closed for unknown fixed volumes.

That behavior is safer than misclassification, but it prevents normal enrollment of a genuinely new physical External HDD/SSD.

This milestone adds the minimum bounded Windows hardware evidence required to classify previously unknown physical storage safely while preserving Volume GUID v2 as durable Source identity.

This milestone may produce Windows Helper 0.5.2.

Do not reopen the accepted Ingestion UX.

# 8. Windows Evidence Collection

Use the smallest reliable read-only collector.

For each candidate mounted root:

A. Existing checks

Retain:

- `GetDriveTypeW`;
- Volume GUID / mounted-volume identity;
- current runtime root.

B. Partition association

Map the exact root to exactly one Windows partition.

Use exact DriveLetter or AccessPaths evidence as appropriate.

Reject:

- zero matches;
- multiple matches;
- contradictory mapping.

C. Disk association

Map the partition to exactly one disk.

Collect only bounded normalized evidence needed for classification.

D. Physical media support

Use physical-media evidence such as HDD/SSD/SCM/unspecified only as supporting evidence.

Do not require reliable HDD-vs-SSD reporting because some USB bridge chipsets do not expose it correctly.

An external SSD behind USB should still be eligible when external physical backing is otherwise proven.

E. Device / topology evidence

Where necessary, inspect bounded Windows device properties for:

- device class;
- bus type;
- removal policy;
- removable/eject/surprise-removal capabilities;
- parent-device ancestry sufficient to prove an accepted external connection.

Raw hardware IDs and serial numbers should remain internal to classification logic and should not cross the Helper protocol boundary unless separately justified.

# 12. Virtual / Cloud Drives

Google Drive or equivalent virtual/cloud-mounted storage must not appear as External merely because it has a drive letter or Windows reports a fixed-like mounted root.

A candidate must positively prove accepted physical backing.

Failure to prove virtuality is NOT sufficient to classify External.

No Google Drive provider is introduced in this milestone.

# 13. Network Storage

- SMB/NFS-style remote volumes;
- iSCSI;

Do not absorb NAS into Windows External.

# 14. Internal Physical Storage

Internal physical storage remains Local, not External.

Internal SATA/NVMe/SAS/RAID/SCSI evidence without positively verified external topology must not be offered as a new External Source.

Do not weaken the Local volume model.

---

# 15. Thunderbolt / USB4

Do not block USB External support while trying to solve every Thunderbolt implementation.

A disk reporting NVMe is NOT automatically External.

Accept Thunderbolt/USB4 External only if bounded Windows topology evidence positively proves the disk is downstream of an accepted active USB4/Thunderbolt route and other evidence is consistent.

If positive evidence is unavailable:

fail closed.

Legacy/vendor-specific Thunderbolt heuristics are not required for this milestone.

Document limitations explicitly.

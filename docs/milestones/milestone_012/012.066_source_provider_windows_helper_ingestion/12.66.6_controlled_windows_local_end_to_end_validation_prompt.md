# 1. Purpose

Validate the complete Windows Local ingestion workflow as one coherent operator-driven Photo Organizer flow using the architecture established in 12.66.1–12.66.5.

The intended user concept is:

Create/Select Windows Source
→ Run Ingestion

Internally Photo Organizer may perform:

Helper authentication
→ Source identity/readiness
→ bounded inventory
→ acquisition planning
→ Windows file acquisition
→ verified Linux receiving
→ common Source Intake
→ Vault / Asset / Provenance

The Windows Helper remains a technically separate Windows process, but it must function as infrastructure beneath the Photo Organizer ingestion workflow rather than as a separate ingestion product.

12.66.6 is primarily an orchestration and end-to-end acceptance milestone.

Do not create another provider, transfer mechanism, or ingestion engine.

# 20. Cross-Acquisition-Run Repeat Semantics

12.66.5 proved idempotency when the SAME acquisition run is bridged again.

12.66.6 must also validate a NEW end-to-end workflow invocation against the same unchanged Source.

If a new acquisition run re-acquires unchanged files, the bridge must not create new Asset/Vault/Provenance state for the same:

Profile
+
provider-native Source path
+
verified content

A minimal provider-neutral cross-acquisition-run reuse check is authorized if required.

It may use previously successful acquisition-item linkage to recognize:

same Profile
same normalized provider-native lineage
same verified SHA-256
→ already represented successful Source observation

Then reuse the existing Asset/Provenance linkage rather than launching duplicate common-ingestion work for that item.

Distinct Source paths with identical content must remain distinct lineage observations.

Do not collapse different source paths solely because SHA matches.

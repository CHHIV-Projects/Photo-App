## 2. Implementation Summary

The existing Ingestion page was simplified in place around `Add Source`, `Manage Computers`, the Source Selector, the provider workbench, and Run Ingestion. The implementation added bounded Windows portable-device discovery and fresh route resolution, enforced the v1 Windows Local Endpoint invariant, introduced `Server` as presentation over Mounted Local, retained the current registered NAS, and kept the existing plan/confirm and common-ingestion authorities.

The Product Owner-requested browser adjustments were also completed: registered/offline computer status is explicit, Helper launch and readiness waiting occur within the first detection action, false External candidates fail closed, Server terminology is user-facing, and existing Endpoint aliases are no longer offered for rename in normal Source creation.

## 3. Preserved Architecture

The accepted hierarchy remains:

```text
AccessNode
→ SourceEndpoint
→ Source Profile / IngestionSource
→ provider readiness/acquisition
→ common Source Intake
```

No replacement identity model, ingestion engine, acquisition model, pairing protocol, persisted `server` source type, schema migration, or durable-row rewrite was introduced. A Windows computer remains an access route; Local, External, and Removable devices remain distinct durable Endpoints.

## 4. Ingestion Page Structure

The existing page now exposes compact `+ Add Source` and `Manage Computers` actions. Source creation is no longer permanently expanded. The Source Selector and Ingestion Workbench remain the normal recurring-use surfaces, and unrelated Ingestion page behavior was not redesigned.

## 5. Add Source

Add Source presents the normal Source Types Local, External, Removable, Server, NAS, and iCloud. Optical remains visibly deferred. Each Source Type displays only its relevant normal-user fields, then uses the existing review and create/reuse confirmation boundary. Provider mechanics and Access Location are not exposed in the normal workflow.

## 6. Register / Manage Computers

Manage Computers lists registered Windows computers, separates durable registration from current Helper availability, and provides the existing Register Computer flow. A paired computer is displayed as either:

- `Registered — Available`; or
- `Registered — Helper offline`.

Registration still uses the existing hidden pairing-code prompt and installed Helper command. Rename, unpair, credential reset/revocation, retirement, deletion, and migration remain outside scope.

The custom-URI `Open PhotoOrganizerWindowsHelper.exe?` prompt is browser-controlled external-protocol security behavior and was not bypassed. The smallest safe quieter options are a user/browser remembered permission where supported or a separately approved per-user login/background Helper lifecycle.

Automatic Windows-hostname suggestion was not added. A browser cannot safely obtain the Windows hostname, and Helper 0.5.1 does not report it. The smallest safe future implementation is a versioned enrollment-protocol extension in which the Helper supplies a bounded hostname suggestion during pending registration, the UI allows the user to keep or edit it, and the alias becomes immutable only when registration is finalized. That requires separate Product Owner approval, Helper tests, rebuild, and replacement.

## 7. Access Location Removal

The normal `Access Location`, `This server`, and `Windows device` controls were removed. Source Type now determines the normal provider route:

- Local → registered Windows computer / Helper;
- External and Removable → current verified Helper observation;
- Server → Mounted Local on the Photo Organizer host;
- NAS → current registered Mounted NAS;
- iCloud → existing provider-specific workflow.

## 8. Local Source UX

The normal Local form contains Computer, Folder, and Profile name. One registered computer is presented informationally; multiple computers would produce a selector; zero computers directs the user to registration. A new Local Endpoint receives the selected computer's immutable friendly alias for presentation, while the Volume GUID fingerprint remains durable Source identity.

Existing Endpoint 2 (`Chuck_Notebook`) and its Profiles remain unchanged.

## 9. Local Endpoint Invariant

The selected AccessNode is locked during confirmation and active Local Endpoint state is rechecked within the transaction:

- zero active Local Endpoints permits creation only after existing strong identity and containment validation;
- one Endpoint with the same fingerprint is reused;
- one Endpoint with a different local-volume fingerprint is blocked as an unsupported additional local volume;
- multiple active Local Endpoints fail closed.

No simplistic uniqueness constraint or weakened Volume GUID identity was added.

## 10. Local Existing-Data Compatibility

The historical accepted shape—one Local volume-backed Endpoint with multiple bounded Profiles—remains supported. Endpoint 2 and Profiles 3 and 4 were not renamed, migrated, rewritten, or duplicated. Offline Helper state leaves configured Profiles visible and disables unavailable operations rather than requiring Source recreation.

## 11. External Source UX

External creation is device-focused: the user detects a connected device, optionally enters a bounded folder, and supplies a Profile name. The observing Windows computer is not a normal form field. A known durable fingerprint reuses the existing immutable Endpoint alias.

Optical drive type is excluded. Because Helper 0.5.1 reports native drive type and Volume GUID but no authoritative physical-backing evidence, an unknown `fixed` drive cannot safely be distinguished from virtual/cloud storage. Unknown fixed candidates therefore fail closed. Previously enrolled External devices remain discoverable only when a fresh observation matches their durable fingerprint. This excludes the observed Google Drive and optical BD-RE entries while preserving the known External device.

Supporting safe enrollment of a new unknown External device requires a separately approved, versioned Helper capability that reports bounded authoritative physical-storage evidence, such as a fail-closed Windows storage-device/bus classification, without weakening durable volume identity.

## 12. Removable Source UX

Removable uses the same device-focused flow. Native Windows `removable` classification is required, current drive letter is secondary access evidence, and the Volume GUID fingerprint remains durable identity. Known devices reuse their immutable alias; a genuinely unknown Removable device may receive one new immutable Device name after detection.

## 13. Portable Cross-Computer Route Resolution

Fresh Helper volume observations—not historical observed-path rows—are the runtime route authority. For an already identified External or Removable Endpoint:

- zero currently verified online routes reports `Device not connected`;
- exactly one route is selected automatically;
- more than one route fails closed into exceptional route selection.

Route choice is short-lived, bound to the matched Endpoint and fresh observations, and never becomes Source identity or a persisted preferred computer.

## 14. Exceptional Multi-Route Handling

The computer selector appears only when the backend proves that the same durable portable Endpoint is simultaneously available through multiple current, paired, online, fingerprint-matching Helper routes. The selected route is revalidated and constrained to the current readiness/run context. It is not shown in ordinary zero-route or single-route operation.

## 15. Server Source Type

`Server` is now a normal presentation Source Type for storage local to the machine hosting Photo Organizer. The Add Source surface identifies the machine as `Photo Organizer Server` and separately presents `Server Photos` as an approved location on that server. Arbitrary host browsing and unrestricted filesystem roots remain prohibited.

## 16. Server Durable-Type Preservation

Server classification uses durable metadata:

```text
provider_kind = mounted
AND Endpoint source_type = local
→ Server
```

The underlying Endpoint `local`, Profile `local_folder`, Mounted provider, filesystem identity, and configured paths remain unchanged. No persisted `server` type or migration was added.

Normal Server review shows `Source Type: Server`, `Server: Photo Organizer Server`, and the approved location name. Persisted `local`, filesystem UUID, identity fields, observed paths, and mount details are confined to Advanced Details/diagnostics.

## 17. NAS UI Simplification

The current configured `Photo Organizer NAS` remains the only registered NAS location for this milestone. The normal form presents NAS location, bounded folder, and Profile name without IP, authority target, namespace slot, broker, or mount mechanics. No NAS discovery, second hard-coded NAS, or generalized NAS registration was added.

## 18. iCloud Preservation

iCloud remains a top-level Source Type and retains its existing authentication, acquisition, cleanup, durable Profile, and common-intake behavior. No Windows computer, Server selection, or Access Location was added to its flow, and no iCloud mutation was performed.

## 19. Optical Deferral

Optical remains `Optical — Coming later`. Optical drives are not treated as External candidates, and no Optical ingestion path was enabled or tested.

## 20. Source Selector

The Source Selector continues to use Source Type → durable device/Endpoint alias → Source Profile. Provider presentation distinguishes Windows Local from Mounted Server using durable metadata. Raw paths are secondary information, not primary dropdown labels. Configured unavailable Sources remain visible.

## 21. Disconnected / Offline Presentation

Registered computers remain registered when the Helper is offline. Configured Windows Profiles remain visible when their computer or device is unavailable. The UI reports computer/device availability separately and disables unsafe run actions. Temporary access loss does not require Source recreation.

The first External/Removable detection click now performs one bounded operation: synchronously request custom-URI Helper launch, wait up to 120 seconds for an authenticated online heartbeat, and then begin and resolve volume observation. The user no longer receives the former immediate `No registered computer is currently available` error and need not click Detect a second time after accepting the browser launch prompt.

## 34. Known Limitations / Deferred Work

- Automatic Windows hostname suggestion requires a future versioned Helper/enrollment enhancement.
- Quiet always-on access requires an explicitly designed per-user login/background or tray lifecycle; current on-demand URI launch may show the browser's external-protocol prompt.
- Safe enrollment of an unknown fixed External device requires authoritative physical-storage backing evidence from a future Helper capability. Helper 0.5.1's `fixed` classification alone is intentionally insufficient.
- Helper 0.5.1 has no independent stable physical-computer fingerprint; normal-flow duplicate protection remains bounded to known AccessNode IDs and aliases.
- Multiple internal Local physical volumes, Optical ingestion, generalized multi-NAS registration/discovery, arbitrary Server roots, and Google Drive as a provider remain deferred.
- The accepted historical iCloud non-repeat regression remains unchanged.

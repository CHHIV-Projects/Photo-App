## 1. Repository State

Implementation is on `feature/windows-ingestion-throughput-hardening`. No stage, commit, push, tag, merge, rebase, or reset was performed. Product Owner-authorized packaging, guarded installation, Development deployment, and the controlled performance validation are complete.

## 2. Purpose / 6A Baseline

The accepted Profile 15 warm baseline was 35 files, 27,983,035 bytes, one child, and approximately 478 seconds. Approximately 394 seconds were repeated per-file physical discovery and approximately 52 seconds were active-child empty-claim delay; upload round trips were only approximately 3.5 seconds.

## 3. Child-Bound Physical Identity Design

Helper 0.5.3 advertises `child_identity_attestation` version 1. The backend queues one explicit `attest_child` operation for each bounded acquisition child. A full Windows physical identity probe succeeds before the Helper issues an opaque HMAC-signed token. Helpers without the capability retain the accepted full-probe-per-file path.

## 4. Attestation Binding / Expiry / Invalidation

The token binds protocol version, Access Node, Endpoint, Profile, Source type, durable fingerprint, authoritative root, parent workflow, exact acquisition child, issue time, and expiry. The default lifetime is configurable through `WINDOWS_CHILD_ATTESTATION_TTL_SECONDS` and is safely bounded from 60 to 3,600 seconds; the default is 900 seconds.

The signing key is random and process-local, so restart/replacement invalidates every outstanding token. Missing, expired, or process-invalid tokens cause one fresh attestation and safe retry. A validly signed token with any binding mismatch fails closed. Expiry is checked before opening a file and does not abort an already-open protected read.

## 5. Lightweight Per-File Verification

Optimized acquisition removes repeated physical discovery, not file proof. Every file retains root/relative/full-path validation, containment, expected stat evidence, exact read-only open, opened-handle path equality, pre/post handle and path evidence, mutation detection, source SHA-256, per-chunk SHA-256, resume-prefix re-read, and independent Linux receive/publication verification.

The Helper additionally calls `GetFinalPathNameByHandleW` with `VOLUME_NAME_GUID` for the already-open file, derives the accepted Volume GUID v2 fingerprint, and compares it with the child binding before uploading bytes.

## 6. Mid-Child Device Change Handling

Opened-handle volume mismatch, handle-path mismatch, evidence change, disconnect, or wrong device at the historical drive letter fails the current item and child under existing durable failure semantics. Completed items remain immutable. A resume reopens the exact candidate and replays/hash-validates bytes through the durable Linux offset only after all current file evidence passes.

## 7. Helper / Protocol Changes

Helper version is 0.5.3. Protocol v1 gained explicit optional/versioned child-attestation models and operation type; optimized acquire fields are paired and optional. Backend capability detection prevents attestation work from being sent to 0.5.2. Deployment order is therefore compatible in both directions: new backend plus 0.5.2 uses legacy probes, and 0.5.3 without an optimized request also uses legacy probes.

The approved collateral packaging correction adds `status --output-file <absolute-json-path>`, providing bounded redacted status through a file even when the packaged executable is windowless. Authentication, pairing, and credentials are unchanged.

## 8. Active-Work Claim Redesign

After an attestation or file completes, Helper uses bounded adaptive 50, 100, 200, and at-most-400 ms polling during an approximately two-second active-child transition window. It then returns to the server-provided two-second cadence. Lease, claim, operation identity, completion idempotency, and backend orchestration are unchanged.

## 9. Idle Helper Behavior

The short polling window is entered only after active child work. Normal idle behavior remains the accepted conservative two-second poll, with no long-held server request or permanent high-frequency loop.

## 10. Bridge Validation Snapshot

Planning constructs one immutable in-process snapshot containing the verified ready records, database state digest, file identity/stat evidence, prior-observation decisions, and plan. The same snapshot is passed through execution and response construction. A separate API request builds a fresh snapshot. Changes to durable item state/path/hash/linkage or ready-object device/inode/size/mtime/ctime invalidate it before mutation.

## 11. Prior-Observation Candidate Selection

Historical anchors are first filtered by exact provider lineage and collapsed by `(Asset SHA-256, Provenance ID)`. More than one distinct authority remains a fail-closed ambiguity. Canonical Vault verification occurs only after one authority is selected and shares the already-verified exact-known Vault result within the same transition. No latest-run preference was introduced.

## 12. Inventory Identity Handling

Inventory attestation is deferred by Product Owner decision. The acquisition token cannot be reused cleanly without adding distinct cursor/generation lifecycle authority. The live post-change inventory execution remained 11.506 seconds for this one-page source, essentially unchanged from the 11.533-second warm baseline. That cost is now visible after the acquisition improvement, but a separate cursor/generation authority design is not justified inside this completed hardening change. Reconsider it only as a separately reviewed future optimization, especially for multi-page inventory.

## 13. Windows Local Compatibility

Local retains its absolute Windows root contract and participates in the shared attested acquisition path. No Source identity model changed.

## 14. External Compatibility

External retains discovery authority, durable Endpoint fingerprint, Endpoint-relative Profile root, and drive-letter-independent route reconciliation. The opened handle must still match the accepted durable Volume GUID fingerprint.

## 15. Removable Compatibility

Removable retains its distinct Source type and the same portable relative-root and durable Volume GUID protections while using the shared acquisition path.

## 16. Source Intake / Vault / Provenance Preservation

Common Source Intake remains the sole new-content writer. Source SHA, Linux receiving verification, ready publication, canonical Vault integrity, Asset identity, and Provenance rules remain intact. No transfer skipping, hash removal, chunk-size change, or concurrency was introduced.

## 17. Focused Identity Tests

Focused Helper tests cover valid and expiring tokens, restart invalidation, wrong child/parent/Access Node/Endpoint/Profile/fingerprint/root binding, full-probe fingerprint failure, legacy fallback, optimized no-full-probe execution, opened-handle volume mismatch, handle-path mismatch, resume-prefix hashing, placeholders/reparse points, and pre/post mutation failure. Existing backend Windows suites retain route, drive-letter reconciliation, path escape, durable resume, and child preservation coverage.

## 18. Claim/Orchestration Tests

Focused tests prove the parent waits for attestation, passes the token only after completion, does not queue acquisition prematurely, and uses bounded adaptive short polling after active work without a two-second sleep. Existing channel/workflow suites cover authenticated claims, lease/idempotency, disconnect, restart, child completion, and parent completion.

## 19. Bridge/Vault Tests

## 27. Residual Bottlenecks

Residual work now consists primarily of one 11.144-second full probe per child, source disk latency, guarded per-file read/upload/Linux verification, and orchestration between file operations. The first acquisition took 7.273 seconds of Helper execution because of an external-drive read stall; the remaining files executed rapidly. Source check and the one-page inventory still perform their accepted full physical checks, and volume observation remained expensive at 34.579 seconds. New-content Common Source Intake was intentionally not exercised. No safety hash, handle proof, mutation check, or canonical Vault verification should be removed to improve these numbers.

## 28. Large/New-Content Benchmark Decision

Neither the 259-file/3.21 GiB benchmark nor a new-content benchmark was run. The controlled result proves the targeted fixed per-file amplification is removed. A separately authorized large repeat benchmark would now be useful only for capacity characterization of source-read and transfer scaling; it is not required to accept 12.66.9.6B. A new-content benchmark remains the only way to measure Common Source Intake/Vault creation, but is likewise not required and must retain its separate mutation authorization gate.

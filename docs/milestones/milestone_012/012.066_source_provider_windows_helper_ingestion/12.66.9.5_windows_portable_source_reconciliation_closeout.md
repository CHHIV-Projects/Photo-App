# 12.66.9.5 Windows Portable Source Reconciliation Closeout

## 1. Repository State

Preflight began on `feature/windows-helper-ingestion` with a clean worktree, the expected repository root, and `HEAD` matching its upstream. No stage, commit, push, tag, merge, rebase, or reset was performed. The final worktree contains only the scoped implementation, tests, Development compose setting, and this closeout.

## 2. Purpose / Accepted Prior State

This milestone corrected two related Windows portable-source defects while preserving the accepted 12.66.9.2 through 12.66.9.4 architecture:

- External and Removable creation no longer trusts a browser-composed absolute Windows path.
- A Source with more than 100 candidates is represented by one durable, whole-Source proposal and executed through bounded child acquisitions rather than rejected at the first continuation cursor.

Existing Endpoint, Profile, AccessNode, Volume GUID v2, Helper credential, pairing, Source Intake, Asset, Vault, and Provenance state remained authoritative.

## 3. Existing Windows Portable Architecture

The Windows computer remains an AccessNode. Each physical External or Removable device remains a distinct durable Source Endpoint, and folders on that Endpoint remain Source Profiles. Helper performs Windows-native observation and byte transfer; backend owns identity, proposal, approval, orchestration, Linux verification, common Source Intake, and durable progress.

## 4. Portable Folder Defect

The prior UI combined the observed drive root with user text and sent a browser-authored absolute path. This produced a 500 for forms such as `E:\Chuck iphone`, conflated presentation with authority, and allowed drive-letter syntax into a field intended to mean “folder within device.”

## 5. Corrected Portable Request Contract

External and Removable creation now sends:

- the discovery candidate token;
- the portable Source type;
- the device alias where applicable;
- an Endpoint-relative folder;
- the Profile name.

It does not send `windows_root`. Local creation remains intentionally different and continues to require an absolute Windows path.

## 6. Candidate Token Authority

The backend resolves the fresh discovery token to the completed Helper observation, AccessNode, physical classification, durable fingerprint evidence, Source type, and current observed volume root. The token is not durable identity; it is bounded setup authority for one recently observed candidate.

## 7. Relative Path Validation

Portable relative folders accept empty roots and nested ordinary folder names. Validation rejects drive-qualified paths, UNC paths, leading separators, traversal, dot segments, empty intermediate segments, alternate data stream syntax, invalid Windows filename characters, and trailing spaces or periods. The backend normalizes the relative path, joins it to the authoritative observed root, and proves containment with Windows path semantics.

## 8. Error Handling

Invalid portable folder input fails before service mutation with bounded 4xx behavior. API-level regression proves that a browser-supplied portable `windows_root` returns 422 and never calls the creation service. Frontend validation prevents normal submission and explains that no drive letter is allowed. Pydantic validation arrays are now projected as a safe useful message instead of only `Request failed with status 422`.

Live testing exposed a stale browser bundle after backend deployment. The old UI continued sending the retired contract and received 422. A hard refresh loaded the corrected bundle; both the help text and relative-only request became visible. No durable row was created by the failed attempts.

## 9. Existing 100-Item Limit

The existing limit remains a per-Helper inventory page and per-SourceAcquisitionRun child bound. It is not a whole-Source limit. Helper upload chunks remain normally 1 MiB and never exceed the existing 4 MiB protocol maximum.

## 10. System-Wide Ingestion Invariant

One operator action represents one complete point-in-time Source proposal. The backend may realize that proposal as multiple bounded acquisitions, but the browser does not approve or orchestrate each child. Every completed child retains the existing common Source Intake bridge and canonical Asset/Vault/Provenance behavior.

## 11. Whole-Source Inventory

Backend follows Helper continuation cursors until the terminal page and persists every observed entry in authoritative Helper depth-first order. Eligible and predictable-rejection totals are aggregated across the complete chain. The configurable overall safety ceiling is `WINDOWS_INVENTORY_MAX_ENTRIES`, defaulting to 100,000. Exceeding it fails before approval without truncation.

## 12. Inventory Generation / Cursor Integrity

All pages must use one inventory generation. Page indices must be contiguous; every page must have a result digest; repeated cursors, duplicate candidate references, duplicate normalized paths, invalid cursor results, and generation changes fail closed. Helper restart loses process-local cursor state, so an interrupted inventory requires a fresh proposal and approval. The former incorrect global lexical-order assertion was removed because Helper depth-first order is authoritative and can legitimately cross page boundaries without global lexical order.

## 13. Durable Whole-Source Proposal

New durable tables store the parent workflow, pages, candidates, and child ledger. The proposal records observed, eligible, rejected, byte, and child totals plus the complete ordered candidate evidence. Zero eligible candidates produce a valid empty proposal and clean completion rather than fabricated work.

## 14. Approval Binding

The proposal digest binds the parent identity, inventory-chain digest, counts, bytes, child count, and ordered candidate evidence including path, size, modification time, stable file identifier, residency, and attributes. Approval recomputes the digest before creating children. One confirmation approves the complete proposal.

## 15. Parent Workflow

The durable parent owns Source/Profile/Endpoint/AccessNode binding, inventory generation and digests, approval time, child shape, aggregate counts, progress, terminal status, and safe failure state. The browser restores the latest parent after refresh or navigation.

## 16. Chunk Orchestration

Eligible candidates are partitioned into durable children of at most 100 in Helper order. Exact regression shapes are:

- 0 → no children;
- 1 → 1;
- 99 → 99;
- 100 → 100;
- 101 → 100 + 1;
- 267 → 100 + 100 + 67;
- 356 → 100 + 100 + 100 + 56.

Each child has deterministic idempotency and is advanced automatically after the preceding child and its common Source Intake bridge complete.

## 17. Helper Boundary

Helper remains responsible for native enumeration, physical-storage evidence, exact read-only file access, pre/post evidence, chunk hashing, source hashing, and bounded upload. Volume GUID v2 remains durable volume identity. Helper is not the parent-run authority and no Helper package or protocol file changed.

## 18. Backend Background Execution

An in-process backend worker advances inventory and approved child execution independently of an HTTP request or React component. Frontend polling reads durable status only; loss of the browser or a polling response does not stop healthy backend work.

## 19. Restart / Resume / Idempotency

On backend startup, an interrupted inventory fails closed and requires fresh inventory because Helper cursor state is process-local. An approved running workflow becomes explicitly paused and requires Resume. Completed child rows are never recreated; child acquisition idempotency keys are deterministic. Repeated confirmation and status calls do not duplicate children.

## 20. Disconnect / Drive-Letter Change

Durable matching remains fingerprint-based rather than drive-letter-based. A disconnect, missing path, changed file, changed physical identity, or wrong device fails closed. A new drive letter can be accepted by a fresh route/proposal under the existing durable Endpoint rules; the implementation never rewrites Endpoint identity to follow a drive letter.

## 21. Common Source Intake Preservation

Every bounded child uses the existing SourceAcquisitionRun and common Source Intake bridge. No alternate Asset, Vault, duplicate, or Provenance writer was added. Fully reused prior observations complete without launching a redundant Source Intake run.

## 22. Aggregate Progress / Reporting

The Windows panel reports whole-parent candidates, predictable rejections, completed/total chunks, completed/remaining files, transferred/expected bytes, new library items, already represented items, failures, and stage. It distinguishes transfer from library processing and restores terminal state after navigation.

The global Source Intake status remains the authority for the latest individual common Source Intake child. For a three-child Windows parent, the Windows panel is the aggregate authority. At Product Owner request during live validation, Windows completion refreshes Profiles, Source Intake status, and reports.

The first refresh-only correction proved insufficient on the repeat run: because all 35 observations were already represented, the acquisition correctly launched no redundant common Source Intake run, leaving the prior 59-file Source Intake child as the latest record. The corrected UI now compares durable completion timestamps and promotes the newer Windows parent into a `Last Ingestion Summary`. That summary exposes Source, start/finish, whole-parent inventory/files/chunks, new items, already represented items, predictable rejections, failures, and transferred bytes. It does not fabricate a Source Intake run or report.

## 23. External Compatibility

Known External devices reuse their durable Endpoint. Unknown verified physical External devices retain the 12.66.9.2.1 classification requirements. Optical, network, virtual/cloud, and ambiguous fixed volumes remain excluded or fail closed. Live creation reused External Endpoint 3 and created only Profile 15.

## 24. Removable Compatibility

Removable uses the same candidate-token plus relative-folder contract while retaining its distinct Source type and durable identity flow. Automated regressions cover Removable creation and nested relative paths. No live Removable mutation was required for this milestone.

## 25. Windows Local Assessment

## 40. Deviations

The prompt listed global Last Source Intake Summary/History auto-refresh as out of scope. During live testing, the Product Owner explicitly requested correction because Windows completion left the summary showing an older provider run. The initial implementation added a one-time refresh of Profile, Source Intake status, and reports. Repeat testing proved that insufficient when no redundant Source Intake run was created. The final bounded correction retains that refresh, restores completed Windows parents after navigation, exposes their durable identity/timestamps, and shows the newer parent in a `Last Ingestion Summary`. It does not add generalized polling, fabricate common Source Intake history, or change the detailed Source Intake History table.

The first live portable validation used a browser tab holding the pre-deployment JavaScript bundle. This produced bounded 422 responses until a hard refresh loaded the new contract. The event caused no mutation and led to improved safe validation-message projection.

The live folder validation proceeded through Source creation after review. This was a Product Owner action within the authorized live gate and produced the exact expected single Profile row with no duplicate Endpoint.

## 41. Known Limitations / Deferred Work

- Helper 0.5.2 performs the expensive physical-volume identity probe for every file and polls for operations at two-second intervals. The 35-file, 26.7 MiB run took about 7 minutes 45 seconds; the 259-file, 3.21 GiB run took about 63 minutes. Upload requests themselves were generally only 0.1–0.3 seconds. A future Helper/protocol hardening item should consider a short-lived, child-bound physical identity attestation while retaining per-file lightweight volume verification, exact pre/post evidence, and Linux hash verification.
- Detailed Source Intake History remains child-oriented. A Windows parent promoted into `Last Ingestion Summary` has no synthetic report file; its durable parent status and Windows panel are the aggregate authority, while child Source Intake reports remain available in history.
- The in-process worker is durable through browser/navigation loss, but backend process restart requires explicit Resume for approved work. Inventory restart requires a fresh proposal because Helper cursors are process-local.
- A drive-letter change during active acquisition fails closed; a fresh route/proposal is required rather than rewriting identity.
- The historical iCloud non-repeat regression remains deferred and unchanged.

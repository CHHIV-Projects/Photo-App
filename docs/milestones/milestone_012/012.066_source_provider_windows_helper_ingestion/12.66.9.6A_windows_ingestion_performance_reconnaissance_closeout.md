## 3. Current `Checking Sources` Runtime Map

The backend establishes the Access Node/Endpoint/Profile route, queues a bounded Helper volume-observation operation, probes the selected source, starts a durable parent workflow, and queues one or more inventory pages. Helper claims each operation, performs Windows-authoritative identity work, enumerates/stat's the bounded page, and completes it through authenticated ingress. The backend validates generation, identity, containment, page chain, candidates, counts, bytes, and proposal digest before persisting review state.

Helper receives a two-second poll instruction after an empty claim. The backend parent checks a waiting operation every 500 ms and immediately actionable state every 50 ms. Frontend polling displays durable status and does not drive the worker.

## 4. Current Ingestion Runtime Map

The backend creates one `acquire_item` operation per selected file. Helper performs a full root/device identity probe, path stat, receiving-status request, exact file open and handle/path validation, pre-read stat, one sequential source stream with simultaneous full SHA-256 plus per-chunk SHA-256, normally 1 MiB authenticated uploads, trailing read, post-handle stat, post-path stat, and completion.

Linux hashes each request body, locks receiving state, writes with `pwrite`, calls `fsync`, commits the durable offset, hashes the completed partial object, publishes it, and hashes the ready object. The bridge then reconstructs and revalidates ready records, classifies exact-known/new content, looks for prior observations, and either reuses prior linkage or enters Common Source Intake.

## 10. Physical Identity Probe Findings

Acquisition performed exactly 35 full probes per run, one per file. They averaged 11.279 seconds/file cold and 11.264 seconds/file warm and represented 83.58% and 82.46% of end-to-end ingestion wall time.

Each acquisition probe ran one `vol`, `mountvol`, `fsutil`, `net use`, PowerShell storage-metadata query, and four `pnputil` device queries. The PowerShell storage-metadata query alone consumed 358.524 seconds cold and 358.559 seconds warm—about 91% of probe time. The result is device/root-level evidence that was stable throughout each one-child run; file-specific containment and mutation evidence came from separate inexpensive stat/handle checks.

Volume observation also walks mounted volumes and performs expensive storage classification per eligible fixed/removable drive. Inventory repeats the full selected-source probe once per page.

## 11. Polling / Wait Findings

Twenty-eight of 35 acquisition transitions in both runs incurred at least 1.5 seconds of queue time. Helper logged 28 completed two-second `empty_claim` sleeps per acquisition. Durable mean queue time was 1.531 seconds/file cold and 1.483 seconds/file warm. The cumulative queue totals of 53.582 and 51.914 seconds accounted for 11.34% and 10.86% of wall time.

Cause: after completing a file, Helper immediately claims again; the backend has not always committed/queued the next per-file operation. An empty result then forces a full two-second sleep even though work appears shortly afterward. Backend 500 ms waiting polls overlap Helper execution and must not be summed as independent wall time, though they can add bounded state-detection latency.

## 12. Windows File Read / Hash Findings

Normal acquisition reads each Windows source file exactly once and updates its full SHA-256 during that same stream. It also hashes each upload chunk independently. Forty-two source reads/chunks covered 35 files. Full digest updates cost about 24 ms/run; chunk hashes cost about 24 ms/run.

Cold source reads totaled 7.486 seconds, dominated by one 7.023-second read stall. Warm reads totaled 14.246 seconds, dominated by 7.119- and 7.024-second stalls. These resemble intermittent external-drive latency, but remained small relative to identity probing. There is no separate Windows hash pass to remove.

## 13. Helper-to-Linux Transfer Findings

Forty-two 1 MiB-or-smaller authenticated requests moved 27,983,035 bytes with no retry. Helper-observed upload round trips totaled 3.432 seconds cold and 3.503 seconds warm: 7.78 and 7.62 MiB/s during those calls. Whole-workflow throughput was only 0.057 and 0.056 MiB/s because fixed control work dominated.

Linux request-body receive totaled 0.730/0.804 seconds. Chunk commit totaled 0.613/0.636 seconds, including write+`fsync` 0.423/0.458 seconds and database commit 0.105/0.097 seconds. Upload chunk size is not the first optimization for this source.

## 14. Linux Verification Findings

Per run, Linux performed 42 request-body hashes, 35 assembled-partial hashes, and 35 published-ready hashes. Partial hashes cost 0.271/0.247 seconds; ready hashes cost 0.018/0.018 seconds. These checks protect distinct transport/assembly/publication boundaries and were not material.

Bridge record reconstruction then reread every ready file five times: 175 hashes and 139,915,175 bytes per run. That frequency is orchestration amplification, not a distinct five-boundary requirement.

## 15. Common Source Intake Findings

All 35 items reused prior observations, so Common Source Intake did not stage/hash/create new content in these runs. Bridge lookup and commit completed in about one second after acquisition. This benchmark therefore cannot measure new-item Drop Zone/Vault creation, by Product Owner design.

The reuse path exposed a separate issue. Canonical Vault verification performed 455 hashes/363,779,455 bytes cold and 630 hashes/503,694,630 bytes warm. The extra 175 hashes/139,915,175 bytes in the immediately following run equals five additional passes over the dataset. `_find_prior_observation_reuse` verifies every matching historical acquisition candidate, and the bridge invokes plan/reuse lookup repeatedly. Runtime was sub-second only because this small dataset was page-cached.

## 16. Per-File vs Per-Byte Cost Analysis

Measured fixed acquisition cost was approximately 11.27 seconds/file for identity plus about 1.5 seconds/file of claim queue. Byte-scaled upload cost was 3.4–3.5 seconds for the whole 26.7 MiB dataset, and cryptographic CPU costs were milliseconds. Eliminating 34 redundant full probes within this one child would avoid about 383 seconds. Eliminating the empty-claim race would avoid about another 52 seconds.

## 19. Required vs Potentially Redundant Work

Required: wrong-device fail closed; root containment; pre/post file evidence; one Windows content read and source digest; per-chunk authenticated transfer; independent Linux chunk/assembled validation; exact-known Asset/Vault correctness; provenance identity.

Safely reducible subject to 6B design/tests: full device discovery per file; empty-claim fixed waits during an active child; five bridge ready-object passes; repeated Vault hashing across bridge plan calls and every historical candidate; repeated full source probe per inventory page when a bounded attestation can prove continuity.

A separate pre-existing diagnostic defect was observed during restoration. The packaged windowless Helper `status` subcommand performed an authenticated `GET /api/helper/v1/session` that returned HTTP 200, then exited locally with code 1 and no console output. The URI-launched runtime subsequently heartbeated and polled successfully. This does not affect normal URI service operation, but console subcommands should use an output mechanism compatible with the windowless package or be distributed through a separate console entry point.

## 20. Ranked Bottlenecks

1. Full physical identity per acquired file: 394.2–394.8 seconds, 82.5–83.6% wall.
2. Empty-claim race/two-second sleep: approximately 51.9–56.0 seconds, about 10.9–11.9% wall depending queue versus full-sleep boundary.
3. Intermittent Windows external-drive read stalls: 7.5–14.2 seconds, 1.6–3.0% wall.
4. Helper upload round trips: 3.4–3.5 seconds, 0.73% wall.
5. Status/completion requests and final bridge: low single-digit seconds.
6. Linux hash/write/fsync/database work: under one second per measured category.

Bridge/Vault repeated hashes rank low for this cached small run but high as a scaling-risk defect because read volume grows with both file size and prior-run count.

## 21. Candidate Optimizations for 12.66.9.6B

1. Introduce child-bound physical-volume attestation: one full probe per child, with lightweight per-file same-volume/root/handle and pre/post evidence.
2. Replace the per-file empty-claim race with server-held long polling/event signaling or a bounded active-child claim protocol; adaptive short polling is a lesser fallback.
3. Compute and carry one immutable bridge validation snapshot through plan/execute/return; verify each ready object and canonical Vault object no more often than its security boundary requires.
4. Make prior-observation lookup select a single authoritative lineage candidate before canonical Vault verification rather than hashing every historical match.
5. Apply a similar bounded attestation to multi-page inventory while preserving page generation and wrong-device checks.
6. Consider prior-observation transfer skipping only as a later design with sufficiently strong unchanged-file evidence.
7. Reassess 1-to-4 MiB upload blocks and limited concurrency only after fixed per-file costs are removed.

## 22. Security / Correctness Impact of Each Candidate

Child attestation must bind Access Node, Endpoint, durable Volume GUID v2 fingerprint, source root, child/workflow, issuance time, and expiry. Every file must still prove containment, opened-handle path, expected stat evidence, unchanged post-read evidence, and source SHA-256.

Polling redesign changes scheduling only and must retain authenticated claims, one-operation leases, idempotent completion, crash recovery, and durable backend orchestration.

Bridge snapshot reuse must be transaction/state-bound and invalidated by item/path/hash/state changes. It must not remove independent Linux receive verification or canonical Vault integrity checks; it should remove repeated reads of unchanged objects within one state transition.

Prior-observation selection must fail closed on genuinely ambiguous lineage and retain exact Asset/Provenance validation. Transfer skipping requires a new threat model and is not implied by this closeout.

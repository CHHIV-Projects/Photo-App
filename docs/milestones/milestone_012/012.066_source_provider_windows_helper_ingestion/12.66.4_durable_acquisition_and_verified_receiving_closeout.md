## 3. Acquisition Run / Item Model

`SourceAcquisitionRun` records the provider, Access Node, Endpoint, Profile, inventory generation and chain digest, proposal digest, immutable provider-native root/fingerprint binding, Linux receiving root, state, counts, byte totals, disk evidence, timestamps, and failure evidence.

`SourceAcquisitionItem` records its opaque item ID, ordinal, exact inventory candidate reference, provider-native root/relative/full path, normalized-relative-path digest, expected size/mtime/optional file ID/Windows attributes/residency, partial and ready relative paths, durable committed offset, verification hashes/evidence, state, timestamps, and failure evidence.

Run and item identifiers are independent of Helper operation identifiers.

## 4. Acquisition State Machine

Run states are `planned`, `active`, `completed`, `failed`, and `cancelled`. Item states are `pending`, `transferring`, `verifying`, `ready`, and `failed`.

Planning creates durable non-active run/items without creating a per-run receiving directory. Activation requires the exact stored proposal digest, revalidates immutable Source/proposal evidence and zero-byte state, checks capacity, then creates exact mode-0700 run/partial/ready directories. Acquisition operations are permitted only for an active run and pending/transferring selected item. All five ready items transition the run to completed.

## 5. Inventory-to-Acquisition Binding

Plan creation validates the complete ordered inventory chain from its initial page through a terminal null cursor. Every page must match the exact Access Node, Endpoint, Profile, Source type, provider-native root, durable fingerprint, inventory generation, cursor, request/result digests, and global ordering/uniqueness rules.

The deterministic chain digest is part of the immutable proposal. Each selected item copies its evidence from that reviewed chain. Detached references, duplicates, disconnected pages, non-terminal chains, and binding or digest changes fail closed.

## 9. Binary Transfer Contract

The authenticated Helper protocol adds typed acquisition claim, status, chunk upload, completion, and failure evidence. Every request binds the exact credential/Access Node, operation, run, item, Endpoint, Profile, Source type, root/path, inventory generation, candidate reference, expected identity, and expected metadata.

Chunk upload accepts only the exact allowlisted authenticated binary route and `application/octet-stream`. The Helper cannot choose a destination path.

## 10. Chunk Bounds / Integrity

Normal Helper chunks are `1,048,576` bytes and Linux accepts at most `4,194,304` bytes. The request body is bounded before append to memory. Linux hashes the bounded body independently before any file write and compares the supplied digest.

An item row lock serializes updates. The exact expected offset is required. Linux writes with positional I/O, fsyncs, and only then advances the database offset. Bad digest, oversized body, wrong offset, partial overlap, and conflicting replay fail before offset advancement.

All five live acquire requests carried the exact 1 MiB normal and 4 MiB maximum bounds.

## 11. Resume / Idempotency

Linux durable `committed_offset` is authoritative. An exact repeated committed range is read back from the partial file and independently hashed; identical bytes return idempotent success without rewrite or advancement, while a mismatch fails closed.

Filesystem-ahead/database-behind chunk evidence is reconciled only when the exact physical range hash matches. Expired or lost transfer-control operations can be replaced for the same durable item and resume from the Linux offset. Partial overlap is never accepted as resume.

## 12. Helper Operation vs Durable Acquisition State

`WindowsHelperOperation` is short-lived transport/control state with claim and lease semantics. `SourceAcquisitionRun` and `SourceAcquisitionItem` are durable acquisition truth. Operation expiry or loss does not erase committed receiving progress or authorize a different item.

Exactly five live `acquire_item` operations completed successfully for the five selected items.

## 14. Receiving Filesystem Safety

The configured base must be absolute, non-symlink, and a directory. The per-run path must equal `<configured-base>/<run-uuid>`. Run/item paths cannot escape that root. Directory creation is failure-atomic. Partial files use exclusive/no-follow safe opens and mode `0600`.

## 15. Linux Final Verification

Linux verifies complete partial size, computes the full SHA-256 independently, requires equality with the Helper Source SHA-256, fsyncs the partial, publishes without overwrite, reopens and verifies the ready object, and only then records item `ready`.

Every live Helper hash equals its Linux verified hash.

## 16. Source-Mutation Detection

Successful completion requires equal pre-read handle evidence, post-read handle evidence, and post-read path evidence matching the selected inventory evidence. A short read, trailing byte, path change, size/mtime/attributes/residency change, reparse evidence, or digest mismatch fails the item/run.

The five live items had equal pre/post evidence. Helper logic opened them read-only and performed no Source write, rename, permission, or metadata mutation request.

## 17. Atomic Partial-to-Ready Publication

After complete verification, Linux creates the ready name with an atomic no-overwrite hard-link publication, fsyncs the ready file and ready directory, then removes the partial name. Existing conflicting ready evidence fails closed. Crash reconciliation recognizes only the exact same inode/verified object relationship.

Database `ready` state is committed only after verified filesystem publication. A database-ready item with missing or changed ready data is a hard inconsistency.

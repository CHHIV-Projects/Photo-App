## 2. Executive Conclusion

The accepted architecture can support a Windows Source Helper without redesigning the durable Endpoint/Profile model or creating a second ingestion engine.

The repository already contains substantial reusable Windows identity logic for Local, External, Removable, NAS, and Optical Sources. Its present limitation is placement: `windows_non_admin.py` executes Windows commands and examines paths on the same host as the backend. A Linux backend therefore cannot invoke it directly against a Windows-connected Source. The safe adaptation is to run the Windows evidence collector in a narrowly packaged Windows Helper, send normalized and authenticated evidence to a dedicated Linux provider adapter, and keep all durable identity matching, selection policy, Source Intake, canonical Vault writes, asset persistence, and provenance authority on Linux.

V1 should use an outbound Helper connection through an automatically managed, exact SSH local forward to a backend loopback-only Helper API. This reuses an installed transport and host-key trust boundary without exposing the existing unauthenticated browser/admin API on the LAN. The Helper must also authenticate at the application layer with a revocable per-Access-Node credential.

The existing schema is sufficient for durable Source identity but not for resumable acquisition. Before byte transfer, V1 requires additive, provider-neutral acquisition run/item state and a narrow Helper credential record. No existing Asset, Provenance, Endpoint, or Profile data needs backfill.

The narrow common bridge is the pipeline's existing explicit-source-record path. The Helper may deliver only selected bytes into a bounded Linux receiving area; Linux verifies and publishes complete receiving objects, then feeds exact records to the normal Source Intake pipeline. The Helper must never write the Drop Zone, Vault, application database, or provenance records.

No Product Owner architecture decision blocks 12.66.1. Remaining questions concern bounded defaults and packaging choices that later milestones can resolve with focused evidence.

## 3. Existing Windows Provider Architecture

The current provider is `backend/app/services/source_identity/providers/windows_non_admin.py`, exposed as `windows_non_admin_probe_v1`. It is deliberately non-admin and already models the relevant Windows Source types.

Reusable behavior includes:

- Windows path and drive-root normalization without translating paths into Linux syntax;
- Local/External/Removable volume discovery through `mountvol` and PowerShell volume, partition, disk, and physical-disk evidence;
- NAS mapped-drive resolution to a canonical UNC server/share identity;
- removable/device classification from bus type, media type, system-disk exclusion, and related evidence;
- fail-closed identity matching rather than treating a drive letter as identity;
- Optical physical-drive checks, virtual-media rejection, media readability checks, and a twice-built stable metadata manifest;
- normalized probe responses compatible with the common fingerprint and enrollment services.

The provider currently assumes the probe process and Source are on the same Windows machine. `SourceIdentityProbeService` chooses a provider from the backend runtime OS; on Linux it chooses the Mounted provider. Directly calling the existing Windows provider from the Linux backend is therefore neither possible nor desirable.

Classification:

| Component | Classification | Disposition |
|---|---|---|
| Windows identity/fingerprint rules | EXISTING — KEEP | Preserve behavior and regression fixtures. |
| Windows evidence collection | EXISTING — ADAPT | Move or extract the pure collector behind the Helper protocol. |
| Backend-local Windows execution | DEFER as compatibility path | Do not use for Linux-hosted Helper operation; retain until cutover proves parity. |
| Linux remote-provider adapter | NEW — REQUIRED FOR V1 | Convert authenticated Helper evidence into the existing normalized probe contract. |
| Windows-only NAS acquisition | DEFER | Mounted NAS remains authoritative where Linux already has direct access. |

## 4. Existing Source Creation / Endpoint / Profile Model

The current model is the correct durable foundation:

- `AccessNode` represents the computer/provider presence and stores a stable UUID, OS/provider identity, capability evidence, status, and last-seen state.
- `SourceEndpoint` represents durable media/device/share identity using a versioned fingerprint, not a current path.
- `SourceEndpointObservedPath` records where an Endpoint was observed on a particular Access Node, including the Windows path and safe probe evidence.
- `IngestionSource` remains the durable Source Profile and binds a user-facing alias and `endpoint_relative_root` to an Endpoint.
- one Endpoint may have multiple contained Profiles without duplicating the physical Source identity.

The plan/confirm creation service already recomputes the plan, fingerprints it, requires explicit confirmation, reuses exact durable identity atomically, and enforces alias and root constraints. Those guarantees should remain.

For a Helper-backed Source, the browser must not submit raw evidence as authority. The backend creates a short-lived enrollment/probe job for a paired Access Node. The Helper collects evidence for the exact requested Windows root, and the backend provider adapter converts it to the existing `SourceIdentityProbeResponse`. The existing creation plan then persists or reuses the Access Node, Endpoint, Observed Path, and Profile.

The Source root must be represented as:

```text
durable identity: SourceEndpoint fingerprint
durable contained root: IngestionSource.endpoint_relative_root
provider-native observation/display: Windows absolute root in SourceEndpointObservedPath
temporary Linux receiving path: acquisition-run state only
```

A receiving path is never an Endpoint, Profile root, or observed Windows path.

## 5. Readiness and Source Selection

The existing readiness status vocabulary can remain, but Helper-backed readiness needs provider-specific evidence instead of a backend-local filesystem probe.

Readiness should distinguish at least:

1. paired Helper reachable and authenticated;
2. Helper is the Access Node enrolled for the Profile's Endpoint;
3. expected volume/device/disc identity is present;
4. saved contained root still exists and is readable;
5. the Helper can safely inventory/acquire that root under current limits.

An offline Helper, absent media, wrong volume in a reused drive letter, missing root, and policy denial are different reasons. They should map to safe existing high-level readiness states with a redacted reason/next action, not collapse into “path missing.” The Profile remains visible while offline and does not silently relink.

Current Source Selection assumes a filesystem Profile resolves to a backend-visible root. That must be adapted. A Helper-backed successful selection should return:

```text
workflow: windows_helper_intake (or provider_acquisition)
selected Profile/Endpoint/Access Node: exact durable IDs
provider source root: Windows-native display value
resolved_source_root: null until verified Linux receiving objects exist
readiness context: helper/device/root result, capability version, safe next action
```

The selection must fail closed on an unavailable Helper, identity mismatch, missing contained root, ambiguous media, or unsupported capability. It must not return a fabricated Linux path.

## 6. Common Source Intake Boundary

`RunIngestionDispatchService` currently branches between direct filesystem intake and iCloud acquisition. Direct filesystem intake requires a Linux-visible `resolved_source_root` and calls `start_source_intake`. Helper-backed Sources need a third provider-acquisition branch before that common boundary.

The narrowest existing bridge is `PipelineContext.explicit_source_records` in `pipeline_orchestrator.py`. It already permits a verified, exact set of files beneath a runtime root to enter the normal Drop Zone and processing sequence without scanning the entire root.

Recommended bridge:

1. Helper inventory and selection occur outside Source Intake.
2. Authorized bytes arrive in a bounded Linux acquisition receiving root.
3. Linux verifies size and SHA-256 and atomically publishes each ready receiving object.
4. The provider adapter constructs exact `FileScanRecord` values only for ready objects.
5. Existing Source Intake stages those records into the Drop Zone and retains authority for filtering, canonicalization, hashing/deduplication, Vault persistence, Asset persistence, provenance, and report state.
6. Acquisition records are linked to Source Intake and Ingestion run results.

The bridge requires one focused adaptation: a record must be able to carry the provider-native Windows original path separately from its Linux runtime receiving path. Mounted and iCloud defaults remain unchanged.

## 7. Candidate Inventory / Selection Model

Inventory must precede byte transfer. Copying an entire Windows root merely to discover candidates would violate the provider boundary and create an uncontrolled second staging system.

The Helper should return bounded, paginated, stable inventory pages containing only allowlisted fields:

- protocol, capability, job, Profile, Endpoint, and Access-Node binding;
- inventory generation and digest;
- opaque candidate ID and normalized Windows-relative path;
- filename/extension;
- regular-file/reparse-point status;
- size and high-resolution modified time;
- stable file ID when the filesystem exposes one;
- optional cached SHA-256 and the exact cache-evidence tuple supporting it.

The Helper is authoritative for Windows access checks, Windows path containment, reparse/symlink exclusion, and collecting volatile filesystem metadata. Linux remains authoritative for allowed media policy, limits, known-item comparison, selection, transfer authorization, and whether evidence is sufficient.

The backend should request hashes only for selected, ambiguous, or potentially known candidates. It should then authorize transfer only for candidates whose bytes are needed. Every request and page must be bounded by count, bytes, duration, and recursion policy. An inventory generation change invalidates pending selection rather than mixing generations.

## 8. Windows Helper Transport

Recommended V1 transport:

```text
Windows Helper
  -> outbound HTTP/JSON client
  -> automatically managed exact SSH local forward
  -> Linux backend loopback-only /api/helper/v1 endpoint
```

Reasons:

- Development already binds backend/frontend services to loopback and the Windows operator already demonstrates bounded OpenSSH forwarding, hidden process launch, exact command verification, keepalives, mutex/state handling, and fail-closed startup.
- SSH provides encrypted transport and server host-key verification without creating a new LAN listener or PKI deployment in V1.
- an outbound polling/claim model avoids Linux dialing arbitrary Windows hosts and naturally tolerates reconnects.
- transport remains implementation infrastructure; the user selects a Source and clicks Run rather than operating a tunnel.

The Helper may safely reuse a verified compatible tunnel or start its own narrowly identified forward. It must never accept “a process exists” as proof of the expected tunnel. Port, destination, SSH host alias, process identity, and ownership must all match. Tunnel failure is a transient Helper-offline condition.

This is not permission to expose `/api/admin` or the normal backend API on the LAN. A future direct-LAN transport would require a separate TLS/mTLS threat-model milestone.

## 9. Trust Boundary

| Evidence/action | Windows Helper authority | Linux backend authority |
|---|---|---|
| Helper installation/session identity | Presents credential and capabilities | Authenticates, maps to enrolled Access Node, authorizes scope |
| Volume/device/disc observation | Collects Windows-native evidence | Computes/compares expected fingerprint and Endpoint binding |
| Root existence/readability | Observes exact Windows root | Authorizes saved Profile root and validates containment semantics |
| Relative paths | Derives Windows-relative paths | Validates syntax, uniqueness, generation, and exact requested root |
| Size/mtime/file ID | Authoritative observation at inventory/read time | Treats as volatile; uses for cache/TOCTOU checks, not canonical content truth |
| File SHA-256 | Authoritative claim over remote bytes | Rehashes transferred bytes; permits no-transfer use only under strict evidence and Vault checks |
| File bytes | Reads only authorized candidates | Limits, receives, hashes, accepts/rejects, and publishes ready objects |
| Media type/eligibility | May supply hints | Existing application policy is authoritative |
| Windows full path | Supplies normalized native evidence | Reconstructs/checks against enrolled root plus relative path; never filesystem-joins it on Linux |
| Linux receiving path | No authority | Allocates opaque job-owned paths and controls lifecycle |
| Drop Zone/Vault/Asset/Provenance | No write authority | Sole authority through existing Source Intake |

An authenticated Helper is trusted to observe the remote Source, but it is not trusted to define policy or assert that transferred content is canonical without Linux verification.

## 10. Receiving / Staging Lifecycle

Use a provider-owned area under application storage, for example:

```text
storage/acquisition/windows/<acquisition-run-uuid>/
  partial/<opaque-candidate-uuid>.part
  ready/<opaque-candidate-uuid>
```

Rules:

- Linux allocates every path from opaque IDs; no Windows path component is joined into a Linux path.
- each chunk is bound to job, candidate, offset, expected length, and idempotency key;
- partial files remain non-ready and are never passed to Source Intake;
- Linux enforces total/job/item quotas and bounded concurrency;
- completion requires expected byte count and a Linux-computed SHA-256 matching authorized evidence;
- complete files are atomically renamed into `ready`;
- only a complete manifest generation may produce explicit Source Intake records;
- the receiving area is temporary acquisition state, not a durable Source root, Drop Zone, or second Vault.

After Source Intake has durably linked results, guarded cleanup may remove only exact run-owned partial/ready bytes. Failed or interrupted state follows a bounded retention policy for resume and diagnosis. Ambiguous linkage blocks cleanup.

## 11. Provenance Mapping

The accepted 12.64 runtime mapping should remain unchanged:

```text
IngestionRun.from_path = actual Linux runtime root used by Source Intake
Provenance.source_path = actual Linux runtime candidate path
Provenance.source_root_path = that Linux runtime root
Provenance.source_relative_path = path relative to that runtime root
```

For Helper acquisition, that runtime root is the verified Linux receiving root. It must not be rewritten to a Windows path because 12.64 uses these fields to prove the runtime mapping and verify repeat observations.

Provider-native lineage belongs in a new durable acquisition item linked to:

- acquisition run;
- Profile, Endpoint, and Access Node through the run;
- provider-native Windows root, relative path, and reconstructed full path;
- inventory/hash/transfer evidence;
- Source Intake run, Ingestion run, resulting asset SHA, and Provenance row when applicable.

This produces an auditable reverse join from a normal Provenance record to the exact Windows observation without making a temporary receiving path durable Source identity or weakening the existing Provenance contract.

## 12. Asset.original_source_path Semantics

For the first successful Helper-backed creation of an Asset, `Asset.original_source_path` should be the normalized Windows-native full Source path, for example `E:\\Photos\\family\\image.jpg`, not the Linux receiving path.

The current persistence path uses one `original_source_path` value for both Asset and runtime Provenance. The explicit-record/persistence seam must therefore carry two distinct concepts:

```text
runtime_candidate_path: Linux receiving object used by Source Intake/Provenance
asset_original_source_path: provider-native Windows full path used only when first creating Asset
```

Mounted/default records may continue setting both from the current filesystem path. Helper records set them separately. Exact-known reuse must never rewrite the existing Asset's `original_source_path`; it adds only the legitimate new Source observation and acquisition linkage.

## 13. Exact-Known / Non-Repeat Behavior

The 12.64 rules remain authoritative:

- same Profile plus same relative Source observation already recorded: do not create another Asset or duplicate Provenance;
- different legitimate Source observation with exact-known bytes: verify the canonical Vault object, reuse the Asset/Vault object, and add the new provenance/acquisition linkage;
- missing, damaged, size-mismatched, hash-mismatched, or untracked canonical Vault content: fail closed rather than recopying or declaring success;
- exact-known reuse never overwrites Asset identity fields or canonical bytes.

Helper SHA evidence can avoid transfer only when all of the following hold:

1. the authenticated Helper, Access Node, Endpoint, Profile root, inventory generation, and candidate are exactly bound;
2. the hash is fresh or comes from a cache keyed by strong volume identity, stable file ID where available, normalized relative path, size, and modified time;
3. the backend finds an exact-known candidate;
4. Linux performs the complete accepted Vault size/hash/trackability verification;
5. the common Source Intake known-observation seam records the observation atomically.

Any uncertainty requires transfer and Linux hashing. For a transferred candidate, Linux always computes SHA-256. The Helper must compare file identity and metadata before opening and after reading; a change invalidates the item and inventory generation.

## 14. External / Removable Identity

The existing volume GUID fingerprint v2 is the durable V1 identity for Windows Local/External/Removable volumes. It survives drive-letter changes and ordinary reconnect/reboot behavior. Volume serial, bus/media classification, PnP, and physical-disk observations remain supporting evidence; current code does not prove a complete durable drive-to-hardware serial join and must not pretend otherwise.

Required fail-closed behavior:

- the Helper is the Windows Access Node, not the Source Endpoint;
- the volume/media fingerprint is the Endpoint;
- a current drive letter is only an observed path;
- the Helper reverifies the Endpoint before every inventory/acquisition;
- same drive letter with a different fingerprint fails before inventory or transfer;
- same fingerprint at a new drive letter may update the observed path after successful verification;
- one Endpoint may retain multiple contained Profiles.

Reformatted media naturally becomes a new Endpoint. Stronger physical-device continuity across reformat remains later research and must not weaken V1 matching.

## 15. Optical Media

The current Optical provider already has an appropriate read-only identity direction: require physical optical media, reject virtual/empty/unreadable/audio/movie media, build a complete metadata-only directory manifest twice, and fingerprint stable disc content independently of drive letter, reader hardware, free/used capacity, and timestamps.

That logic should be extracted into the Helper and contract-tested, but live Optical acquisition should follow Local and External/Removable milestones. Optical needs focused Windows hardware evidence for media insertion/removal, stable-manifest timeouts, changing media, reader changes, and error handling. Linux must never require a directly mounted optical path for the Windows Helper provider.

The Helper may enumerate/read an approved data disc only after identity and root selection. It must not eject, alter, finalize, or write optical media.

## 17. Helper Lifecycle

Recommended staged lifecycle:

1. protocol milestones use a foreground CLI for deterministic development and controlled evidence;
2. user-facing V1 packages the Helper as a windowless executable launched on demand by a registered `photo-organizer-helper://` URI or a small verified launcher;
3. the Helper establishes/reuses its verified tunnel, authenticates, claims the requested bounded job, completes or reports it, idles briefly, and exits;
4. a tray application, always-running service, or auto-update agent is later work only if scheduling or product evidence requires it.

Use `%LOCALAPPDATA%\PhotoOrganizer\WindowsHelper` for bounded redacted logs, disposable cache, and non-secret state. Store the raw application credential using Windows DPAPI/Credential Manager, not in the JSON state or logs.

The Development Operator remains a separate tool. Its hidden-launch, mutex, exact-process, tunnel, and local-state patterns are reusable; its UI, fixed Development ports/paths, VS Code/WinSCP actions, and manual tunnel workflow are not the Helper architecture.

## 18. Scheduling Hooks

V1 does not need scheduled intake, but it must avoid blocking it architecturally. Backend acquisition jobs and Helper polling should already be durable and idempotent, so a future scheduler can request a saved Profile without inventing another acquisition path.

Future scheduling still requires:

- an enrolled Helper available without an interactive desktop action;
- explicit user policy for wake/start behavior and Source availability;
- concurrency and quota policy;
- safe handling of absent/remapped removable media;
- credential rotation and unattended tunnel policy;
- the same selection, transfer, Source Intake, and provenance contracts as manual runs.

Do not implement a Windows service merely to reserve this seam.

## 19. Security Model

V1 needs defense in depth:

- SSH encryption and strict host-key verification for the transport;
- a dedicated `/api/helper/v1` surface bound to loopback, not reuse of broad admin endpoints;
- a random, revocable per-Access-Node application token, server-side hash only, raw token protected by Windows DPAPI/Credential Manager;
- one-time, short-lived pairing authorization initiated through the existing trusted browser/admin session;
- explicit binding of every call to credential, Access Node UUID, protocol/capability version, job, Endpoint, Profile, and inventory generation;
- request expiry, nonce/sequence or idempotency keys, replay-safe mutations, bounded bodies, rate limits, concurrency limits, and quotas;
- allowlisted JSON schemas with unknown-field rejection and secret-free error/report output;
- constant-time token checks and prompt revocation/rotation;
- no Helper database credentials, Vault path authority, Docker access, shell-command API, arbitrary Linux paths, or general filesystem upload endpoint;
- Windows reparse/symlink exclusion and containment checks both when inventorying and immediately before/after reading;
- Linux allocation of all receiving filenames from opaque IDs.

The normal browser API is not currently an adequate Helper authentication boundary. SSH alone proves a connection to the server but does not establish which Helper/Access Node is making an application request; the application token is mandatory.

## 20. Failure / Resume / Cleanup

Acquisition must be a durable state machine, not a long synchronous request. At minimum distinguish planned, waiting-for-helper, inventorying, inventory-ready, selecting, transferring, verifying, ready-for-intake, intake-running, completed, failed-retryable, failed-terminal, stopped, and cleanup states.

Resume rules:

- every mutating request is idempotent;
- server state, not Helper memory, is authoritative for accepted offsets/items;
- reconnecting Helper asks for the last accepted item/chunk state;
- a lost response may be reconciled without duplicating bytes or advancing state twice;
- transfer resumes only if Helper/device/root/item identity and current metadata still match;
- changed files, changed inventory generation, wrong media, or ambiguous state trigger re-inventory or a fail-closed stop;
- lease/heartbeat expiry releases active work safely but does not delete evidence;
- Source Intake handoff is retried by reconciling linked run/result state before creating another intake run.

Cleanup deletes only exact acquisition-run-owned temporary bytes after durable terminal state and linkage checks. Retention is bounded by age and bytes. A manual cleanup operation, if later needed, must be scoped to one run and must never infer ownership from a broad directory name.

## 21. Reusable iCloud Patterns

The iCloud acquisition implementation proves several provider-neutral patterns that should be reused conceptually:

- durable acquisition run/item/resource state rather than process memory;
- explicit state transitions, heartbeats, leases, stop/error/next-action fields;
- a secret-free, allowlisted manifest and stable manifest digest;
- bounded selection and exact resource/item identities;
- partial publication followed by size/hash verification and atomic readiness;
- reconciliation after lost responses or uncertain handoff;
- a batch/run readiness gate before common Source Intake;
- explicit-source-record handoff and durable linkage to Source Intake, Ingestion runs, assets, and provenance;
- guarded cleanup only after linked results are known.

Do not reuse iCloud-specific tables, provider schemas, authentication, subprocess protocol, live-photo/resource grouping, cloud identifiers, or cleanup-approval UX for Windows. A Windows filesystem item, removable volume, and optical disc have different identity and retry semantics. The correct reuse is a provider-neutral acquisition pattern, not inheritance from an iCloud implementation class.

## 22. Testing Strategy

Testing should be layered so a large live cross-machine harness is not the first proof:

1. **Pure identity unit tests** — golden and mocked Windows command evidence for volume GUID, UNC, removable classification, drive-letter changes, wrong media, optical manifest stability, and normalization.
2. **Protocol contract tests** — request/response versioning, allowlists, unknown fields, bounds, canonical digest, capability negotiation, idempotency, and redaction on both Helper and backend.
3. **Helper unit tests** — Windows containment, reparse exclusion, TOCTOU detection, inventory paging, cache keys, chunk reads, DPAPI credential wrapper, tunnel identity checks, and redacted logging.
4. **Backend API/security tests** — pairing, token hash/revocation, Access-Node/job binding, replay/expiry, quotas, authorization, wrong helper/device/root rejection, and no admin API authority.
5. **Persistence/state tests** — acquisition run/item transitions, uniqueness, resume, lost response, manifest generations, intake linkage, retention eligibility, and no required backfill.
6. **Receiving tests** — opaque paths, partial publication, offsets, length/hash mismatch, concurrent/replayed chunks, disk/quota failure, atomic ready state, and exact cleanup ownership.
7. **Common Source Intake regressions** — unique content, same-Source repeat, cross-Source exact-known provenance, damaged/missing/untracked Vault failure, Asset original-path immutability, and no Helper write to Drop Zone/Vault/database.
8. **Frontend tests** — capability-gated Source types, offline Profile visibility, actionable readiness, Windows-native display, no receiving-path disclosure, one Run flow, and repository-pinned lint/build.
9. **Controlled Windows integration** — paired Helper against an approved bounded Local fixture, then approved External/Removable hardware and later Optical media. Capture unique, repeat, changed-file, reconnect, drive-letter reuse, interruption/resume, and cleanup evidence.
10. **Provider regression suites** — keep Mounted NAS/Local and iCloud suites independent and green; no test should require one provider to impersonate another.

## 24. Backend Helper API / Provider Adapter Seam

Add a dedicated versioned Helper router, conceptually /api/helper/v1, with narrowly scoped operations:

- enroll/complete pairing and advertise capabilities;
- heartbeat and claim the next job authorized for that Access Node;
- submit probe/readiness evidence;
- start/page/finish an inventory generation;
- receive hash evidence and backend selection/transfer authorization;
- query accepted item offset;
- upload bounded chunks and complete an item;
- report item/job failure or stop acknowledgement;
- query terminal result/cleanup eligibility.

Browser/admin operations remain separate: create pairing authorization, request readiness/creation/selection/run, inspect redacted progress, stop a run, and revoke a Helper. The Helper credential must not grant arbitrary admin access.

Recommended backend component boundaries:

    Helper API/auth
      -> Windows Helper protocol service
      -> remote Source identity provider adapter
      -> acquisition run/inventory/selection service
      -> receiving and verification service
      -> common Source Intake bridge
      -> existing Source Intake/Vault/provenance authority

The adapter should produce the existing normalized identity response rather than teach creation code to trust Helper-specific JSON. Dispatch should add a provider-acquisition workflow branch. Source Intake should receive exact verified records only after the acquisition run is ready.

## 25. Schema Assessment

Existing durable identity tables should be kept. Helper connectivity and resumable acquisition cannot be represented safely by IngestionRun.from_path, Provenance, or an iCloud-specific acquisition table. Add provider-neutral tables before byte transfer.

### Required additive records

**SourceAcquisitionRun** (name may follow repository convention):

- UUID and provider/protocol version;
- Profile, Endpoint, and Access Node foreign keys;
- status, idempotency key, inventory generation/digest;
- provider-native Source root and Linux receiving root;
- selected/transferred/known/failed counts;
- heartbeat/lease, start/completion, failure/stop/next-action fields;
- nullable Source Intake and Ingestion run links.

**SourceAcquisitionItem**:

- acquisition-run foreign key, opaque candidate UUID/ordinal;
- provider-native relative/full Source paths;
- optional hashed file-ID evidence, size, mtime, Helper hash and evidence class;
- transfer state, accepted offset/bytes, received hash, failure state;
- resulting asset SHA and nullable Provenance/Source Intake/Ingestion links;
- uniqueness for run plus candidate and normalized provider-relative path.

**WindowsHelperCredential** (or equivalently narrow Access-Node credential table):

- Access Node foreign key;
- credential version, token hash, status;
- created, rotated, revoked, and last-used timestamps;
- no raw token.

No change is required to SourceEndpoint, SourceEndpointObservedPath, IngestionSource, IngestionRun, Provenance, or Asset columns for V1 if the acquisition item carries provider-native lineage and the runtime record carries a separate Asset original-path value. Existing rows need no backfill. The migration risk is moderate because constraints, lifecycle states, and cleanup linkage must be correct, but it is bounded and additive. Acquisition tables are required before transfer; credential persistence is required before authenticated pairing. Neither should be deferred into live validation.

## 26. V1 Recommended Architecture

1. The user pairs a Windows Helper once through a short-lived authorization from the trusted application UI; the backend binds its credential and capabilities to an Access Node.
2. The user creates/enrolls a Windows-connected Source using a normal Windows root.
3. The backend creates an exact probe job for the paired Helper; the Helper proves its identity and collects bounded Windows device/root evidence.
4. The backend computes/compares the durable Endpoint fingerprint and uses the existing plan/confirm path to persist or reuse Endpoint/Profile identity and an observed Windows path.
5. The saved Profile remains visible. On selection/run, the backend checks Helper availability and creates a durable acquisition run.
6. The Helper reverifies the expected device/disc identity and contained Source root before any inventory.
7. The backend requests a bounded, paginated inventory generation; the Helper returns metadata only.
8. Existing Linux application policy determines eligible/needed candidates and requests hashes only where needed.
9. The backend applies same-Source and exact-known rules. The Helper transfers only authorized candidates whose bytes Linux needs, using resumable bounded chunks.
10. Linux writes opaque partial files, verifies byte count and SHA-256, and atomically publishes ready receiving objects. Strictly proven exact-known observations may skip transfer only after canonical Vault verification.
11. The provider adapter feeds ready objects or exact-known observations through the common Source Intake boundary with separate Linux runtime and Windows original-path evidence.
12. Existing ingestion, Drop Zone, Vault, Asset, deduplication, and provenance behavior remains authoritative.
13. Acquisition items link Windows-native evidence to the resulting normal provenance and run records.
14. Guarded cleanup removes only terminal run-owned receiving bytes; durable run/report state remains resumable and auditable.

## 28. Rejected Designs / Red Flags

| Design | Decision | Reason |
|---|---|---|
| Map Windows drive paths into Linux Mounted paths | Reject | Destroys provider-native identity and invents false Linux access. |
| Mount arbitrary Windows shares in Linux as the primary Windows provider | Reject | Changes authority, credentials, and filesystem semantics and excludes directly connected removable/optical media. |
| Copy an entire Windows Source before selection | Reject | Unbounded, wasteful, and turns staging into a second Source scan. |
| Trust drive letter as identity | Reject | Letters are mutable observations; existing volume fingerprints already solve this. |
| Let Helper write directly into Vault | Reject | Bypasses Linux hash, canonical conflict, and Source Intake authority. |
| Give Helper database write access | Reject | Breaks trust boundary, transactions, validation, and auditability. |
| Build a second ingestion pipeline in Helper | Reject | Duplicates filtering/dedup/Vault/provenance and will drift from 12.64. |
| Let Helper perform canonicalization | Reject | Canonical media policy and output belong to the common Linux pipeline. |
| Trust Helper SHA without verification policy | Reject | Remote evidence alone cannot establish received/canonical byte integrity. |
| Permit unbounded directory transfer | Reject | Violates capacity, safety, and candidate-selection requirements. |
| Expose transport-specific UX | Reject | Tunnel/URL/chunk mechanics are infrastructure, not Source semantics. |
| Make temporary staging path durable Source identity | Reject | Receiving paths are job-local and cannot replace Endpoint/Profile/Windows lineage. |
| Expose the normal admin API directly on the LAN | Reject | Current browser/admin surface is not a Helper authentication boundary. |
| Reuse iCloud tables or provider classes for Windows | Reject | Reuse lifecycle patterns, not cloud-specific schema and semantics. |
| Join raw Windows path components into Linux receiving paths | Reject | Enables traversal/collision and misrepresents path semantics. |
| Require an always-running Windows service in first implementation | Reject for V1 | Adds install/privilege/lifecycle risk before protocol and run behavior are proven. |
| Treat Helper cache as durable truth | Reject | Cache is an optimization and must be fully evidence-bound and disposable. |

## 30. Regression Boundaries

- **Mounted NAS:** keep direct Linux provider, broker/namespace identity, Runtime Root mapping, selection, and live intake unchanged. Windows Helper must not become a second route to the accepted NAS.
- **Mounted Local:** preserve the accepted architecture and deferred live proof; do not require Helper enrollment where Linux has approved direct access.
- **iCloud:** preserve independent Cloud acquisition, durable state, exact selection, staging, and cleanup. Reuse patterns without sharing provider tables or auth.
- **Windows identity:** retain existing versioned fingerprints, Windows-native paths, drive-letter fail-closed behavior, UNC canonical identity, and optical stability rules.
- **Source Selector:** retain durable Profile-first selection and offline visibility. Add a provider-acquisition workflow without weakening direct filesystem selection.
- **12.64 Vault/provenance:** preserve Linux Source Intake authority, runtime mapping, exact-known canonical verification, same-Source idempotency, cross-Source provenance, and Asset immutability.
- **Development/Test isolation:** no Test or Production mutation during development; backend/frontend rebuilds and controlled Profiles/intakes require milestone-specific authorization; PostgreSQL/Redis/volumes remain bounded by each prompt.
- **Source safety:** Helper performs read-only Source access. No marker files, metadata repair, permission changes, renames, deletes, or Source-side staging.

Each implementation milestone should run the focused provider tests it touches plus the smallest relevant common regression set. Avoid provider-wide rewrites and broad live repair loops.

# 1. Purpose

Implement and validate the first real Windows Helper **trust and communication boundary**.

12.66.1 already established:

- the shared Windows identity collector;

- strict Helper protocol v1;

- Windows-native path semantics;

- deterministic/redacted wire contracts;

- no networking/authentication/acquisition behavior.

12.66.2 must now add:

```text
Helper pairing
→ durable Access-Node-bound credential
→ authenticated Helper API
→ capability registration
→ Helper presence / heartbeat
→ verified outbound SSH forwarding
→ controlled live pairing/channel proof
```

This milestone must **not** introduce Source inventory or file transfer.

Before 12.66.3 can trust remote Windows identity/readiness evidence, 12.66.2 must first prove:

```text
Who is this Helper?
Which Access Node is it bound to?
Can Linux authenticate it?
Can the credential be revoked?
Can another Helper/node misuse it?
Can communication occur without exposing the normal backend/admin API to the LAN?
```

# 9. Credential Model

Preferred conceptual record:

```text
WindowsHelperCredential

id / public credential identifier
AccessNode foreign key
credential version
token hash
status
created_at

```

Use repository naming conventions where they differ.

Required:

- raw long-lived token is never persisted on Linux;

- server stores a cryptographically strong password/token hash suitable for verification;

- credential is bound to exactly one Access Node;

- credential can be revoked;

- only active, non-revoked credential authenticates;

- rotation can invalidate/replace the prior credential cleanly;

- no credential can authorize another Access Node merely by changing a request field.

Do not store Helper secrets in:

- AccessNode evidence JSON;

- application logs;

- protocol diagnostics;

- Source Profiles;

- environment output.

# 16. Windows Secret Storage

The raw Helper application token must not be stored in plaintext.

Implement a narrow credential-store abstraction.

For actual Windows operation, use Windows protected secret storage.

Preferred V1 direction from reconnaissance:

```text
Windows DPAPI
```

A DPAPI-protected blob under:

`%LOCALAPPDATA%\PhotoOrganizer\WindowsHelper`

is acceptable.

Windows Credential Manager is also acceptable only if it is materially simpler under current dependencies.

Requirements:

- raw token not written to normal JSON state;

- raw token not logged;

- raw token not printed by status commands;

- decrypt only when needed for authenticated request;

- tests use fake/mock credential stores;

- Linux unit tests must not require Windows DPAPI availability.

Do not add a large Windows dependency merely for credential storage if a safe standard-library/ctypes implementation suffices.

Document the exact choice.

# 18. SSH Trust Requirements

The tunnel manager must verify more than “ssh.exe exists.”

At minimum:

```text
expected SSH executable
expected SSH host/alias
strict host-key verification
exact local forwarding destination
exact backend loopback target
ServerAliveInterval / ServerAliveCountMax or equivalent bounded keepalive
ExitOnForwardFailure
no remote shell
no remote command
```

Use an SSH form equivalent to:

```text
-N
-L <helper-local-port>:127.0.0.1:<backend-loopback-port>
```

but determine exact safe arguments from existing project/operator evidence.

Do not use:

```text
0.0.0.0 local bind
GatewayPorts
reverse tunnel
dynamic SOCKS proxy
remote shell
```

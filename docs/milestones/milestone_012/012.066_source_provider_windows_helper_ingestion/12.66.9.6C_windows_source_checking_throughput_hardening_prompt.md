# Milestone 12.66.9.6C — Windows Source Checking Throughput Hardening

## Purpose

Reduce the remaining user-visible delay in Windows `Checking Sources` for existing Local / External / Removable Sources.

12.66.9.6B successfully reduced approved ingestion of the 35-file Profile 15 benchmark from approximately 478 seconds to 38.6 seconds while preserving identity/integrity guarantees.

The remaining performance problem is now the pre-ingestion Source-checking phase.

Accepted 12.66.9.6B Profile 15 warm measurements:

Volume observation:       34.579 s
Selected-source probe:    11.026 s
Inventory page:           11.506 s

The inventory page itself performs almost no expensive file work; the approximately 11-second floor is physical identity work.

The current normal existing-Source path therefore still spends roughly one minute repeatedly proving device-level facts before the user can approve ingestion.

This milestone must optimize that path without weakening:

- AccessNode authority;
- Endpoint/Profile identity;
- Volume GUID v2 / durable fingerprint identity;
- wrong-device fail closed;
- Source-root containment;
- drive-letter-independent portable identity;
- inventory generation/cursor integrity;
- point-in-time proposal semantics;
- per-file acquisition integrity established in 12.66.9.6B.

This is not a redesign of Source creation or discovery.

# 6. Primary Goal — Avoid Broad Volume Observation for Normal Known-Source Checking

The normal ingestion path for an existing registered Source should not enumerate/classify every attached Windows volume unless that information is actually required.

The backend already knows:

- selected AccessNode;
- Endpoint;
- Profile;
- Source type;
- durable fingerprint / Volume GUID identity;
- authoritative provider-native Source root or accepted route evidence;
- previously established Source classification.

For normal checking of an existing Source, prefer a targeted verification of the selected Source.

Conceptually:

Existing Profile selected
→ backend supplies expected durable Source contract
→ Helper verifies that exact Source/current route
→ inventory begins

rather than:

Existing Profile selected
→ rediscover/classify all attached volumes
→ locate selected Source among them
→ probe selected Source again
→ inventory probes it again

Do not remove broad volume discovery from Add Source / Manage Source flows where it is still required.

---

# 7. Targeted Known-Source Verification

Design the smallest safe verification for an already-enrolled Source.

Where technically reliable, reuse the Windows-native identity concepts accepted in 6B:

- open/resolve the expected Source root;
- derive current Volume GUID/native volume identity;
- compare against the approved durable Endpoint fingerprint;
- prove current root belongs to that volume;
- prove containment;
- verify current route belongs to the expected AccessNode/Profile.

Do not use drive letter as identity.

For External/Removable:

same Volume GUID at a different drive letter
→ may be accepted according to existing route-reconciliation rules.

different Volume GUID at the historical drive letter
→ fail closed.

For Local:

retain the accepted Local absolute-root contract and durable machine/volume authority.

# 8. Missing / Stale Route

Normal fast checking must not convert stale cached routing into blind trust.

If the expected route is unavailable:

do not claim Ready merely because it was valid previously.

Use the smallest safe route-recovery path.

Preferred behavior:

known current route works
→ targeted verification

known route missing/stale
→ bounded resolution for the expected durable volume

exact durable volume found
→ update/reconcile current observation according to existing rules

different/ambiguous device
→ fail closed

Broad all-device discovery should be fallback behavior only when targeted resolution cannot safely locate the expected Source.

Document when and why fallback occurs.

# 10. Inventory Attestation Binding

Bind the checking/inventory attestation at minimum to:

- protocol/token version;
- AccessNode;
- Endpoint;
- Profile;
- Source type;
- durable fingerprint / Volume GUID;
- authoritative current Source root;
- exact Windows parent workflow/check session;
- inventory generation where technically appropriate;
- issue time;
- expiry.

Cursor integrity remains independently validated.

Do not allow an attestation from one Profile/workflow/generation to authorize another.

---

# 11. Inventory Generation Semantics

Preserve the accepted point-in-time proposal model.

The inventory attestation must NOT mean:

“anything on this device during the next N minutes is approved.”

It only establishes device/root continuity.

The proposal is still defined by the deterministic inventory generation/cursor chain.

Preserve:

- complete ordered inventory;
- one generation;
- contiguous page chain;
- no repeated cursors;
- unique candidate refs;
- unique normalized relative paths;
- proposal digest;
- one user approval of the completed proposal.

New files appearing after approval still wait for a later ingestion.

---

# 12. Attestation Expiry / Helper Restart

Use a bounded lifetime.

Prefer reuse of the security model/pattern established in 6B where appropriate, but keep inventory scope distinct.

Helper restart must invalidate process-local attestation authority.

If an attestation disappears/expires during inventory:

- do not silently trust prior state;
- do not fabricate continuation;
- determine whether the exact inventory generation/cursor chain can safely continue after fresh verification.

If Helper restart invalidates its process-local cursor state, retain the accepted behavior:

inventory abandoned
→ fresh inventory
→ fresh proposal
→ fresh approval

Do not attempt to reconstruct lost cursor state.

# 13. Remove Repeated Full Probe Per Inventory Page

The current page path must no longer perform the approximately 11-second full physical discovery for every continuation page when a valid inventory-scoped attestation proves device/root continuity.

Each page must still verify:

- valid attestation;
- exact workflow/Profile/Endpoint binding;
- current route/root continuity;
- inventory generation;
- cursor continuity;
- candidate containment;
- current Source availability.

If lightweight evidence detects ambiguity or mismatch:

fail closed or require fresh full verification according to the exact condition.

Do not silently continue.

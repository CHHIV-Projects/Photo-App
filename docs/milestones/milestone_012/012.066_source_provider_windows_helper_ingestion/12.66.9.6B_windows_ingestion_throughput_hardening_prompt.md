# Milestone 12.66.9.6B — Windows Ingestion Throughput Hardening

## Purpose

Implement the measured, security-preserving throughput corrections identified by 12.66.9.6A.

12.66.9.6A conclusively established that Windows Local / External / Removable ingestion is dominated by fixed control-plane work rather than file-transfer bandwidth.

Measured Profile 15 results:

- 35 files;
- 27,983,035 bytes;
- one child;
- approximately 472–478 seconds approval-to-completion;
- approximately 394 seconds spent performing full physical-device identity probes once per file;
- approximately 52–54 seconds spent in Helper/backend operation-claim queue delay;
- only approximately 3.4–3.5 seconds spent in actual Helper upload round trips.

The first two mechanisms explain approximately 94% of current ingestion wall time.

The milestone must improve throughput without weakening:

- Volume GUID v2 durable identity;
- wrong-device fail closed;
- Source-root containment;
- opened-file handle/path verification;
- pre/post mutation evidence;
- Windows source SHA-256;
- Linux independent received-byte verification;
- exact-known Asset/Vault guarantees;
- Provenance;
- common Source Intake;
- durable backend orchestration.

This is an implementation milestone, not further open-ended reconnaissance.

# 4. Optimization A — Child-Bound Physical Identity Attestation

## Current defect

During acquisition the Helper currently performs one full physical-device identity probe for every file.

Measured:

35 files
→ 35 full probes
→ approximately 394 seconds

Average:

approximately 11.27 seconds per file

The PowerShell storage-metadata query dominates the probe.

The physical probe establishes primarily device/root-level evidence.

Per-file security evidence is already separately available through:

- root/path containment;
- file stat evidence;
- opened-handle path evidence;
- pre-read evidence;
- post-read evidence;
- source SHA-256.

## Required correction

Perform the expensive full physical identity verification once for a bounded child acquisition rather than once per file.

Conceptually:

BEGIN CHILD
→ full physical identity verification
→ establish short-lived child-bound attestation

FOR EACH APPROVED FILE
→ validate attestation
→ lightweight proof current file remains on expected volume/root
→ containment
→ handle/path verification
→ pre-read evidence
→ one source read + source SHA-256 + transfer
→ post-read evidence

END CHILD

Do not simply cache an arbitrary previous probe result.

The attestation must be explicitly scoped and validated.

# 6. Attestation Lifetime

The attestation must be short-lived and child-bound.

It must NOT survive arbitrary unrelated work.

Invalidate/fail closed on:

- child completion;
- child cancellation;
- Helper restart;
- Helper process replacement;
- AccessNode mismatch;
- Endpoint/Profile mismatch;
- durable fingerprint mismatch;
- source-root mismatch;
- route/device disappearance;
- expiry;
- explicit physical evidence mismatch.

Do not persist an indefinitely trusted device token.

Prefer process/session/child-scoped state unless durable persistence is actually necessary.

---

# 7. Lightweight Per-File Verification

Removing the full probe per file must NOT remove file-level proof.

Every acquired file must still prove:

- requested candidate belongs to approved child;
- relative path is contained under approved Source root;
- current path resolves under the expected volume/root;
- opened handle corresponds to expected path/file;
- expected size/timestamp/stable evidence as currently required;
- pre-read evidence;
- post-read evidence;
- file did not materially change during read;
- Helper source SHA-256;
- Linux received-byte verification.

Determine the smallest Windows-native lightweight check needed to prove the file remains on the attested volume/root.

Do not rely solely on drive letter.

---

# 8. Mid-Child Device Change

If the device is removed, replaced, remounted incompatibly, or physical identity evidence becomes inconsistent during a child:

fail closed.

Do not continue because an earlier attestation once succeeded.

If a lightweight per-file check detects ambiguity:

- stop/pause current child safely;
- require a fresh full physical identity probe before resuming;
- preserve completed files;
- do not duplicate completed work.

Wrong device at the same historical drive letter must never pass.

# 10. Optimization B — Active-Work Claim Coordination

## Current defect

After completing one file, Helper immediately requests another operation.

The backend may not yet have committed/queued the next per-file operation.

Helper receives an empty claim and sleeps for two seconds.

Measured Profile 15:

28 of 35 transitions
→ two-second empty-claim sleep

approximately:
52–54 seconds of durable queue delay.

## Required correction

Eliminate the fixed two-second race during an active child.

Prefer the smallest durable design that allows Helper to wait efficiently for imminent authorized work.

Acceptable architectural directions include:

- bounded server-held long poll;
- explicit active-child waiting claim;
- event/wakeup semantics compatible with current channel;
- adaptive short polling as a fallback.

Choose the smallest safe implementation consistent with the existing authenticated Helper channel.

---

# 11. Claim Safety Invariants

Any claim redesign must preserve:

- authenticated Helper;
- AccessNode binding;
- one-operation lease/claim semantics;
- no duplicate simultaneous acquisition;
- durable operation identity;
- idempotent completion;
- safe Helper disconnect;
- backend restart safety;
- cancellation;
- bounded timeout;
- no browser orchestration.

Do not create a persistent uncontrolled HTTP request.

Any long poll must have a bounded timeout.

---

# 12. Idle Helper Behavior

Do not optimize normal idle behavior into a tight polling loop.

The goal is:

ACTIVE CHILD
→ efficient transition to known imminent work

not:

NO WORK
→ high-frequency permanent polling.

When no workflow is active, Helper may retain a conservative idle cadence.

# 13. Optimization C — Bridge Validation Snapshot

## Current defect

6A measured that the reuse-only bridge rebuilt/revalidated ready records five times per child.

For 35 files:

175 ready-object hashes
139,915,175 bytes reread

per run.

This was page-cache cheap on the small benchmark but represents unnecessary scaling amplification.

## Required correction

Within one stable bridge state transition, construct one immutable/state-bound validation snapshot and reuse it through:

- planning;
- prior-observation determination;
- execution;
- result construction

where security boundaries permit.

Each ready object should be fully verified no more often than required by distinct trust boundaries.

Do not eliminate independent receiving verification.

Do not eliminate canonical Vault integrity verification.

---

# 14. Snapshot Invalidation

A bridge validation snapshot must be invalidated if relevant state changes, including:

- item path;
- expected hash;
- file size;
- receiving/published state;
- candidate identity;
- Source/Profile binding;
- child/acquisition identity;
- canonical Asset/Vault identity where applicable.

Do not reuse validation evidence across arbitrary future runs.

This is state-transition-local reuse, not a global integrity cache.

# 15. Optimization D — Prior-Observation Candidate Verification

## Current defect

Prior-observation lookup currently verifies every matching historical acquisition candidate's canonical Vault object.

6A observed:

cold:
455 canonical Vault hashes

warm:
630 canonical Vault hashes

The additional completed acquisition increased the next lookup by exactly five additional dataset passes.

## Required correction

Determine the authoritative prior lineage candidate first using durable database evidence.

Then perform canonical Vault verification on the selected authoritative candidate.

Do not hash every historical match merely to discover which candidate should be authoritative.

Preserve fail-closed behavior for genuinely ambiguous lineage.

Do not alter exact-known Asset/Vault semantics.

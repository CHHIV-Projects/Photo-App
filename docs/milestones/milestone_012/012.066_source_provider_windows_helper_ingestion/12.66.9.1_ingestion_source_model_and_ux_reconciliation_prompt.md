# Milestone 12.66.9.1 — Ingestion Source Model and UX Reconciliation

## Purpose

Perform a bounded Product Owner / architecture reconciliation of the completed ingestion provider model and the current Ingestion UI before any further implementation.

12.66.9 is technically accepted.

This milestone exists because the underlying provider architecture is working, but the current UI exposes too much implementation detail and the Source creation flow is no longer sufficiently clean or intuitive after introducing:

- Linux-hosted execution;
- Windows Helper / AccessNode registration;
- Mounted Source Provider;
- Windows Local / External / Removable providers;
- NAS source namespace;
- provider-specific access routing.

The goal is to define and document the simplest user-facing Source model that preserves the accepted architecture underneath it.

This is a RECONNAISSANCE / UX-DESIGN milestone.

Do not implement the redesign in this milestone.

# 3. Controlling Product Direction

The accepted provider architecture should remain underneath the UX.

Do not redesign the ingestion engine.

Do not create another Source identity model.

Do not create another Endpoint/Profile model.

Do not replace Windows Helper.

Do not replace the Mounted Source Provider.

Do not replace common Source Intake.

The problem to solve is primarily:

"What concepts should the user see and in what sequence?"

rather than:

"How should providers work internally?"

Windows Helper, AccessNode routing, runtime mount paths, broker plumbing, and transport mechanisms should normally be hidden from routine Source creation.

---

# 4. Current Product Problem

The current Create Source UI exposes concepts such as:

- Access Location;
- This server;
- Windows device;
- Add / Pair Windows Device;
- Windows computer;
- provider-specific transport distinctions.

Although technically correct, these concepts make Source creation feel like infrastructure configuration rather than photo-source setup.

The Product Owner wants the normal workflow to be based on physical/logical things users recognize:

- Computer;
- Local storage;
- External drive;
- Removable device;
- Server;
- NAS;
- iCloud;
- eventually Optical.

The UX should ask the user only for information that is necessary to identify and configure the Source.

---

# 5. Target Conceptual Hierarchy

Audit the existing implementation against this proposed hierarchy:

COMPUTER
Who is Photo Organizer allowed to communicate with?

SOURCE DEVICE / ENDPOINT
What physical or logical device supplies the photos?

SOURCE PROFILE
What bounded folder/root on that device should be ingested?

INGESTION
Select an existing Profile and run it.

The user-facing workflow should keep these concepts distinct.

In particular:

Windows computer registration
is NOT
Source-device registration.

# 6. Step 0 — Register a Windows Computer

The Product Owner prefers the user-facing term:

Register Computer

rather than:

Pair Windows Device

The underlying operation may still use Helper pairing internally.

Audit and design a normal flow approximately like:

Register Computer
→ Photo Organizer identifies/suggests the Windows computer name
→ user accepts or adjusts friendly display name
→ existing Helper pairing mechanism completes silently/boundedly
→ AccessNode becomes available
→ computer can expose Local / External / Removable Sources

Requirements to evaluate:

- Windows hostname should preferably seed the friendly computer name;
- hostname must not become the sole durable identity;
- AccessNode ID / authenticated credential remain durable authority;
- existing AccessNode rows must remain preserved;
- registration should normally happen once per Windows computer;
- pairing protocol details should not dominate the Source UI;
- registration should not create External or Removable Source Endpoints merely because the computer was registered.

Determine where "Register Computer" belongs in the UI.

Candidates may include:

- a small computer/device-management control near Ingestion;
- an Add Source prerequisite only when no registered Windows computer exists;
- an Admin/Devices management surface.

Recommend the simplest v1 placement.

Do not implement it.

# 7. Local Source Definition

Use this proposed product definition:

Local
=

storage physically local to a registered user computer.

The computer itself should correspond to exactly one durable Local Source Endpoint.

Proposed invariant:

one registered Windows AccessNode
→ at most one Local Endpoint

one Local Endpoint
→ zero or more Source Profiles

Profiles represent bounded folders/roots on that computer, for example:

Pictures
Scanned Photos
OneDrive Photos

Do not create another Local Endpoint merely because another folder is added.

Audit whether the current durable model can support this cleanly.

Identify:

- current Local Endpoint creation behavior;
- whether multiple Local Endpoints can currently exist under one AccessNode;
- how current Local Profile creation works;
- what backend invariant would need enforcement;
- compatibility effect on existing Endpoint 2 / Chuck_Notebook and Profiles 3 and 4.

Preserve existing accepted durable records.

Do not rewrite existing identities during this milestone.

If the proposed one-Local-Endpoint-per-computer model conflicts materially with accepted architecture, explain why and propose the smallest reconciliation.

# 9. External Source Definition

External
=

a durable externally attached storage device whose identity remains the same regardless of:

- drive letter;
- reconnect;
- which registered Windows computer currently provides access.

The Source Endpoint represents the external device.

The AccessNode represents only the currently available access path.

The user should normally select the External device, not the computer providing access to it.

Audit whether current Endpoint identity is truly portable across AccessNodes or whether any current identity/matching logic is implicitly scoped to one AccessNode.

This is a critical reconnaissance question.

Expected desired behavior:

Family Archive Drive
connected to Chuck-Desktop
→ Endpoint X

same Family Archive Drive
later connected to Family-Laptop
→ same Endpoint X

different drive using same drive letter
→ different Endpoint / fail closed

If current architecture cannot do this safely, identify the exact blocker and smallest architectural correction.

Do not implement it in 12.66.9.1.

External

# 11. Removable Source Definition

Apply the same principle to Removable.

Removable
=

a removable physical storage device identified durably across:

- drive-letter changes;
- disconnect/reconnect;
- different registered Windows computers where supported.

Normal user interaction should focus on the removable device itself.

Do not require the user to understand the Helper route used to observe it.

Audit whether current Removable identity already supports AccessNode-independent recognition.

# 12. Server as a Source Type

The Product Owner proposes adding:

Server

as an explicit Source Type.

For v1 define:

Server
=

storage physically local to the machine hosting this Photo Organizer installation.

Do NOT generalize this milestone to arbitrary discoverable LAN servers.

The current Mounted Source Provider and existing server-local location infrastructure should be reused.

Evaluate replacing:

Local + Access Location = This server

with simply:

Server

Expected user flow:

Server
→ choose/configure server-local Source location
→ bounded folder/root
→ Source Profile name
→ Review Source

Determine:

- what current server-local Source locations exist;
- whether the current fixed `Server Photos` location is a deliberate v1 boundary or accidental hard-coding;
- what would be required to safely support more than one approved server-local root;
- whether v1 should discover approved host locations or use explicitly registered/admin-approved roots.

Do not implement arbitrary filesystem browsing that weakens the existing Source boundary.

# 14. NAS — Current Limitation Audit

The current accepted NAS setup is intentionally bounded around:

//192.168.1.171/PhotoOrganizer

with a fixed Photo Organizer namespace slot.

This solved reliable access to the existing Synology NAS but does not necessarily constitute a general multi-NAS enrollment design.

Audit the current architecture and answer explicitly:

1. What happens today if a second NAS appliance is added to the network?
2. Can the current location registry represent more than one NAS?
3. Can the namespace service safely mount more than one NAS/share?
4. Which portions are hard-coded to the existing Synology IP/share?
5. Which portions are generic already?
6. Does Endpoint identity represent NAS appliance, share, or configured Source location?
7. What data would be required for durable NAS identity independent of IP address?

Do not modify NAS infrastructure.

---

# 15. Desired NAS Product Flow

The Product Owner's desired concept is approximately:

NAS
→ discover or choose available NAS
→ identify NAS by reusable friendly/device name
→ select/register share or location
→ choose bounded folder/root
→ Source Profile name
→ Review Source

Network discovery should be treated as convenience, not as durable identity.

Evaluate a safe v1 model such as:

Discover NAS
→ select server
→ register NAS/share
→ provide credentials/configuration if needed
→ thereafter use friendly registered NAS identity

Consider:

- SMB discovery;
- hostname/mDNS/NetBIOS where available;
- stable NAS identity;
- changing IP addresses;
- share discovery;
- authentication;
- credential storage;
- Linux mount lifecycle;
- namespace slots;
- unavailable NAS behavior;
- duplicate NAS detection;
- multiple NAS appliances;
- multiple shares on one NAS.

Do not assume that discovering a device automatically grants safe access.

# 22. Disconnected Sources

Existing configured Sources should not disappear when unavailable.

Desired behavior:

known Source
→ remains in Source Selector
→ displays availability/readiness state
→ Run Ingestion disabled when inaccessible

Examples:

External drive disconnected
→ still listed
→ "Device not connected"

Registered computer offline
→ Local Profile still listed
→ "Computer not available"

NAS unavailable
→ Profile still listed
→ "NAS not available"

No Source recreation should be required merely because access is temporarily unavailable.

## 2. Purpose / Accepted Baseline

The accepted 6B live checking baseline for existing External Profile 15 was 34.579 seconds of broad volume observation, 11.026 seconds of selected-source probing, and 11.506 seconds for its one inventory page: approximately 57.111 seconds before a proposal was ready. Those stages redundantly rediscovered an already-enrolled durable Volume GUID v2 Source. The accepted correction was a capability-gated known-Source path using targeted durable verification and an inventory-scoped attestation without weakening unknown-device enrollment.

## 3. Original Checking Sources Runtime Path

The original path performed broad all-volume observation, a full selected-source physical probe, and another full physical probe for every inventory page. PowerShell/CIM/PnP classification therefore dominated the checking phase even when the exact Endpoint and last registered Access Node were already known. The inventory cursor protected enumeration ordering but did not authorize lightweight durable-root continuity, so it could not remove those repeated probes by itself.

## 4. Known-Source vs New-Source Security Boundary

The optimized path is restricted to registered Sources whose Endpoint identity uses `source_endpoint_volume_guid_v2` and whose Helper advertises `known_source_inventory_attestation` version 1. Legacy identities, ambiguous evidence, unsupported Helpers, and fallback cases retain the prior full-verification path. Add Source and unknown External/Removable enrollment continue to require broad discovery, positive physical-storage classification, durable identity extraction, candidate-token authority, and wrong-device protection.

## 5. Targeted Known-Source Verification

Helper 0.5.4 implements `attest_inventory`. It opens the exact expected Source root as a directory handle, obtains the native Volume GUID associated with that handle, compares the resulting v2 fingerprint with the enrolled Endpoint, verifies the handle/root relationship and containment, rejects reparse roots, and binds the success to the exact Access Node, Endpoint, Profile, workflow, generation, root, and Source type. The implementation uses one bounded `mountvol` route mapping and does not perform CIM/PnP physical classification or inspect unrelated volumes on this fast path.

## 6. Volume Observation Correction

Known-Source route checking now targets the registered eligible Access Node first. When that node and exact durable route are available, it creates one `attest_inventory` operation directly and creates no `observe_volumes` operation. Broad observation remains a bounded fallback used only to locate the already-enrolled durable volume when the preferred route cannot do so; it is not used merely because the drive letter changed.

## 7. Selected-Source Probe Correction

The successful targeted attestation now supplies the readiness and durable-identity evidence previously obtained through `probe_source`, so the optimized path does not schedule a second approximately 11-second selected-source probe. During the first live attempt, `SourceProfileReadinessService` still parsed every operation as a legacy probe and returned `windows_inventory_not_started`. The service was corrected to recognize `attest_inventory`, validate the completed attestation, and adapt it to the existing readiness contract. Regression coverage now proves both readiness and Source Selection accept the targeted evidence. No inventory or ingestion began during the failed attempt.

## 8. Inventory Attestation Design

The inventory token is a distinct `iat1` HMAC-signed authority and is not the 6B child acquisition token. It proves the durable device/root context for one checking workflow and inventory generation; it does not redefine the immutable proposal or replace cursor-chain integrity. Inventory pages validate the token and perform lightweight directory-handle, Volume GUID, fingerprint, containment, and pre/post root-continuity checks instead of full physical rediscovery.

## 9. Attestation Binding / Expiry / Invalidation

The token binds protocol/token version, Access Node, Endpoint, Profile, Source type, durable v2 fingerprint, verified runtime root, exact parent workflow, inventory generation, issuance time, and expiry. The default lifetime is 15 minutes. A page may finish if time expiry occurs after its valid start, subject to normal pre/post continuity checks; a subsequent page requires fresh verification and a new token. The signing authority is process-local, so Helper restart invalidates outstanding tokens. Binding mismatch, wrong volume, wrong root, ambiguity, or unavailable identity fails closed.

## 10. Inventory Generation / Cursor Preservation

The targeted verifier creates and binds one inventory generation before enumeration. Existing cursor digests, generation matching, DFS ordering, page chaining, and proposal persistence remain authoritative. Attestation refresh preserves the same workflow and generation only after fresh exact verification. Helper restart with lost cursor/session state abandons the incomplete inventory and requires a fresh generation, proposal, and user approval; no cursor reconstruction was added.

## 11. Route Loss / Drive-Letter Change Handling

The exact durable Volume GUID may resolve at a different current drive letter. That new route is accepted as runtime evidence without rewriting Endpoint identity, Profile identity, or the persisted/historical Profile root. Zero matching routes reports unavailable; multiple plausible routes, fingerprint mismatch, or a different device at the historical letter fails closed. Automated coverage proves changed-letter success and wrong/missing/ambiguous-device rejection.

## 12. Local Compatibility

Local Sources retain their absolute Windows-root compatibility contract and legacy durable checks. The optimized portable route logic does not reinterpret Local Source identity, and shared inventory behavior retains root containment, cursor, and proposal guarantees.

## 13. External Compatibility

External Sources retain Endpoint-relative Profile roots, Volume GUID v2 durable identity, drive-letter-independent reconciliation, and distinct current route evidence. Profile 15 live validation proved the optimized External path against its existing registered Endpoint and 35-file root.

## 14. Removable Compatibility

Removable remains a distinct Source type with the same portable relative-root and durable Volume GUID protections. The shared capability-gated attestation path applies only when its accepted v2 identity and exact route are available; otherwise it safely retains legacy verification.

## 15. New Source Discovery Preservation

## 33. Deviations

The first live proposal attempt exposed an integration defect not found by the initial focused workflow tests: readiness still assumed a legacy `probe_source` result. Separate micro-timing for token validation versus enumeration was not retained; the combined Helper interval is reported, consistent with the requirement to remove benchmark-only telemetry.

## 34. Known Limitations / Deferred Work

Local and Removable compatibility are automated rather than separately live-benchmarked. Frontend tests require the containerized toolchain because npm is not installed directly on the host. Transfer skipping, concurrency, upload tuning, generic job queues, other providers, and unrelated UI/history work remain out of scope.

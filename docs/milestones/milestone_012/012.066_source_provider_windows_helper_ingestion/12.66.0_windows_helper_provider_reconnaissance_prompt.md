# 1. Milestone Purpose

This is the first milestone of:

`12.66.x — Source Provider / Windows Helper Ingestion Completion`

12.65 is complete and accepted on `main`.

Do **not** reopen Linux deployment stabilization.

Do **not** implement the Windows Helper yet.

This milestone is reconnaissance only.

Its job is to determine the smallest safe architecture and implementation sequence for Windows-connected filesystem Sources while preserving the accepted common ingestion pipeline and all 12.64/12.65 guarantees.

The controlling provider model is:

```text
1. Mounted Source Provider
   Linux server legitimately has direct filesystem access.

2. Windows Source Helper Provider
   A native Windows helper owns trustworthy access to Windows-connected
   Local / External / Removable / Optical Sources.

3. Cloud Provider
   Provider-specific acquisition such as iCloud.
```

Provider-specific access must converge on the **existing common Source Intake boundary**.

There must not be a second ingestion engine.

# 5. Locked Architecture

The reconnaissance must preserve these decisions.

## 5.1 One ingestion engine

Windows Helper is an **access/acquisition provider**, not a new ingestion pipeline.

Eventually:

```text
Windows Source
→ Windows Helper provider
→ authenticated/bounded transfer
→ Linux receiving/acquisition boundary
→ existing Source Intake
→ existing IngestionRun
→ existing Asset/Vault/provenance/canonicalization pipeline
```

Do not design:

- a Windows-side Vault;

- a Windows-side Asset database;

- a duplicate ingestion engine;

- a second provenance system;

- Windows-specific canonicalization;

- a second cleanup system.

---

## 5.2 Source-oriented UX

Normal user flow remains:

```text
Create Source
→ Source Selector
→ Ingestion Workbench
→ Run Ingestion
```

The user should select a Source, not choose infrastructure plumbing.

“Windows Helper” is primarily an implementation/provider concept.

Do not require normal users to understand helper transport details.

---

## 5.3 Windows path authority remains Windows-native

Do not translate:

```text
C:\...
D:\...
E:\...
UNC paths
optical-drive paths
```

into invented Linux paths merely to reuse the Mounted provider.

The Windows helper owns Windows path interpretation, device verification, and local Source access.

Linux runtime paths should represent only actual Linux-side receiving/acquisition paths where needed by the existing common intake boundary.

The reconnaissance must identify precisely how provenance should distinguish:

- durable Source identity;

- original Windows Source evidence;

- Linux receiving/runtime acquisition path.

Do not silently overload one field to mean all three.

---

## 5.4 Durable Source identity remains authoritative

Preserve the established Source model:

```text
durable device / provider identity
+
immutable alias
+
one or more Source roots / Profiles
```

Multiple roots may belong to the same enrolled device/alias.

External drive letter reuse must not be trusted by drive letter alone.

A removable/external Source must reverify durable identity before acquisition.

NAS remains separately represented by its appropriate provider identity.

---

## 5.5 12.64 protections remain locked

The reconnaissance must explicitly account for preservation of:

- selected Source Profile ID;

- IngestionRun identity;

- provenance identity;

- canonical Vault immutability;

- exact-known duplicate behavior;

- same-Source idempotency;

- cross-Source provenance;

- damaged/conflicting Vault fail-closed behavior;

- `Asset.original_source_path` historical semantics;

- no alternate orphan hash pathname;

- no schema/backfill unless later proven necessary.

Do not propose weakening these to simplify Windows support.

# 31. Required Proposed V1 Architecture

The closeout must include one concrete recommended Windows Helper v1 flow.

Use a sequence like:

```text

2. Helper proves device/helper identity.

4. User later selects saved Source.
5. Backend checks helper availability.
6. Helper reverifies durable device identity and Source root.
7. Linux requests bounded candidate inventory/selection evidence.
8. Existing application policy determines needed candidates.
9. Helper transfers only authorized candidate bytes or proves known content.
10. Linux verifies received content/integrity.
11. Provider adapter feeds common Source Intake boundary.
12. Existing ingestion/Vault/provenance behavior remains authoritative.
13. Temporary receiving state is cleaned safely.
14. Run/report state remains resumable/auditable.
```

Modify this only when code evidence requires it.
